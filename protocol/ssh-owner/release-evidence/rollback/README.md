# Offline B-to-A rollback boundary checker

This checker compares normalized observations from one rehearsal against an independently frozen plan. It reads only two explicitly named local JSON files. It does not open SQLite (including WAL), inspect processes, hash artifacts, take a lock, run a rollback, or access the network. Use only redacted tokens and digests from an authorized isolated rehearsal; never supply live user data, paths, process arguments, environment, or credentials. Keep the underlying observations and how each fingerprint was derived in the controlled evidence store.

`rollback-boundary-conforms` means the supplied observations agree on a compatible A/B pair and an offline switch fenced by the product's own mechanisms. It does not authenticate the observations or show that the product refused an unsafe rehearsal. It does not establish build A release precedence, the pre-A/fresh DB cases, the A-to-B re-upgrade, pane-record compatibility, stale-write fencing, or release acceptance. Those remain separate [matrix lanes](../matrix/README.md); reference a reviewed finding only after verifying the underlying rehearsal.

**Product model (v2).** B's storage revocation happens inside its drain, not as a separate event: the Rust owner closes its masters and leases, clears its attach record and exits; then B commits its own retirement record (`ssh_owner_retirement`, scope `backend`, target `owner-build-drain`, state `retired`: artifact, owner epoch, drained leases and the owner's shutdown counts) in one transaction, checkpoints WAL and releases the lock. A′'s legacy marker is left unchanged. By the time the drain answers, the backend may already have exited, so revocation is observed as the drain's answer plus the committed record, not as a moment with B still bound. The fence is the `<stateDir>/backend.lock` holder plus that durable record, not one continuous product lock: the lock is free between B's exit and A's start, and that interval is covered only by a complete capture with no other A or B starts. v1 inputs (with `storageRevokedAt` and `fenceContinuous`) are refused.

## Input contract

All objects have exact fields. Identifiers use the [matrix token syntax](../matrix/README.md); SHA-256 fields are lowercase hex and sequence positions are distinct positive integers from one recorder ordering, not wall-clock timestamps.

**Plan**: `{ kind: "rollback-boundary-plan-v2", binding, metadata, aImageSha256, bInventory, bRecordArtifactSha256 }`.

- Copy `binding` from the independently reviewed **required** matrix cell, including profile/target, artifact IDs, digests, and DB domain; do not derive it from the observed run.
- `metadata` is `{ schemaCeiling, schemaSha256, migration, migrationSha256 }`. Freeze the schema ceiling, the digest of the canonical schema at that ceiling, the preparatory migration ID and a digest of the exact preparatory migration definition. Measure A and B independently using the same normalization; the migration digest is not a hash of its ID. The ceiling and migration ID must agree with the cell.
- `aImageSha256` is the expected executable image of A that first opens the database, distinct in purpose from the distribution artifact digest. Independently freeze `bInventory` as one `{ component, role, imageSha256 }` per expected managed B process alive before drain, with a unique component token for each occurrence. Use roles `launcher`, `owner`, and `transport`; include at least one launcher and exactly one owner matching the cell's owner digest. Include detached launchers and drained transports relevant to this rehearsal, not unrelated user processes. Reviewers must verify this inventory covers all applicable B authority; the checker cannot discover omissions from both inputs.
- `bRecordArtifactSha256` is the SHA-256 of the exact artifact ID string B writes into its retirement record (for example `bigbud-server@<version>`), frozen from the B build, not from the observed record.

**Observations**: `{ kind: "rollback-boundary-observations-v2", binding, a, b, capture, before, drain, drained, retirements, boundary, aStart, aOpen }`.

- `binding` identifies the observed cell. `a` and `b` each contain `{ artifact, executor, metadata }`. `artifact` is the observed `{ id, build, sha256 }`, and the executor roles are respectively `legacy-ts` and `rust-owner`.
- `capture` is `{ complete, lostEvents, otherBStarts, otherAStarts }` for the entire interval from `before` through `aOpen`, including the free-lock interval. Require a complete lifecycle/DB-holder observation, zero lost events, and no other managed A or B launches. Do not turn missing or ambiguous observations into zero counts or use just process snapshots as verified exits.
- Each of `before`, `drained`, `boundary`, and `aOpen` is `{ seq, lock, db }`, where `lock` is the process lifetime token holding `backend.lock` (or `null` while it is free) and `db` is `{ domain, instance, metadata, logicalSha256, holders }`. Use one stable redacted DB instance token derived from the underlying file identity (not a path, filename, or content hash). Use holder instance tokens, not raw PIDs. For `logicalSha256` use one canonical committed-state fingerprint including migration history, the rollback-relevant tables (including `ssh_owner_retirement` and the legacy marker tables), timestamps, and WAL-visible commits. Do not compare raw DB/WAL bytes or assume an unchanged pathname proves continuity.
- `before` records known live B DB holders, and its `lock` must be an inventoried B launcher. `drain` is `{ seq, status: "drained", owner, record, legacyMarkerSha256 }`: `seq` is B's observed drain answer; `owner` is the answered owner report `{ masters, leases, attachCleared }` and must have `attachCleared: true`; `record` is B's committed retirement record read from the DB, `{ artifactSha256, ownerEpoch, owner }`, whose artifact digest must equal the plan's, whose epoch token must be present, and whose owner counts must equal the answered report; `legacyMarkerSha256` is `{ before, drained }`, digests of A′'s canonical marker and record rows, which must be equal (B never rewrites them).
- `drained` is the first committed-state observation after the drain answered; it includes B's record. Its `lock` is either still the same B launcher (which must then exit after it) or `null`. Each `retirements` item is `{ component, before, exit, status: "verified-exit", seq }`, with matching `{ instance, imageSha256 }` observed before drain and at verified exit. An instance token must distinguish process lifetimes even when PIDs are reused. Every frozen B entry must exit before `boundary`; a B holder still observed at `drained` cannot already have exited, and the lock-holding launcher must exit after the drain answered.
- `boundary` is after exit of all inventoried B processes and closure of all DB handles; it records no holders and a free lock. `aStart` is `{ seq, process: { instance, imageSha256 } }` for A, after the boundary. `aOpen` is A's first DB open with only this instance holding the DB and the lock, before any workload writes or repairs. The DB identity and metadata must stay the same throughout, and the committed-state digest must agree at `drained`, `boundary`, and `aOpen`. A′ ignores B's retired record (it reads only its own marker tables and unresolved owner rows), so the digest is unchanged by its first open.

## Run locally

From the repository root using existing Bun dependencies:

```sh
bun run protocol/ssh-owner/release-evidence/rollback/verify.ts /path/to/rollback-plan.json /path/to/boundary-observations.json
bun run vitest run --config protocol/ssh-owner/release-evidence/rollback/vitest.config.ts protocol/ssh-owner/release-evidence/rollback/check.test.ts
```

Exit 1 refuses incomplete, uncertain, mismatched, or out-of-order evidence. Exit 0 reports `rollback-boundary-conforms` with `observationsAuthenticated: false`, `rollbackQualified: false`, and `s4Accepted: false`. The tests use synthetic records only.
