# S4 release matrix: offline claim coverage

This tool answers one question: do the supplied **references to independently verified claims** cover the reviewed A/B plan and the minimum lanes encoded in [the catalog](catalog.ts)? It does not read the referenced claims, authenticate the inputs, inspect or verify artifacts, run products, or accept S4. Synthetic inputs exercise the checker only. A passing report always says `referencesAuthenticated: false` and `s4Accepted: false`; it is not activation or transfer M0 approval.

Start from the [S4 plan](../../../../docs/plans/2026-11-22-rust-ssh-ownership-plan.md), the [profile matrix](../../../../docs/plans/2026-11-22-rust-ssh-ownership-s0-profiles.md), and the [qualification ledger](../../../../docs/plans/2026-11-22-rust-ssh-ownership-s0-ledger.md). Freeze the scope and bindings independently of the collected results. Keep the reviewed records in the controlled evidence store; use only redacted identifiers here, not raw paths, hostnames, secrets, argv, or environment. The checker reads just the two explicit local JSON inputs. [Preflight](../README.md) can help inventory inputs, but its output is never a claim. A conforming [paired cutover trace](../cutover/README.md) can be referenced for `managed-launches` only, after independently checking its profile/target/cell, DB domain/schema, artifact IDs/digests and owner digest against this matrix. It does not establish retirement or rollback.

## Minimum scope

| Profile   | Required scope                                                                                                                                                                                                                                                                                                                                                                                                 |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D         | Both Mac DMGs, Linux x64 AppImage, Windows x64 NSIS. Record Linux arm64 and Windows arm64 installer exclusions, not runtime refusals. Mac requires Developer ID/notarization; AppImage uses verified release members; NSIS needs Authenticode or an explicit approved unsigned-release decision.                                                                                                               |
| V-E / V-B | Independently declare support for each cataloged candidate, including Linux arm64. Unsupported development targets need explicit decisions; unavailable runners or missing traces are not decisions. Freeze each supported runtime/ABI/PTY selection independently and include all reviewed variants in the plan. The checker does not establish the development support list.                                 |
| N         | Both standalone Node `web` and `desktop` modes across all six native staging targets, including supplemental Linux and Windows arm64; GNU and MSVC where applicable. Require actual clean distribution and CLI delegation claims, not native staging alone. The catalog keeps all six as required pending authoritative resolution; musl and targets outside the native matrix have explicit scope exclusions. |
| R         | Both release-trusted signed GNU graph targets. Shared-client operations, authorized account/agent PTY and pinned coordinator are positive claims; access and local-only route denials and inbound/worker/agent/viewer non-initiation have separate cases. Foreign base PTY denial requires separate accounting for preparatory probes. Non-Linux and musl are explicit graph exclusions.                       |

Every supported Windows x64 slot has **separate** Win10 22H2/inbox 8.1p1 and Win11/inbox cells; the arm64 Windows candidate rows are Win11, not inferred Win10 support. Supply the product-resolved inbox version, OS build and SSH digest. Within each supported Windows cell, key, login password, keyboard-interactive, unqualified-password refusal and ConPTY are separate lanes. Qualified login password or keyboard-interactive requires native askpass identity; if a Windows cell has a helper identity for any flow, include the helper verification and missing-helper case. Replacing a qualified-auth claim with a denial requires an explicit compatibility decision for that exact cell/method and a verified refusal before collecting credentials. Key auth is not replaceable by a denial. The original S2 Windows prompt, host-key, console, environment and acceptance requirements still apply to the referenced records.

## Local input contract

- The plan is `{ "kind": "s4-matrix-plan-v1", "scopeReview": "<review token>", "cells": [...] }`. Each cell is exactly `{ slot, cell, disposition, identity }`. `slot` is the exact catalog ID, such as `D.win32.x64.nsis.win10-22h2` or `R.linux.arm64.signed-gnu-graph`. `cell` uniquely identifies the exact reviewed OS/runtime/config variant. Multiple required cells may share a slot when distinct variants must be independently covered. Static exclusions and explicitly unsupported development slots use `disposition: "unsupported"` and `identity: null`; other cells use `"required"`.
- Required `identity` fields: `a` and `b` (each `{ id, build, sha256 }`), `artifactVerification` (catalog value), `dbDomain`, `schemaA`, `schemaB`, `migration`, `platform`, `owner` and `askpass`. `platform` is `{ os, arch, osBuild, abi, runtimeBuild, sshOrigin, sshVersion, sshSha256 }`; use `electron-…`, `bun-…` or `node-…` runtime identifiers as applicable, `19045` or `19045.<revision>` for Win10, and `win11-<build>[.<revision>]` for Win11. `sshOrigin` for Windows is `windows-inbox`; store the version token such as `OpenSSH_for_Windows_8.1p1` without its trailing library information. `owner` is `{ image: { id, build, sha256 }, protocol }`; `askpass` is an image object of the same shape or `null` when not applicable. Hashes are lowercase SHA-256. Identifiers are redacted tokens of up to 128 characters (letters, digits, `_`, `-`, `.`; starts alphanumeric). Schema ceilings and migration IDs are positive integers. All required cells must bind the same A/B build pair and schema, with equal A and B ceilings that include the preparatory migration.
- The claim bundle is `{ "kind": "s4-matrix-claim-references-v1", "scopeReview": "<same review token>", "cells": [...] }`. Each entry is exactly `{ binding, claims }`; `binding` is an exact copy of the reviewed cell. Each claim is exactly `{ lane, status, result, ref, decision }`. The expected lane/result pairs are in `catalog.ts`. Set `status: "verified"` only for a claim a reviewer actually verified outside this tool. Use a unique redacted `ref` for each lane finding; multiple distinct findings may refer to parts of the same underlying report. `decision` is otherwise `null`, but requires a review token for unsupported development, unsigned NSIS provenance, or a Windows credential lane using `result: "approved-auth-denial-before-collection"` instead of `"qualified-auth"`. Static artifact scope exclusions need their own `scope-exclusion` reference; they do not stand for runtime denial cases.

A/B claims are independent: `build-a-first` references the already-shipped migration-aware TS floor; `legacy-retirement` and `legacy-writers` reference verified fencing/drain of live PTYs, relays and monitor, each managed legacy restart attempt and no late writes. `pre-a-and-fresh-db` covers migration and sticky state; `offline-rollback` covers drain/revoke/retire B, offline A and re-upgrade on the same live DB including committed state, timestamps and stale-receipt handling. `unsafe-rollback` and `too-old-rollback` cover refusing unsafe ownership and schema cases without editing state. `consumer-parity` must point to independent reviewed caller and structural assessment, not just the presence of trace files. The verifier cannot decide whether the underlying findings support those claims or whether the reviewed scope omitted a platform variant; that remains release review work.

The [offline rollback boundary checker](../rollback/README.md) compares structured A/B, process, fence, and DB observations for the B-to-A switch. Its output does not replace an `offline-rollback` or `unsafe-rollback` finding: re-upgrade behavior and observed product refusal still require independent review.

Each required cell also needs a distinct `pane-record-rollback` reference (`drained-pane-stays-closed-uncertain-pane-blocks-rollback`). The referenced findings must show the supported A binary exercising pane lookup/reattach/restore on actual B pane records in the same DB/WAL after confirmed drain and retirement: the drained pane stays closed without respawn. A separate uncertain-termination case must show that the reservation stays fenced, unsafe rollback and admission are refused, and no replacement spawns. A generic DB rollback finding, raw SQL read, or mock is not this evidence.

Each required cell needs a distinct `stale-write-fencing` reference (`stale-epochs-rejected-without-mutation-or-teardown`). On the cell’s actual A/B artifacts and live SQLite DB, the finding must show that a delayed old-epoch Connect cannot undo a newer Disconnect, and a delayed old-epoch Disconnect cannot undo a newer Connect or tear down its transports. Exercise epoch rotation after a committed write whose reply was lost, then reject delayed pre-rollback requests after offline A and re-upgrade to B. Check the actual disconnect rows, timestamps and transition sequences, admission after restart, and exactly-once effects of the committed transition. Neither legacy-writer quiescence nor a generic same-DB rollback finding substitutes for these checks.

## Run locally

From the repository root using existing Bun dependencies, without installing or downloading anything:

```sh
bun run protocol/ssh-owner/release-evidence/matrix/verify.ts /path/to/matrix-plan.json /path/to/claim-references.json
bun run vitest run --config protocol/ssh-owner/release-evidence/matrix/vitest.config.ts protocol/ssh-owner/release-evidence/matrix/check.test.ts
```

Exit 1 rejects invalid, missing, mismatched, duplicate or unverified claim inputs. Exit 0 reports `matrix-claim-coverage-conforms` for the supplied bindings and references only.
