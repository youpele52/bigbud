# cua-driver 0.38.0 static schema fixtures

Captured statically from the upstream source of `cua-driver-rs-v0.38.0`, release API target commit [`85e2b1318bd77ccf3cfa88ccdf875a4bb7eaed19`](https://github.com/trycua/cua/tree/85e2b1318bd77ccf3cfa88ccdf875a4bb7eaed19/libs/cua-driver), on 2026-10-26. No 0.38.0 binary was downloaded, staged or executed for these files, and nothing was built from the upstream source. They are dormant test fixtures: legacy 0.9.1 remains the selected Driver, and the 0.9.1 fixtures beside this directory are unchanged historical evidence.

Every upstream file was fetched from `raw.githubusercontent.com` at the pinned commit and checked against its git blob SHA in the commit's tree (`GET /repos/trycua/cua/git/trees/<commit>?recursive=1`).

## How `live-schema.darwin.json` was produced

The upstream portable contract deliberately covers only a subset of the live platform schemas, so the live macOS schemas were transcribed from source:

1. Each tool's `input_schema: serde_json::json!(...)` literal was converted to JSON by a text-only transcriber that implements Rust string escapes, line continuations, raw strings and comments.
2. Every non-literal expression was resolved from its pinned definition and is listed in the file's `resolutions` array. These are helper functions whose body is a single `json!` literal, `&str` and integer constants, `delivery_mode_schema_with(...)`, and one `format!` with only inline constant names. `get_window_state` merges `window_state_view::schema_properties()` as `extend_input_schema` does.
3. The advertising rules of `cua-driver-core/src/tool.rs` were applied: `ToolDef::to_list_entry` (lines 159-209) and `advertised_runtime_input_schema` (lines 610-637). A closed schema gains `session` if absent, and the seven typed-target tools (`TARGETED_TOOLS`) gain the portable contract's `target`. Only six of them are in this fixture: `move_cursor` is not part of the captured profile. The session tools use their manifest schemas exactly (`ToolDef::from_contract`).
4. `outputSchema` follows `cua-driver-contract` `advertised_tool_output_schema`: action tools use the shared `ActionResult` success schema (identical for every action tool in the manifest), other tools use their manifest `success_output_schema`, and either is wrapped as `{"type":"object","anyOf":[success, refusal envelope]}`. Tools without a contract advertise none (`null`).

Tool descriptions, capability tokens and risk metadata are not transcribed.

**Independent cross-check:** the plan's approved probe A (2026-10-25) recorded the real 0.38.0 darwin-arm64 executable's `describe` output for the same 17 tools (`A-evidence/schemas.json`, SHA-256 `7b608fe08fc5582caec51504f60e22f13b372b7fed13095d01f9e005e11e5291`). All 17 transcribed input schemas are deep-equal to it, including every description string. `get_session` was not part of that probe. Output schemas were not part of the probe either; they come from the exact generated manifest.

These files do not qualify any platform. Windows and Linux live schemas are not captured.
