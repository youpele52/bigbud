## 2. Goal, decisions and definition of done

Replace the embedded two-version execution whitelist with an explicit native contract and a separately maintained, evidence-backed qualification registry. A stable V2 release must pass **both** runtime compatibility checks and semantic qualification before canonical execution. This is not unconditional forward compatibility.

### Exact decision provenance

The parent supplied the implementer's exact question-tool provenance, corroborating working-ledger lines 9–11. The user's preceding freeform request was:

The alternatives were **“Qualify installed 2.0.28”** (parent describes using the existing binary in disposable fixtures, retaining 26 and replacing the mandatory 27 target) and **“Support contract-compatible V2”** with the recorded description **“Amend the plan for capability/ABI-based V2 minor support instead of an exact-version allowlist; this requires broader compatibility design and tests.”** The user selected **“Support contract-compatible V2.”** Only the second option's description is quoted verbatim; the first description is parent-relayed substance.

This planner then directly asked:

> For a future stable V2 release that passes all runtime API, bootstrap and source checks but has not undergone bigbud’s native semantic qualification, should canonical tools run? Read-only checks cannot prove permission-filtering and lifecycle behavior. This choice does not authorize any live native operations.

Options:

- **Allow with clear warning:** “Admit contract-compatible V2 releases, clearly distinguish runtime compatibility from tested qualification, and block any known or observed incompatibility. Accept residual untested native-semantic risk.”
- **Require qualification first:** “Keep models visible but block canonical execution until disposable native semantic qualification exists for that release. This is stricter than runtime contract checks and delays support for new V2 releases.”

The user selected **“Require qualification first.”** This narrows the earlier broad-support choice: unknown releases do not execute merely because their version or OpenAPI looks compatible. Qualification eligibility will still be release-specific; describe that honestly rather than relabeling a whitelist as unlimited support. Adding a newly qualified release must not change bootstrap bytes, protocol bytes or immutable handler identities when its contract is unchanged.
