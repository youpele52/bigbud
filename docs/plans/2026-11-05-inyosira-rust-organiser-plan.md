## Summary

Move the complete automatic thread-organisation reactor into Rust, with TypeScript retaining canonical facts, authorization, SQLite, command validation and persistence. First prove and cut over existing behaviour; only then enable the agreed active-work, manual-override, global Present target and notification UX. Never run two production schedulers.

The target UI order is **Needs you, Present, Later, Done**. Running providers, subagents and terminal/background jobs are uniformly work. Needs you takes precedence while actionable requests remain; its row can also show running work. Organisation never stops work.

**Readiness:** M1's isolated Rust timing foundation is **Ready for implementation** after the parent-launched independent plan review (5 November); parent authorized proceeding strictly within its four source/test paths. The complete migration is **not Ready for implementation** until G1/G2 are resolved. No migration or source implementation had begun when this plan was authored. ## Problem

The current TypeScript reactor has separate event, snooze and idle loops. It can move to Present after one response without checking other requests, ignores provider-output-only activity for promotion, and the UI acknowledges Needs you on deliberate open. None implements the new uniform activity policy, fixed manual override, global target, engagement leases or replay-safe automatic-move notifications.

Existing older-thread timing has an additional unfinished baseline defect: the query uses `MAX(last_activity_at, organization_changed_at)`. Automatic idle-to-Later moves advance `changedAt` and therefore restart older age. Preserve durable wall-clock aging across server restarts/sleep **and** remove this automatic-move age extension with source-aware persisted anchors; merely porting the query is insufficient.

## Goals

1. Complete Rust scheduling/event ownership, not a helper for a competing TypeScript timer.
2. Compact versioned snapshots/facts; no conversation, credentials, process scanning or DB access in Rust.
3. Durable deadlines, lost-ACK dedup, instance/generation/revision fencing, bounded queues and fail-closed recovery without interrupting manual moves/chat/terminals.
4. Preserve short-idle rules, older-before-short, policy grace, snooze identity fencing, paging, retry pacing and terminal uncertainty safeguards before introducing new UX.
5. Implement all product criteria in the acceptance matrix, with focused tests and independent review per milestone.

## Non-Goals

- Provider protocol changes, process termination on moves, independent native domain truth, another process monitor, full conversation snapshots, retention/deletion policy changes.
- Background backend hosting, new native executable/crate, dependency upgrades, broad cleanup, Git publication or full-workspace validation.
- Claiming atomic OS process-start detection from sampled facts, or detecting intentionally detached/untracked external jobs without an existing owner. Missing/uncertain owner facts must protect cleanup, not be invented as idle.

## Phases

### M0: Resolve gates and record architecture

**Scope:** this plan and a follow-up narrow scheduling ADR before production cutover. No existing ADR is weakened.

**Chosen boundary:** extend existing `bigbud-desktop-supervisor` with a `--thread-organization` mode, in `src/organization/`. The authoritative TS server launches one dedicated organisation process using the **same packaged binary**. It does not run inside Electron, does not depend on a delivery consumer, and has separate failure/backpressure isolation from delivery. This reuses platform artifact identity, prost generation and process-lifetime patterns without a new crate or dependency. A shared delivery/organisation process would couple stalls; remote-agent would export domain scheduling to the wrong capability boundary; FFI would remove process crash containment.

The ADR explicitly authorizes this **narrow extension from systems-only work to scheduling derived organisation proposals**, not native canonical domain state. Rust decides reactions, eligibility, priorities and deadlines from supplied facts; TS persists validated results and may veto stale/unsafe proposals but never chooses another candidate or sets an independent timer. Other Rust services and provider boundaries are unchanged.

**Exit:** independent plan review, G1/G2 resolutions recorded, dependency-free design retained. M1 timing-only code can start without the unresolved new snooze UX or overlapping wiring; no runtime cutover implied.

### M1: Pure Rust parity foundation (safe first implementation slice)

**Scope:** `crates/bigbud-desktop-supervisor/src/organization/{mod,timing,timing_tests}.rs`, one module declaration in `lib.rs`. No production caller, protocol, Cargo or dependency edits. Goal is deterministic timing primitives to be consumed by M2, not to claim a migrated reactor.

- Encode short-rule restart/long-gap barriers and durable older-rule policy barriers separately; optional older barrier means no startup wait, not a magic serialized infinity.
- Preserve each rule's independent policy change and equality boundary; preserve older-before-short in later scheduler composition.
- Model clock observation explicitly: monotonic duration for live waiting/retry, supplied wall time for durable deadlines. Backward time must not cause negative elapsed or early expiry; large forward discontinuity restarts short wait, not older age. No reads of real clock in pure tests.
- Cover restart, sleep/forward gap, backward time, policy changes, disabled rules, cutoff equality and overflow-safe arithmetic. No product defaults for target/manual/snooze are introduced here.
- Export only a small typed timing API; do not make a reusable catch-all crate. No imported module starts tasks.

**Exit:** crate-scoped formatting, Clippy and focused timing tests pass; independent code review; unused-at-runtime status is explicit. Later migrations must actually use the API or remove it, not leave a second implementation.

#### Wire and ordering

- Versioned hello negotiates organisation capability and hard limits. Owner identity is backend nonce + fresh sidecar generation; all frames carry that epoch. No provider IDs, credentials, paths, texts or conversation snapshots needed.
- TS compact snapshot transaction reads all live standard organisation rows plus a canonical event frontier, in stable pages. Capture events before starting snapshot; drain only facts newer than its frontier. Ephemeral owner facts carry generations and are merged through the same sequence allocator. Replace stale observations rather than permitting a late concurrent fact read to overwrite a newer one.
- Snapshot begin/page/end include generation, page index, row count/digest and policy version. Stage snapshot separately; activate only after end validation and buffered ordered facts catch up. Incomplete snapshots never authorize moves.
- Facts use contiguous organiser stream sequence (not filtered domain-event sequence), per-thread fact version and canonical source frontier. Explicit duplicates are idempotent; conflicting duplicates, gaps, queue overflow or underlying replay gap pause proposals and require full compact resync. Do not lose intermediate new-request/manual-move ordering through coalescing; only observational refreshes can coalesce before sequencing.
- Rust owns one global decision coordinator and deadline queue. Independent TS fact reads may run at concurrency 3; publish in reserved order with stale-result fences. Per-thread proposals are serial. Global target reservations share one count; release rejected reservations and reconcile committed moves before subsequent target decisions.
- Proposed bounds: 1 MiB frame, 256 rows/page with byte preflight, 2,000 pending fact frames capped also at 8 MiB, 32 outstanding proposals, 100,000 compact live rows capped at 64 MiB. Exceeding a negotiated limit makes organisation visibly degraded, never silently truncates global counts. Generation reset clears retained staging and ephemeral queues.

#### Proposals and recovery

- Proposal includes stable operation ID, immutable digest/payload/created time, epoch, snapshot/fact frontier, thread revision/version, policy version, reason, source/destination and deadline proof. Before dispatch TS verifies live owner/generation, full current activity/attention/snooze/manual/grace facts and expected versions at serialized command acceptance; conditional SQL update and receipt/event share transaction. A veto is a typed stale/no-op result, not a substitute decision.
- Reuse canonical command receipt/digest infrastructure. Persist prepared automatic operations before acceptance so a lost ACK can be answered with the same immutable outcome after restart. A no-op receipt cannot permanently consume a future deadline. Distinguish terminal stale/superseded refusal from a confirmed `not-due` result carrying the authoritative deadline. For `not-due`, Rust retains a deadline occurrence and schedules its next attempt no earlier than that deadline and the bounded retry interval; expiry may create a new durable attempt ordinal/operation ID even if the thread fact version is unchanged. Only a confirmed no-op permits that new attempt; an uncertain/lost ACK must reconcile/retransmit the identical operation first. Persist occurrence ID + attempt ordinal before dispatch so restart cannot recreate consumed IDs or fork unknown outcomes. Minimum retry spacing is 1s, repeated early results use capped exponential backoff (max 60s), and all retries revalidate current epoch/policy/revision. Query prior receipt before deciding whether a retry is stale. No timestamp regeneration during retransmission. Test an early/no-op delivery followed by clock advance at the same fact version, repeated early replies without a hot loop, and lost ACK at each attempt boundary.
- Timings requiring durability are proposed/stored before Rust treats them as effective; no acknowledgement of a manual move or Undo before its override/grace is committed. Explicit manual operations stay available without Rust; TS records facts/deadlines dictated by that operation but makes no automatic scheduling decision.
- Connection/hello 5s, snapshot progress deadline 10s (60s total), proposal ACK 5s, same-ID retries 3 with 200/400/800ms backoff, heartbeat 5s/15s deadline; then fence and resync/restart, at most 3 attempts/30s before degraded latch. A late ACK can reconcile a receipt, never reactivate old generation. Runtime capacity/deadline constants are tested and observable.
- Shutdown rejects new proposals, fences generation, settles persisted outcomes, closes stdin and waits within 2s then terminates/kills owned child within 5s total. Bounded reader/writer workers must be cancellable; a blocked pipe must not cause an unbounded join. Chat/terminal/manual paths do not await native recovery.

**Exit:** shared protocol golden tests; consistent snapshot/live handoff; durable restart/lost-ACK/stale-epoch/gap tests; parity fixture decisions agree with preserved behaviour and the explicit age correction.

### M4: New activity, attention and manual-override semantics

**Depends on:** parity acceptance and snooze decision G1.

Priority order on every accepted fact/deadline:

1. Reject deleted/deleting/archived/nonstandard targets and stale/unknown eligibility for cleanup.
2. Genuinely new actionable request immediately cancels older manual suppression (and snooze under the proposed G1 policy). Existing requests replayed/re-observed do not. Aggregate all unresolved request types; one response does not clear the others. Request identities/watermarks come from authoritative projections, not arbitrary latest message.
3. Honour an unexpired explicit move to **any** section for exactly 10 minutes; store server acceptance deadline and attention watermark. Repeating the same-state explicit move renews the intentional period, with an idempotent command ID. All explicit move entry points, including authorized tools and bulk moves, use the same semantics. Organisation does not stop work.
4. At override expiry, Needs you if still actionable, otherwise Present if active, otherwise keep chosen section. No forced return when inactive. Honour the resolved snooze policy separately.
5. Outside suppression, actionable requests mean Needs you; active provider/subagent/terminal/managed-background work means Present. Unknown protects against cleanup without claiming known running work. Needs you displays running indicator when both facts hold.
6. No old open-to-Present acknowledgement: deliberate navigation now grants bounded engagement, not an answer or manual organisation move. Human messages/responses cannot demote a thread with another unresolved request.

Manual active Later confirmation uses the exact approved text: **“Moved to Later. If work is still running in 10 minutes, this thread will return to Present so you can keep track of it.”** Adapt section and known facts truthfully. If unresolved attention may determine expiry, state Needs you precedence instead of promising Present. Do not claim running work for unknown state, or toast an unconfirmed/no-op move.

**Exit:** multi-request precedence, duplicate/new request distinction, all sections, no-stop assertion, terminal/subagent/silent background activity, override restart/expiry/new-request races and navigation browser tests.

### M5: Global Present target, grace, engagement and Undo

**Depends on:** M4. Extend server-owned settings: enabled/disabled, integer target default 7 (positive bounded integer), shared grace integer 2–10 minutes default 5. Target is across all live standard threads/projects on connected server; filters/collapsed groups/pagination never alter count. Exclude archived/deleting/deleted/nonstandard threads consistently with sidebar catalog eligibility.

- Above target, choose least recently **active** eligible Present thread, stable thread-ID tie-break. Use global authoritative compact facts, not creation time/client ordering. If all are active, unknown, awaiting action, overridden, snoozed or protected, remain over target indefinitely without overflow warning.
- Keep three distinct rules: target moves to Later after its grace, normal idle uses its configured full idle timeout/destination, older uses full configured age to Done. Shared grace is a minimum protection, NOT a replacement timeout: normal idle/older eligibility requires both their own full inactivity/policy wait and grace. A separately enabled target may intentionally move an eligible thread sooner than a longer idle rule; label this distinction in settings. With target disabled, no existing idle timeout is shortened.
- Work-to-idle completion, manual return and successful Undo grant shared grace independently of idle-rule enabled flag. Preserve longer terminal quiet-time requirements for normal rules. Persist deadlines; do not restart old-age clocks on automatic Later moves.
- Enabling/lowering target sets durable global target-drain-not-before to now + grace before first cleanup. One global coordinator limits each drain batch (50 moves max) and waits for committed results before recalculating. This is a soft target, not a quota.
- Engagement uses authenticated existing WebSocket connection identity, generation and thread ID; no new socket. Visible focused thread plus actual read/scroll/key/input interaction obtains a 60s server lease; refresh at most every 15s, only with interaction within the past 60s. Opening grants one lease; visibility/focus alone, timers and stored drafts do not perpetually renew it. Multi-client protection is the max live lease. Disconnect/replacement revokes that connection; expired/suspended tabs cannot pin forever. Clamp times on server and bound per-connection/thread entries; no draft content transmitted.
- Undo identifies automatic move operation and resulting revision. Restore prior section only if that move remains current and current attention/work safety permits restoration; a newer manual move, new request or later auto move makes it a reported no-op. Persist restoration and grace transactionally. Idempotent duplicate Undo returns original outcome.
- Successful Undo also pauses global **target** draining for shared grace, so returning one thread does not immediately evict another. Other established idle/older rules retain their independent windows; restored thread is protected from all cleanup. Partial batch Undo reports only actual restorations.

**Exit:** global multi-project/filter-independent target tests; ties/recent activity vs creation; protected overflow; >50 protected rows fairness; grace with idle off; longer idle unchanged; target enable/lower crash recovery; two-client engagement expiry; conditional Undo and no immediate replacement eviction.
