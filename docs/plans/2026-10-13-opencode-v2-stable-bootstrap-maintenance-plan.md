## 3. Background and evidence

### Failure mechanism

The frozen v3 installer replaces a global shim whenever the emitted native artifact digest changes. `PluginSetup.publication.ts:183–187,260–275` consults enrollment leases before replacement, but intervening awaits and independent native admission remain possible. First insertion has no equivalent upgrade check. `PluginSetup.upgrade.ts:5–32` only scans optional acknowledged/pending expiry fields: it neither strictly decodes the complete enrollment state nor observes native work or physical callback settlement.

The native `Plugin.activate` implementation retains only an unchanged prefix of plugin IDs/revisions, closes the healthy suffix in reverse order, then reloads it. A new global entry can therefore unload existing later plugins, including post-builtins. The parent debugger established this on pinned 2.0.26/2.0.27 source; this planner independently fetched and compared `plugin.ts`, `plugin/supervisor.ts` and `plugin/module.ts`: all three are byte-identical between the pinned commits below. Tag/source association is not binary-byte attestation.

`Orchestration.plugin.ts:65–66` calls `state.close()` on unload. `Orchestration.plugin.registry.ts:90` aborts the lifetime and enrolled owner controllers. Already captured native tool snapshots may still call executors, but the old lifetime, health marker and registry are invalid. Canonical work might already have been accepted; failure must retain uncertainty, not resend. This does **not** establish that every native chat stops or history is deleted.

**Confidence:** high for the source-level reload/abort mechanism and inadequacy of lease-only idle inference; future two-generation production behavior remains unqualified. No fresh tests, paid prompts, user-native API calls, service actions or configuration writes were performed by this planner.

#### 2a. Exact implementation boundary and build identity

Implement this ordering in `Orchestration.bridge.ts`, `.callback.ts`, `.receipts.ts` and the narrow reuse boundary in `Execution.orchestration.ts`:

Endpoint/token/redirect/body/response bounds remain mandatory.

Response parsing or interpretation failure after dispatch leaves the reservation uncertain; never dispatch again to obtain a “better” result.

#### 3a. Legacy/new wire compatibility and durable retirement

**L** = frozen v3 plugin/owner protocol `bigbud.thread.v1`; **N** = the new bootstrap/owner protocol above. `info` is a no-owner `{}` request; its schema is chosen by the verified installed bootstrap, not the desired owner. Matrix entries describe native capability **and new-app policy**:

| Installed bootstrap | Owner encoding | `info`                           | `enroll`                                | `renew`                                                                | `inspect`                              | `detach`                                                         |
| ------------------- | -------------- | -------------------------------- | --------------------------------------- | ---------------------------------------------------------------------- | -------------------------------------- | ---------------------------------------------------------------- |
| L                   | L              | Exact legacy schema              | Native supports; new app does not issue | Native supports; only old app's existing lifetime, not new-app renewal | New app emits exact L cleanup envelope | New app emits exact L cleanup envelope                           |
| L                   | N              | Legacy schema still identifies L | Reject; app must activate N first       | Reject                                                                 | Reject; never downgrade N owner        | Reject; preserve N cleanup evidence until compatible N available |
| N                   | L              | New schema identifies N          | Reject, including replays               | Reject, including replays                                              | Exact L **cleanup-only** verifier      | Exact L **cleanup-only** verifier/tombstone                      |
| N                   | N              | New schema                       | New authenticated enrollment            | Exact acknowledged owner only                                          | Exact signed owner                     | Exact signed owner/tombstone                                     |

Freeze legacy owner field order, strict envelope field set and signed array bytes in `Orchestration.protocol.legacy.ts` and a matching small emitted cleanup verifier. Preserve old public/encryption keys and old `artifactDigest` meaning; new fields never appear in L requests. L inspect/detach use `owner:null`, null lease fields, fresh request ID/deadline and the original owner digest/nonce. N branches to this verifier **only for inspect/detach**, checks original issuer/signature/operation/bounds, and namespaces cleanup tombstones by protocol/digest/nonce; it cannot create a callback owner, renew a lease, revoke an unrelated N successor or revive L authority. Keep `Client.guard.orchestration.ts`'s exact body/Location/session cleanup binding for both encodings.

`Orchestration.enrollment.ts` delegates retirement to `Orchestration.enrollment.retirement.ts`; extend the signed record store with a separate `retirements` namespace. Each record retains the exact prior signed enrollment envelope/revision (or a byte-exact archived copy), original scope/digest/nonce/wire version, and phases `retiring`, `detach-acknowledged`, `settled`, `replacement-bound`. It must not overwrite the only legacy owner evidence with a new owner or turn local `revoked` into “native detached.” Writes use exact-record revision plus the cross-process ownership lock described in step 5.

Retirement ordering:

1. Verify legacy/new record, original scope and current matching native Location. Pause new local owner mutations as specified in 4c; await already-running mutations and physical operations. For a pending initial enrollment or renewal, inspect and reconcile its **exact** retained proposal without starting a new nonce; ambiguous evidence blocks. A pending initial enrollment proven never active has no invocation authority, but still receives exact detach/tombstone.
2. Persist `retiring` before sending detach; preserve acknowledged and pending lease evidence. For known-live idle local owners, synchronously fence future callbacks and stop renewal without cancelling active work (activity must already be zero). Crash/foreign owner records require independently proved no unresolved dispatch; absence or lease expiry is insufficient.
3. Send inspect/detach to the **actually installed** L or N bootstrap using the matrix. Strictly validate returned ack shape, original digest/nonce, `state:"revoked"`, integer revision/expiry and consistency with reconciled owner evidence. For a present entry accept only its reconciled exact revision/expiry. For an absent entry accept the defined zero/zero cleanup ack, label it `registry-absent`, and **do not** infer physical settlement. Stale/later/different-owner acknowledgements are rejected.
4. Persist `detach-acknowledged` with the validated ack, installed-bootstrap identity and native transport generation. Only separately proved local physical settlement plus no unresolved creation/admission/receipt evidence permits `settled`. A missing native registry, plugin unload, HTTP completion, timeout or expired lease cannot supply this proof. Pending/uncertain canonical receipts remain intact and blocking; no TTL clears them.
5. Publication requires `settled` retirement for every affected known local owner. After publication and per-Location N verification, an explicitly authorized foreground request may create a new N owner for the **same** native session and persist `replacement-bound`; old retirement/nonce/receipt evidence stays immutable. No background job reenrolls a session or resubmits its prompt.

On crash after detach but before ack persistence, retry **only cleanup** with fresh authentication; never enroll to test whether the old owner existed. On crash after `settled → published` but before new owner, reconcile the exact publication and retirement records, validate N `info`, then let subsequent foreground attach enroll the same session. A cleanup-only N zero/zero reply cannot fill a missing physical-settlement record. If persisted retirement is incomplete and physical state cannot be established, report the blocker rather than fabricate a successful upgrade. `detach()` itself must validate/persist this acknowledgement; fixing only `startExclusive()` is insufficient.

A uniquely verified **N-compatible manual entry** remains reusable. A legacy L manual entry is classified `legacy-manual-bootstrap-update-required`: the new app may perform exact cleanup but cannot create L authority or rewrite the user's config to N. Retain history/models and provide this exceptional remediation status, never add an autoload duplicate. Known app-managed L entries use automatic best-effort replacement; unchanged older apps' live L enrollments defer that replacement as external owners.

### 4. Replace lease-only upgrade with automatic best-effort activation

Do not instantiate per RPC or separately inside either consumer. **Job states:** `checking → ready` for an already compatible bootstrap; otherwise `prepared → waiting-for-idle → closing-gate → retiring → publishing → verifying → ready`. Exceptional terminal states are `blocked`, `failed`, `uncertain`, `cancelled`, `deferred`. Implementation-only selection bypasses activation/generation invalidation entirely.

#### 4a. Coordinator-owned lifetime, not the RPC caller's lifetime

- `requestSetup(scope, callerInterest)` creates/joins a job keyed by canonical root, issuer, consent revision, native transport generation and desired bootstrap digest. Limit 32 jobs and 32 interests per job; conflicting proposals return a safe conflict. Setup status reads never call this method. Only acknowledged foreground work or explicit settings acknowledgement/retry may create an interest; hidden work/model discovery/settings-open cannot.
- At creation, the service independently captures a **job-owned `V2ConsentPermit`** and borrows its own connection-only lease for the already verified shared descriptor. Do not reuse `currentV2RequestContext().permit`, a request-local client, or a released `runAuthorizedV2` scope for timers. Run every job read/RPC/publication continuation in `runV2RequestContext` with the job permit, exact transport and execution intent, plus operation-specific RPC authority. The job also retains its own abort controller. Capture before first await; recheck scope after acquisition and close a late acquisition immediately if revoked.
- Each initiating request owns an opaque **interest ID**; a waiter is merely its current observer. A 30-second foreground wait timeout converts that interest to a bounded continuation interest and returns `waiting-for-idle`/job ID, rather than cancelling it. All continuation interests expire at the job's original **five-minute creation deadline**; joins never extend that deadline. The coordinator's internal lifetime keeper stays attached to `publishV2ManagedPlugin` while any authorized interest survives. Thus `.publication.ts:101–104` cannot abort a valid background job just because an RPC waiter returned.
- Explicit cancellation of a request/interest is different from its wait timeout: remove that interest (including its continuation if already transferred). Cancelling one interest cannot cancel another's. When the last interest is explicitly cancelled, abort the job and remove the internal publication keeper. Expose internal `cancelInterest(jobId, interestId)` and bind any setup-RPC cancellation to the issued handle/current scope; passive status subscribers create no interests. Closing a status view only detaches that observer; it is not a cancellation of another foreground request. Provider disable, root/consent change, transport loss or service-scope close abort **all** interests immediately.
- On the five-minute deadline or terminal result: cancel timers/new work, detach the publisher keeper, fence late continuations, settle already-issued physical operations, close the borrowed connection **once**, then release the job permit **once**. Do not release the permit on foreground/RPC return: it must remain in `V2ConsentAuthority.pending` so revocation aborts waiting work. Application and setup request finalizers close only their own leases/permits; only the coordinator finalizer owns job resources. Physical operations that have not settled remain bounded quarantined records; do not free their capacity or start a successor writer merely because a wrapper timed out.
- A deferred startup/send returns a classified setup result **without a new native binding dispatch intent, prompt admission or canonical callback dispatch**. Background success updates setup status only: it never stores/resubmits the caller's prompt, creates its session, or reenrolls it. A still-live foreground caller may continue its original pre-admission operation after readiness; a returned/timed-out/cancelled caller requires a later normal foreground action.

#### 4b. Executable admission contract and lock ordering

Maintain one gate per shared transport generation/native-root scope across local V2 runtimes, plus per-Location readiness. Operations have distinct states:

| State                                | Counts as activation-busy?       | Permitted effects                                                                                                     |
| ------------------------------------ | -------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `setup-wait` / read-only preparation | No                               | Bounded read/provenance checks; join setup, no durable creation/admission reservation or native mutation              |
| `reserved`                           | Yes                              | Exact local reservation after readiness; native mutation/durable dispatch intent may now begin under that reservation |
| `dispatched` / `native-running`      | Yes                              | Existing operation/call/turn settlement and callbacks; no new unrelated reservation while gate is closing             |
| `uncertain`                          | Yes, quarantined evidence        | Read-only reconciliation/authorized exact cleanup; no timeout-based release or resend                                 |
| `settled`                            | No after physical/journal checks | Release reservation exactly once                                                                                      |

`Runtime.starting` still prevents duplicate starts and enforces capacity, but add a phase/reservation slot to `V2StartAttempt` in `Runtime.start.ts`; `setup-wait` entries are **not** physical busy evidence. Similarly, `admissionInFlight` is set only after actual local reservation, never while awaiting setup. Explicit operation tokens, not `starting.size` or lease expiry, drive the gate's busy count.

Coordinator methods/contracts:

- `awaitReady(directory, requirement, interest, signal)` runs **outside** `withSession`, `withV2AdmissionOperation` and `mutations.withNamespace`. It returns either deferred/error or an immutable `ReadyStamp {scope, epoch, directory, bootstrapDigest, setupInstanceId}`; it never reserves execution. Hidden jobs use a passive gate/Location check, not installer activation or canonical readiness/credentials.
- `tryReserve(stamp, operationKey)` is synchronous with `tryCloseGate`: it rejects stale epoch/Location readiness, a closed gate or changed authority; otherwise registers one idempotently releasable operation token. No awaits between that check and registration. Losing this race is a **pre-admission retry/deferred sentinel**, not a native execution failure.
- `assertReservation(token)` is repeated after awaits and at `prepareSharedCreation`/`admitV2Turn` before durable dispatch intent and immediately before actual native mutation. A held valid token prevents this process's coordinator closing the gate; consent/owner loss still independently revokes authorization.
- `dispatch(token, begin: () => Promise<T>)` marks dispatch synchronously **before invoking the thunk**, then retains its underlying physical promise, not merely a timed wrapper. `settle(token, evidence)` releases only after physical promise settlement and the appropriate durable outcome/native-turn drain are proved. Prompt acknowledgement transfers the reservation to the admitted session/turn until terminal native evidence and no outstanding callbacks/mutations; HTTP acknowledgement or request return alone does not mean the native turn finished. Failed/unknown dispatch transfers into existing mutation/admission/receipt quarantine rather than decrementing busy to zero. Reuse `Mutation.ts`, `Runtime.mutations.ts`, journal reconciliation and `Execution.owners.ts`; add non-cancelling busy/settlement accessors rather than using `cancel()` as an idle test. Removing a start attempt, disposing a runtime owner or timing out a caller must transfer unresolved reservation evidence, not drop it from the coordinator's busy inventory.
- `registerOwner(exactOwnerKey, participant)` connects bridge lifetime to the coordinator. The participant exposes read-only execution/control counts, synchronous `pauseRenewal`/`resumeRenewal`, `joinControl(signal)` and exact `retire(signal)` implementing 3a. A join deadline stops waiting, **not** the underlying renewal/proof; it cannot manufacture physical settlement by cancellation. Unregister only after settlement or transfer its unresolved evidence to the bounded quarantine. Scheduled controls and callbacks consult this same owner/gate state; a late new callback during gate closure cannot acquire invocation authority.

Required call-path changes:

1. **Startup:** in `Runtime.ts`, `Runtime.preparation.ts` and `Runtime.sessions.ts`, split read-only target/binding resolution and borrowed acquisition from mutation. Set the bounded start attempt to `setup-wait`, perform `awaitReady` **before** `mutations.withNamespace` and before `prepareSharedCreation` calls `repo.reserve`. Once inside the namespace queue, revalidate owner/stamp and synchronously reserve; on stale stamp exit the queue and wait/retry outside it. Only then reserve/transition the durable binding and create/update native history. Return the held token with prepared resources to the start attempt; release the namespace queue before canonical-resource activation, startup reconciliation and enrollment attach. The token, not the queue lock, stays held through physical mutation settlement and attach acknowledgement; attach's readiness check is read-only against the held stamp, never recursive installer waiting. If startup discovers a still-running retained turn, transfer into its native-running/quarantined ownership rather than treating attach completion as idle. Uncertain creation remains quarantined even if startup returns an error.
2. **New turn:** `Runtime.send.ts` first reads the existing journal/owner without holding the session queue. An existing admission takes the current read-only reconciliation route, never setup-driven resend. For a new admission, perform `awaitReady` outside queues. Enter `withSession`, reread the journal and current owner; if still new, `tryReserve` before setting `admissionInFlight`, model/instruction mutations or calling `admitV2Turn`. A stale stamp exits the queue with a sentinel; retry readiness only outside the queue and only while the original caller is live. Split `threadBridge.ensure` into external readiness versus lease/auth ensuring; the inner path must never call the installer. Pass the reservation through `Runtime.admission.ts` and assert before journal intent and `session.prompt`; retain its lifetime as described above.
3. **Enrollment/control/callback:** `Orchestration.bridge.ts` and `.enrollment.ts` register short owner-control operations before enroll/renew/proof, and track physical invoke/approval work separately. Under a held startup/turn reservation, lease/auth ensuring uses that existing reservation, not a second activation wait. Scheduled renewal obtains a short control token synchronously; if renewal is paused it schedules no new proposal. Read-only reconciliation/cleanup and completion of already-issued operations never need a _new_ execution reservation or wait behind the activation job. Hidden native startups/turns obey the same local admission exclusion without receiving tools or initiating installation.

## 9. Risks and rollout

- **Accepted residual race:** another native client can admit work after observation; hidden native activity may not appear. Mitigate with conservative bounded checks and the stable bootstrap; disclose rather than claim prevention.
- **Bootstrap still reloadable:** other plugin/config/native changes can invalidate it. Exact-owner fail-closed recovery remains mandatory; no universal native execution containment claim.
- **False plug-and-play promises:** unsupported platform/version, absent service, manual/foreign collisions or uncertain history still block. Keep model discovery visible and diagnostics specific; never silently start a private service.
- **Version theatre:** only labels changing is not version pinning. Freeze the full pure-handler dependency closure, enforce source/manifest drift checks in the trusted build, capture both preparation/interpretation, and persist final interpreted receipts before response. The manifest is not runtime byte attestation.
- **Security drift:** pinned business interpretation never bypasses current shared auth/approval/receipt gates. Native crypto/schema changes are breaking; retain explicit signatures and no arbitrary module loading.
- **Starvation/deadlock:** setup waiters must not count themselves as busy or hold queues needed by settlement. Continue using a compatible N bootstrap while only waiting, but invalidate every old readiness stamp before replacement. Bound gate/jobs separately; a lost native/physical outcome remains quarantined beyond those timeouts. Do not stop peers merely to complete an update.
- **Background authority leaks:** waiter timeout is not permission lifetime. The coordinator retains its own tracked permit/borrowed client until finalization, and explicit last-interest cancellation/revocation/deadline stops new work. Background completion never replays a prompt.
- **Legacy/manual upgrade:** retain exact L wire bytes and durable detach/settlement evidence. N's cleanup-only L verifier grants no execution and registry absence proves no physical exit. Foreign/manual configuration edits remain outside automatic authority.
- **Disk evidence retention:** do not auto-delete uncertain artifacts/receipts on a timer. Generation capacity blocks new versions rather than forgetting evidence; broader retention/compaction is separate scope.

Roll out source in phases: tests/boundary proof → versioned owner/dispatch → activity coordinator → runtime/UI → qualification. Do not activate on the user's actual machine as a release test. Rollback changes the app-side default only when safe; bootstrap rollback uses the same activity-aware publication path.
