## 2. Goal and definition of done

### Summary

Keep xterm.js as the terminal emulator and renderer integration. Improve bounded delivery, scheduling, renderer lifetime, and recovery first. Add optional WebGL rendering with a reliable DOM fallback. Introduce an independent Rust local PTY owner only as a separately gated process-isolation milestone; Rust does not render the terminal or decide bigbud product state.

The user wants a smooth terminal in both DOM and GPU modes, optional GPU rendering, resistance to failures, and evidence rather than language-based performance promises. Ghostty was explicitly abandoned. Subsequent decisions require Windows parity before native-owner rollout and exact cold TUI recovery. The user authorized designing a maintained xterm checkpoint extension/fork and an independent TypeScript state process, per-PTY backpressure instead of authoritative output loss, and expanded existing windows-sys bindings. These approvals authorize the design direction, not an unproven exactness claim.

### Corrected recommendations

1. Optional WebGL can improve some rendering workloads, but cannot fix unbounded output, parser work, slow storage, or a blocked server. DOM must receive the same delivery fixes.
2. Process/thread boundaries and bounded nonblocking control lanes provide containment; using Rust alone does not. A native addon or WASM running on the renderer thread is not independent supervision.
3. A write callback proves xterm parser progress, **not that pixels were painted correctly**. Missing callbacks are evidence to investigate, not proof of GPU failure. A timer/probe in a wedged JS event loop cannot report its own failure.
4. Keep the PTY alive when replacing a view. Keeping a PTY alive does not preserve every xterm screen mode or restore a destroyed owner.
5. Do not replace remote receipt ACKs with renderer ACKs mechanically. Transport receipt, retention credit, durable custody, and parser completion are different contracts with different consumers.
6. Reuse and harden the Rust PTY capability, not the remote supervisor's locking/fan-out architecture or remote environment policy verbatim.
7. No native GPU renderer, Rust VT parser, or beta Electron/xterm migration is justified. Exact recovery now justifies evaluating an explicitly owned, versioned xterm checkpoint extension; scattered private-field access from bigbud UI code remains prohibited.

## 4. Plan assumptions and unresolved decisions

### Verified assumptions and how to revalidate

- xterm stays the emulator; Ghostty stays out. Supported by the user's explicit direction. Reopen only if the user changes that direction.
- TypeScript owns authorization, provider semantics, canonical thread/project state, ownership bindings, leases, and user-facing recovery policy. Rust implements authorized systems capabilities. Supported by both accepted ADRs and `crates/AGENTS.md`.
- Existing terminal history is a convenience history, not an exact emulator checkpoint. Supported by reset/replay of the sanitized line-capped string. Verify with alternate-screen and resize fixtures in P0/P1.
- Separate local PTY and TS emulator-state ownership is required for the approved backend-crash survival/exact recovery target. Both must be outside the backend kill tree. Process isolation supplies the fault boundary; language choice does not.
- Numerical bounds below are initial engineering budgets, not measured optima. P0 records baseline; tests must enforce whatever values ship. Any upward change needs memory/latency evidence, and no queue may become unbounded.

### Settled decisions — do not ask again without contradictory evidence

1. **D1 (user-authorized override, 2026-10-10):** Auto/On/Off; **Auto is the default for omitted/reset settings and attempts WebGL now**, independent of packaged-validation status. Preserve explicit Off/On. Both Auto/On obey app acceleration disablement, crash protection, visibility and context budgets, with same-xterm DOM fallback. Never silently clear Linux fallback markers. See section 17 for the consolidated default record; native packaged validation remains unproven.
2. **D2:** **Windows parity required before independent PTY-owner rollout on any OS.** Renderer/backend crash preserves shells; explicit close/restart, normal quit, and update terminate them. Main crash uses a five-minute authenticated reattach lease; backend/renderer loss alone does not start it. Standalone distribution keeps legacy ownership unless separately equipped and validated. No macOS/Linux-first production rollout.
3. **D3:** **Exact cold TUI recovery**, not best-effort raw history. No new disk journal is approved. Preserve this requirement even when it prevents release.
4. **D4 (follow-up approved):** Pursue a pinned, maintained xterm full-state checkpoint extension/fork and independent TypeScript emulator-state process. Keep xterm and TS; no Rust VT parser or Ghostty. Approval to design this is not proof it is feasible or permission to use uncontrolled private accesses throughout the application.
5. **D5 (follow-up approved):** At authoritative retention/state saturation, backpressure the affected PTY; do not drop authoritative output. Other PTYs and control remain responsive. Slow _view_ consumers may detach and reacquire an exact checkpoint without forcing every producer to wait for their parser.
6. **D6 (follow-up approved):** Extend existing **windows-sys 0.61.2** for ConPTY, Job Objects, and secured named pipes rather than add portable-pty. Inspect and test unsafe calls/feature cost before release; a further crate or materially different dependency still needs approval.

**Fidelity definition:** equality of both emulator buffers including retained configured scrollback, cells/attributes/wrap metadata, active buffer, cursor/saved state, margins/tab stops/charsets/modes, incremental decoder/parser state, and subsequent emulator behavior for identical ordered output, resizes, and user input. This is terminal semantic state, not identical GPU pixels, font rasterization, transient selection, or recovery of a dead PTY. No arbitrary shell application is excluded merely because it uses alternate buffers, split escapes, queries, or resizing. Unsupported new emulator addons/protocol extensions must fail exact-capability negotiation, not silently reduce fidelity. Existing xterm limits (e.g. configured scrollback) define the uninterrupted reference too; recovery must introduce no additional truncation.

**Remaining technical gates:** prove full-state export/import on pinned headless and browser builds; complete platform descendant-containment proof or retain cleanup-unknown fences; independently review the narrow protocol/security specification below and this revised plan. No further product question is currently pending. If feasibility reveals a need for new storage, weaker exactness, different platform scope, or new dependencies, stop and ask rather than changing D1–D6. Full plan remains Draft.

## 6. Repository findings and target architecture

### Current topology

```text
Electron main ── launches / stops / restarts ──> TS backend
      │                                           ├─ local BunPTY/NodePTY ─> shell
      ├─ renderer + xterm DOM                      ├─ remote client ─SSH─> Rust remote PTY owner
      │     ↑ WS terminal stream                  ├─ Rust orchestration-delivery supervisor
      │     └─ events → Zustand ring → batcher     └─ ephemeral local Rust workspace watcher
      └─ existing native system-monitor integration

Renderer failure ≠ PTY-owner failure; backend failure currently includes local PTY ownership.
The orchestration supervisor is not on the terminal delivery path.
```

### Approved design direction; implementation/release proofs still required

```text
Electron main (TS policy + actuator + lifecycle)
  ├─ renderer(s): xterm DOM or WebGL, ordered parser callbacks, bounded health reports
  ├─ TS backend: domain authority, authorization, terminal bindings, WS consumers
  └─ independent bigbud-terminal-owner process (outside backend kill tree)
       ├─ authenticated reconnectable local data/control endpoint
       ├─ bounded per-PTY read/write actors → PTY descriptors/handles → shells
       ├─ bounded replay ring + opaque complete checkpoint store (memory only)
       ├─ independent TS state host (pinned xterm headless, per-PTY workers)
       └─ watchdog thread → separate bounded control channel → Electron main

Authority: owner → TS state worker → checkpoint + committed source cut → owner
Views: checkpoint + ordered suffix → backend → WS credit window → renderer scheduler → xterm
Health: renderer → allowlisted preload IPC → Electron → native control channel
Decision: native timeout evidence → Electron validates generation/policy → recover view/window
Remote PTYs: remote service remains PTY owner; upgraded retention → relay → TS state authority.
```

The native owner accepts opaque authorized session identities, not thread commands or provider messages. TS persists the mapping from `(threadId, terminalId)` to `(ownerInstanceId, ptyId, terminalGeneration)`. A daemon-held mapping is execution/delivery state, never a replacement domain database.

The state host implements emulator mechanics, not application domain policy. For packaged desktop, the native owner launches it using the verified packaged Node/Electron run-as-Node executable and a separate bundled entry (`apps/server/src/terminal-state/main.ts`, proposed); reuse `backend/backendEnv.ts:51–55` and artifact path patterns without passing unrelated provider credentials. It is **not** a backend worker or Electron utility process whose lifetime ends with main/backend. Native owner retains a complete validated checkpoint plus unapplied suffix so a dead state host can be reconstructed; a dead native owner remains interruption. Per-PTY TS workers isolate parser stalls; the state host control loop and native control lane must never wait on one worker. No lazy parsing only when a view is visible.

Checkpoint semantics are implementation work in a version-pinned upstream extension/fork, not direct browser access to `_core`. Ship paired headless/browser artifacts from the same reviewed commit; pin addon compatibility to that build. Document ownership, upstream issue/PR status (none verified yet), reproducible build hashes/license, update tests, and removal when upstream supplies the equivalent contract. Do not invent an upstream acceptance promise or publish a fork package without authorization. Fork source changes also follow the 400-line authored-file rule; avoid vendoring an entire unmanaged upstream tree.

### P5a — Narrow local protocol and security specification (review prerequisite)

- Protocol namespace `protocol/terminal-owner/`: typed hello/auth, lifecycle, input/status, output-credit, checkpoint-transfer, and health messages; separate bounded control and bulk connections, both bound to the same authenticated role/session. Reuse framed-codec mechanics but not remote-agent `v1::Frame`. No generic exec, filesystem, arbitrary signal, JavaScript evaluation, or renderer-originated native command endpoint.
- Roles: main owns lifecycle policy/lease; one current TS backend controller authorizes spawn/close/resize/input and reconciles bindings; state host consumes source bytes, submits opaque checkpoints, and submits sequenced emulator responses; renderer only uses existing authorized WS/allowlisted Electron channels. Owner enforces opaque capabilities and fences, not project/provider semantics. State-host capability is limited to already-authorized PTYs, not arbitrary spawn.
- Hello deadline 5 s; authenticate a fresh connection challenge with profile-private secret through private inherited/bootstrap channel; bind protocol/build/owner epoch/role/controller generation to the session. Reject incompatible majors or missing required capability before admission. No token in argv, shell environment, renderer, or diagnostics. Directory/file owner and permissions and Unix peer UID/Windows pipe SID validate isolation; the secret is not a defense against already-compromised same-user code.
- Control encoded-frame limit 64 KiB, bulk encoded-frame limit 64 KiB, checkpoint page payload <=48 KiB. Check length before allocation, require message payload, checked arithmetic, UTF-8/string limits, safe u64 decimal conversion, and 5 s partial-frame deadline. No compression before a bounded decompression contract. Handshake negotiates lower limits only; remote protocol remains compatible.
- Admission reserves a ledger slot, execution slot, and maximum terminal-response byte/item capacity **before side effects**. A disconnected/full writer cannot destroy the outcome; retain it for `getStatus`, subject to safe expiry floors. Completion/control has a 256 KiB/256-item peer budget and 4 MiB/4096-item profile budget; pending admissions <=128/profile. Slow control writers get a 5 s deadline and disconnect without cancel/replay of accepted mutations. Do not accept new work when response reservations cannot be made.
- Heartbeat/health is separate coalesced state: one latest report per registered view (<=128/profile), <=4 KiB/report, 512 KiB/profile. Telemetry never consumes mutation-response reservations. Native timeout thread writes only to nonblocking bounded queues, never to sockets/stdout. Recovery intents have bounded IDs/outcomes and generation checks like other control; saturation yields degraded/unavailable, not an unbounded priority queue.
- Frame/request digest fixtures include role spoofing, wrong owner/controller epoch, missing payload, extreme geometry/length, replayed nonce, different-payload duplicate, expired operation ID, ACK past produced/committed cut, unauthenticated bulk reconnect, queue reservation rollback, and **saturated control socket while mutation completes**. An independent security/protocol review must approve this specification before implementation of owner admission; do not leave the architecture for an implementer to choose ad hoc.

Generated FFI has an unsafe calling surface; use narrow RAII wrappers, ownership diagrams, checked Win32 results, and adjacent SAFETY comments. Its 0.61.2 installed manifest exposes `Win32_System_Console`, `Win32_System_JobObjects`, `Win32_System_Pipes`, `Win32_System_Threading`, `Win32_System_Environment`, `Win32_Security_Authorization` alongside existing Foundation/Security/IO/Storage. Enable only used features, share the pin through workspace dependencies, measure binary/build change; approval D6 covers this direction, not unspecified third-party crates. Microsoft maintains the bindings; no claim of security certification or measured size benefit.
- Use `CreatePseudoConsole`/`ResizePseudoConsole`/`ClosePseudoConsole`, separate input/output pipe owners, and `STARTUPINFOEX` pseudoconsole attribute. Construct UTF-16 environment and correctly quoted argv without invoking a surprise shell; preserve NodePTY's existing shell/cwd/drop-path behavior. ConPTY requires Windows 10 1809+; packaged Electron target requirements may be stricter. Capability-probe the actual packaged OS and fail before creation on unsupported hosts.
- Create shell **suspended**, assign it to a private Job Object without breakaway permission, then resume; if assignment fails, terminate the suspended process and return failed-before-spawn. Hold process/job handles rather than naked PID authority. Query job membership/accounting and wait on job-empty/process exits; use `TerminateJobObject` for forced cleanup. Keep job handle non-inheritable. Nested job/launcher constraints must fail explicitly, not fall back to uncontained spawning. Native owner must not remain in a main/backend kill-on-close job; prove independent launch or keep feature unavailable.
  Set `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` on the shell job, held solely by the native owner: owner death closes containment handles, whereas main/backend death does not. Verify no duplicated inherited handle keeps it alive. This Windows-specific cleanup behavior does not mean Unix owner death is equally confirmed or that PTY recovery survives owner death.
- ConPTY communication channels use dedicated blocking reader/writer threads as required by the API, not overlapped assumptions copied from owner IPC. Closing pseudoconsole can block while output drains: shutdown must cancel/coordinate pipes and drain completion on dedicated workers, never the native watchdog thread. Prove cancel/join bounds with a child not reading stdin and saturated output. Partial write counts feed the same input uncertainty state machine.

Existing resource-cleanup Win32 wrappers illustrate checked handles, not PTY containment.

Test native Windows x64 (and every additional shipped Windows architecture), executable locks, spaces/non-ASCII profile/cwd, PowerShell/cmd/default user shell, resize, close/update, main/backend hard kill, and reconnect. ### P5c — Descendant containment and parent-loss proof

Unix shell process-group kill plus `waitpid(shell)` is **not** whole-tree cleanup: job-control foreground/background processes occupy other groups and descendants can daemonize. Define resource disposition as `live`, `terminationPending`, `confirmedTerminated`, or `cleanupUnknown`; only confirmed termination releases destructive worktree/update fences. Persist/reconcile unknown dispositions in existing TS lease storage. Owner disappearance cannot erase those leases.

Launch owner in an independent Unix session/process group (no parent-death kill tied to backend/main); close/mark CLOEXEC all bootstrap sockets/secret descriptors and do not let shell inherit owner lifetime channels. State host lives under owner policy, not stdin EOF from backend/main. On Windows use explicit inheritance lists/non-inheritable job handles and prove absence of parent job containment. Kill main/backend with SIGKILL on Unix / hard process termination on Windows, not merely graceful IPC, to establish survival.

For Unix cleanup, inventory terminal session members and all observed descendant identities using native PID+start identity/session/group facts, signal all owned job-control groups, repeat discovery while stopping forks, and reap owned children. Linux subreaper/delegated cgroup mechanisms and macOS process enumeration have different guarantees; **periodic ancestry sampling alone cannot prove no escaped descendant**. An adversarial setsid/double-fork fixture or unobservable child produces cleanupUnknown and retains fences, never a successful tree-kill result. Windows job containment can supply a stronger ordinary descendant boundary but its breakaway/owner-death behavior still needs proof. A reviewed cross-platform containment proof (including its honest unknown cases) is a remaining technical blocker, not permission to promise universal cleanup from a PID list. Do not add privileged helpers/cgroup requirements or narrow the user-visible guarantee without review.

Required fixtures on every platform: shell with foreground job, background job, grandchildren and active respawner; detached/daemonized descendant; shell exits before child; PID reuse/stale identity; owner death; main/backend hard kill; normal quit/update; forced cleanup timeout. Verify process/resource disappearance rather than only shell PID, listener closure, or direct-child exit. Unknown cleanup blocks updater and worktree deletion even after the 5 s budget; expose a recoverable error and reconciliation path rather than leaking ownership silently.

### P6 — Exact checkpoints, single emulator authority, and ACK custody

**Order:** P6a feasibility precedes P5 implementation approval; P6b/c integrate after P1/P4/P5 primitives. **Deliverable:** exact cold recovery, not a raw journal. This is the largest newly approved design obligation and remains unproven.

#### P6a — Checkpoint extension feasibility and ownership

1. Create a focused compatibility harness under proposed `scripts/terminal-reliability/checkpoint.*` and tests beside proposed `apps/server/src/terminal-state/checkpoint.*` and `apps/web/src/components/terminal/TerminalCheckpoint.*`. Evaluate a versioned full-state export/import extension built inside paired xterm headless/browser 6.0.0-derived artifacts. Keep the application-facing adapter in `packages/shared/src/terminalCheckpoint/` with explicit subpath exports, schemas in `packages/contracts/src/workspace/terminalCheckpoint.ts`, and no dependency from Rust to xterm. Do not install serialize as a supposed solution. Dependency packaging/pinning of the maintained extension is a design deliverable to review before production integration; no new published package name or upstream support exists today.
2. Inventory every continuation-relevant field in xterm's buffer, buffer line, terminal/core, input handler, charset/mode, Unicode, decoder and parser services. Schema includes both buffers and scrollback limits; cells/graphemes/widths/attributes and extended underline/hyperlink data; wrap flags/reflow state; cursor including wrap-pending, saved cursor/attrs/charset; margins/tab stops; current attrs/protection; all modes including mouse/focus/paste/origin/insert; charset designations; terminal geometry; title/palette state where emulator-visible; decoder carry (UTF-8 and UTF-16 string writes); partial CSI parameters/collect state, OSC/DCS payload and handler state; and pending ordered control metadata. No inference from painted cells or ANSI synthesis. Schema/build/Unicode/handler-set fingerprint rejects incompatible imports.
3. Snapshot at a quiescent operation boundary after the current write callback and resize/control operation settle. That callback **does not imply the escape parser is in ground state**; export valid partial-sequence state. No JS closure/Promise can be serialized: wait for an active asynchronous parser hook to settle before the cut; timeout pauses that PTY and fails the checkpoint, never drops the hook. Current terminal integration has no custom parser-hook/Unicode addon registration (source search); any future hook requires a checkpoint-aware serializable handler contract and matching registration fingerprint. Built-in partially collected control-string state is still mandatory. New unsupported addons fail exact capability explicitly.
4. Import into a fresh, detached terminal with input and external side effects gated. Validate sizes/indices/references/enums before allocation, construct cross-service references consistently, restore before normal render/open where supported, invalidate render caches, then attach public Fit/WebGL addons and render from restored state. Import is not a VT write and cannot execute historical queries, bell/clipboard/window side effects or protocol responses. Imported size is original geometry; new visible size enters the ordered resize lane afterward.
5. Differential tests compare canonical full state **and continuation** against uninterrupted execution, both headless→headless and headless→browser. Include the four reproduced failures; arbitrary cuts within UTF-8, CSI, OSC, DCS; saved/alternate buffers, margins, wrap/reflow/resize, Unicode/wide/combining cells, palette/hyperlinks, mouse/paste/key encoding, queries, and asynchronous hook pause/resume. Fuzz chunk/cut/resize boundaries with deterministic seeds. Add state-field coverage review: passing screenshot fixtures alone is not a completeness proof. Exact feature stays off if any supported-state mismatch remains.
6. **Blocking exit:** reviewed complete schema/field inventory, reproducible pinned paired artifacts and maintenance/removal policy, passing fidelity harness, and bounded memory/import/capture evidence. The current public APIs fail this gate. Do not call the whole plan ready merely because a future fork is permitted.

#### P6b — Authority, source cuts, and side effects

1. Introduce `apps/server/src/terminal-state/{main.ts,session.worker.ts,authority.ts,checkpoint.*,protocolReplies.*,limits.*}` as a separately bundled executable subsystem, not a service in backend's event loop. TS worker per active PTY consumes immutable raw output/control records; owner remains byte/handle custodian. Checkpoint metadata binds owner epoch, PTY generation, emulator build/schema, source output cut, ordered resize/control revision, and protocol-response ledger cut. The owner stores opaque bounded bytes; it never parses VT or decides thread state.
2. Serialize output, resize, reset/clear, and exit into one per-PTY authority lane. Resize is a revisioned barrier: stop scheduling reads, settle already-read records, resize emulator and invoke native PTY resize before admitting subsequent reads; record ordered result. Bytes already in the kernel are ordered by this defined read/barrier contract, not a claim to reconstruct the producer's wall-clock order. If resize partially applies/fails, fence further mutations and reconcile actual geometry or show unknown; don't claim both peers committed. Read replica applies precisely these records, not its own independent refit state changes. Keep existing last-accepted resize policy.
   - In exact mode, every emulator-mutating write must have authority provenance: audit `writeSystemMessage`, open/write failure helpers, clear commands, and local banners. Route required in-terminal notices as typed sanitized authority display records with protocol replies suppressed, or keep failure/status UI outside the emulator. Never let renderer-only writes silently diverge from checkpoint state. Theme/font-only UI changes need not enter the VT stream; geometry changes do.
   - Backend `serverEpoch` may change while PTY/state authority lives. Reconnect maps relay cursors to stable owner epoch/terminal generation/source cuts; it cannot treat a new server epoch as a new shell or invent a fresh source sequence. Establish and test this mapping in terminal delivery contracts and bindings.
3. The authority alone emits **output-generated protocol responses** to the PTY. A checkpoint extension must distinguish protocol responses from user-originated keyboard/paste/mouse/focus data; xterm `onData` alone conflates them. Renderer suppresses protocol responses in live AND replay modes, forwarding only typed user-originated data through existing authorization. Authority has no DOM: any enabled query that needs viewport/font/pixel data must consume versioned, ordered trusted geometry metadata matching the active size policy. Audit all handlers; unavailable required query state is an exact-capability blocker, not a guessed response. Browser-only UI side effects are allowlisted and deduplicated by source event ID; replay suppresses them.
4. Authority response IDs derive from terminal generation, source record/response ordinal, and bytes digest; native input admission reserves outcome identity before writing. Checkpoint+response ledger commits together in owner memory. On worker replay, generated responses query the existing ledger and are not re-emitted; ambiguous/expired outcome fences input. A worker crash between response generation, acceptance, write, and checkpoint must not repeat a query response or bypass `partialUnknown`. User input and protocol responses use the same per-PTY serialized writer but distinct origin metadata, not competing writers.
   - Response emission itself needs bounded admission inside the extension: suspend parsing at an awaitable response boundary when capacity is unavailable, rather than letting synchronous `onData` callbacks allocate an unbounded outbox or drop a response. Such a suspended parse cannot be checkpointed as a completed cut. Drain/resume when writer capacity returns; uncertainty fences it. Pin replay-required response identities against TTL eviction; trigger checkpoint/stop source before ledger exhaustion. Do not claim existing xterm `onData` provides this contract.
5. Capture initial empty state **before spawning/unblocking initial shell output**, then checkpoint at least every 1 MiB of authority-consumed output or 1 s of progress (whichever first), also at idle/resize boundaries as needed. Snapshot freezes only that PTY worker; other workers and native watchdog continue. Transfer pages with backpressure. Commit only after owner has validated entire schema envelope/length/digest and atomically installed checkpoint plus cuts/response state; until then retain old complete checkpoint and all suffix bytes. Latest consumed-output cursor alone is not reclaim authority. On memory pressure pause that PTY before unretained reads/authority operations; no unbounded copies, no sanitizing live bytes, no journal fallback.
6. Owner can discard source bytes <= committed checkpoint cut only when that checkpoint is complete, replay-response status is safe, and any active bounded transfer pins have been released or cancelled. Keep one previous checkpoint until replacement commit; readers hold generation-scoped references under the aggregate budget. A slow view gets a newer exact checkpoint, not an authoritative source gap. A state worker crash restores latest complete checkpoint+suffix; a simultaneous owner+state loss is outside memory-only survival and is reported as interruption. Retain enough response dedup identity for the oldest replayable checkpoint; TTL compaction cannot make automatic replay unsafe.

#### P6c — Views, remote boundary, legacy compatibility

1. Name ACK stages: `received` (transport), `retained` (memory bytes), `checkpointCommitted` (owner holds full emulator state+cut+response ledger), `parsed` (specific view's contiguous callback/import completion). None means durable-on-disk or pixels-painted. A discard/detach releases its transport credit only, never successful parser/custody credit.
2. P1 paged install uses checkpoint at S plus bounded suffix to fixed H; input disabled and no historical responses until completed import/parse + installed(H). Then stream H+1. All view reconstruction paths (tab switch, renderer crash, parser recovery) use this same protocol. In-place WebGL fallback needs no checkpoint or PTY operation.
3. For **desktop remote terminals**, remote agent remains PTY owner. Negotiate read-credit/retention capability in P4; relay to the independent local TS authority and store its opaque checkpoint in the local recovery owner under a remote owner-epoch/PTY-generation namespace. This does not grant local Rust control of remote domain state. Remote retention credit can advance only after actual checkpoint+suffix custody at the independent local recovery owner, not backend enqueue or a cursor file. Backend/SSH interruption pauses remote read credit once bounded retention fills; reconnect resumes the same generation. Test every crash point across remote read → relay → authority → local checkpoint commit → remote release.
4. Old remote agents without pause/retention capability and standalone backends without the independent state/recovery-host distribution cannot advertise this exact crash-recovery capability. Preserve existing legacy mode explicitly until upgraded, and do not count it as D3 completion. No silent recreate or weakening of remote unknown-input protection. Standalone exact view recovery can use an authority tied to its server lifetime, but backend-crash survival requires a separately validated independent deployment; do not widen current distribution/lifecycle scope implicitly.
   - This is compatibility sequencing, not a product exemption from exact view recovery. New exact-mode local/remote sessions must pass the same cold-view fidelity gate; unsupported capability blocks enabling that mode. Existing legacy sessions remain visibly legacy until explicit close/new generation; no automatic restart to migrate them.
5. Existing sanitized history remains convenience/legacy data and its current persistence can stay bounded. New exact sessions require authority from generation creation; cannot synthesize missing past parser state for an already-running legacy session. Feature gating affects new generations; never restart a live shell just to migrate it. On exact chain loss/mismatch, keep shell and input visibly paused, offer explicit diagnostics/retry/close, and never mark truncated history as exact recovery.
6. No new journal, checkpoint disk persistence, or disk-retention UI in this plan. If memory-only design cannot meet agreed fault boundary/capacity, stop for approval rather than add persistent terminal secrets. Host/OS restart, power loss, and lost native-owner memory do not promise live-shell restoration.

### P7 — Independent health decision lane and safe Electron actuation

**Dependencies:** P3/P5/P6, approved D2/D3, verified exact renderer restoration. Not necessary to ship P1/P2.

1. Extend local owner `health/` and `protocol/terminal-owner/health.proto` with registration, latest progress, probe request/result, visibility/suspend/disconnect state, and recovery intent. 3. Distinguish: (a) renderer responds but parser progress stops with outstanding bytes; (b) renderer heartbeat stops but Electron still responds; (c) backend disconnects; (d) Electron control is unavailable; (e) no pending output. Only (a) requests a local FIFO probe and potential view recreation. In (b), a probe cannot run, so report renderer-unresponsive evidence, not a confirmed parser/GPU defect. Explain possible loss of unsaved renderer-only state and shared-process impact. Repeated crash/reload uses a circuit breaker and native retry/error UI. ## 9. Risks and rollout

- **False certainty:** source risks are not diagnosed incidents. P0 is mandatory before performance claims; no “Rust makes it fast/crash-proof.”
- **Migration breadth:** TS delivery/WebGL may be staged independently, without claiming exact-recovery completion. Harden native mechanics before extracting them. Exact-checkpoint extension and watchdog actuation are separately reviewed milestones; no implementation starts under this planner.
- **Recovery damage:** whole-renderer reload can lose unrelated renderer-only state or affect shared webContents. Prefer in-place addon disposal/view-only repair; ask before forcing an unresponsive process and enforce circuit breakers.
- **Semantic output loss:** D3/D5 require a full checkpoint+suffix chain and per-PTY backpressure. Unbounded pending parser state and checkpoint peak memory remain feasibility risks. Never fabricate exact snapshots from a tail or silently truncate to fit a budget.
- **ACK mistakes:** false parser/durable ACK destroys recovery evidence. Keep ledgers separate, fence generations, and inject failures between every custody transition.
- **Native I/O hazards:** fork/exec, input partial writes, blocking fan-out and shutdown are correctness work, not cosmetic refactors. Unsafe changes need focused review and native tests.
- **New service lifecycle:** independent owner survival introduces orphan cleanup, profile authentication, worktree lease and updater obligations. A detached daemon without these is not ready to ship.
- **Windows parity:** not present today; required before independent owner rollout anywhere. Existing bindings reduce dependency sprawl, not Win32 correctness work. Native test/packaging access is a release prerequisite, not evidence already obtained.
- **Checkpoint maintenance:** a private full-state extension couples both xterm builds, parser schemas, Unicode and query behavior. Treat upgrade drift as an incompatibility; review field inventory and regenerate fixtures on every version change. Current public serialization demonstrably cannot substitute.
- **Privacy:** checkpoint memory contains terminal secrets. Do not log dump bytes, input, output, capabilities, or environments; synthetic fixtures only. No new journal/checkpoint disk persistence. Existing history persistence remains a separate legacy feature, not new exact custody.
- **Rollback:** Off disposes GPU addon in place. Disable new exact/native generation admission without downgrading existing sessions; they retain pinned compatible owner/state-host/xterm artifacts until explicit close/quit. Existing exact sessions may remain paused if their compatible renderer is unavailable; never silently reattach through legacy history. Do not hot-swap checkpoint schemas, move live PTY handles, overwrite in-use binaries, erase uncertain bindings, or auto-respawn on legacy. Protocol/custody rollback keeps leases and known/unknown operation outcomes intact.

### Implemented source and regressions

- `pty/input.rs` owns one nonblocking writer per PTY. Input identity/digest is reserved before work reaches that writer. A same-sequence/same-payload duplicate observes the existing outcome without replay; changed bytes conflict. Outcomes distinguish accepted, writing with known byte count, written, failed-before-write and partial-unknown. Partial uncertainty permanently fences all later input, including queued entries. Five-second deadlines start at **admission**, not worker start. Cancellation holds the admission permit through queue settlement, preventing accepted work from racing behind the final drain. An unexpected legacy wait timeout closes admission rather than allowing delayed execution past a rejected response.
- Input bounds include queued and in-flight bytes/items: 64 KiB request, 512 KiB/256 entries per PTY, 8 MiB aggregate payload; 4096 retained status entries per PTY, 8 MiB aggregate conservative ledger charge, ten-minute completed TTL. Compaction advances an expired-through floor; expired identities never execute again. These are internal generation-local primitives, **not** the required epoch/controller wire digest or lifecycle reservation protocol.
- `pty/platform.rs` owns parent descriptor setup/rollback, nonblocking flags and CLOEXEC. Failed clone/writer setup terminates/reaps the owned child with a bounded verification loop. Child `chdir` failure exits 126 before exec. Changed/new unsafe sites have adjacent invariants/SAFETY comments. This is not a descendant containment or native Windows proof.
- `session/pty_controls.rs` resolves owned handles under `AgentSession` and executes input waits, resize/signal and close/join outside it in supervisor dispatch. Input stops when restart admission is fenced, while close/ACK remain available. This does **not** claim all legacy spawn/workspace/journal I/O has been removed from controller locks.
- `supervisor/writer.rs` gives every socket one FIFO writer, bounded stream admission and five-second I/O deadline. Producer fan-out performs no socket writes. Slow/dead subscribers detach independently; duplicates and disconnect references are removed. Connection admission precedes creation of its reader thread (64 connections), at most eight subscribers per operation, 256 KiB/256 stream frames per socket, 8 MiB aggregate queued/in-flight bytes. Legacy file/replay replies retain the existing 1 MiB protocol-frame ceiling and are paced on the connection thread in a separately bounded reply lane, never on producer/state locks. Replies drain before successful close/restart exit. A lost PTY-create response still starts the accepted child's retention/reap worker. Process/watch semantics are not reinterpreted as terminal ACKs.

## 18. Orca-derived delivery and rendering phases (O0–O6) — 2026-10-21

**Status:** O0–O5 implemented and validated on the working tree (2026-10-21; not committed). O6 stays behind the unchanged D2 Windows-parity gate. See "Implementation record" at the end of this section for as-built deviations and evidence.

### Why

The user reports bigbud's terminal "moves like 1–2 fps" next to Orca (`stablyai/orca`, inspected at `be4e0719b8949dd44b6b1681f70499b486a6c1a3`, MIT) and that opencode's palette looks off. Orca also uses xterm.js, so the gap is in delivery, scheduling, renderer attach and terminal identity, not the emulator. Research evidence (reproducible probes, not product benchmarks):

- opencode 2.1.1 wraps every frame in DEC 2026 (590 BSU/ESU pairs in 12 s); macOS PTY reads are ≤1024 bytes, so one frame spans several messages; sustained volume while typing is ~38 KB/s. Latency/jitter per hop matters more than throughput.

**Deviations from the O5 spec, with reasons.**

1. No 2 ms server flush timer and no interactive fast path. bigbud has no timer-based send batching to bypass: the PTY coalescing worker already merges reads, each item is offered immediately, and Effect RPC's stop-and-wait ACK batches whatever accumulated while a chunk was in flight. A 2 ms timer would only add latency. Orca needs both because it batches IPC sends on a timer.
2. Adjacent output events are split but never merged on the server: merging events with different `createdAt` would break the view's snapshot-cutoff dedupe (lost or duplicated output).
3. Hold when **any** scoped subscriber passes high water, not when all are saturated: this bounds every subscriber's backlog (slowest-consumer backpressure). Holds are released when a subscription ends, so a closed or failed view cannot keep a shell paused.
4. Overflow ends the stream instead of emitting a typed item; the client's normal resubscription then triggers an exact snapshot replay (D3/D4) rather than pausing the view. This is reachable only when the PTY cannot be paused (BunPTY, remote adapters).
5. Hydration-pending events are acknowledged on receipt (bounded by the intake's existing 1 MiB / 4096-item budget), so credit cannot strand during open.
