## 4. Assumptions and trust model

- **Trusted root:** the launched, integrity-verified desktop main package and verified native owner, with the logged-in OS account and kernel enforcing ordinary file/IPC access. Package-anchor provisioning is a release prerequisite (§11), not assumed present because files exist.
- **Untrusted:** renderer/guest/subframe messages, PTY output, IPC bytes, claimed roles/PIDs/builds, profile filesystem entries, reconnect state and stale responses. Backend and state host receive least-authority protocol credentials; neither receives root material. TS backend still authorizes user/domain requests.
- **Honest scope limit:** same-user unrestricted native code can read same-user files, inspect processes or replace a user-writable installation. A 0600 secret/DACL does not sandbox a compromised unrestricted backend or hostile shell running under that same account. This design prevents protocol role escalation, accidental credential propagation, cross-profile/foreign-user access and untrusted-renderer command injection; it does not claim protection against an already compromised main/account/kernel. Stronger same-user process isolation requires a separate approved sandbox/privilege design.
- **No new cryptographic dependency:** SHA-256 already exists in the workspace; TS uses node:crypto. Standard HMAC-SHA-256 construction and fixed-length constant-time tag verification require focused review/test on the native side, not an invented cryptographic protocol primitive or an unapproved crate. Implementation may not add a dependency to bypass that review.
- **No output journal:** only credentials/rendezvous identity and existing TS domain binding/lease/operation reservations persist. Native operation outcomes/high-water/floors live for the owner epoch in bounded memory; owner death makes its old operations unknown, not reusable.
- **No future-code claims:** current P4/checkpoint sources are owned by another agent and deliberately uninspected. Adapter contracts below are requirements that must later be reconciled, not assertions about that work's completion.

## 5. Scope

**In:** local owner authentication, capability issuance, epochs/takeover, bounded protocol framing/outcomes, profile rendezvous, trusted launch/minimal env, Windows handle rollback, coordinated lifecycle/update, P7 recovery IPC guards, tests and release gates.

**Out:** editing/rewriting P4 mechanics or checkpoint serialization, deciding provider/domain behavior, installing new dependencies, changing approval D1–D6, introducing disk output retention, native GPU/Rust VT/Ghostty, live launch, elevation/services/privileged helpers/new cgroup requirements, or silently weakening Windows parity/Unix cleanup claims. Remote transport authorization is not replaced by this local protocol.

Stale native identity never licenses a new shell.

## 7. Executable security design

### 7.1 Identities, capabilities, and operation-role matrix

All IDs are opaque; native must not parse thread/project/provider identities. Random values use 256-bit OS CSPRNG material; epochs are random 32-byte values, generations/counters unsigned u64 with overflow fatal to further admission (no wrap). JS wire cursors are validated decimal strings, not unsafe numbers.

| Identity                                              | Issuer / lifetime / binding                                                                                                                                                                   |
| ----------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `profileIdentity`, `profileDigest`                    | Main supplies existing resolved profile facts; native independently opens/verifies root object identities. Full canonical tuple below; digest is not a substitute for tuple equality.         |
| `artifactSetDigest`                                   | Verified package manifest; pinned for the entire owner epoch and all its children. Self-hello cannot change it.                                                                               |
| `ownerEpoch`, `endpointInstance`                      | Owner, only after exclusive profile lock; fresh every actual owner process. Endpoint instance also changes on a newly bound endpoint, invalidating old lane tickets.                          |
| `mainGeneration`, `mainSession`                       | Owner authority actor on successful root-main acquisition, never supplied/incremented by a client. Exactly one current main.                                                                  |
| `controllerGeneration`                                | Owner at current main's CAS replacement request. Exactly one admitted backend controller; takeover is initially reconciliation-only.                                                          |
| `hostGeneration`                                      | Owner for verified host launch/credential rotation. Host process identity is recorded separately; reconnect is not an implicit process restart.                                               |
| `grantId`, `scopeRevision`, `authSession`, `laneId`   | Owner, bounded ledger. Role, parent main generation, backend/host generation, capabilities, PTY allowset, expected child process identity and artifact digest are immutable grant attributes. |
| `operationSequence`, `ptyGeneration`, `inputSequence` | Stable owner-epoch/per-PTY ledgers, not reset by controller/main replacement. Existing TS terminal generation remains authoritative.                                                          |

Root secret `Kprofile` (32 bytes) is accessible only to main/owner by contract; never passed to backend, state host, shell, renderer or logs. Persist it in the protected native identity directory using §7.7. Its existence is not proof of a running owner. Owner derives epoch-specific root-auth key from `Kprofile`, full profile digest, owner epoch and artifact digest. Current main alone requests grant issuance/revocation/controller replacement; native owner issues and enforces scoped grants. Owner may rotate a host grant only under the already-installed current-main host-launch policy, never because host asked for broader rights.

Root derivation is exactly `HMAC-SHA256(Kprofile, C("bigbud/terminal-owner/root-auth/v1", profileDigest, ownerEpoch, artifactSetDigest))`; scoped Kauth is the independently random per-grant key, not Kprofile or a client-chosen role-derived key. Capability/scope/limits in the handshake must match the owner-held grant and the child's private bootstrap description exactly.

### 7.2 Credential issuance and mutual-authentication state machine

**Bootstrap:** main verifies artifact set/profile (§7.6–7.7), launches owner through a private inherited duplex/bootstrap channel, and supplies only owner root bootstrap there. Owner never trusts root config received over an unauthenticated public endpoint. For reattach, main loads protected profile root material and authenticates the live owner without spawning first. Missing/mismatched root for an existing locked owner is `ROOT_IDENTITY_UNAVAILABLE`, not “delete and recreate.”

Main asks owner `IssueGrant` with role, immutable capability set, maximum quotas, authorized PTYs or controller create budget, expected launched process identity, and parent generations. Owner returns a random `grantId`/32-byte secret only on main's authenticated control response. Main delivers a backend grant by private bootstrap fd3; owner delivers host grant by its separate private host management/bootstrap pipe. Grants never appear in rendezvous, argv/env, error strings or renderer bridges. Parent closes its write end after bounded bootstrap; unrelated children inherit neither end. Grant TTL before use is 30 s by owner receiver clock, one successful authentication only; no client-selected expiry or TTL renewal.

Expected child identity is established **before grant issuance**: launch the verified child into a bootstrap-wait state with no domain/native admission, obtain its OS handle/start identity, then issue/deliver its grant. Failed grant delivery terminates/reconciles that waiting child rather than granting an unknown PID. Existing host credential rotation uses a retained private owner-host management channel with a fixed credential-rotation message; that channel has no host-to-root command facility. It is not inherited by shell workers. Close it only at host shutdown, unlike one-shot bootstrap.

For backend credential rotation, retain a distinct main→backend private credential-management pipe after initial fd3 bootstrap, with only a typed replacement-grant message. Do not reopen a credential channel through renderer IPC or environment. If that pipe is lost, ordinary running-state recovery replaces/reconciles the verified backend under existing policy; quiescent recovery uses only the bounded exception in §7.8a. It is not permission to keep reissuing credentials to an unverified process.

No application work or authority CAS yet. Lost finish/ack consumes a scoped credential but cannot acquire main.                                                                                       |

**Authentication is not authority acquisition.** Root authentication has a required `RootIntent.mode` and `RootIntent.use`, both MAC-bound. `mode = ACQUIRE | RESUME | ROTATE | HANDOVER | STATUS_ONLY`; `use = ORDINARY | CLEANUP_ONLY | READ_ONLY`. Mode/use, root operation sequence/attempt ID, expected main generation/session, expected authority revision, subject process identity and handover ticket ID cannot change between Hello, proof, FinishAck and RootCommit. Status-only uses zero mutation identity and READ_ONLY; it never renews/cancels orphan lease, acquires main, mints grants or changes lifecycle.

| Root mode   | Authentication result                                            | Only authority-changing commit allowed after SessionReady                                                                                                                                                                                                                                                                                                                        |
| ----------- | ---------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ACQUIRE     | Candidate; no current-main rights                                | RootCommit CAS requires expected current main generation/session/revision and no live incumbent (bootstrap zero or proven dead prior main). ORDINARY requires bootstrap or unexpired orphan state. CLEANUP_ONLY permits quiescent/unknown state after incumbent death but keeps all shutdown/admission fences; never revives expired sessions. New main generation = previous+1. |
| RESUME      | Candidate for same verified main process                         | RootCommit CAS requires same main process identity/generation, exact old disconnected mainSession, permitted lifecycle/use. Fence old lanes; replace mainSession without incrementing generation. Only ORDINARY unexpired-orphan resume cancels that lease; cleanup resume does not.                                                                                             |
| ROTATE      | Candidate while old current-main session stays active            | RootCommit CAS requires exact current main generation/session and same verified process. Atomically install candidate session and fence old lanes; same generation, no orphan interval. No ordinary rotation can switch use to cleanup or vice versa without the lifecycle's required authority transition.                                                                      |
| HANDOVER    | Candidate bound to current main's one-use PrepareHandover ticket | RootCommit CAS consumes ticket only if old main generation/session and named replacement process still match, ticket unexpired, lifecycle/use unchanged. Increment main generation once and fence old authority.                                                                                                                                                                 |
| STATUS_ONLY | Authenticated read-only root observer                            | No RootCommit or other mutation accepted. Only GetAuthorityStatus, GetRootTransitionStatus and bounded inventory/operation status. It may learn current fences to prepare a later new handshake, never upgrade this session in place.                                                                                                                                            |

RootCommit is the **only** main authority CAS: atomically reserve/record the root operation outcome, validate the complete RootIntent again, install main session/generation/use, consume handover ticket if any, revoke superseded grants/lanes and update applicable orphan state. Then return the retained result on that candidate session. Candidate deadline is 5 s after SessionReady; authority has not changed if it expires before commit. SessionReady and RootCommitResult are distinct messages; there is no implicit first-command acquisition. Current-main sessions have 10 min lifetime with explicit rotation before expiry; root status sessions last at most30 s. Root candidates count against reserved root slots while awaiting commit.

Handshake-derived session keys do not change on RootCommit. Its one matching authenticated RootCommitResult may advance the candidate's expected main generation/session to the exact committed result; validate MAC, candidate session, pending attempt/digest and legal +1/same-generation transition **before** installing those receive fences. No arbitrary status/frame may advance them. If result is lost, root status reconciliation followed by RESUME is required; do not accept generic newer-generation frames as acquisition proof.

**Lost-response algorithm:** before RootCommit, lost OwnerFinish/FinishAck/SessionReady means no main acquisition; discard candidate and authenticate afresh (a consumed scoped credential requires fresh main-issued credential). If RootCommit may have been sent, open STATUS_ONLY and query `(ownerEpoch, rootOperationSequence, attemptId, intentDigest)`; owner returns notCommitted, committed(result), pending or expiredUnknown. It never changes authority. A committed result includes main generation/session/use and is immutable; query/retransmit of the same root operation cannot reapply CAS. If that committed session was disconnected, use a **new RESUME intent/sequence** naming the returned generation/session, not a new ACQUIRE. Pending/expiredUnknown blocks automatic acquisition until status/current-process identity reconciles it. Root sequence floors persist for the owner epoch; expired attempts never execute again. On a still-live candidate session a duplicate exact RootCommit returns the retained result only.

`notCommitted` must be **terminal**, not a transient absence in the mutation ledger: if the named authenticated candidate is still live, has a queued RootCommit or an unresolved close/timeout, return pending even when no CAS has run. Retire that candidate only through ordinary disconnect/deadline processing in the same authority actor, fencing/discarding all unadmitted queued commits and retaining a bounded terminal notCommitted record. Query itself does not retire/fence/acquire anything. A new candidate cannot bind an already-live or retired `(sequence,attemptId)` to another session. Authenticated candidate registration reserves a bounded tentative attempt slot; retirement records notCommitted and preserves epoch-wide high-water/floor semantics without installing main authority. Unauthenticated Hello/status-only never consumes mutation sequences. A requester that never registered a verified candidate gets unknown rather than proof that a delayed attempt cannot exist. Fresh acquire/resume after loss uses authenticated status's next available sequence only once the earlier candidate's terminal status is established; a late old commit is fenced, not allowed to win after a supposedly final notCommitted reply.

Scoped session/key rotation is root-issued and uses the immutable-scope replacement below; authentication alone cannot activate a replacement or a reconciliation-only backend. Only one pending replacement per role. Expired host session while main is absent pauses its source until permitted root reauthentication; it cannot self-renew or extend the orphan lease. Grant revocation is immediate at the authority actor; prior admitted work settles under §7.5.

#### 7.2a Immutable scope replacement, including a newly created PTY

Choose **replacement of the whole immutable role grant**, not a mutable allowset or caller-created per-PTY capability. Each active backend/host grant has owner-issued `scopeRevision` (u64); each scope entry is exactly `(ownerEpoch, ptyId, terminalGeneration, capabilitySet)`, with no wildcard generation. Role upper bounds, expected process, parent main/controller/host generation and artifact set remain bound. Host checkpoint/response/source messages must name an entry exactly; a new terminal generation requires a new scope grant even if ptyId is reused.

1. `BindPtyScope` is main-only **PrepareScopeReplacement**. It carries root operation identity, expected old grantId/scopeRevision/sessionId, and complete proposed new Scope; native checks current main use/lifecycle, role ceilings, typed entries against its authorized pending/live inventory and TS reservation receipt, then records a pending replacement. New scopeRevision = old+1, fresh grant secret/ID; old scope remains active. Client may propose a binding through ordinary TS UX but cannot issue, expand or activate it. Capability reduction uses the same path; revoke may fence immediately.
2. Main delivers new grant privately to the same verified backend process, or owner to the same verified host via its management pipe. The child authenticates in `SCOPED_REPLACEMENT` mode, bound to old grant/session/revision and replacement ID. After FinishAck/SessionReady it is **dormant**: status for replacement only, no source/input/checkpoint operation. Auth response includes full canonical granted Scope, revision, digest and immutable limits, protected by owner proof/finish; a request/notification is not authenticated scope authority.
3. Main sends `CommitScopeReplacement` with expected old grant/revision/session and authenticated candidate session/replacement ID. Owner CAS installs new grant/scope, fences old control/bulk sessions and tickets, stops/discards unadmitted old queued work, and retains accepted outcomes/cursors. Clients accept new stream traffic only under the new session/scope and resume via existing contiguous source/parse cursors; late old-lane frames cannot mutate state or advance credit. Complete prior admitted input/replies under their recorded identities; do not retry them under the new grant.
4. Prepare/auth/commit deadlines are each bounded by the 30 s grant TTL; one pending replacement/role and existing connection/ledger quotas. If preparation/auth fails **before commit**, revoke candidate only; old grant remains until its original expiry. If commit response is lost, current main queries the retained root operation/replacement result; it cannot restore old scope or commit another expansion blindly. After commit only new scope is valid, even if notification is lost. Old session closure is not new grant proof.
5. New PTY startup: original authorized SpawnPty reserves opaque PTY identity/generation and a `pendingSpawnReceipt` before launching/resuming shell output. Root prepares backend/host scopes from that native reservation, not an unverified renderer-supplied ID. Commit scope and satisfy the separately approved initial-checkpoint/read-credit prerequisite before executing the original accepted spawn. Pending spawn uses its original operation ID; setup failure/timeout settles failedBeforeEffect if no child was started, otherwise unknown/cleanup as appropriate. No unscoped host response or duplicate spawn may bridge this interval. Cancellation invalidates its receipt and any late replacement inclusion. The native mechanism of P4/P6 is not reimplemented here.
6. Ordinary grant/scope replacement is denied during quiescence. Only the fixed shutdown-reconciler grant in §7.8a is permitted; it cannot add PTYs or host capabilities. No client-side expansion, automatic same-ID scope edit, or reuse of a revoked scope revision.

At BeginQuiesce, cancel incomplete pending-scope startup reservations before launch and settle their original accepted spawn as failedBeforeEffect only when no process was created; if launch may have begun, retain accepted/unknown and cleanup evidence. Do not wait for a forbidden quiescent scope expansion to let a pending spawn finish. Already-active PTYs are closed/reconciled under root lifecycle authority, not a new ordinary grant.

**OS peer facts are additional checks, not credentials:** Unix same effective UID; Windows required user and logon SID; recorded process handle/start identity where available. Claimed PID/path/build alone never proves a role. Main/owner package trust must exist before bootstrap. Plain local IPC has integrity/authentication via MAC and OS access isolation, not confidentiality against privileged/same-user process inspection; no terminal content is sent before mutual authentication.

### 7.3 Canonical bytes, transcript, frame schema and fixtures

Use standard SHA-256 and HMAC-SHA-256 with 32-byte keys/tags, distinct domain separators, and fixed-length constant-time MAC verification. #### 7.4a Single bounded cleanup parent and deterministic child outcomes

**Chosen correction:** BeginQuiesce is the only new root-ledger cleanup mutation. It creates one parent `{ownerEpoch, shutdownId, root sequence/attempt, accepted-inventory cut}` in the protected slot. All close, reconciler-attempt and coordinator actions are deterministic children of that parent, **not distinct RootOp mutations**. Parent admission atomically fences ordinary launches and captures all already-admitted resource reservations, including spawns whose execution/ACK is still pending. A lost BeginQuiesce result is queried/replayed with that same RootOp; one parent maximum for the owner epoch, including BLOCKED_UNKNOWN and retries. Orphan-expiry quiescence creates the same reserved parent through the owner actor, not an unaccounted second cleanup tree. A later user quit/restart/update can change only handoff intent under existing policy, not create a new parent or budget.

**Resource admission invariant:** before any PTY spawn is accepted, reserve one of64 owner PTY resource slots, covering live PTYs **plus every accepted not-yet-launched or uncertain spawn**. A slot is not reused while an old resource may exist, a spawn may complete, or cleanup disposition is unknown. Thus `live + pending + uncertain <=64`, not `live<=64` with unbounded pending additions. The quiesce/admission actor race assigns every accepted spawn to a slot before the cut or rejects it notAdmitted after the cut. A late spawn completion updates its already-reserved slot; it does not create a65th child. This64 bound is the resource-inventory ceiling, not a change to the32-entry per-grant handshake scope bound. Conservatively retain extra terminal generations/old resource identities until proven disposed; do not free them merely because a binding/view is deleted.

Reserve32 auxiliary resource slots as well: at most30 ordinarily registered non-PTY process/resource cohorts (host, backend and existing launched helpers), plus **two non-borrowable shutdown-reconciler attempt slots**. A cohort has one immutable owner-issued resource identity and an aggregate disposition referencing the already-budgeted systems handle inventory; it is clean only when all its descendants/handles/workers are proved disposed. Do not hide unbounded new resources inside a cohort or replace missing per-handle accounting with its digest. Every installed helper/pending launch participating in final cleanup must register and reserve its cohort before launch; exceeding30 rejects that launch before effect. Registration/pinning is an eventual desktop/native integration prerequisite, not an assertion about current code. No new helper/platform privilege is introduced. ### 7.5 Admission, retained outcomes, expiry, and wire errors

Admission pipeline: bound frame → authenticate MAC/strict lane sequence → validate role/scope/generations → semantic digest → query duplicate/floor → reserve response/ledger/execution bytes/items → authority CAS admit → execute outside locks → persist bounded in-memory outcome → notify if writable. Every reservation includes queued + executing + unacknowledged completion + transport-owned copies; disconnect releases transport memory, not accepted outcome custody.

| Operation state                     | Meaning and replay rule                                                                                                                                                                                     |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `NOT_ADMITTED`                      | No side effect and no sequence commitment; explicit overload/validation/revocation reply. Same intended identity may be resubmitted only after status confirms this result and current authority allows it. |
| `ACCEPTED / RUNNING`                | Identity/digest and completion slot reserved before any side effect; query only on reconnect. No new ID/prefix retry.                                                                                       |
| `SUCCEEDED`                         | Concrete operation result (spawned identity, resize revision, bytes accepted by PTY, or confirmed close); input success is not shell-command completion.                                                    |
| `FAILED_BEFORE_EFFECT`              | Settled failure with proof zero effect; retained ID cannot be executed again. A genuinely new user-authorized operation requires a new reservation.                                                         |
| `PARTIAL_UNKNOWN / CLEANUP_UNKNOWN` | May have side effects. Fence subsequent conflicting input/spawn/close transitions and preserve leases; never auto-reexecute.                                                                                |
| `EXPIRED_UNKNOWN`                   | Identity <= committed expiry floor but detailed result gone. Must never execute it again. Unknown is not notAdmitted.                                                                                       |

Retain mutation high-water and contiguous settled expiry floors for the entire owner epoch, across main/controller changes. Input ledger scoped to PTY generation; lifecycle/spawn ledger scoped to owner epoch, not controller generation. Completed outcome detail TTL 10 min (receiver time); unsettled/uncertain/live-binding and checkpoint-replay-required response identities are not evicted on TTL. Below floor always returns expiredUnknown. Do not compact over an unsettled hole: if necessary reject admission before ledger fills. Operation namespaces/cursors and authoritative existing terminal generation must be reconciled with P4 by parent, not reset during this document's integration.

Initial separate ledger budgets: input <=4096 records/PTY and <=8 MiB/256K records/profile; lifecycle <=4096 records/4 MiB/profile; outstanding admitted mutation completions <=128/profile, terminal response <=4 KiB (large inventory/checkpoint data is paged separately). Pending write queue retains its tighter P4 budget; exact-state recovery pins outcome identities until safe commit. Budget exhaustion is typed before-effect rejection or per-PTY pause, never unsafe eviction. Native owner death invalidates the whole owner epoch; TS keeps old bindings uncertain and does not retry automatically against the new epoch.

Wire error envelope (bounded enum+structured IDs, no payload/secret echoes): `{code, admissionDisposition, ownerEpoch, authorityRevision, operationIdentity?, retryClass, retryAfterMs?}`. `admissionDisposition` is `notAdmitted | accepted | unknown`; disconnected transport cannot invent it. `retryClass` is `none | reauthenticate | statusOnly | laterBeforeAdmission | explicitUserAction`.

| ------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `AUTH_FAILED`, `PEER_MISMATCH`, `GRANT_EXPIRED`, `GRANT_CONSUMED`, `ROLE_DENIED`                        | Close unauthorized lane; generic bounded pre-auth response, no existence/secret oracle. Main can issue fresh scoped grant; no mutation retry assumption.         |
| `PROFILE_MISMATCH`, `ARTIFACT_MISMATCH`, `OWNER_EPOCH_MISMATCH`                                         | Fail closed; no deletion/launch fallback after possible prior acceptance.                                                                                        |
| `STALE_MAIN`, `STALE_CONTROLLER`, `STALE_HOST`, `SCOPE_REVOKED`                                         | Reject unadmitted work; prior accepted identity queried by current authorized custodian.                                                                         |
| `MAIN_BUSY`, `LEASE_EXPIRED`, `QUIESCING`, `CLEANUP_UNKNOWN`                                            | No new mutation; status/reconciliation only, leases retained on uncertainty.                                                                                     |
| `PROFILE_CONFLICT`, `ROOT_IDENTITY_UNAVAILABLE`, `INDEPENDENT_LIFETIME_UNAVAILABLE`, `CONTROL_DEGRADED` | No automatic deletion/credential reset/privilege escalation or post-acceptance legacy fallback. Root lifecycle status remains available where transport permits. |

### 7.6 Package trust root, pinned artifacts, and minimal launch environment

**Manifest source of truth:** add a build-produced `terminal-owner-manifest.v1` in the packaged desktop application trust boundary, with its expected SHA-256 embedded in the main bundle at build time. Manifest has version/app channel/release/target tuple, protocol compatibility, checkpoint schema/paired emulator build identifiers, and <=64 artifact records `{role, packageRelativePath, bytes, sha256, executable, target}`. Include native owner, exact runtime executable/helper, TS host entry and all its loadable chunks/dependencies, browser/headless paired xterm artifacts and addon compatibility identity. No absolute paths, traversal, links escaping the package, duplicate/case-colliding paths, or unhashed external modules. Prefer a self-contained host bundle; any remaining module is explicitly listed and verified. Maximum manifest 64 KiB.

**Anchor:** manifest digest must come from the verified main application, not a mutable adjacent `.sha256` or child self-report. macOS: signed sealed application and verified resource identity. Windows: verified publisher/runtime and authenticated main-bundle integrity (ASAR integrity + OnlyLoadAppFromAsar or an equivalently release-reviewed verified packaging path). Linux: authenticated release/package artifact and main-bundle trust; an AppImage/APPDIR string is not authenticity. Existing signing/integrity/release-anchor provisioning has not been inspected in this limited task and is a **blocking release integration check**. Do not add a signing dependency, public key distribution system, or pretend package.json commit metadata is proof. A release manager must identify the actual trusted build/install anchor and record its verification evidence before enablement; dev explicitly uses a dev-only manifest and cannot assert packaged trust/parity.

**Acyclic artifact trust DAG (normative build order):** finalize leaf payloads first → hash leaf payloads into manifest M → embed `SHA256(M)` in desktop main bundle → package main ASAR A → set main executable's ASAR integrity record `SHA256(A)`/required fuses → sign/seal main package P → existing authenticated release/installer anchors P. M must **not** hash A, P, the main executable that embeds A's integrity, itself, or any artifact which embeds M/A/P hashes. That would be a cycle, not a build-time solution. Leaf payloads include owner, an independently finalized TS runtime, complete host/reconciliation entry and dependency closure, and standalone paired browser/headless xterm modules finalized before the importing main bundle. Hash finalized signed leaf bytes; no later re-signing/fuse mutation of a leaf without rebuilding M/A/P in that order. Browser xterm identity cannot be the enclosing main bundle's hash if that bundle embeds M; package it as a separate immutable dependency chunk with no back-reference.

For Windows, **do not use the running main executable as the manifest-hashed host runtime**. Select a separately packaged, finalized instance of the already-approved runtime/toolchain (e.g. the existing Electron helper distribution configured for fixed RunAsNode execution), whose bytes do not embed the bigbud main ASAR hash and whose dependency closure is covered by M. This is artifact packaging of the existing runtime, not authorization for a new runtime dependency/download. If no existing-runtime artifact can satisfy that separation and required signing policy, keep the gate closed and return the concrete packaging blocker; do not invent a new dependency or hash-exclusion trick. macOS nested helper signing and Linux package finalization must follow the same leaf-first DAG. Main independently verifies/pins final leaf hashes; OS/release anchor verifies main root bytes externally, so M need not and must not attest its own ancestor. Dev-only unsigned M remains explicitly non-release evidence.

Release provisioning gate: build/release owner must identify the actual existing trusted signing/release identities, demonstrate main ASAR integrity enforcement on pinned Electron40.6.0 and the independent runtime's loader closure, and show DAG rebuild/tamper tests. This planner neither inspected build/signing sources nor approved missing signing infrastructure. Manifest source-of-truth above covers executable/runtime **leaves**, with main executable anchored externally as described; adjacent hashes and self-hello remain insufficient.

**Launch algorithm:** verify package anchor → parse bounded manifest → resolve artifact handles under anchored package root → reject writable untrusted redirection/symlink/reparse escapes → verify size/hash/target/permissions and file identity from handles → pin manifest/artifact identities in main and owner for the live epoch → launch exact verified executable/entry with fixed args/private bootstrap → verify bootstrap challenge and actual opened process identity. Revalidate identity immediately around launch; if platform cannot ensure the verified path still resolves to verified artifact, fail closed. An already-compromised same-user installation remains outside the trust model; path existence plus own hello is never the protection. A valid handshake proves possession of bootstrap key, not independent code attestation.

Native owner accepts runtime/host artifact descriptors only from root bootstrap/current-main policy, never backend/host/user argv. Host restart uses the same pinned artifact set, not current contents at a path. If update changed the bytes, keep the existing process if still healthy or mark recovery unavailable; do not load incompatible code into a live owner epoch. Updater cannot replace these resources until §7.8 confirms cleanup. No hot migration or auto-download.

**Host/native environment builder is new and allowlist-only; never spread `process.env` or call `buildBackendChildEnvironment`.**

| Allowed value                                      | Source / rule                                                                                                                                       |
| -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ELECTRON_RUN_AS_NODE=1`                           | Only for verified Electron-based TS host runtime; omit for native owner. Preserve required RunAsNode capability rather than blindly changing fuses. |
| Windows `SystemRoot`/`WINDIR`                      | Verified OS directory obtained from OS API, not inherited arbitrary value; omit duplicates differing only in case.                                  |
| `LANG=C`, `LC_ALL=C`, optional `TZ=UTC`            | Fixed deterministic host values; xterm parsing uses explicit byte decoder, not shell locale.                                                        |
| `TMPDIR` / `TEMP` / `TMP` if runtime requires them | Protected profile-owned scratch directory verified by the same path rules, bounded cleanup; no transcript/heap-dump persistence.                    |
| Explicit nonsecret host mode/target flag           | Compiled/verified launch policy only; profile/scoped credential/config data travels in bootstrap, not arbitrary environment.                        |

Do not inherit HOME/USERPROFILE if host does not need them; pass any essential resolved path through bounded typed bootstrap. No PATH search: executable/entry are absolute verified package paths; cwd is verified runtime directory, never a workspace. No NODE*OPTIONS, NODE_PATH, `--require`/`--import`/loader/inspector args from parent, ELECTRON_RUN_AS_NODE inherited override, Electron logging/debug flags, LD_PRELOAD/LD_LIBRARY_PATH, DYLD*\*, arbitrary DLL search overrides, provider/API/SSH/cloud credentials, backend WS token, root secret, or backend grants. Host heap limits are fixed reviewed argv flags, not user-provided Node options. Verify packaged runtime's own loader behavior on all OSes. Absence of an allowlisted needed variable is a startup error to investigate, not permission to inherit everything.

**Separate shell launch:** TS retains current shell/env/cwd/argv resolution and explicitly supplies authorized PTY spawn input. Do not apply the headless-host scrub to user shells or replace local policy with remote allowlists. Control credentials are never present in any ancestor shell-inheritable env/FD/handle, regardless of user env contents.

### 7.7 Profile identity, rendezvous, and platform algorithms

Canonical profile tuple contains protocol identity version, OS user identity (Unix UID / Windows binary user SID), release-channel and dev/packaged namespace, resolved backend base directory identity, resolved Electron userData directory identity, and canonical diagnostic path bytes for each. Directory identities are Unix `(device,inode)` or Windows `(volume identity,file ID)` from opened handles, not normalized path strings alone. Main reuses `resolveDesktopMainConfig`/`resolveUserDataPath` results including legacy migration; native verifies them. Hash canonical tuple for endpoint selection; authenticate the **full tuple** as well. Same directory via path aliases must converge or be rejected explicitly if canonicalization cannot establish it. Two different tuples sharing the same backend data-root identity must not run conflicting owners: hold a data-root guard and return `PROFILE_CONFLICT`, not create two native namespaces over one domain database.

Use full SHA-256 for authenticated profileDigest; socket/pipe basename uses first 24 hex characters for path length only plus random endpoint-instance suffix. Collision compares full tuple and returns conflict, never attaches. No profile paths/secrets in socket filename or ordinary telemetry. Credential directory is an owned child of backend `baseDir/userdata`; runtime socket directory may be short platform runtime location but is bound by object identity to that profile. Do not change existing profile migration or require a new privileged filesystem location.

**Shared data-root guard, before profile lock (both OSes):** from the pinned backend base directory handle, resolve/pin its existing `userdata` child then safe-create/open `.terminal-owner/` as the private native identity directory. The stable guard is `.terminal-owner/data-root.guard`, **never** under a profileDigest/channel/userData-specific path. All profiles referencing the same pinned backend directory object reach this same guard, even through aliases; compare resulting directory object identity, not spelled path. If a configured userdata alias cannot be resolved to the same pinned data root safely, fail conflict, never create another guard elsewhere. Profile credential/lock/rendezvous children live at `.terminal-owner/profiles/<full-profileDigest>/`; this only organizes already-authorized identity metadata, not a new journal/output store.

Acquisition order is always `pinned backend root → pinned userdata/native directory → data-root.guard exclusive ownership → profile child/profile.lock exclusive ownership → credentials/endpoints/rendezvous publication`. Never hold a profile lock while waiting for data-root.guard. Candidate owner alone owns both locks for the **whole owner lifetime**, including orphan/quiescent/cleanupUnknown state; no inheritance into main/backend/host/shell. Release in reverse order only after confirmed resource settlement and owner exit; process death releases OS locks but does not establish descendant cleanliness. Main may inspect protected credential/rendezvous read-only to authenticate an existing owner without acquiring exclusive locks.

Unix guard: safe-open regular0600 file relative to pinned native dir using O_NOFOLLOW|O_CLOEXEC, verify UID/type/link-count/file identity, then nonblocking exclusive flock. Keep that exact descriptor/inode, never unlink or atomically replace the guard file; all writes of diagnostic ownership go to separate `data-root.owner` rendezvous metadata under the held guard. Windows guard: handle-relative safe open of the same leaf via NtCreateFile, OPEN_IF, regular non-reparse object, explicit DACL, **share mode zero**; retain identity-bearing handle, do not transfer an assumed LockFileEx lock. Neither OS truncates guard as an acquisition attempt. Creation race uses one stable file; loser reopens/verifies that same object and must win OS exclusive ownership, not a PID test. Profile.lock uses the corresponding platform primitive under the already-held guard.

Winning owner publishes bounded nonsecret `data-root.owner` containing full profileDigest, ownerEpoch, endpointInstance and identity-bound profile rendezvous location; metadata atomically replaced handle-relatively while both locks held. Losing launcher/owner does **not** acquire a different profile lock, load/reset another profile root, unlink anything or spawn a PTY: read bounded protected owner metadata, compare full profile tuple through authenticated rendezvous; same profile can reattach, different profile returns PROFILE_CONFLICT. If record absent/partially published, wait at most5 s for winner then report OWNER_BUSY/unknown; never steal lock. A dead/reused PID, timeout or unavailable endpoint cannot make a held guard available. If exclusive guard becomes available after death, acquire it first, then verify stale metadata/object identities before cleanup/new epoch; old TS leases remain uncertain. Simultaneous launch tests must use **different profileDigests over the same backend root**, not merely identical-profile contention.

**Unix algorithm:**

1. Resolve/open intended existing profile roots from trusted config; explicitly resolve allowed configured symlink aliases once, then pin final directory identities. Traverse/create the new private native child using directory-relative `openat`/`mkdirat`, `O_NOFOLLOW|O_CLOEXEC`, verify owner/type/mode at each new child. Private dir 0700; root credential/lock/rendezvous regular files 0600 and link-count/type checks. Do not reject existing platform root aliases by globally banning all ancestors; after canonical root capture, no traversal may follow new untrusted links.
2. Owner obtains the shared data-root.guard first, then the profile.lock using the algorithm/order above; both stable flock descriptors remain held for its lifetime. No endpoint, grant, PTY or ownership publication before both locks. Losing candidate returns OWNER_ALREADY_RUNNING/PROFILE_CONFLICT/OWNER_BUSY as appropriate and exits without changing either lock or winner metadata.
3. Under lock, initialize/load Kprofile with exclusive no-follow temp file, complete write/fsync/rename in pinned directory and directory sync; partial/corrupt existing identity fails closed rather than rotates automatically. Main obtains/validates the root via private bootstrap on first creation or protected root file on reattach; it never accepts a root key from public rendezvous. Separate full-profile metadata is canonical and bounded (<=8 KiB).
4. Bind sockets under protected short directory, mode0600, record endpoint object inode + random instance + owner OS process identity + manifest digest + profile tuple digest. Publish complete nonsecret rendezvous via atomic rename under lock. Never publish secret/grant in it. Authenticate peer UID and full transcript after connection.
5. Stale recovery requires acquiring the lock **and** validating old root/rendezvous/endpoint object identities under directory handles. An occupied lock/authenticated live owner forbids cleanup; a dead PID alone grants nothing. Under held lock, unlink only a verified owned stale socket/record with matching instance/object identity, not arbitrary path contents. Uncertain identity/type/permissions/replaced inode returns conflict with no deletion. Keep TS old-epoch bindings/leases uncertain; acquiring a new owner lock does not prove prior descendants gone.
6. Owner lives in its own session/process group, outside main/backend kill tree; close/mark CLOEXEC all unintended descriptors before shell/host exec. Parent EOF starts orphan policy, not automatic immediate owner exit. No parent-death kill tied to main/backend. Full descendant cleanup is §7.8, not assumed from this launch topology.

**Windows algorithm:**

1. Obtain user SID plus logon SID/session ID from real token, pin backend/userData directory handles and volume/file IDs. Existing configured junction aliases may be resolved to final root once; below pinned native directory use a reviewed handle-relative `NtCreateFile` wrapper (`OBJECT_ATTRIBUTES.RootDirectory`, component-at-a-time, `FILE_OPEN_REPARSE_POINT`), reject unexpected reparse tags, and verify identities. Use existing windows-sys/native bindings, not a new crate. Rename/delete by verified opened file handle (`SetFileInformationByHandle` with pinned target directory), not a later full-path reopen. Win32 full-path opens with FILE_FLAG_OPEN_REPARSE_POINT are not sufficient to stop intermediate junction traversal. A path-prefix check is insufficient. Use explicit protected DACL; no inherited Everyone/Users access for root/grant data.
2. Owner opens stable data-root.guard with share mode zero first, then profile.lock under its profile child, verifying both identities with no delete-sharing. No inherited-LockFileEx assumption. Only the winner creates/loads root metadata and publishes endpoints/rendezvous. Losing candidates use the shared guard's bounded owner record as above, never a different profile lock to evade data-root exclusion; no forced deletion on PID timeout.
3. Use separate local root/control/status and bulk named-pipe endpoint instances, `PIPE_REJECT_REMOTE_CLIENTS`, `FILE_FLAG_FIRST_PIPE_INSTANCE` on the first instance, overlapped IPC I/O and bounded instances. DACL permits required user/logon SID access only; clients request explicit FILE_READ_DATA/FILE_WRITE_DATA/attributes/SYNCHRONIZE rights, not broad generic-write grants that accidentally include FILE_CREATE_PIPE_INSTANCE. Owner requires server-instance creation rights under its own token. Same-account ACL cannot distinguish all same-user processes: random endpoint instance, role credential and mutual transcript binding remain mandatory.
   A pair of allow ACEs for user SID and logon SID is not an intersection check. Prefer logon-scoped client rights and independently verify **both** expected user and logon/session facts after token inspection; owner rights remain explicit. Do not claim DACLs isolate main from every other same-user process or that client access masks alone prevent namespace squatting.
4. Clients use explicit security-QoS flags restricting impersonation to identification. If server impersonates to read client token SID/logon/session, do so on a dedicated auth worker in a tightly scoped guard, copy only required token facts, and **unconditionally RevertToSelf on every success/error path before any other work**. No filesystem/process/PTY work under a client token. Revert failure poisons the owner and triggers fail-closed process termination; do not return that worker to a pool still impersonating. Test this failure. Main treats lost owner as interruption/cleanup uncertainty, not proof of success.
5. OS pipe server/client process IDs must be paired with opened process handle/creation identity and transcript instance, not treated as auth by themselves. Bind bulk to authenticated parent session/ticket; validate both lane peers. Namespace squatting/server substitution produces auth/instance failure; never weaken ACL or fall back to TCP.
6. Owner verifies early that it is not in a parent job that would couple its lifetime to main/backend. Baseline design rejects job-contained owner launch if independence cannot be proven. Do not request elevation, install a service, add breakaway flags, or loosen parent/shell job policy. On normal installed launch outside such jobs, prove main/backend hard-termination survival with native tests. CI launch constraints are not permission to weaken production containment; unsupported host context leaves gate closed with a typed capability error.

ConPTY teardown order: stop new user/input admission → settle accepted input or mark partialUnknown → stop/cancel input writer → graceful child/job termination (2 s) then forced job termination if needed → close pseudoconsole on dedicated worker **while output reader continues bounded draining**, including final frame → observe close/EOF/worker completion, then close remaining pipe/process/job handles. Teardown drain may discard terminal output only after explicit session termination; it is not a successful exact-recovery ACK. Total target 5 s; timeout means cleanupUnknown, not “close succeeded.” Native tests must prove no blocking final-frame deadlock and correct handle counts for failure after every acquisition.

Unix shell process-group kill/reap is not a whole descendant proof. Track proven owned identity sets, terminate all owned job-control groups/children and report unknown for escaped/unobservable descendants. Do not call periodic ancestry sampling a containment guarantee. Setsid/double-fork/respawner/PID reuse fixtures are required; privilege/cgroup/helper solutions require separate approval. Even Windows Job Objects do not prove termination of processes launched through external brokers/services; declare that uncertainty rather than claim arbitrary “all descendants” from job-empty alone. Unknown resources retain worktree/update fences.

Direct Unix child lifecycle must retain the unreaped owned-child relationship until signaling/wait disposition is settled; do not reap then later signal its reusable PID. For non-child descendants, if the platform cannot provide safe identity-bound termination, do not treat a before/after PID+start-time scan as atomic authority: retain cleanupUnknown instead of risking a recycled unrelated process. This interface requirement is handed to the owning native work, not implemented here.

**Coordinator:** new `main.shutdown.ts` owns one shared promise/state machine for quit, restart and update. All main.ts/floating-assistant/menu/update paths call it. Do not set `quitTeardownComplete`, schedule app.relaunch, or call quitAndInstall until confirmed completion. Synchronously `preventDefault` on the initial ordinary before-quit event; await coordinator and then permit one deliberate reentrant quit. Updater's awaited preparation hook runs coordinator **before** invoking updater; before-quit-for-update only observes the already-prepared state.

Separate `admissionQuiescing`/coordinator state from final `isQuitting`: current updater checks `getIsQuitting()` immediately after awaited preparation and skips handoff if true. During update preparation keep that final flag false while fencing starts through installed-process/coordinator quiescence; the updater's existing handoff step sets it only after READY_TO_HANDOFF. A private reason/shutdownId token identifies the one owned reentrant quit/update event so it joins completed cleanup rather than starting a conflicting ordinary quit. Renderer cannot supply that token. Extend tests for this exact early-flag regression.

Freeze unadmitted work; accepted operations settle/unknown. Fixed-cut inventory/outcomes feed TS durable settlement, never a fabricated success from native inventory alone.                                                                              |

Reconcile confirmed/unknown cleanup with TS before releasing worktree leases. Any unknown blocks transition.                                                                                |
| `CHILDREN_STOPPED → BACKEND_STOPPED`     | Backend acknowledges durable domain settlement and native inventory complete; then await backend stop and bounded pending-launch settlement. No background restart allowed. Never clear uncertainty because only backend exited.                                                                                                                                 |

Update calls quitAndInstall once; restart calls relaunch once then quit; quit just quits.                                                                                                              |
| Any cleanup phase → `BLOCKED_UNKNOWN`    | Keep leases/artifact pinning and quiescence; return typed recoverable error with native status/retry UI. Five-second native cleanup target and five-second individual IPC waits are not unbounded whole-app waits: coordinator gets a 30 s active-time overall preparation deadline, reports blockedUnknown at expiry, and retains state for explicit retry. Pending installed starts must settle or remain identified unknown within it; do not await an unbounded Set drain forever. Ordinary user cancellation may abort **before** owner quiesce commit only; after commit do not silently resume closed sessions. OS force-quit/logout/hard kill may bypass Electron hooks (notably Windows); treat as parent loss/owner orphan policy, not successful coordinated shutdown. No new force-cleanup product override is introduced.

There is one shared **in-flight attempt** promise, not an eternally rejected promise: BLOCKED_UNKNOWN settles that attempt; explicit retry creates a new attempt with the same shutdownId, inventories, outcome identities and fences. Do not clear state or create fresh close IDs. While an attempt is running, competing handoff reasons are busy. After a blocked update preparation, an explicit user quit/restart request may replace only the eventual main-owned handoff intent once the uninvoked update token is invalidated; it still must complete the same cleanup before quitting/relaunching. This preserves existing restart-required updater UX without letting a retry silently install an update or bypass cleanup. After updater handoff was actually invoked, retain existing handoff-failure policy; do not schedule another action automatically.

Extend `windowsUpdateTargets` from the same pinned manifest inventory for owner/independent-runtime/host/reconciler files and all opened installed resources. The main image is externally anchored, not a host leaf (§7.6); retain existing NSIS exception for main's still-running executable. Update admission and before-quit-for-update cannot reset pins/fences. A new build may not replace in-use owner/host/checkpoint/reconciler artifacts; unconfirmed cleanup blocks installation with the existing restart-required/degraded UX semantics.

#### 7.8a Backend-dead shutdown: bounded reconciliation-only exception

Durable domain settlement remains owned by TS using existing persistence/binding/lease APIs, never Rust or Electron main inventing domain rows. The single permitted launch during committed quiescence is the **verified existing backend artifact in a dedicated shutdown-reconciliation entry mode**, not the ordinary backend startup path. Bundle that entry as a leaf with the same backend runtime/dependency closure in §7.6; no new service/dependency/storage. Main launches it through a private bootstrap with profile identity, shutdownId, immutable inventory cut and a root-issued `shutdownReconciler` grant. It must skip ordinary bootstrap, migrations during cleanup, public WebSocket listeners, providers, PTY/host creation, timers, recovery, UI serving, and general command dispatch. If installed schema is incompatible, fail closed rather than migrate while cleanup is blocked.

**Permission/limit:** current main with ordinary or cleanup-only authority may issue AuthorizeShutdownReconciler only after BeginQuiesce is committed, previous backend/writer's exact process exit and existing persistence single-writer ownership are confirmed, and owner admits the bounded attempt. Quiescence stays true. Before launching, root reserves a shutdown launch attempt in owner state (kind40 below) to prevent two reconnecting mains each spending one; only then can a private, non-exported coordinator launch helper bypass the ordinary installed-process start prohibition for that exact artifact/entry/shutdown ticket. It still registers its pending launch with quiescence tracking. This is **not** a Boolean bypass on generic startBackend and not available to renderer/backend/host. Launch enters bootstrap wait; main captures real ProcessIdentity before kind31 grants credentials. Consume reservation on launch attempt even if bootstrap fails; one in-flight reconciler, at most **two launch attempts per shutdownId/owner epoch**, shared across main takeovers and explicit retries. Each runs within that coordinator's30 s deadline; no auto-restart loop or budget reset. If owner epoch/attempt inventory is lost, no fresh cleanup launcher until existing writer/TS authority is reconciled; this spec does not supply a shortcut.

Kind40 launch reservation and kind31 grant issuance use the parent's coordinator child slots9/10 or12/13; their process/resource outcomes use auxiliary slots30/31. They never allocate fresh root-ledger records, even if launch/grant ACK is lost. Revocation/termination uses coordinator11/14 and those same auxiliary entries. This is the only cleanup quota/outcome change; existing role/issuer/timing/termination restrictions remain intact.

Owner issues generation-tagged Scope with role4/use shutdownReconcile, createBudget0, caps9 scoped-status +10 durableShutdownSettlement, exact existing PTY generations from fixed cut, same artifactSetDigest and shutdownId. Reconciler needs no bulk/telemetry lane; its status/control use reserved cleanup partitions. Current main drives native CloseForShutdown using accepted stable identities while reconciler consumes disposition updates. Native does not count reconciler acknowledgement as process cleanup proof.

TS reconciler reads existing durable reservations/bindings/leases and queries native accepted identities to a cut; persist confirmed results or conservative unknown through existing domain APIs before returning a receipt. Receipt is a digest of `(shutdownId, ownerEpoch, inventoryCut, outcomeCut, existing durable transaction/readback identity)` and is **evidence of that TS persistence transaction**, not a new journal/file. An idempotent retry reads existing transaction/binding facts; no new spawn/input or lease release absent proof. Native freezes the final cleanup cut only after all admitted work and resource dispositions settle; main requires a matching receipt for that final cut. Earlier intermediate receipt cannot authorize update/quit. Unknowns must be durably recorded with leases retained and yield BLOCKED_UNKNOWN, not success. If existing persistence cannot represent/re-read this settlement without new storage, that is an explicit P4/domain integration blocker: do not add storage or bypass the requirement.

### 7.9 Capacity isolation and deadlines

Budgets are initial engineering limits to validate, not product approvals or measured resource proof. They cap items **and** bytes including in-flight copies. Preallocate/account response reservations before admission; expensive hashing/copy/process work never holds authority locks. Bulk cannot borrow unused root/status reserves.

**Connection counts are partitioned, not a shared first-come pool.** Maximum64 authenticated **or reserved-for-promotion** physical connections/profile, with non-borrowable partitions: root control2 (current main+candidate rotation/handover); root/status2 (status-only observers/current-main dedicated status); shutdown reconciliation4 (control2+status2 including one replacement/verification peer); ordinary backend control2 (active+replacement); host control2 (active+replacement); telemetry4 (main/host each2); bulk48 (backend24+host24). Sum=64. Unused bulk slots cannot admit a third root/control or conversely take a root/status reservation. Backend read/status normally uses its own control, never dedicated root/status slots. Cleanup max1 actual reconciler despite reserved transport overlap. Per-parent bulk max2 and role byte limits still apply, so slots never imply permission to launch48 writers or consume48 full queues.

Pre-authentication is separate bounded **40 accepted physical connections**: public32, root4 and root/status-cleanup4 on distinct listeners/accept queues. Public pre-auth memory256 KiB plus root32 KiB plus status/cleanup32 KiB. SYN/listener backlogs/pipe pending instances are finite and counted per listener independently; full public backlog never closes root/status accept. A connection in CHALLENGED remains in its pre-auth partition and owns exactly one destination promotion slot from the64 count, reserved only after syntactic/role/grant lookup but before sending challenge; no destination slot means immediate bounded capacity rejection. Reserving a slot does not consume a credential or grant authority. FINISH_PENDING/dormant scopes/candidates retain their destination reservation. FinishAck atomically moves source accepted count to destination authenticated count without releasing/reacquiring destination; timeout/failure releases both, preserving consumed-token/outcome semantics. Total physical sockets<=104 and authenticated+promotion reservations<=64 at all times (a promoted connection is never double-counted physically). Public clients cannot reserve root/cleanup slots merely by claiming role: only root listener root-key lookup or owner-issued shutdown role grant on dedicated cleanup listener can use those partitions; require proof before expensive tasks. Hostile same-account root-listener flooding is still outside a DoS guarantee, not misrepresented as solved by a hidden endpoint.

Execution resources: root auth has2 dedicated bounded workers/queue4; status/cleanup auth2 workers/queue4; public auth4 workers/queue32. Root/status control dispatch and writer mailboxes are separate from backend/host/bulk executor queues. Bulk copying/hashing uses fixed2 workers with no jobs holding authority locks; role control each has a nonblocking bounded dispatcher; watchdog/lease timer has its own thread. A blocked public auth call or bulk worker cannot borrow/reserve those root/status workers. Deadline cancellation cannot free in-use native buffers; keep its slot until actual completion and declare its own partition degraded if stuck. No global semaphore other than small counter/CAS operations may serialize these lanes behind bulk I/O. Slot promotion/cap checks are metadata-only critical sections.

## 9. Risks, compatibility, and rollout

- **Protocol crypto/identity mistakes:** transcript and typed-role fixtures plus independent security review precede production integration. Standard primitives still need correct native implementation/constant-time validation; no novel secret hashing shortcut.
- **False package trust:** signed executable alone may not bind mutable ASAR/extraResources; Linux APPDIR is untrusted input. Concrete release anchor evidence is mandatory. This document does not grant new signing infrastructure/dependency approval.
- **Lifecycle deadlock:** exact custody, host parsing, ConPTY final drain or stale accepted work can block shutdown. Bound waits and retain unknown state; never trade safety for a falsely successful update.
- **Same-user threat overclaim:** ACL/0600/scoped tokens are not an OS sandbox. Do not call unrestricted same-user backend compromise contained by this contract.
- **Compatibility:** negotiated new local namespace, fixed released enum/field values, conservative unknown capabilities; no reinterpretation of existing remote ACKs. Old sessions stay on original owner/epoch until explicit close; no live protocol/PTY migration.
- **Rollout:** disabled until security review, package-anchor evidence, exact checkpoint gate and native Windows parity/containment matrix pass. Stage pure modules/contracts without changing routing. P7 actuation separately gated from health reporting.
- **Rollback:** stop new native admissions and recovery actions; retain existing pinned owner/runtime/schema/credential lifecycle to cleanly close known sessions.
