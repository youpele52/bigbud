## Authoritative implementation deltas (13 October, 2026)

- The user's subsequent **rename other threads** direction supersedes the original exactly-four inventory. The required inventory is now five tools, adding `bigbud_thread_v1_rename_thread({title,targetThreadId?})`. Its HTTP action is `rename`; `threadId` remains the token-bound caller, and `targetThreadId` is the optional eligible destination. Canonical same-project/direct-child access, stable paired invocation/source IDs, engine receipts and title locking remain authoritative. No native-session rename substitutes for canonical metadata.
- Independent foundation reviews reproduced four source defects: concurrent enrollment overflow, forgotten required-session recognition, post-await lease exposure, and an unbounded native-read/proof phase. Regression tests reproduced all four before correction. Managed-session recognition remains bounded at 32 per loaded Location; capacity is refused rather than forgetting a required boundary. Reload/unload remains an explicit native user action, not an app fallback or universal containment guarantee.
- The reviewed callback-port-rebinding defect requires both confidentiality and fresh server authentication, not bearer-only HTTP. Callback transport remains literal IPv4 loopback POST `/invoke`, but **no callback token or tool arguments are sent in plaintext headers/body**. A persistent private X25519 app key accompanies the private Ed25519 issuer; its public key is rendered into hashed `crypto.mjs`. Each native request creates an ephemeral X25519 key, derives an AES-256-GCM key with HKDF-SHA256 (request IV salt, `bigbud.thread.encrypted.v1:request` context), and encrypts `{token,payload}`. Request/response AAD domains are distinct. Wire limits remain 32 KiB/128 KiB; encrypted request plaintext is capped at 22,000 bytes, signed result JSON at 90,000, and encrypted response plaintext at 95,000.
- Every response is encrypted and Ed25519-signed over `["callback-response",ownerDigest,enrollmentNonce,requestNonce,requestedLeaseRevision,requestedLeaseExpiry,acknowledgedLeaseRevision,acknowledgedLeaseExpiry,operation,SHA256(JSON.stringify(exactRequestPayload)),SHA256(JSON.stringify(exactResult))]`. The transport nonce is fresh 128-bit randomness and never enters durable canonical invocation IDs. The native verifier requires the exact request/owner/operation plus the registry's current acknowledged lease, then executor/hook current-owner, abort and expiry fences. The separate existing callback-proof signature remains intact. Malformed crypto/JSON/fetch errors project only fixed safe diagnostics. This protects callback traffic from a foreign-UID rebound listener; it does not claim containment from trusted native host-user/root code that can read app keys.
- Canonical HTTP credentials remain app-internal. Token-owned cleanup now preserves successor records in shared, MCP and Pi resource cleanup. Only a current owned internal token can refresh its existing TTL; missing/changed credentials are not recreated during renewal. Retained native policies/instruction/admission fingerprints are not rewritten to obtain these tools.
- **User-approved native permission-contract correction:** owned 2.0.26 and published/Core contract inspection disproved the original custom-tool native-ask assumption. `Tool.Options.permission` filters native denied tools but does not ask before custom execution; the public plugin API has no ask method. The user accepted preserving native rules/order/deny filtering and requiring the existing canonical once-only exact-action approval for all five actions in required/auto-edits modes. No private permission API, native-question substitution, permission override or persisted grants are authorized. Double-ask UX is not claimed; unrelated native built-ins retain their existing asks.

The historical phase descriptions below describe the accepted four-tool baseline where they say “four.” The five-tool and encrypted-callback deltas above are authoritative; they do not expand the shared plugin to browser/workspace/computer/file tools or authorize native installation/reload/service administration.

## Problem

**Observed (user):** the V2 assistant receives another thread's `smile` instruction and responds, but refuses to send its result back because the attached thread context is read-only. Models are now available; the recovered inventory/error issue is separate.

**Expected (clarified):** canonical app-owned create/message tools match other providers, including provider/model-independent addressing and existing approval/access rules. Native OpenCode subagent spawning remains a separate operation. No silent native global/project plugin/config writes, trust grants, service restart/replacement, paid prompts, or real-thread mutation.

**Confirmed root:** shared V2 has no outbound canonical tool registration, resources, or authentication capability. Read-only attachment text describes the supplied history correctly; it cannot manufacture an outbound command path.

Prioritized hypotheses and outcomes:

1. Shared composition bypasses tool registration/resources — confirmed directly and with disposable preparation reproduction.
2. Canonical access checks reject cross-provider destinations — not supported by source: messaging checks projects/delegation, not provider/model equality.
3. Model-specific instruction misunderstanding alone — insufficient: there is no registered shared V2 tool to call regardless of prompt wording.

**Separate confirmed prompt defect:** `ProviderCommandReactorSessionOps.threadContext.ts:132–134,173` filtered current-thread attachments, then prohibited messaging all other attachments unless they were the current thread. The exception was unreachable. Shared attachment guidance now distinguishes immutable quoted history from explicitly user-requested canonical messaging/creation, retains project/direct-child and approval boundaries, and never promises unavailable tools. This is a real correction for all providers but does not fix missing shared V2 registration by itself.

## Goals

- Expose exactly `create_thread`, `send_thread_message`, `get_thread_status`, and `list_threads` to enrolled bigbud V2 sessions, with real executable native tool definitions.
- Route to existing canonical dispatch, including attribution, queuing, delegation, idempotency, and access checks; do not introduce a second thread engine.
- Preserve per-action canonical approval, cancellation, durable uncertain-outcome handling, disable/revoke fences, and independent child ownership.
- Keep unrelated native sessions, tools, permissions, environment, user instructions, plugin configuration, and shared daemon lifecycle unchanged.
- Preserve isolated disposable fixture semantics and protect all other provider registrations with focused regressions; isolated V2 is no longer a production route.
- Remove production V2 private-profile/CLI/SSH/development routing and settings controls; preserve isolated test fixtures and read-only historical classification. Protect Kilo's separate legacy SDK manager.

## Non-Goals

- Mutate attached history; use native fork/create/prompt as canonical cross-provider thread operations; allow native `subagent`; change model catalogs/error diagnostics.
- Switch/reinterpret existing isolated histories as shared, auto-switch providers, or create replacements for unavailable retained history.
- Automatically add native MCP servers, install a global/project plugin, restart the service, copy credentials, or replace session environment.
- Promise arbitrary provider/model selection in `create_thread`: the existing canonical create API inherits the caller's selection. Messaging can address eligible existing threads regardless of provider/model. Any new creation-selection API is separate scope.

### Native contracts and why obvious shortcuts are unsafe

Official documentation read on 12 October 2026:

- [V2 plugins](https://opencode.ai/v2/docs/build/plugins): tool transforms and session `context` hooks require an already loaded plugin. Transforms are Location/plugin runtime registrations; per-model hook filtering and executor enrollment guards are needed for exact-session scope. Tool snapshots remain executable after later disposal, so executor revocation cannot rely on tool removal alone.
- [V2 client](https://opencode.ai/v2/docs/build/client): network client RPC calls can invoke an installed plugin; importing an RPC definition does not register/load it.
- [V2 plugin RPC](https://opencode.ai/v2/docs/build/plugins/rpc): installed plugin implements `ctx.rpc.register`; generic HTTP RPC route exists for client enrollment.
- [V2 SDK](https://opencode.ai/v2/docs/build/sdk): `OpenCode.create({plugins})` embeds a new owned host; it does not inject plugins into the existing shared service. Do not substitute a new host for retained native storage.
- [V2 API](https://opencode.ai/v2/docs/api): parent inspected official raw OpenAPI and found no tool-registration HTTP path. Runtime MCP add/remove is not advertised session-scoped and is not an acceptable silent shared mutation.
- Installed `apps/server/node_modules/@opencode/client/package.json:5` is **2.0.26**; reported user native service is **2.0.27**. Generated `dist/promise/generated/client.d.ts:32–92,131–140,183–185` has session instructions/environment and Location MCP/RPC, but no session tool registration API.
- Generated `types.d.ts:2836–2862,7156–7166`: environment mutation replaces a string map and returns void; `SessionInfo` exposes no environment map or readback method. Replacing unknown existing environment is not a safe preserving merge.
- Existing Pi bridge is a registered Pi extension (`PiOrchestrationBridge.template.ts:30–59,98–123,174–180`), not a standalone canonical shell CLI. A new shell bridge would need a trusted identity/idempotency and approval contract; it is not a minimal DRY adaptation of that code.
