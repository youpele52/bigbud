## 2. Goal and definition of done

**Summary.** An opt-in setting lets bigbud keep working after the desktop app quits. A new Rust service owns the provider-neutral process lifetime and restarts a crashed TypeScript backend without Electron. TypeScript keeps all provider, conversation and recovery truth. The plan builds on the dead-thread recovery and delegated model-choice machinery that landed since the plan was first written, instead of duplicating it.

### Agreed requirements

1. Background operation is **off by default**, including existing profiles that lack the setting.
2. Off: quitting the app shuts down the backend and its sessions. macOS window-close versus quit and the existing floating-assistant behavior are preserved.
3. On: an ordinary quit detaches Electron. The same TypeScript backend, providers, running turns and backend resources continue. Reopening attaches without a duplicate backend or session and without replay.
4. Rust owns the provider-neutral background and process-supervision core. It restarts a crashed TypeScript backend autonomously, with backoff and crash-loop protection, without Electron.
5. Provider SDKs and protocols, conversation and session state, persistence, orchestration and recovery policy stay in TypeScript.
6. Rust restores the backend process; TypeScript loads persisted truth and reconnects or resumes supported sessions. Unrecoverable turns become interrupted. Ambiguous delivery never permits replaying prompts, tools, approvals, steers, schedules or any other possibly accepted work.

### Acceptance criteria

- Fresh, legacy and corrupt settings default to off. Enabling succeeds only with a durable preference, a compatible staged runtime, native lifecycle capability and an acknowledged policy.
- Enabled quit during a turn keeps backend and provider identity; the turn completes and persists with no Electron process, and reopening observes the completion once.
- A backend crash without Electron causes a bounded restart (a new generation and a new `BackendInstance`) and gated TypeScript recovery. Only an actual unresolved **managed resource** can force recovery-only startup; ordinary SDK, shell or PTY use cannot permanently taint a profile.
- Repeated ordinary Unix SDK, shell and PTY use, clean quit and reopen, and clean updates work without a reboot, assumption-reset buttons or retained blanket uncertainty.
- Concurrent launches yield one service and one backend per canonical state root. CLI or incompatible owners are never displaced implicitly.
- No engine startup flush, reconciliation, lifecycle queue flush, provider command, schedule, learning job, delegated model-choice expiry or automatic fork overtakes recovery classification. This includes cold persisted threads and recovery that takes longer than 60 s.
- Each previously active turn is justified as recovered and active, interrupted, or specifically ambiguous and blocked. Conversation resume alone is not active-turn continuation.
- After a Rust-driven restart, OpenCode V2 threads recover through the existing owner-backend-dead proof and per-instance receipt fence. The service writes no V2 record and adds no second proof kind.
- Control replay rejects expired or evicted sequences without re-execution across reconnects and epoch changes.
- Default quit, Stop, OS session end and updates stop managed resources within a bound. Updates fail closed on actual unresolved owned resources, provider-specific ownership or file-replacement failures, **not** on hypothetical proofs that no daemon exists anywhere.
- Packaged tests on macOS, Windows and Linux (AppImage) prove lifetime, native notifications, signal delivery, auth and discovery, runtime closure, update and coexistence, and the absence of automatic duplicate side effects.

### 3.3 Machinery landed since `d293d06f1` that this plan must reuse

- **Backend instance.** `BackendInstance` (`startup/backendInstance.ts`) exposes the lock holder's nonce, PID, start token, hostname, machine id, `assertHeld()` and `classifyOwner()`. A backend restarted by Rust acquires a new lock with a new nonce, so it is a **new backend instance**.
- **OpenCode V2 dead-backend recovery.** Signed `instances/` records: an owner marker `bigbud.thread.backend-owner.v1` written before each enrollment, and a per-instance receipt fence `bigbud.thread.receipt-fence.v1` written at the first V2 orchestration open of each instance (`OpencodeV2/Orchestration.instances.ts`). On the next send, `Orchestration.enrollment.deadBackend.ts` proves the previous owner dead (lock held, marker missing or foreign with `classifyOwner` = dead, native session inactive) and settles with `bigbud.thread.retirement-proof.owner-backend-dead.v1`. A stalled reboot retirement is superseded only when its own proof fails. Normal V2 shutdown detaches thread tools within `V2_THREAD_TOOLS_SHUTDOWN_MS` = 5 s (`Runtime.shutdown.ts`, started by `Runtime.ts:388` via `Runtime.teardown.ts:71`). This 5 s bound applies only to V2 thread-tools retirement inside the backend's finalizers. `Runtime.close()` then awaits `manager.close()`, whose `closeOwnedChild` (`ServerManager.child.ts:85–108`) ends stdin and escalates TERM and KILL at 1 s steps, adding up to about 3 s; worst-case V2 shutdown is therefore about 8 s.
- **Typed turn-start failures.** `TurnStartFailureClass` (`contracts/src/orchestration/orchestration.turnFailure.ts`): `busy`, `context-limit`, `session-dead`, `auth-or-quota`, `invalid-request`, `unsafe-to-replay`, `provider-unavailable`, `unknown`. `ProviderTurnFailureClassification.ts` classifies; `…recovery.dispatch.phase.ts` holds the **no-resend-after-dispatch rule**: a failure is resendable only when proven to precede dispatch; any later `session-dead` is reported `unsafe-to-replay`. The dispatch phase is in-memory per attempt and is not persisted.
- **Revive, replay, fork.** `withTurnStartRecovery` (`…recovery.turnStart.ts`) gives a `session-dead` turn start at most one revive (resume cursor) and one fresh session with transcript replay that drops the uncertain trailing turn (never for OpenCode V2). After that, `ProviderCommandReactorHandlers.fork.ts` forks automatically through the idempotent `thread.fork` command (migration 128 adds the lineage columns). A pending message goes to the fork only when it was never admitted; otherwise it is held. Only the user's "Send now" (`userRelease: true` on `thread.queued-prompt.flush`) releases a held queue.
- **Delegated model-choice holds.** A held delegated first turn blocks dispatch until it is picked or expires (`DELEGATED_MODEL_CHOICE_HOLD_MS` = 10 s). Expiry and sweep live in `ThreadWatchReactor.modelChoice.ts` (§3.2). `DesktopSupervisorDelivery.hasOpenConsumer()` (`desktopSupervisorDelivery.presence.ts`) decides whether to hold at all: with no open desktop or web consumer, the fallback is applied at once (`no-client`); mobile does not count. `hiddenComposerProviders` moved to server settings, so it applies with no client connected.
- **PTY and shell.** `node-pty` is on the latest stable release, `^1.1.0` (resolved 1.1.0 in `bun.lock`), by the user's decision on 2026-10-16 to prefer stable releases. 1.1.0 leaks one `/dev/ptmx` descriptor per spawn on macOS (two on a failed spawn); `1.2.0-beta.15` fixes it but is a prerelease. `NodePTY.leak.test.ts` marks the leak cases as expected failures on macOS while 1.1.0 is installed, so a fixed stable release is detected. `ThreadShellRunner` startup is bounded by the command timeout and releases its lease and lock on failure.
- **Desktop artifact.** `scripts/lib/desktop-artifact/serverRuntimeDependencies.ts` installs the staged server with `npm install --omit=dev --install-links` (flat layout, real copied directories, optional platform packages kept for the Copilot CLI) and a `node-domexception` override shim that is deleted after install.

## 4. Engineering decisions and assumptions

These are explicit engineering choices, not additional user agreements.

1. A new, separately packaged `bigbud-background-service` crate and binary; the existing desktop-supervisor is unchanged. One native lifecycle implementation serves both the final foreground-owned mode and background mode.
2. Both production modes launch from an immutable staged runtime, so hot enable and disable change policy without a restart. An explicit unstaged legacy, dev or staging-failure fallback is background-incapable; enabling then offers a user-confirmed staged restart, never a hot transplant.
3. Per-user, logged-in session only: no root service, autostart, linger, sleep prevention or post-logout operation. Backend crashes are recovered without Electron; supervisor self-resurrection is not promised.
4. Disabling affects the next quit, not current work. Explicit Stop is separate; relaunching an enabled app restarts only the client. Data attachment requires the exact build; stable admin v1 supports stop and quiesce across builds.
5. The authorized background CUA physical daemon is preserved; permission and install UI stay desktop-only. GUI-only calls fail explicitly while unavailable, with no automatic grants or replay. The control plane is local only; the existing mobile and Tailscale data policy is unchanged.
6. **Managed-process contract:** the service guarantees lifecycle for declared provider roots, app-created groups, native agents and PTYs, and registered helpers. Their acknowledged or native settlement suffices for normal shutdown and update. It does not certify the absence of every daemon that user shell code or opaque tools launched after intentionally escaping registered groups. Such escaped descendants are an existing Unix limitation, not a default global fence.
7. Abrupt loss fences an execution only on concrete unresolved managed ownership, native admission or provider-specific cleanup evidence. Parent exit alone cannot settle a still-owned registered group; theoretical daemonization is not evidence of unresolved managed ownership. No unconditional reboot fallback. The existing stronger OpenCode V2 and remote cleanup fences remain authoritative.
8. **Reuse the landed recovery machinery (new).** The backend's `BackendInstance` lock is the only proof that a previous backend is dead. OpenCode V2 retirement, the receipt fence, `TurnStartFailureClass`, the no-resend-after-dispatch rule, revive/replay, `thread.fork` and model-choice hold supervision stay the TypeScript authorities. The service reports physical evidence and generation identity only; it never writes provider or V2 records.

No unresolved product decision is required. Guaranteeing arbitrary Unix daemon containment would be a separate sandbox or privileged platform project and is out of scope; do not promise it silently or make ordinary use unusable trying to prove it.

## 5. Scope and authority

In scope: the Rust host, control, admin, discovery, logging and native OS lifecycle; managed spawn registration and cleanup; the staged runtime; desktop policy and UX; TypeScript startup gates and recovery; CUA and monitor ownership; update and coexistence; tests and rollout.

Out of scope (non-goals): Rust provider or domain truth, blind replay, legacy OpenCode revival, hot fd migration, autostart or linger, a privileged universal Unix sandbox, adopting arbitrary external daemons, new remote authority, guaranteed terminal survival after backend loss, independent service auto-update, and changes to the dead-thread or model-choice rules.

## 7. Phases: ordered implementation specification

### 7.1 Native crate, control, discovery, admin and bounded replay

1. After D1, create `crates/bigbud-background-service/` and add it to the root workspace. Keep `main.rs` thin, with capability folders `lifecycle/`, `ipc/`, `discovery/`, `process/`, `platform/` and `logging/`. Put reusable native registration in the existing `bigbud-system` only when both the service and the remote agent consume it; never depend on an executable crate.
2. Add `protocol/background-service/` source schemas (beside `desktop-supervisor`, `remote-agent` and `system-monitor`), Rust generation, and a TypeScript codec under `packages/shared/src/background-service/` with explicit subpath exports and golden fixtures (shared because both Electron and the backend consume it; existing codecs live per app, e.g. `apps/server/src/desktop-supervisor/desktopSupervisorProtocol.codec*.ts`). Frames are versioned, length-prefixed protobuf with at most 1 MiB, checked before allocation. Malformed, empty, truncated, partial and version-invalid frames are handled within bounds.
3. Identity is the canonical state root plus OS user plus release identity; the build is separate. A shared `BIGBUD_HOME` cannot create independent same-root backends through a different channel. Use an OS-held service lock plus the existing TypeScript `backend.lock`. The private directory is 0700 or current-user ACL; reject symlinks, reparse points and insecure ownership. The socket path is a short hash, validated against the full root at hello.
4. Atomic, non-secret discovery records the epoch, PID and start token, root digest, admin endpoint, protocol, data build and runtime digest. Capabilities are separate and private, with OS peer or ACL authentication; desktop and backend-generation credentials differ. No secrets in argv, logged URL tokens or renderer persistence. There is no isolation promise against a fully compromised same-user profile; other users and the network are denied.
5. Only a matching owner epoch and nonce may remove discovery. Prove death or a start-token mismatch before a stale takeover. Denied, busy, timeout, malformed, foreign or unknown owners fail closed and never mean "absent". Never signal a PID read from a stale file without authority.
6. Data hello requires the exact build, runtime, root and protocol; readiness is an authenticated ready message, not socket existence. Keep the configured mobile/LAN data policy; control stays local.

**Stable admin v1:** distinct magic and major version, at most 16 KiB per frame, same-user authenticated capability, and only the verbs `status`, `stop`, `quiesce` and `operation-status`. No exec, start, provider or credential export. It survives data protocol changes. An incompatible new app can warn about active work, explicitly stop the old service and prove its death before migrating. For a future admin mismatch, use `--control` from the matching retained, **verified manifest** runtime, never an executable supplied by discovery; pass the secret over stdin or a private channel. Without a compatible verified controller, tell the user to open the old version and stop it; refuse implicit kill, lock deletion or downgrade. A CLI owner follows the existing stop or different-home guidance.

**Mutation sequencing:** hello issues a monotonically increasing `leaseNumber` within the service epoch plus a random secret. At most 16 live leases, one writer connection per reconnect generation. Retired numbers are never reissued: an absent number at or below the issuance high-water mark is expired; a higher one is invalid. Each lease accepts only sequence H+1 and atomically reserves the digest and H before execution. A gap beyond H+1 is rejected. Within the retained window [F, H], the same digest returns the prior or in-progress result and a different digest is a conflict; below F is expired and never executes. At most 256 completed results are retained globally, each for at most 10 minutes. Eviction removes only the contiguous oldest completed prefix of a lease and advances F; no holes and no in-flight eviction (report busy instead). Long stop and quiesce operations return a queryable operation handle. Idle leases expire after 10 minutes only when no work is in flight. Reconnect returns H, F and state; replay of the same sequence and digest works only within the window. An expired or unknown mutation leads to state reconciliation or an explicit user retry, never an automatically reassigned sequence or new lease. An epoch change invalidates all leases. Persistent policy revisions and maintenance operation handles support reconciliation, not exactly-once durability. Provider calls keep using TypeScript durable receipts and admission journals, never a native cache.

### 7.2 Native lifecycle, bootstrap, output, signals and OS session end

- States: starting, running, recovering, recovery-only, backoff, failed, quiescing, stopping, stopped. The backend generation fences all callbacks. Backoff starts at 500 ms, doubles, caps at 30 s and adds ±20 % jitter. Five unexpected failures within 120 s latch `failed`; the counter resets only after 60 s of stable, usable operation. Configuration, migration, auth and ownership errors are not retried. Retry never overrides an actual cleanup, maintenance or session-end fence.
- **Restart ordering with the backend lock (new):** before spawning generation N+1, the service waits for and reaps generation N. The new backend then takes over `backend.lock` through the existing dead-owner proof (PID, start token, machine id) and gets a new `BackendInstance` nonce. The authenticated ready message reports that nonce, and the service records generation ↔ nonce for diagnostics only. If the old backend cannot be proven dead, the restart stays in backoff or `failed`; never delete the lock.
- The service owns null or private stdio, not Electron pipes. Unix `setsid` separates the controlling terminal, not the logged-in GUI context. On Windows, escape the parent's kill-on-close job with a verified breakaway launch and inspect the outcome; refuse background mode if unavailable, with no WMI or elevation fallback. The backend is assigned its own Job Object before it executes.
- When a foreground desktop owner connection dies, allow 5 s to reattach, then stop. In acknowledged background mode, a disconnect is not cancellation. No wall-time heartbeat expiry during sleep. Every native task and listener has cancel and join.
- Add a portable bootstrap-over-stdin mode in `apps/server/src/startup/{bootstrap,config,startupStatus}.ts` and the bin composition: a private envelope, then authenticated ready and drain over IPC. Keep the old fd3/fd4 path for CLI and dev during migration; do not assume Rust Windows handles map to Node's extra-fd conventions. The envelope carries auth, control generation, `baseDir`, bind, dependencies (including the staged desktop-supervisor path) and observability settings; no secrets in argv.
- `control-ready` within 60 s means the state lock and persistence are held and gates and subscriptions are installed; classification progress and `usable` are reported separately. Recovery may take minutes without a restart; never kill a healthy recovering backend at 60 s. Report the actual bound URL; port races are bounded; a slow provider is not proof of a backend hang.
- The native host drains output independently of the UI: at most 1 MiB per diagnostic stream, 128 status records per subscriber, and 10 files of 10 MiB per log family. A full disk or slow subscriber drops sanitized diagnostics with counts and gaps; it never blocks SDK pipes or grows memory without bound. Only structured lifecycle logs; secrets, prompts and tool output are excluded. No native conversation replay store.

#### Child signal reset at every native exec boundary

Host signal masks used by `sigwait` are **host policy only**. POSIX blocked masks and ignored dispositions survive exec; do not assume `std::process::Command` or `execve` restores them.

1. Define a child launch baseline: an empty blocked mask and default dispositions for every catchable signal whose disposition the host or guard changed (at least TERM, INT, HUP, QUIT, PIPE, CHLD and the internal wake signal). Never touch KILL or STOP. A detached host must not leak `SIG_IGN`. Payloads and SDKs may install their own handlers after exec; never preinstall host handlers in them.
2. For the direct backend exec, precompute everything in the parent and use narrow async-signal-safe `pre_exec` steps: `sigaction(SIG_DFL)` and `sigprocmask(SIG_SETMASK, empty)` immediately before exec. Report failure through the spawn error channel and **do not exec**. `posix_spawn` paths use `POSIX_SPAWN_SETSIGMASK` and `POSIX_SPAWN_SETSIGDEF`. No allocation, locking or logging in child `pre_exec`. Reset only in the child; never unblock host worker masks.
3. The native launch guard starts with a documented guard mask and installs its own control forwarding; its **payload child** resets to the baseline again immediately before the final exec. Only the guard may keep its signal-wait mask. A held-before-commit payload waits for the grant without running user code, then resets; EOF or an invalid generation exits without exec. Forkpty paths also reset before the final real-command exec; resetting TTY foreground or control state does not substitute for this. Reusing a first-party managed helper must not skip this boundary. For `node-pty` 1.2.0-beta.15, do not rely on its internal child setup: the guard is the exec boundary.
4. Fixtures: the backend readiness fixture inspects its actual blocked mask and receipt of a TERM handler. Guarded provider and PTY payloads start while the service masks TERM, INT and HUP, and verify that graceful TERM runs the handler, writes a completion marker and exits **before KILL escalation**. A separate default-disposition fixture verifies that TERM terminates a payload without a handler while the host stays alive. Test HUP, INT and PIPE; a failed reset prevents execution; existing PTY Ctrl-C, resize and EOF behavior is unchanged. Windows does not use POSIX masks; separate handle and job tests apply.

#### Native OS lifecycle with Electron absent

One native event queue plus an independent, atomic, highest-priority session-end/stop latch; queue overflow cannot lose a shutdown. Check the latch before every child commit, exec and retry. The backend gate closes through authenticated control. The OS may force-kill early; graceful completion is not promised.

- **Windows:** a hidden **top-level** native window and message pump (not message-only). `WM_QUERYENDSESSION` sets a tentative no-spawn/no-admission fence and returns TRUE immediately, with no irreversible cleanup. `WM_ENDSESSION(TRUE)` commits drain with no restart; FALSE clears only the tentative OS fence, not an independent update or failure fence. WTS logoff of the owning session commits stop; lock and disconnect only mark the GUI unavailable. Unregister, destroy and join the pump. A console-handler-only detached design is not acceptable.
- **macOS:** an AppKit main-thread loop with activation prohibited and no Dock UI, an `NSApplication` delegate and the `NSWorkspace` notification center. Power-off, termination, TERM and INT fence and drain. Reply to termination within 3 s; never use an indefinite `NSTerminateLater`. Sleep, wake and session active/resign change availability and are not proof of logout. Once shutdown is committed, another app cancelling logout does not restart the service; the next explicit open revalidates the session. Use documented notifications and retain and remove observers correctly; no non-GUI Mach bootstrap migration.
- **Linux:** dynamically loaded sd-bus/logind matches `PrepareForShutdown`, `PrepareForSleep`, `SessionRemoved`, and the own session's changes and `Lock`/`Unlock`. `GetSessionByPID` plus the uid pins the owning session, not untrusted environment variables. Subscribe first, then query the preparing flags and session state. Closing or removal of the own session commits stop. Sleep suspends retry-deadline accounting and GUI availability; wake revalidates. `PrepareForShutdown(false)` removes only an uncommitted tentative fence. No linger, service registration or polkit. A missing library, symbol, bus or session refuses background mode while foreground works. If monitoring is lost while background mode is active, fence starts, retry observation for at most 5 s, then stop; never persist silently without session authority.
- **Unix signals:** masks and the `sigwait` thread are set up before workers; TERM and INT commit stop; HUP from a detached terminal is ignored by the **host only**. The dedicated thread has wake and join. Verify OS monitor capability before acknowledging enable. Sleep does not cancel work; a forced stop persists partial-state recovery evidence on a best-effort basis.

### 7.3 Managed process registration and three settlement paths

**Scope boundary:** owned resources are explicitly launched or registered SDK roots, app-created detached or group scopes, first-party agent command and PTY leaders (including backend `node-pty` PTYs), and their declared helpers and group cleanup domains. Arbitrary user or tool subprocesses that deliberately detach outside those domains are not silently adopted. Do not label SDK, shell or PTY activity "cleanup-unconfirmed" at launch. This feature is neither a sandbox nor a universal daemon census.

**Ledger:** per-scope states `reserved → registered-held → running → stop-requested → settled`, with `cleanup-unconfirmed` only for a specific observed failure or lost required authority. Store launch and owner epochs, nonce, role, process identity, registered groups and helpers, and settlement evidence; no prompts or secrets. Persist before granting execution wherever a scope can outlive the backend. At most 4,096 live scopes; exhaustion rejects before exec. Compact completed evidence after a durable terminal or cleanup acknowledgement; no permanent generic risk bit.

**Pre-exec registration:** backend-only `reserve-spawn` and `register-held-scope` tickets bind an approved executable identity and an opaque scope ID; there is no renderer exec API. A trusted guard creates and holds a group anchor, reports PID, start token and PGID, and waits for the native commit before running the payload. If TypeScript dies before the grant, no user code runs. The guard preserves raw stdio and signal and exit semantics and parses no provider protocol. The service registers scopes even when the original parent is short-lived; the group anchor prevents signaling a recycled PGID. For remote-agent groups and forkpty, allocate the child gate before fork, perform only async-signal-safe setup, let the parent register, and have the child wait for commit or EOF before the real exec and the signal reset (§7.2). A PTY guard keeps controlling-terminal and foreground behavior; shell job-control groups are not all registered just because of the initial PGID. The existing directly owned PTY reap authority stays the sole reaper.

Overflow blocks the affected thread and requests an authoritative resnapshot where supported; evidence is never dropped and followed by ready. Reserve engine capacity for recovery. Drain only admitted observations through the watermark; never wait on gated execution. The coverage frontier comes from a consistent database read transaction and stable IDs; a failed inventory read keeps the global gate closed (never catch, log and open). Deletion and retention epoch fences prevent resurrection.

Each adapter resume is bounded at 45 s, matching normal session starts (corrected from a separate 30 s deadline, which would cut legitimate starts). The bound is not applied on the recovery path today: extract `PROVIDER_SESSION_START_TIMEOUT` into a shared provider module, keep it on the normal start (`ProviderService.startSession.ts:149`) and apply it to the resume at `ProviderServiceSessionRouting.ts:137`; observation drain per thread is bounded at 30 s. A timeout yields interrupted or blocked, never inferred cancellation of external side effects. Aggregate recovery may exceed 60 s. Publish native `control-ready` after storage, subscriber and gate safety; `usable` after coverage. Losing a subscription immediately closes dispatch and reconciliation until replay or a scan restores safety. One slow item cannot hold all read-only history hostage. A durable classification, expected session epoch and turn guard precede release; late callbacks cannot open the gate. Constructors allocate state only and queue no execution.

### 7.8 Shutdown, update and rollback transactions

1. Native quiescence latches: no starts, tickets, retries or policy enables before acknowledgement; the TypeScript execution gate closes; the existing desktop `installedProcessQuiescence` still fences its commands and installers.
2. TypeScript drains accepted writes, runs provider stop-all (including OpenCode V2 thread-tools retirement, bounded at 5 s) and declared agent and PTY shutdown, and publishes the complete generation inventory barrier from §7.3. Normal clean SDK and shell use is settleable; no generic opaque marker. Codex async cleanup, Claude close failures and Copilot `Error[]` are aggregated accurately. Native verifies each required root, group and helper settlement separately from the TypeScript event.
3. **Backend stop timing (corrected):** the ordinary stop bound is 12 s from the stop request, sized from the worst-case finalizer sum: 5 s V2 retirement, about 3 s owned OpenCode child close, other provider stops and database close, plus margin. With a control channel, the drain request itself starts provider stop-all (including V2 retirement), and the backend exits on its own; TERM is sent only if it is still alive 10 s after the request. A TERM arriving after drain started does not restart the finalizers: they are idempotent and share one shutdown signal (V2 `beginShutdown` reuses its signal). Without a control channel, TERM at the request is the first signal and starts the same finalizers. In both cases KILL follows at 12 s. The original "KILL 2 s after TERM" would preempt these finalizers, which the dead-thread work added to make dead-backend recovery the exception; leftover V2 records stay safe either way. After backend exit, native managed settlement of registered roots, groups and helpers is bounded at 10 s, so a service stop operation completes within about 22 s. Native child signal resets make TERM actually reach the backend. The OS deadline can be shorter. A remaining exact owned resource or uncertain identity blocks an overlapping replacement or update. Successful forced physical termination may settle with a warning; provider-specific delivery or enrollment ambiguity is separate. Do not block an update for a hypothetical unregistered daemon without actual dependency or lock evidence. Measure these values in packaged qualification and adjust the constants together.
4. The desktop stops its own commands and monitor, extends `windowsUpdateTargets` to the service and runtime resources, and keeps the existing Windows process sweep, replaceability probe and restart-required failures. No claim that all arbitrary Unix processes are gone. The service sends a final quiescent operation result after managed physical proof and exits; the updater verifies service death before handoff. The updater waits on the service's stop-operation handle with a 30 s deadline (above the 22 s stop plus settlement), never `stopBackendAndWaitForExit()`'s 5 s default (`main.bootstrap.ts:263`). On timeout the update fails closed: no install handoff, restart-required error, maintenance fence kept.
5. A persistent maintenance nonce, epoch and runtime fence prevents concurrent relaunch during install; update failure or cancellation does not age-clear it. The next explicit app start validates the install and the old owner's death, offers to resume and clears the matching transaction. The admin protocol is the same across versions; no old timers restart.
6. Explicit Stop uses the same machinery without a replacement. Enabled ordinary quit only detaches. A service crash closes backend control and the gate and triggers bounded backend shutdown; the next discovery uses live guards, the ledger and the lock. If all managed scopes can settle, a normal restart proceeds without a reboot; an unresolved exact scope keeps its targeted fence. Reboot is optional last-resort evidence for an actually lost local owner, never a blanket requirement; remote effects stay ambiguous.

## 9. Risks, observability and rollback

- Native managed cleanup and TypeScript domain settlement are different gates; neither may infer the other. Log the concrete scope, phase and reason, not a blanket opaque risk.
- Unregistered, intentionally daemonized Unix descendants are outside the lifecycle guarantee, as today. Do not advertise universal containment and do not break updates or reopen trying to prove a negative. Known first-party detached groups are registered before execution; an observed unresolved managed owner keeps its fence.
- Signal-mask inheritance can silently defeat graceful shutdown; the explicit reset is release-critical.
- Shutdown timing: a KILL that preempts backend finalizers leaves V2 enrollments for dead-backend recovery (safe, but it defeats the dead-thread plan's goal G3). The legacy Electron path (`backendShutdown.ts`, KILL after 2 s, 5 s wait; fire-and-forget on quit) keeps that weakness until it is removed in rollout step 5.
- Recovery gate versus landed reactors: model-choice expiry, revive/replay, automatic fork and lifecycle flushes are new execution paths since the original plan. Missing any of them in the gate would execute before classification; the regressions above name each one.
- `node-pty` stable 1.1.0 leaks a `/dev/ptmx` descriptor per spawn on macOS, so a long-lived background backend slowly exhausts the machine's pseudo-terminals (`kern.tty.ptmx_max`). The fix exists only in `1.2.0-beta.15`. Rollout step 4 is blocked until a stable `node-pty` release with the fix is adopted and qualified on Windows ConPTY, the Linux runtime and full packaging, or the user explicitly approves the beta for this feature.
- The immutable Electron runtime costs disk, signing and closure work; foreground staging is intentional and the fallback is explicit and background-incapable. The unlocked `npm install` makes staged contents build-dependent; manifests must be computed from the staged tree. Preserve the CUA host identity.
- When native OS monitoring is unavailable, background mode is refused safely and foreground stays usable; losing monitoring fences and stops within bounds. No login autostart, linger or sleep inhibition.
- Resuming a conversation is not resuming a turn; delivery ambiguity survives physical cleanup. No prompts, tools or approvals are resent automatically. Explicit new user work after managed fences clear is allowed under existing policy, including the dead-thread revive, replay and fork rules.
- The user sees enabled, resource and billing status, Stop, native startup and recovery progress and scoped errors. Logs and counters are sanitized and bounded; no provider content, token or environment telemetry.
- Rollback: stop through admin or the controller, settle managed native resources and the existing file and ownership requirements, keep the database, history and runtime controller, and use the supported foreground launcher. No automatic fallback for an uncertain owner, no state or lock deletion, and no unsupported database downgrade. Migration 128 and later stay; this plan adds none unless P1's durable recovery generation needs one (next number 129, additive only, registered in `Migrations.ts`).
