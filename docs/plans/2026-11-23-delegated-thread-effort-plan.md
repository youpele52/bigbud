# Delegated thread reasoning effort across providers

## Goal

A user can say “Start a new thread with Opus at high effort,” and bigbud sets the child runtime's effort on its first turn. The parent and user can see what was requested and what was configured. Every selectable provider follows the same tool contract: use a supported native level, or explicitly report why the requested level was not applied. Support is per provider, sub-provider, model, and execution target—not a promise that every model has an effort dial.

This plan covers creating new standalone threads, both as the caller and as the worker. It does not add a setting override to `send_thread_message`, change existing threads, alter provider defaults, or re-enable retired providers.

## 1. Extend the existing tool contract

- Add optional `modelSelection.effort` to `create_thread`. Treat it as a bounded, trimmed string validated against the resolved model's exact advertised values, not a global enum. This allows levels such as `xhigh`, `max`, or a provider-defined variant without pretending those values are interchangeable. Keep raw `options` off the public tool and ignored on input; callers cannot configure unrelated model behavior.
- Let `list_available_models` expose the IDs, labels, and known defaults of explicitly selectable effort levels for each usable model. Distinguish confirmed lack of support from unknown capabilities; do not present an inferred default as a selectable effort. Use the same capability and option mapping for discovery and apply so anything advertised can actually be set. Do not make a live provider call for each delegation.
- Keep `get_thread_status` and the `create_thread` result backward-compatible. Add an optional effort decision with the requested level (if well-formed), the explicit level set by this request (if any), and a separate reason from the model-choice reason: `invalid-effort`, `unsupported-effort`, `capabilities-unknown`, `model-not-selected`, or `agent-choice-disabled`. Keep the inherited/default configuration in the existing model selection; don't label an inherited value as a request that was applied. Distinguish configured on the child from provider-observed: an accepted tool call or a configured setting is not proof the runtime started or honored it. Do not invent an effective default when none is known.
- Extend the existing tool schema, capability guides, and provider-injected instructions. Audit every binding rather than assuming the shared schema covers them: MCP and direct HTTP tool dispatch, Codex dynamic tools, Copilot SDK, Pi extension, and OpenCode V2's bootstrap. The [frozen OpenCode V2 tool ABI](/Users/youpele/DevWorld/bigbud/apps/server/src/orchestration-tools/threadOrchestrationBridge.shared.ts:109) does not expose model choice at all today. Add provider/model and effort together via a negotiated/versioned ABI, preserving the old artifact and rolling compatibility. Older bindings must not advertise effort until they can carry it. Verify both caller and worker coverage, including CLIProxyAPI as a caller. Preserve the existing cross-project confirmation.

## 2. Resolve once and keep fallback predictable

Extend the [model choice resolver](/Users/youpele/DevWorld/bigbud/apps/server/src/orchestration-tools/ThreadOrchestrationTools.modelChoice.ts:140) and [persisted decision contracts](/Users/youpele/DevWorld/bigbud/packages/contracts/src/orchestration/orchestration.delegationModelChoice.ts:29). Resolve provider and model first, then validate effort using that exact model's catalog entry and target. A provider-only request uses the existing most-recent-model selection; it does not search for a different model just to match effort. To change effort while keeping the parent's exact model, pass its provider, model, and sub-provider when applicable. A request without a provider does not opt in.

| Request                                               | Behavior                                                                                                                                                                                                                         |
| ----------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Effort omitted                                        | Existing behavior: inherit the full parent selection for the same model or use the other model's normal defaults.                                                                                                                |
| Model usable, effort supported                        | Set only the provider-native effort field, preserving other options that would normally be inherited.                                                                                                                            |
| Model usable, effort invalid, unsupported, or unknown | Keep that model and its normal inherited/default configuration. Report the reason; no extra wait, substitution, or silent clamping. Parse effort separately so a bad effort cannot invalidate an otherwise usable model request. |
| Model or provider unusable, or agent choice disabled  | Keep the existing fallback and, where applicable, short user-pick window. Never transfer the requested effort to a different fallback or user-picked model. Report that it was not applied.                                      |

The existing delegated model-choice setting gates agent-selected effort too. Persist the decision alongside the existing delegation result before dispatch and reuse it for retries and restart recovery; do not recalculate it on duplicate invocation. Ensure the exact selection reaches child creation and first-turn dispatch (including holds and queued starts) and persists as the child's normal selection unless the user changes it. Add optional fields only; old activities, snapshots, and delegation records must still decode without a data backfill. Surface explicit and unapplied effort in the existing model-choice notice without adding noise to calls that omit it.

## 3. Verify provider and target parity

Start from the [provider registry](/Users/youpele/DevWorld/bigbud/packages/contracts/src/constants/provider.constant.ts:9) and reuse [the existing `patchProviderEffort` mapper](/Users/youpele/DevWorld/bigbud/packages/shared/src/model/model.effortFields.ts:59). Check the exact catalog capability and its provenance before patching and validate the resulting `ModelSelection` afterward. The composer can accept unverified values in some cases; don't reuse that permissive behavior here. Verify the actual first-turn request for each provider; catalog metadata alone is not evidence the setting reaches the runtime.

| Provider         | Existing model option | First-turn checkpoint                                                                                               |
| ---------------- | --------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Codex            | `reasoningEffort`     | App-server `turn/start` effort; check the active model list on the runtime host.                                    |
| Claude           | `effort`              | Agent SDK startup/turn effort. Exclude prompt and workflow traits like `ultrathink` and `ultracode`.                |
| CLIProxyAPI      | `effort`              | Proxy-advertised tier survives the Claude-transport translation.                                                    |
| Copilot          | `reasoningEffort`     | SDK session/model config; don't infer tiers for `auto` or unverified custom entries.                                |
| Cursor and Devin | `reasoning`           | ACP `session/set_config_option` before prompting; verify each adapter against its live choices.                     |
| Muse Code        | `reasoningEffort`     | Native effort on `turn/start`; missing qualified catalog levels are unknown.                                        |
| OpenCode V2      | `variant`             | Native variant passes admission for the exact upstream model and location; caller tool update remains separate.     |
| Pi               | `thinkingLevel`       | `set_thinking_level` follows model selection and precedes the prompt; use the exact upstream sub-provider metadata. |

Legacy OpenCode remains readable in historical records but isn't a new child target.

- For proxy/router/custom models and OpenCode variants, require known support for the exact account/provider/model identity. Never infer capabilities from a family name or copy them from a different sub-provider. If a provider has a working effort input but no trustworthy discovery, wire the metadata first or report capabilities as unknown. If it has no effort input, return unsupported rather than injecting a prompt instruction.
- Validate remote targets only where the provider is actually supported. Today Codex and Pi support remote provider runtimes; a local runtime using a remote workspace is a separate capability. The current [model listing](/Users/youpele/DevWorld/bigbud/apps/server/src/orchestration-tools/ThreadOrchestrationTools.listAvailableModels.ts:44) filters for the caller's target, but the cached registry isn't a catalog queried from that host. Label the listing scope and establish target-qualified capability evidence before advertising remote effort. Always revalidate for the child's actual target, including cross-project delegation, and verify its transport preserves the option. A local model with the same ID is not evidence of remote support. Keep existing trust, preview, availability, and target rules intact. The separate `delegate_to_host` tool is outside this plan.

## 4. Implementation order and release gates

First prove discovery-to-first-turn on one existing effort path and lock down the persisted decision contract. Then complete the provider and caller matrix, including any missing runtime mappings and the OpenCode V2 ABI update. Treat the first working provider as a milestone, not completion: release only when every selectable provider has a verified effort path or an explicit, tested unsupported/unknown outcome, and every provider that offers delegation can pass the new field (or identifies its compatibility limit).

1. **Contracts and resolution:** old and new payloads; omitted, malformed, supported, unsupported, and unknown effort; inherited settings; permission-disabled choice; provider-only selection; model aliases and same-slug sub-providers; remote catalog unavailable and local/remote capability disagreement. Use a coverage table keyed by selectable provider kind so a new provider cannot silently miss classification.
2. **Transport:** tool schemas and forwarding on each enabled caller binding; old clients still create children; OpenCode V2 compatible and incompatible artifact versions; initial result, status, and UI agree about requested and configured effort. Verify no raw provider options slip through.
3. **Runtime:** assert the first native request for every adjustable provider with protocol/SDK fixtures; include queueing, duplicate tools, retry/restart, user-pick/timeout, and reconnect where applicable. Verify unsupported providers still start the expected child and report why effort wasn't applied. Exercise mixed-provider calls in both directions so testing a provider only as a worker doesn't hide a broken caller binding.
4. **App acceptance:** with approved available accounts, run “Start an Opus thread at high effort” and an equivalent cross-provider request, check the resulting thread setting and first outbound request, then exercise an unsupported model and verify the notice. Cover each supported target with fixtures; do not claim live coverage on unavailable accounts or targets.
5. **Completion:** run scoped file-length, format, lint, package type checks, and focused Vitest/browser tests for changed files and affected packages. Get separate approval before wider checks. Update user documentation and changelog after verified behavior.
