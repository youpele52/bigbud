### U15 design entry: production owner Git receive (push) (26 November 2026)

The upload entry above applies unless stated here. This entry closes the blocker "no trusted approval producer for expected old OIDs".

- **What the approval guarantees.** A push to a bigbud target writes exactly one ref, `refs/heads/<upstream branch>`. It moves that ref from the OID the user last saw (the expected old OID) to the user's current `HEAD` (the source OID), as a fast-forward. It writes no other ref and never deletes one. If the remote ref moved since the user's view, the push is refused as stale and nothing is written.
  - **First publish (added 26 November 2026).** A branch with no upstream is published under its own name with the expected old OID all zeros. The owner requires the ref to be absent from the live advertisement; if it is present, the push settles `stale`. The owner admits only `<zero> <source> <ref>`, and local Git sees no ref, only the live tips as `.have` lines (the capabilities on the first one, as receive-pack writes them), so it can send a thin pack. The push uses `-u <remote> refs/heads/<b>:refs/heads/<b>` to record the upstream. The owner still pins the source OID, so a moved branch is refused, not pushed.
  - Every other push shape stays refused.
- **Trusted producer.** The approval is produced only by the user-initiated push (the `git.runStackedAction` RPC; no provider or agent reaches `pushCurrentBranch`). At that moment the server reads, through the fenced local Git executor (`--no-lazy-fetch`, no network):
  - the repository identity;
  - the tracked branch (`branch.<b>.remote` and `branch.<b>.merge`);
  - the source OID (`HEAD`);
  - the expected old OID, which is the tracking ref `refs/remotes/<remote>/<branch>`. Background upstream refresh keeps this ref current through the same owner upload lease (U15 upload), so it is the remote state the status UI showed.

  The existing guard `pushSelectedInitiatingBranch` (`GitCore.initiatingPush.ts`) then re-checks the scope (single push URL, mirror/followTags off, tracked ref, identity) and calls the bounded transport once, through `makeIsolatedInitiatingPushOwner` (`GitCore.initiatingPush.composition.ts`).

- **Why the local tracking ref is enough.** Safety does not rest on it. A forged expected old OID can only make the owner refuse (stale); it cannot widen the write. These four checks hold independently of it:
  1. The owner compares the expected old OID with the live receive-pack advertisement, read over its own pinned channel.
  2. The owner's command gate admits only `<expected old> <source> <ref>` (for a first publish, `<zero> <source> <ref>` with the ref absent).
  3. receive-pack's compare-and-swap on the old OID applies at write time.
  4. The owner-fixed remote config enforces `receive.denyNonFastForwards=true` and `receive.denyDeletes=true`.
- **Verbs.** Request `git_receive_open` (110), `git_receive_status` (111) and `git_receive_close` (112). Reply `git_receive` (66). In `v1.workspace_git.proto`:
  - `GitReceiveOpen { lease, workspace_root, repository_path, destination_ref, expected_old_oid, source_oid }`;
  - `GitReceiveLease { lease }`;
  - `GitReceiveState { lease, phase, socket_path?, receipt }`;
  - `GitReceivePhase` (listening, streaming, finished, closed, lost, rejected, unconfirmed);
  - `GitReceiveReceipt` (accepted, unchanged, rejected, stale, refused).

  No new ErrorCode is needed: stale, refused and rejected are settled receipts, and admission uses the existing codes. The verbs are production verbs, admitted on macOS and Linux production owners.

- **Owner checks before any process.**
  - Both paths pass the upload `admits` rule.
  - The destination ref is a valid `refs/heads/…` name.
  - Both OIDs are 40 or 64 lowercase hex characters, nonzero and of the same width. Otherwise the request fails with `invalid_operands`.
  - There is one live receive lease per target, in a lane separate from upload. The receive lane is reaped on revoke.
  - The pinned SSH is the same as for upload (`pinned_git_upload_ssh`): the target's own key or policy CA, no forwarding, and no agent or connector route.
- **Process.** The guard is shared with upload; its verb operand is fixed by the owner. The command is `exec /usr/bin/env -i LC_ALL=C HOME PATH=/usr/bin:/bin GIT_CONFIG_NOSYSTEM=1 GIT_CONFIG_GLOBAL=/dev/null /bin/sh -c <guard> … receive`. After the symlink-resolved containment check, the guard exports `GIT_CONFIG_COUNT=2` (`receive.denyNonFastForwards=true`, `receive.denyDeletes=true`) and execs `git-receive-pack <resolved path>`. The repository's own hooks still run, as with any push to that repository.
- **Owner conductor (per lease worker).** This is not a byte pipe: the owner sits between the local socket and receive-pack. The steps are:
  1. Accept one connection within 15 s, then spawn the pinned child with piped stdin/stdout.
  2. Read the full v0 advertisement. Bounds: 16 MiB, 65,520 bytes per packet, exactly one entry for the destination ref, and an object format that matches the OID width.
  3. If the live OID is not the expected old OID, or the ref is absent, settle with receipt `stale`. Nothing has been forwarded.
  4. Send local Git a synthesized single-ref advertisement with the capabilities narrowed to `report-status`, `side-band-64k`, `ofs-delta` and `object-format`.
  5. If the expected old OID equals the source OID, read the client's flush and settle with `unchanged`. Nothing is written.
  6. Otherwise, gate exactly one command and its flush with `authorize_receive_prefix`. Any deviation settles `refused`, with nothing forwarded.
  7. Revalidate the lease (not cancelled, within the deadline), then forward the prefix.
  8. Pump the pack. The pack cap is 1 GiB and the report cap is the gate's limit.
  9. Classify the report with the gate's parser: `accepted` or `rejected`. Forward the report bytes to local Git only for a confirmed receipt.
  10. Any I/O failure, cancellation or deadline after the prefix was forwarded settles `unconfirmed`, and the write is never replayed. A watchdog kills the process group and shuts down the socket on close or at the 120 s deadline.
- **Server transport.** `BoundedInitiatingGitTransport.receiveTrackedPush` covers exactly one destination; a multi-URL push is denied before dispatch. The steps are:
  1. Pick the target and workspace root as for upload.
  2. Open the receive lease and bridge it through the same one-connection shim socket (`openOwnerGitStream`, generalized over the lease opener).
  3. Run `git push --no-follow-tags --recurse-submodules=no --no-signed <remote> <source OID>:<ref>` (first publish: `-u <remote> refs/heads/<b>:refs/heads/<b>`) under the sanitized environment plus the shim. The exact source OID, not `HEAD`, is pushed, so a moved `HEAD` cannot change the update.
  4. Wait (at most 15 s) for the lease to settle, then close it. Map the settled receipt to `TrackedReceiveReceipt`: `accepted`, `unchanged` and `rejected` as is; `refused` becomes `rejected` (nothing was forwarded). A rejection carries Git's own bounded reason from its ` ! [rejected]` status line: no URL or path, and "behind the remote" phrased as "Pull, then push again". The UI therefore shows "The selected Git push was rejected: <reason>" instead of a generic rejection; `stale` becomes the new push outcome `stale`, with the typed message "The remote branch changed since it was last fetched. Pull, then push again". A lease that closed, lost its transport or was refused by the guard before forwarding is a denial; anything else is `unconfirmed`. Git's exit status never decides.
- **Selected-mode push routing (U7 and U14 applied to push).** The push URL is classified like a fetch URL:
  - HTTP(S), file or local path: ordinary local `git push` under `GIT_ALLOW_PROTOCOL=http:https:file`.
  - SSH to a host that is not a target: fenced local Git (U14 fence).
  - SSH to a bigbud target, or when the target set is unknown: the owner receive path.
  - Anything else: refused.

  Legacy push semantics are kept for the ordinary routes (`-u` when there is no upstream). On the owner route, a branch with no upstream is a first publish (above).

- **scp-style remotes (user-approved 26 November 2026).** `[user@]host:/abs/path` and `ssh://` hosts are resolved through `~/.ssh/config` with the same bounded, no-spawn resolver as targets (`resolveProfileHostAuth`). The resolved HostName, User and Port are used for:
  - **target matching** (fetch and push routing), which keeps the U14 rule that an unstated user or port cannot disprove a match;
  - **owner serving** (upload and receive), which requires exact equality with the descriptor. An unstated user defaults to the local account, as OpenSSH does, and an unstated port to 22.

  A config the resolver cannot evaluate fails closed (U17): routing goes to the owner path, and serving refuses. A relative or `~` scp path is refused, because the owner admits only absolute paths.

- **Evidence.** See the ledger section "U15 production owner Git receive".

### U22 entry: user-authentication key algorithms (26 November 2026)

- **Built.** A single constant, `config::PUBKEY_ACCEPTED_ALGORITHMS` (`config/fixed_policy.rs`), holds the list in OpenSSH 10's default order: `ssh-ed25519`, ECDSA P-256/384/521, `sk-ssh-ed25519@openssh.com`, `sk-ecdsa-sha2-nistp256@openssh.com`, `rsa-sha2-512`, `rsa-sha2-256`. Every launch passes it through `AUTH_METHOD_OPTIONS` (`transport.rs`).
- **User config.** A user `PubkeyAcceptedAlgorithms` is admitted when it lists only algorithms from that set. A `+`/`-`/`^` modifier, SHA-1 `ssh-rsa`, `ssh-dss` or a certificate form is refused.
- **Unchanged.** Private-key file checks.
- **Not changed (checked):**
  - Windows `windows_transport/inbox.rs` still passes `PubkeyAcceptedKeyTypes=ssh-ed25519`; it cannot be built or tested on this host.
  - Host-key verification is still ed25519-only: `transport/host_key.rs` parses only the ed25519 blob, the trust store (`trust_store/extended.rs`) admits only `ssh-ed25519` records, `config/host_verification.rs` has only `ssh-ed25519` and its certificate, and keyscan, pin snapshot and approval fingerprints assume it. A server without an ed25519 host key (rare since OpenSSH 6.5) is refused. Widening this to OpenSSH defaults minus SHA-1/DSA is a trust-store change: multi-type key parsing, fingerprints, keyscan types, record matching and approval UI. It is left as its own item.

### U23 entry: host-key algorithms (26 November 2026)

- **Types.** The owner pins `ssh-ed25519`, `ecdsa-sha2-nistp256/384/521` and `ssh-rsa` host keys. RSA is verified only with `rsa-sha2-512`/`rsa-sha2-256` signatures. DSA, security-key types and unknown types are never pinned.
  - Each key is validated exactly against its RFC 4253/5656 wire format (`transport/host_key/wire.rs`).
  - RSA moduli must be 1024 to 16384 bits, OpenSSH's `RequiredRSASize` floor.
  - Fingerprints are OpenSSH's `SHA256:` form for every type.
- **First use.** `ssh-keyscan -t ed25519,ecdsa,rsa` collects every offered key, at most one per type. The challenge is the most preferred one: ed25519, then ECDSA P-256/384/521, then RSA. The approval dialog already shows the key type beside the fingerprint (`SidebarUnlockSshKeyDialog`).
- **Pinned.** A pin holds at most one key per type (`trust_store/pin.rs`). The most preferred offered key of a pinned type must be pinned. A different key of that type, or only unpinned types, is `HostKeyChanged`. Approval re-checks that the approved key is still offered.
- **`known_hosts` records.**
  - Existing ed25519 records read unchanged, with no migration.
  - A user `known_hosts` line for another accepted type joins the pin.
  - A second line of the same type with a different key is `HostKeyChanged`.
  - DSA, security-key and unknown types are skipped, as OpenSSH skips them; before, they refused the host.
  - Certificate authorities stay ed25519 only; certificate handling was not extended.
- **Launch.** `HostKeyAlgorithms` lists exactly the pinned types, ed25519 first, with RSA only as `rsa-sha2-512,rsa-sha2-256`. The snapshot holds every pinned record.
- **Limits.** The simple store allows one record up to 4 KiB (a 16384-bit RSA key) and 64 KiB in total; it was 256 bytes and 4 KiB.
- **Config.** A user `HostKeyAlgorithms` drawn only from the accepted list selects key pinning. A modifier, SHA-1 `ssh-rsa`, DSA or another certificate is refused.
- **Unchanged and ed25519-only by design.** Peer coordinator keys (peer enrollment), the jump-route host-key observer and the Windows transport's host keys (`HostKeyAlgorithms=ssh-ed25519`).
- **U22 on Windows.** `windows_transport/inbox.rs` now passes the shared list (`ssh_algorithms.rs` macros) without the security-key forms, which the Windows 8.1 inbox client does not know.

Rejected: per-request pairing operands (A; RPC would supply the pin) and making the worker a registry target (C; ordinary trust would stand in for a peer grant).

### U17 design entry: SSH config tolerance (26 November 2026)

- **Principle.** The owner launches `ssh -F /dev/null` and passes every option explicitly. Among the forced values are `IdentitiesOnly=yes`, `AddKeysToAgent=no`, `ClearAllForwardings=yes` (except its own fixed forward), `ProxyCommand=none` and `ProxyJump=none`. A user directive therefore matters only if the owner translates it. Directives the owner never translates and that cannot change the destination, identity or trust are accepted and ignored instead of refusing the alias:
  - `UseKeychain`, `AddKeysToAgent`, `IdentitiesOnly`;
  - `TCPKeepAlive`, `Compression`, `LogLevel`, `VisualHostKey`, `EscapeChar`, `IPQoS`, `ConnectionAttempts`, `FingerprintHash`, `NumberOfPasswordPrompts`;
  - user `LocalForward`, `RemoteForward` and `DynamicForward`.

  The implementation is the owner's `config::is_inert`, mirrored by the TS directive table.

- **`IgnoreUnknown`.** The first active value applies, and it covers only keywords OpenSSH does not know. A shared OpenSSH 9.x keyword list (Rust `config/ignore_unknown.rs`, TS `sshConfigOpenSshKeywords.ts`) decides that. A listed keyword that OpenSSH knows is applied by OpenSSH, so it is still evaluated or refused.
- **`Match`.** Criteria evaluated: `all`, `host`, `originalhost`, `user` and `localuser`, with `!`, in order, against the route so far. Any other criterion (`exec`, `canonical`, `final`, ...) refuses the host only while every earlier criterion matched. An earlier false criterion proves the block cannot apply, so it is skipped. The Rust owner already did this; the TS resolver now does the same per host, instead of refusing every `Match` globally.
- **Unknown keywords (TS).** They are decided per host: only a host whose active blocks contain one is refused. Previously any unknown keyword anywhere refused the whole config.
- **Includes outside `~/.ssh` (TS production resolution only).** A `~/` Include resolves against the account home. The file must be regular (after resolving links), owned by the account or root, writable by no other account, within 256 KiB, and in a directory chain no other account can modify (a root-owned sticky directory is allowed). World-readable is fine: a config is not a secret. The isolated profile resolver keeps its owner-private rule. This machine's `~/.orbstack/ssh/config` (0644 in a 0700 directory) qualifies.
- **Still refused.**
  - `LocalCommand`.
  - A `Match` that could apply but cannot be evaluated.
  - A keyword OpenSSH knows but bigbud doesn't translate (for example `Ciphers`) in an active block.
  - An Include another account could write, or beyond the depth or file bounds.
  - The owner's existing route rules: `ProxyCommand` other than `nc %h %p`, `ProxyJump` outside the qualified jump policy.
- **Fail closed.** A config either resolver cannot evaluate is refused: no "host as written" fallback for remote routing (owner path) or serving (refusal). This replaces the earlier residual.
- **Owner scope ("like the old path", decided 26 November 2026).** The production owner (`RouteFacts::production`) now applies OpenSSH's own safety checks instead of the fixture's private scope (`config/source.policy.rs`):
  - A user config at `<home>/.ssh/config` is rooted at the real home, so `~/` resolves to the home. A symlinked home is followed, and its canonical mapping is bound and rechecked.
  - Relative operands start at `~/.ssh`, as OpenSSH resolves user Includes.
  - Every config, Include and directory on the way must be owned by the account or root and writable by neither group nor others. The home's ancestors must pass the same rule or be root-owned sticky directories.
  - Known-hosts files follow the same rule. Private keys must be owned by the account and readable by no one else.
  - An unset `UserKnownHostsFile` defaults to `~/.ssh/known_hosts`, as in OpenSSH; it must exist and pass the rule.
  - The system config (`/etc/ssh/ssh_config`, root-owned) gets the same rule. The fixture's owner-only rule could never open it.
  - Includes outside `~/.ssh` but inside the home pass when they meet these checks (for example `~/.orbstack/ssh/config`).
- **Default identities ("like the old path", decided 26 November 2026).** When a host sets no `IdentityFile`, both resolvers (owner `config/identities.rs`, TS `sshOwnerProductionTargets.identities.ts`) use OpenSSH's default keys in the order of the OpenSSH in use. That is 10.5p1 on this Mac (`ssh_config(5)`): `~/.ssh/id_rsa`, `id_ecdsa`, `id_ecdsa_sk`, `id_ed25519`, `id_ed25519_sk`, `id_mldsa44_ed25519`.
  - This replaces the order first proposed (ecdsa first, with xmss and dsa); OpenSSH 10 no longer has DSA or XMSS and lists RSA first.
  - Only keys that exist and pass the private-key rule are used (a regular file, not a link, owned by the account, readable by no one else, 1 byte to 64 KiB), as OpenSSH skips an unprotected key.
  - No usable key is still refused. Only the home-rooted production scope defaults; the fixture never does.
  - The owner admits only ed25519 (`PubkeyAcceptedAlgorithms=ssh-ed25519`), so another default key is passed but cannot authenticate.
- **Still refused by the owner.** Paths outside the home (or outside the system config's directory), symlinks below the root, and every routing or trust rule above. The fixture scope is unchanged.
- **Discovery.** Production discovery (`aliases.rs`, now split into `aliases.entries.rs`) uses the same scope and replays `IgnoreUnknown` like admission.
- **Target set.** An alias target's HostName, User and Port come from the config-only resolver, so a credential problem cannot hide its HostName. If that config cannot be evaluated, the target set is unknown and SSH remotes fail closed to the owner path. Before this, a different alias to the same host could route to the U14 fence.
- **Evidence.** See the ledger section "U17 SSH config tolerance and U15 push follow-ups".

### T-shell decisions: provider bridge tools and ACP string ids (accepted 26 November 2026)

- **Bridge `bash` envelope (decision A).** On the owner path, exactly `remoteCommand: "sh"`, `remoteArgs: ["-lc", <text>]`, with no further argv and no stdin, is the bash tool's command text. It runs as `runProviderWorkspaceShell` with that text. The fixed-tool first-word check does not apply to it. Plain command text, extra argv and stdin stay refused. The bridges keep sending this envelope because it is also what the legacy transport runs.
- **Typed bridge file tools (decision C).** The generated MCP and Pi bridges send read, write, edit (read then write), list, grep and `apply_patch` as a typed `remoteTool` on `remote_workspace_process`. Under production activation the server runs them on the owner's typed workspace verbs (`toolTransport.ssh.owner.production.ts`) for the authorized target and root. Paths must lie inside the root. Writes create missing parents. `apply_patch` is parsed and applied in memory and written per file, all-or-nothing. On the legacy path the server runs the fixed scripts the bridges used to send. Owner grep is fixed-string and case-insensitive, so a regex pattern is a typed refusal that points to `rg` through bash; a target without `rg` answers `proofRipgrepUnavailable`. `glob` stays a bash-envelope command.
- **ACP string JSON-RPC ids (decision 2a).** `effect-acp`'s stdio transport maps a non-decimal agent request id to a synthetic decimal id above 2^53 and restores the exact original string id in the response. Decimal ids are unchanged.
- **Decided as U21 (option 2, built).** Real ACP agents (Devin) issue general terminal commands (`ls -la`, internal helpers). The production ACP terminal is the fixed `pwd` recipe (C11), so those are refused as `unsupported-command`. Options: (1) keep `pwd`-only, so agents fall back to their own reasoning; (2) admit ACP `terminal/create` commands as a separate, per-command-approved, non-interactive ACP shell grant with the provider-shell bounds; (3) route ACP terminal commands into the existing `runProviderWorkspaceShell` grant. Recommended: (2), which keeps the ACP authority distinct from G2. A typed `glob` bridge tool (owner workspace index plus server-side matching) now replaces the `sh -lc` glob envelope.

### U25 design entry: remote-agent control parity through the production owner (26 November 2026)

**Decision.** Option A: full legacy parity. The legacy install manager and the sixteen control modules keep their transaction logic. Every remote script they used to send as text is one kind of an owner-compiled verb family (`v1.agent_control.proto`). Wire (as built): Request 140 `agent_control_open`, 141 `agent_control_status`, 142 `agent_control_cancel` with Reply 81 `AgentControlState`. Request 143 `agent_proxy_lease_open`, 144 `agent_proxy_lease_status`, 145 `agent_proxy_lease_close` with Reply 82 (the relay lease state message, reused). There is no new error code; refusals use `invalid_operands`, `operation_denied`, `session_quota` and `outcome_unknown`. Request 146–169, Reply 83–95 and ErrorCode 63–70 stay reserved for this track.

**One source for every script (as built).** The owner templates are generated from the legacy builders, not ported by hand. `remoteAgentControl.templates.ts` compiles each legacy builder with sentinel operands. It then replaces each sentinel by a variable that a generated header binds from one positional argument (`"${N}"`), and writes `owner_agent_control/templates/*.sh` (41 files, the largest 312 lines). The owner embeds those files with `include_str!`. Run `bun run --cwd apps/server agent-control:templates` to regenerate them; a vitest and `agent-control:templates:check` fail when a file is stale. Generation fails if a sentinel is left behind, or appears outside a quoted word for an operand that is not a safe single word. Only two transforms exist, both for streamed bytes. The install upload reads raw bytes (`cat > "$staged"`) instead of the legacy base64 stdin. The registry CAS reads its expected bytes (`head -c`) and its next bytes (`cat`) from the lease socket instead of base64 embedded in the script, and checks each one's size and SHA-256 (exit 65).

**Lease model (reuses T-backend).** `agent_control_open` carries a caller-chosen 32-byte lease token, an `AgentControlKind` (28 kinds; `SUPERVISOR_OBSERVE` takes one of 8 modes) and typed operands only. A kind admits exactly its own operands. Each operand is validated in Rust with the legacy TypeScript rules (runtime descriptor, attempt, epoch, reservation and fence ids, version, digest, sizes). The command is `exec sh -lc <template> bigbud-agent-control <operands>`, the legacy login shell. It runs over the target's pinned SSH base through the shared deployment step worker and `lease_worker`, in the target's lanes: exact target and generation, at most 4 running leases, and the last 64 outcomes kept for reattach. Deadlines and output caps are the legacy ones: 30 s and 2 MiB by default, 10 min for removal, 8 s for the platform probe, 60 s for install and inbox, and 15 s for read-only status. Re-opening or reading a known token returns the kept outcome and never runs it again. A dispatched lease without a confirmed result settles `OUTCOME_UNKNOWN`, and the TypeScript side reports it as a timed-out command that is not replayed. Two kinds stream bytes over a per-lease 0700/0600 socket instead of a frame. `INSTALL_UPLOAD` carries the artifact; this replaces the 48 KiB `agentAction` frame and is the chunked staging lane. `REGISTRY_CAS` carries the expected and next registry, each at most 1 MiB. The remote template checks size and SHA-256 before it publishes anything. **Correction to the draft:** the owner does not read the streamed bytes itself; the socket is the child's stdin, as in T-backend.

**Root and paths.** No operand names the control root: every template header computes `bigbud_arg_root=$(readlink -f -- "$HOME")/.bigbud/agent`, the same value the legacy `CONTROL_ROOT` script returns. A managed runtime must match the layout under that root: the binary at `root/bin/<version>/<sha256>/bigbud-remote-agent`, and the state at `root/runtimes/<generation>` holding `supervisor.sock` and `supervisor.log`. A `legacy-external` runtime must have its state at `root/state`. Anything else exits 86 before the legacy body runs. A legacy-external or configured binary path must be absolute, normalized and free of control characters, and its bytes are hash-checked before use, as before.

**TypeScript seam (as built).** `runRemoteAgentControlOp(control, op)` takes a `RemoteAgentControlOp`. A legacy control has no `exec`, so the op is compiled by the existing builders into the byte-identical script and passed to `run`, with the same deadline. A production control has `exec`, which sends the typed lease, and its `run` refuses script text. Inline scripts moved verbatim into named builders (`remoteAgentControl.scripts.ts`, `remoteAgentUpdate.prepare.scripts.ts`). The install-side steps are the platform probe, read-only status, upload, placed probe, inbox adoption and identity or binary check. They go through `makeOwnerRemoteAgentInstallDependencies`, which plugs into the unchanged `makeRemoteAgentInstallManager`. Signature and byte verification stay in TypeScript exactly as before. Under `SSH_OWNER_PRODUCTION_ACTIVATION` (`remoteAgentControl.selection.ts`) these call sites go through the owner: `openRemoteAgentControl`, the install manager defaults, `probeRemoteAgentPlatform`, `readRemoteAgentRegistryReadOnly` (D1/D4/D5 evidence) and the server layer's identity probe. There is no fallback. Classifying script strings was rejected as unsound. `mobileOptionalPublication.authority.ts` runs on the remote backend host itself, not over SSH, so it needs no kind.

**Kind map.** `CONTROL_ROOT`, `REGISTRY_READ`, `REGISTRY_CAS` (absent and present variants), `STAGE_FENCE_REVOKE`, `INVENTORY`, `SUPERVISOR_OBSERVE` (retirement state and exit, launch exit, raw, candidate startup and exit, replacement readiness and death), `ADMISSION_DEATH_OBSERVE`, `STATE_ABSENT`, `SUPERVISOR_SHUTDOWN`, `SUPERVISOR_RESTART`, `ISOLATED_LAUNCH` and `REPLACEMENT_LAUNCH` (managed only), `RETIREMENT_DELETE` (managed only), `REMOVAL`, `REMOVAL_RESUME`, `REMOVAL_OUTCOME`, `HOST_CLOCK`, `ORPHAN_DELETE`, `BACKEND_RUNTIME_PROBE`, `SOCKET_LIVE`, `SOCKET_GONE`, `RUNTIME_PROBE` (default `bin/current` or external), `PLATFORM_PROBE`, `READ_ONLY_STATUS`, `INSTALL_UPLOAD` and `INBOX_ADOPT` (reserved and unreserved), `PLACED_PROBE` and `IDENTITY_CHECK` (managed, default or configured binary). Builders called only from retired paths get no kind: the `activation.ts` takeover helpers, `remoteAgentInstall.transaction.ts` and `manualInstall`.

**Proxy binding (as built).** `RemoteAgentProxyOwner` already took the registry runtime. `makeProductionRemoteAgentProxyOwner` opens one `agent_proxy_lease` for that exact runtime. The owner runs its existing installed-agent recipe, which checks the private directories and the SHA-256 of the opened descriptor before `--proxy` (exit 126 otherwise), and streams the bytes over a per-lease socket through the relay worker. Under activation the managed composition's pool `create` uses it, binding through `remoteAgentAdmission.resolveBinding`, which reads the registry through the owner. The custom-binary observation path uses it as well. `observeOwnedInstalledSupervisor` is the production observation: the pinned hello, identity and epoch through one proxy lease. `composeInstalledRemoteAgentStartup` now accepts it as `observe`. **Decided (a), 26 November 2026, and built:** the trusted startup binding is the local owner store's bound runtime and expected epoch per target (`remoteAgentOwners().getBinding`), never a registry snapshot.
