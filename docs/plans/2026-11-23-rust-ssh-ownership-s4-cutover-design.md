## Principles carried from the plan

1. One composition change activates every consumer in every profile. There is no per-target or per-consumer selector, no hot fallback, and no period where both owners run.
2. Build A (legacy TS only, B-compatible schema ceiling) ships first and is the rollback floor. Build B activates the owner and removes the legacy launch paths in the same artifact.
3. If retiring a launcher cannot be proved, block activation. Never kill unrelated user `ssh`, and never blindly delete sockets.
4. Durable disconnects, known hosts and remote durable jobs are preserved. Rollback is never made to succeed by removing, replaying or widening them.

**Disposition key.** **Delete**: the legacy builder, executor, credential cache or teardown authority is removed in B. **Convert**: the caller stays, but it calls a typed owner operation and receives a handle or result, never argv, env or an executable. **Keep**: typed adapter, product authorization, presentation, or something outside managed SSH.

Owner operation names follow the plan's private protocol catalog (`protocol/ssh-owner/v1*.proto`). Where the exact RPC name isn't frozen, the name below is descriptive and is marked as an open question (Q1).

## (b) Per-profile disable and fence list

The backend state lock is `<stateDir>/backend.lock` ([stateDirLock.ts](/Users/youpele/DevWorld/bigbud/apps/server/src/startup/stateDirLock.ts), acquired in [server.ts:266](/Users/youpele/DevWorld/bigbud/apps/server/src/server.ts) before the port binds and persistence opens). Every in-process launcher in §a (rows 1–51) runs inside the lock holder, so **holding the lock excludes them** (X1). These outlive it:

- **X2 detached terminal host.** [localTerminalHost.launch.ts:106–127](/Users/youpele/DevWorld/bigbud/apps/server/src/terminal-host/localTerminalHost.launch.ts) spawns with `detached: true` and `unref()`. It can hold direct SSH PTYs that A launched through row 24's fallback.
- **X3 masters, askpass and relays.** A password master started by row 6 persists for `ControlPersist=600`. Client and peer relay children (rows 47–48) and provider children (rows 40–43) can be reparented after a crash.
- **Standalone and offline entries.** The `bigbud` CLI ([apps/server/scripts/cli.ts](/Users/youpele/DevWorld/bigbud/apps/server/scripts/cli.ts), package `bin`) and the relay entries ([clientRelay.entry.ts](/Users/youpele/DevWorld/bigbud/apps/server/src/remote-backend/clientRelay.entry.ts), [peerRelay.entry.ts](/Users/youpele/DevWorld/bigbud/apps/server/src/remote-backend/peerRelay.entry.ts)) are inbound bridges, not initiators. Any CLI subcommand that delegates to a running backend is covered by the lock. One that opens the DB directly must take the same lock (Q5).

## (c) Upgrade and drain sequence

**Build A (legacy TS only).** It ships first with:

1. B's schema ceiling: every migration B needs, with the native-owner tables inert ([plan: durable disconnect schema](/Users/youpele/DevWorld/bigbud/docs/plans/2026-11-22-rust-ssh-ownership-plan.md#durable-disconnect-schema-transaction-and-rollback)), so A can reopen a DB that B used.
2. A **drain-on-quit** path. On a supported upgrade (installer, updater or CLI `stop --for-upgrade`), A stops SSH admission, then closes in this order: monitors (rows 15–16), relays (47–48) with half-close, provider children (40–43), and managed SSH PTYs with a user-visible notice. Drained panes are marked closed with no auto-respawn. Then A runs `ssh -O exit` for masters it started (row 8). It writes a **retirement record** (A artifact ID, drained lease set, pending items) in the same SQLite transaction that sets an `sshLegacyRetired` marker, checkpoints WAL, and releases the lock.
3. Recognition of an X2 host that B left behind (rollback case; see §d).

**Build B (activation).** Startup order under the lock:

1. Acquire `backend.lock` (X1 holds).
2. Before persistence writers start, read the retirement marker. If it is missing, A was not drained (crash or unsupported path): enter **refusal**, with SSH admission closed and the UI showing the interrupted-session notice. Offer the user an explicit "drain identified panes" action, which goes through step 3. Never infer retirement from an idle interval or a missing socket.
3. Quiesce the X2 host: get its inventory and identity. Drain and close legacy SSH panes only with user approval. Require SSH-spawn retirement to be acknowledged, or the host to exit. Non-SSH panes may continue.
4. Start or attach the owner under the exclusive owner fence, verify artifact identity, and negotiate protocol v1. A missing or incompatible owner means SSH is unavailable.
5. Hydrate durable disconnects, known hosts and pane bindings into the owner. Only then open admission.
6. After admission, any attempt through a retired entry returns `legacyEntryFenced`, with zero SSH launched.

**Live relay, terminal and monitor rehearsal** (the plan's S4 bullet 2): start A with an active client relay, a direct SSH terminal producing output and a running monitor. Run the supported upgrade. Verify that:

- The relay viewer sees a typed close, not a hang.
- The pane shows a drain notice, is marked closed, and is not respawned under B.
- The monitor stops sampling before the lock is released.
- No SQLite write carries A's writer identity after the retirement marker (compare the WAL frame sequence or a committed-state digest as in [rollback/README.md](/Users/youpele/DevWorld/bigbud/protocol/ssh-owner/release-evidence/rollback/README.md)).
- Relaunching A's desktop, CLI and terminal-host entries after B admission yields zero managed SSH.

**Refusal paths** (each a typed error, no SSH): missing retirement marker; X2 inventory unavailable; owner missing, unverified or incompatible; schema newer than B; a live A lock holder; Windows password without qualification; an R peer follower whose pin doesn't match.

## (d) Rollback

1. **Stop and drain B.** Close admission, drain owner-held SSH PTYs (user notice, marked closed), close relays and providers, and have the owner close its masters. Owner and X2 host exit or acknowledge retirement. Write a B retirement record in the same DB. Release the lock.
2. **Verify no native ownership remains.** Check the owner fence file or pipe is released, no process of the verified owner image exists in the domain, and no live lease rows remain. This uses process lineage, not a `ps` name match. Validate with the existing [offline rollback checker](/Users/youpele/DevWorld/bigbud/protocol/ssh-owner/release-evidence/rollback/README.md) (exact A/B pair, schema digest, frozen B process inventory, same DB instance).
3. **Restore A offline** with the same DB/WAL. A treats owner tables as inert and does not delete, replay or widen durable disconnects. Panes bound to B leases appear closed in A.
4. **Never hot-fall back.** B contains no TS executor to fall back to, because rows 1–50 are deleted. Owner crash in B is recovered only by restarting or reattaching the Rust owner under the fence.
5. **Re-upgrade A→B** runs §c again, using A's retirement marker.

The static check catches structure. Indirect launches (Git or `gh` → ssh, OpenSSH config helpers) are caught only by the existing `cutover/` trace checker, so both are required for S4.
