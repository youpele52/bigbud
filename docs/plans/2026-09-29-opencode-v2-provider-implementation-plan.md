## 2. Goal, Settled Decisions, and Definition of Done

### Agreed goal

Add an independent OpenCode v2 provider using an external OpenCode server and the `@opencode/client` Promise client. Keep existing OpenCode and KiloCode behavior unchanged.

| Permanent ID | Initial display name  | Future display name | Runtime                                 |
| ------------ | --------------------- | ------------------- | --------------------------------------- |
| `opencode`   | OpenCode              | OpenCode Legacy     | Existing V1 integration                 |
| `opencodeV2` | OpenCode v2 (Preview) | OpenCode            | Separate V2 integration                 |
| `kilocode`   | KiloCode              | KiloCode            | Existing Kilo/V1-compatible integration |

The user wants both providers available side by side until V2 is stable, then intends to remove V1. This intent does not authorize removal now or define stability criteria. The future rename is display-only. Timing, default-offering changes, and legacy retirement require separate release decisions, including historical access and continued Kilo/V1 SDK needs.

### Invariants

1. Persisted provider IDs, native-session bindings, resume cursors, model preferences, usage identity, and historical events are never reinterpreted through a different provider.
2. A V2 failure never silently retries through V1, and a V1 failure never silently retries through V2.
3. Retain `@opencode-ai/sdk` while V1 or Kilo uses it. Do not substitute its `/v2` export for the released OpenCode 2 client.
4. Use an external process, not embedded `@opencode/sdk`. Keep V2 protocol types out of the V1/Kilo adapter.
5. Reuse provider-neutral orchestration, persistence, supervision, and UI infrastructure. Do not fork an entire V1 adapter or introduce a second turn-liveness policy.
6. Missing, incompatible, disabled, or unavailable V2 must not prevent bigbud startup or alter another provider’s readiness or selection.
7. Do not change `DEFAULT_PROVIDER_KIND`, currently `codex`, or rewrite saved selections.

Existing provider-neutral fallback for separate unattended text-generation workloads is not session migration. Preserve its requested/actual-provider reporting; do not introduce a V1/V2 session fallback disguised as background-work routing.

### Observable acceptance criteria

- **AC1 — Identity:** V1, V2, and Kilo settings and session bindings round-trip independently through persistence, restart, replay, and settings import/export. Display-label changes do not change routing.
- **AC2 — Coexistence:** V1 and V2 run simultaneously using verified compatible executable/configuration/storage arrangements. V2 setup does not overwrite or migrate V1/Kilo resources.
- **AC3 — Ownership/security:** Each owned V2 process has authenticated, loopback-only access, one Promise client, one live event subscription, bounded resources, generation fencing, and deterministic cleanup.
- **AC4 — Turn correctness:** Successful generation, provider failure, interruption, uncertain admission, and event loss produce correctly correlated canonical output. Request/native admission correlation is durable before dispatch and survives retry/restart; identical new submissions remain distinct. Full authoritative final text replaces partial canonical text before terminal settlement, without append duplication. Terminal observations settle once; no retry is permitted to risk duplicate execution on unproven admission state, and no exactly-once upstream guarantee is claimed beyond Phase 0 evidence.
- **AC5 — Recovery:** Reconnect repairs authoritative message/interaction state. Confirmed owned-process loss is reported as interrupted and invalidates pending requests; no transparent restoration of active execution or approvals/forms is promised. Unknown execution/admission status remains visibly unconfirmed rather than becoming fabricated success or failure. No automatic resend follows uncertainty; a new user submission requires duplicate-work risk guidance.
- **AC6 — Isolation:** Thread-owned MCP tools cannot be discovered or invoked by another session. Synthetic remote workspaces cannot access local workspace tools through fallback paths.
- **AC7 — Integration:** Settings, model/variant selection, usage, attachments, UI requests, and declared workloads work for V2 or explicitly report unsupported behavior before unsafe dispatch. Every required adapter member is covered; adapter capabilities and server snapshot metadata agree on verified execution strengths, with explicit unsupported rewind/fork and no implied native steering or process-loss recovery.
- **AC8 — Release evidence:** Local macOS/Windows/Linux, SSH provider runtime, and local-runtime/remote-workspace operation pass conformance, including learning reviews and other declared workloads. At least 25 simultaneously generating V2 sessions pass correctness and approved resource/latency budgets, with separate V1/Kilo coexistence and saturation tests. Rust offload is assessed from profiling, not presumed necessary. Rollback preserves history and IDs.

A side-by-side preview satisfying these criteria is the implementation milestone. Future relabeling or V1 retirement is not required to complete that milestone.

## 3. Background and Evidence Boundaries

### Repository facts inspected for this rewrite

- `apps/server/package.json` depends on `@opencode-ai/sdk@^1.17.13`; the root Effect catalog uses `4.0.0-beta.43`.
- `Layers/Kilocode/Adapter.ts` imports V1 OpenCode session/event machinery and the same `OpencodeServerManager` service. Changing those protocol modules risks both providers.
- The existing manager keys processes by provider, execution target, and executable. Its child launcher parses V1 readiness output and does not implement the reported V2 authentication/stdin-lease contract.
- Existing adapter methods conform to `provider/Services/ProviderAdapter.ts`; this includes session lifecycle, turn control, active-turn inspection, requests, snapshots, rollback, and a canonical event stream.
- `ProviderTurnSupervisor.ts` owns turn-health policy. It uses a 90-second silence threshold, 10-second inspection timeout, bounded inspection concurrency, and backoff. Unconfirmed or missing state does not automatically become a successful or failed terminal turn.
- `ProviderService.turnLiveness.ts` and the liveness repository coordinate terminal claims. Recovered output must not be bypassed by a premature terminal claim.
- `OptionalProviderRegistrations` supports additive providers, but its current concrete composition is supplied by `Layers/CliProxy/Composition.ts`. Two competing layers providing that service would not concatenate registrations automatically.
- `PersistedModelSelection` accepts open-ended provider strings; live `ModelSelection` is a discriminated union. Persisted session inventory and routability are deliberately distinct.
- Provider descriptors drive pickers and settings. `ProvidersSettingsSection.logic.ts` enumerates descriptors independently of server registration, so an unregistered provider is not necessarily hidden.
- The shared picker already displays five models initially and appends 20. Preserve that behavior rather than introduce V2-specific pagination.
- `managedServerProviderDiscovery.ts` imports V1 SDK types. Managed catalog helpers narrow their provider type to V1/Kilo and the fallback loader assumes their cache paths.
- `Adapter.session.query.ts` currently deletes the V1 native session during stop. This is evidence of current behavior, not approval to copy deletion into V2.
- Admission identity is currently lost at the caller boundary: `packages/contracts/src/orchestration/provider.ts:69–80` has no request/message/command ID; `ProviderCommandReactorHandlers.ts:151,275–291` resolves the persisted user message but passes only its content; `ProviderCommandReactorSessionOps.send.ts:169–177` sends no identity. `provider/Layers/ProviderService.ts:186–196` dispatches before `ProviderService.sendTurn.record.ts` records acceptance. Existing turn liveness cannot close a crash between native admission and that write.
- Stable source identity already exists: `orchestration/deciderThreads.turn.start.ts:107–153` emits the user message and turn-start intent with the same message ID; `OrchestrationEngine.commandProcessing.ts:152–182` persists events and projections transactionally. `ProjectionPipeline.projector.threadTurns.ts:31–38,52–65` persists the pending message ID and later links it to the accepted turn. `QueuedPromptFlush.logic.ts:47–60` derives the combined message ID from queued IDs, not prompt text. The replaceable pending projection and in-memory handled-command cache are not an admission journal.
- Learning reviews have a second admission boundary: `provider/Layers/ProviderService.backgroundReview.ts:26–33,124–128` creates process-local/random review thread IDs and calls `adapter.sendTurn` directly without message identity, bypassing `ProviderService.sendTurn`. `learning/LearningReview.ts:206–215` already supplies the durable `jobId` and `ownerThreadId`; `provider/Services/ProviderService.ts:75–84` carries them. V2 learning therefore needs stable job-backed identity, persisted session ownership, and shared admission handling, not only foreground caller plumbing.
- Final-text repair requires a canonical seam change: `ProviderRuntimeIngestion.processor.runtime.assistant.ts:118–145` accepts authoritative final detail only for listed existing providers. `ProviderRuntimeIngestion.processor.helpers.ts:57–105` supplies replacement text to `thread.message.assistant.complete` only when `authoritativeText` is provided. V2 adapter reconciliation alone would leave already-streamed partial text unrepaired.
- Capability omissions are unsafe defaults: `ProviderServiceSessionRouting.ts:89–142` rejects explicit unsupported recovery but otherwise may restart from a cursor; `CheckpointReactorRevert.ts:123–138` allows omitted rewind metadata through. `providerSnapshot.ts:172–214` currently derives native steering by provider/version, sets inspection unavailable and continuation true, and advertises app-level steering universally; its `supportsSteer` input does not override that behavior.

## 5. Scope and Compatibility Boundaries

### In scope

- Independent V2 contracts/settings, provider service, server manager, Promise-client boundary, event hub, and adapter.
- Authoritative recovery, interaction handling, MCP isolation, resource cleanup, and declared local/remote modes.
- Additive UI/catalog/workload integration; persistence and V1/Kilo regression coverage.
- Learning reviews with durable job-backed identity, isolated background-session ownership, and safe retry/restart behavior.
- Opt-in preview preparation, security/load evidence, rollback, and future display-only rename tests.
- Profiling and a documented Rust-core offload assessment for the 25-active-V2-session target; assessment only, not Rust implementation.

### Out of scope

- Replacing the V1 SDK or migrating Kilo to V2.
- Converting V1 native history/resume cursors into V2 sessions.
- Embedded OpenCode runtime adoption, upstream protocol fixes, or global default-provider changes.
- A downloader/bundled V2 executable under the approved user-installed provisioning policy.
- Rust lifecycle/offload implementation, a new provider watchdog, or a broad provider-framework rewrite. Any profiling-backed Rust proposal requires separate scope approval before code changes.
- Legacy retirement or removal of persisted-ID decoding.
- Native rewind, fork, or in-flight steering. Verifying an upstream API does not itself expand scope; implementing these requires separate explicit scope approval and exact adapter-semantic parity evidence.

Preserve existing V1/Kilo behavior, provider-neutral workload fallback, execution-target semantics, and current UI pagination. Shared refactors must be behavior-preserving and justified by actual reuse.

### V2 lifecycle and retention policy

This table implements approved D3/D7 intent; Phase 0 must attach exact native operations and Phase 3 must test races and finite cleanup. It does not grant new native recovery capabilities.

| Action                 | Approved boundary                                                                                                                                                                                                                                                                       |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Interrupt              | Cancel the verified current admission, retain native history and request correlation, and settle only on supported evidence. Do not delete the session or replay the prompt to implement cancellation.                                                                                  |
| Stop                   | Release owned transport/session handles and bridge leases with bounded cleanup. Retain native history, unresolved admissions, and anti-replay evidence; a live shared process remains leased by other owners.                                                                           |
| Archive                | Preserve native history and admission evidence. Any runtime release follows stop semantics; archival is not native deletion.                                                                                                                                                            |
| Application shutdown   | Close owned streams/processes/forwards/leases with finite deadlines, without native-history deletion. Persist uncertainty before losing runtime ownership; later startup does not automatically replay unfinished work.                                                                 |
| Explicit chat deletion | Remove only owned native history when active/uncertain work and shared resources are safely resolved. Defer or reject unsafe native deletion explicitly; never cascade-delete unresolved admissions or the evidence preventing replay. Include owned learning jobs in the safety check. |
| Reconnect/reinitialize | Repair the same retained native binding only with Phase 0 evidence. Keeping history does not prove a dead process's execution/forms/approvals can resume.                                                                                                                               |
| Confirmed process loss | Report interrupted execution and invalidate stale requests under D3; preserve output/history and unresolved admission evidence. Unknown execution/admission remains unconfirmed; user-initiated new work is not a same-request automatic retry.                                         |

Document journal/result retention and tombstone bounds before Phase 3 acceptance. Cleanup must remain bounded without making an old retried request executable again; no unapproved TTL may turn uncertainty or terminal deduplication into a new admission.
