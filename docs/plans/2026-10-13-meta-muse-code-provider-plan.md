## 2. Goal and definition of done

### Agreed outcome

Add **Muse Code**, Meta's coding-agent harness, as a first-class bigbud provider. This is not a standalone Meta inference client, a model alias for OpenCode, a browser scraper, or a Meta AI consumer-chat integration.

User decisions, explicitly confirmed during research:

1. Integrate **Muse Code provider**, rather than Muse models through another harness or a direct Meta API provider.
2. Reuse **Muse Code browser sign-in**. Do not request or copy credentials into bigbud.
3. Ship **local-workspace functionality first**: chat/coding, native tool activity, approvals, cancellation, and restart recovery. Remote workspaces, advanced Muse workflows, and background learning are deferred.
4. **Fail closed** on unproven or unavailable access-mode mappings. Never weaken permissions silently or automatically pass `--yolo`.
5. Research and update this plan only. The 2026-10-29 authorization permits this Markdown revision and focused document validation, not product implementation, dependency installation, native qualification, code tests, repository-wide checks, commit or push.
6. **User decisions 2026-10-29 (supersede earlier defaults where they conflict):** (a) sign-in is performed by the user in the terminal via native `muse` (Muse TUI/device login); bigbud never performs programmatic sign-in. (b) Contributor (training) catalog models, including a contributor catalog default, are acceptable **with explicit disclosure** before project content is sent; they must never be selected silently or presented as non-training. (c) Minimum shippable result is an approval-gated coding mode (writes + shell under native approval); read-only-only or unrestricted-only stays disabled. (d) First enablement requires macOS, Windows **and** Linux all qualified; until all three pass, Muse stays disabled/unavailable on every target. (e) Implement all phases (Phase 0 qualification in parallel with Phases 1–6 behind the default-disabled flag), rather than gating Phase 1 on Phase 0 exit; runtime enablement still requires the Phase 0/6 gates.
7. **Enablement amendment 2026-10-29 (supersedes decision 6(d)):** enablement is now **macOS-first** — macOS is the only platform with live qualification (see the validation record) and may become ready when the user enables Muse in settings. Windows and Linux remain **unqualified and report unavailable per platform** (fail-closed per platform, not blanket enablement everywhere and no longer a blanket block on macOS). Windows/Linux qualification remains outstanding work with the kit in `docs/validation/muse-windows-linux-qualification-kit.md`. Muse stays default-disabled; the auth lane must still be native `accountLogin`; only the qualified `auto-accept-edits` mode mapping is supported.
8. **Enablement amendment 2 — 2026-10-29 (supersedes amendment 7's per-platform block):** the user decided Muse must be supported on **macOS, Windows and Linux** regardless of live qualification status. All three platform flags are on; Muse stays default-disabled (user opt-in). Safety moved from a per-platform block to per-machine runtime checks: a host reporting `sandboxAvailability: "unavailable"` is refused with a reason-specific remedy (bubblewrap / user namespaces / `muse sandbox windows setup`), because the only supported access mode promises sandboxed workspace edits. Windows launch and workspace-root handling were adapted from upstream t3code's shipped driver (PATHEXT resolution, `.cmd`/`.bat` under ComSpec with escaping, verbatim `\\?\` canonical roots, plain host cwd). Windows/Linux live qualification is still owed as verification, no longer as an enablement gate.

### Acceptance criteria

- **AC1 — Setup:** An explicit opt-in Muse Code settings card discovers a user-installed, qualified `muse` binary, reports its version/auth state, and links to official setup. Disabled or missing installations never delay other providers. Existing native browser login works; an API-key override is not silently used instead.
- **AC2 — Selection:** Users choose a real catalog model and supported reasoning effort. Stale/missing models, unknown effort metadata and an empty catalog are truthful states, not fabricated ready models. Existing thread selections are preserved.
- **AC3 — Interactive work:** Two successive turns and two concurrent local threads preserve their own native session/model identities, stream text and tool activity correctly, and produce exactly one truthful canonical terminal outcome per turn. Stop also settles an accepted queued submission: authoritative reclaim yields interrupted; failed launch yields failed even without a start event. Neither path hangs, cancels another turn, nor automatically resubmits input, including after restart.
- **AC4 — Safety:** At least one useful coding access mode is demonstrated equivalent to its bigbud promise. Unsupported modes are disabled with reasons and rejected server-side before tool execution. Approvals, staged commands, questions, cancellation and workspace trust retain native enforcement; no approval is upgraded to a persistent grant.
- **AC5 — Continuity:** Restart resumes only the exact owned native session. Missing/invalid cursors, a foreign writer lease, transport loss, truncated history, and an uncertain send never create a replacement session or execute a fresh-ID duplicate prompt automatically. Automatic fork fallback and automated sleep continuation are fenced off for this milestone; explicit Stop cannot be undone by background recovery. Terminal outcomes recover across native-journal, shared-liveness and canonical-delivery crash windows without reopening settled work.
- **AC6 — bigbud integration:** Canonical thread tools work through bigbud's existing authenticated MCP bridge, including after resume. Local project/worktree identity, thread deletion fencing and canonical event ownership remain intact.
- **AC7 — Honest limitations:** Remote targets, unverified attachment delivery, plan mode, rewind/fork, steering, advanced workflow controls and unattended workloads are not advertised as supported. Unsupported submissions fail before side effects.
- **AC8 — Regression and delivery:** Existing providers and historical state remain compatible; targeted tests and required repository checks pass. Live qualification records the exact CLI/SDK, operating system, runtime, auth lane and safety configuration for every release target enabled.

Full implementation is **not ready to proceed past Phase 0** until the blocking evidence gates below are closed. A mocked adapter alone does not satisfy AC4 or AC5.

### Verified published capabilities, not live-tested claims

- Official Muse Code overview links `@muse-code/sdk` and `muse schema`. On 2026-10-29 the official SDK redirect still selected the **1.4** documentation, and npm's latest metadata returned **`@muse-code/sdk` 1.4.14**, Node `>=20`, repository `meta-models/muse-code-sdk` (`clients/sdk-ts`), described as having zero runtime dependencies. The original 2026-10-13 lookup returned 1.4.7. Treat 1.4.6 (the pairing upstream t3code ships [S21]) as the qualification baseline and 1.4.14 as an upgrade candidate, neither as a tested dependency pin; recheck the released CLI/SDK pair at Phase 0. No package was installed. [S3, S6, S17]
- The 1.4 landing page inspected on **2026-10-13** identified source commit `d8c53d25bd30cda15ab32b18b9bb9961df9c4be0` and fingerprint `sha256:0d803007acbd02ad07a6cec4d5a63b834f4db743886bbaf865b8738116dc212f`. **These are historical documentation-provenance values, not current 1.4.14 or installed-CLI fingerprints.** Record actual package provenance and handshake evidence in Phase 0. [S6]
- `spawnMspConnection` owns a `muse serve` child. Initialize before traffic, then install notification and server-request handlers before session creation/resume. The connection has one notification handler; replacing it drops the previous handler. Acknowledgements mean admission, not completion. [S7]
- `model/list` works without creating a session. Rows carry native provider/model identities, defaults, optional limits/costs and effort metadata; catalog presence does not prove billing entitlement. `session/setModel` is confirmed by native state/event, not the ack. [S10]
- `session/start`, `session/resume`, `turn/start`, `session/read`, `view/page`, `approval/decide` and `userInput/*` are published methods. Cancellation is **two distinct published methods, not a name conflict** (desk-cleared 2026-10-29): `turn/cancel` cancels on the normal command lane with no retract (pairing retract with it is durably rejected `not_paired_interrupt`), and the official cancel cookbook maps the user Stop gesture to it, with `turn/completed` terminal `"cancelled"` — not the ack — as the outcome, and `already_terminal` as the only benign rejection; `turn/interrupt` stops the running turn on the priority lane, is described as the “user pressed stop” gesture, and optionally pairs a durable `retract` intent. bigbud's candidate mapping is exact-ID `turn/cancel` (bigbud Stop does not restore/retract input; see §5); `turn/interrupt` may be substituted only on live Phase 0 evidence that the priority lane is required, and then only with `retract: false` explicitly. Installed-CLI acceptance and terminal behavior for the chosen method remain Phase 0 live confirmation, not an open naming question. `account/read`, account login methods and `permissionProfile/list`/selection have experimental surfaces. Negotiate deliberately; do not treat all installed builds as equivalent. [S8, S14, S22]
- **SDK facade limitation:** `StartSessionOptions` explicitly excludes `config` pending facade MCP grant support. The wire `session/start` and `session/resume` do admit `config.mcpServers`; `sessionMcp` is a negotiated capability. Therefore use the official **low-level connection plus SDK fold**, not a cast around `MuseClient.startSession`, if supplying bigbud MCP. [S13]
- MSP command IDs are UUIDv7, with durable deduplication for session/turn admissions. A reused ID with changed payload is a conflict. Turn start IDs derive from command IDs. Cancel/interrupt dedupe is host-lifetime-only: always name the exact turn to avoid affecting new work after restart. [S9]
- Queued submissions already have a turn ID. Exact-ID `turn/unqueue` reclaims queued input; authoritative `turn/unqueued` carries the original submission's command ID, not the unqueue command ID. Reclaim emits neither `turn/started` nor `turn/completed`; launch failure can emit failed `turn/completed` without `turn/started`. These no-run exits must settle independently of running-turn lifecycle. Queued state is durable and appears in `queuedTurns`; absence from that list alone is not reclaim evidence. [S9, S20]
- Full items replace older revisions; deltas append transiently and are not replayed by paging. Completed items are authoritative. Recovery handles inline/snapshot/suffix/none history explicitly; unknown modes are not empty history. Opaque cursors must not be parsed. [S11–S12]
- Permission profiles and approval modes are separate from sandboxing. CLI `untrusted` still allows in-workspace file writes; it is **not** proof of bigbud's “approve all file changes” mode. Auto-review may involve a native reviewer. Staged approvals have requirement identities and server-issued choices/scopes. [S5, S15]
- Native browser login is stored by Muse. `META_API_KEY`, then a stored API key, override browser login. Meta Managed Accounts cannot use browser sign-in. Subscription credentials are Muse-Code-only; additional API keys are pay-as-you-go. **Subscriptions default to Contributor mode**, under which content can train future Meta models. The 2026-10-29 subscription documentation distinguishes headless defaults: without a settings file contribution defaults off, while an existing file without a saved preference can enable it; settings are computer-specific and overrides/organization policy can affect the effective state. Verify the effective lane and privacy configuration during qualification rather than inferring them from login or headless execution. Preserve native settings but disclose the training implications before sending project content; do not imply login means non-training mode or free/unlimited inference. [S4, S18]
- Meta documents macOS, Linux and Windows CLI support. Linux sandbox helper availability and Windows first-use UAC differ. Published platform support is not bigbud packaged-runtime validation. [S3, S5]
- Documentation has a caveat: the concepts guide calls the protocol pre-1.0 and says no changelog, while the compatibility page now links a generated changelog and describes additive evolution with pre-1.0 exceptions. Prefer the specific current compatibility guidance: unknown fingerprint alone warns, unknown fields are tolerated, required missing/incompatible methods fail clearly. Do not promise unconditional backward compatibility. [S8, S16]

### Upstream t3code Muse implementation — adapt, do not copy [S21]

Upstream `pingdotgg/t3code` has already shipped this provider as `packages/provider-muse` (inspected 2026-10-29 at upstream `fe219c4d`, `@muse-code/sdk 1.4.6`). It is existence proof for the basic MSP surface, not a transplant source: upstream uses provider packages plus OrchestrationV2, while bigbud registers providers in server `Layers` behind `ProviderAdapterShape` and the canonical `ProviderService` flow. Per `AGENTS.md`, read, understand and adapt; never copy a file that violates the 400-line dot-notation rule (upstream `adapter.ts` is ~2,377 lines, its test ~1,768 lines).

Proven upstream patterns to adapt into bigbud-shaped modules:

- **Host lifecycle (`sdk.ts`).** `spawnMspConnection` behind a small host seam; 20s handshake deadline; close the child even when initialize never replies; abort settles startup; protocol-envelope version check; fingerprint mismatch warns only; bounded stderr tail. Adapt into `Muse/Client.lifecycle.ts`, not a copied `sdk.ts`.
- **Windows launch.** `.cmd`/`.bat` resolution through `cmd.exe`, verbatim workspace-root paths, and `MUSE_NO_AUTO_UPDATE=1`. bigbud has no equivalent today; add it in the client seam and qualify per platform in Phase 0.
- **Predetermined session identity.** The adapter mints the native session ID with `mintCommandId()` before `session/start`, then rejects a mismatched returned ID. This complements, and does not replace, the durable `MuseSessionBindings` table in Phase 3: upstream persists identity in its OrchestrationV2 provider-thread record, while bigbud startup rollback can delete the runtime-directory row.
- **Read-only discovery host.** A separate short-lived read-only host calls `model/list` without creating a session and rejects a non-`meta` catalog `providerId`. Adapt into `Muse/Provider.discovery.ts` on the existing `makeManagedServerProvider` seam.
- **Protocol schemas (`protocol.ts`).** Item, approval (including `currentRequirementId` and staged choices), user-input, usage, retry and compact result schemas are a proven fixture starting point. Re-express them as bigbud Effect schemas in `Muse/Client.schema.ts`; keep native types out of canonical contracts, as Phase 4 already requires.
- **Session MCP grant check.** Initialize requests `sessionMcp`; a session that needs MCP fails when the grant is absent. Keep bigbud's required stdio bridge semantics (Phase 3.4); upstream's `streamableHttp` in `optional` mode is a different product choice and is not adopted.
- **Confirmed model switch.** `session/setModel` is applied only when the target differs, and session state is updated from the native result. This matches AC2 and Phase 3.7.

Upstream choices explicitly **not** adopted (see also §5):

- Hardcoded permission mapping (`full-access` → `:unrestricted`/`allowAll`/`--disable-sandbox`/`--trust-workspace`; approval-required → `:ask-me`/`promptUnmatched`). A mapping is not equivalence evidence; the Phase 0 fail-closed matrix remains the gate.
- Silent stripping of an inherited `META_API_KEY`. bigbud detects the override lane and rejects it with remediation (Phase 2.3); it does not unset or store keys.
- Fabricated fallback efforts when native variants are `unknown` (upstream invents `low`–`max`, default `high`). AC2 forbids fabricated effort metadata.
- `ready` from a non-empty catalog despite no native auth signal (upstream comments that MSP has no auth signal). bigbud keeps auth `unknown` distinct from authenticated (§4, Phase 2.5).
- Provider-package layout, multi-instance registry, custom models, launcher self-update checks, and the 2,377-line adapter shape.

Upstream has no equivalent of bigbud's durable turn-admission journal, `MuseSessionBindings`, queued `turn/unqueue` reclaim, or liveness-to-canonical delivery reconciliation. Those Phase 3 designs are retained unchanged; upstream is not evidence they are unnecessary.

## 5. Scope

### In scope

- Internal provider key **`muse`**, display name **Muse Code**, optional composition, default disabled.
- User-installed CLI, existing native home/account, explicit enable and install/login guidance; background detection never signs in.
- Local repository/worktree sessions, authoritative native model/effort selection, streamed text/reasoning/tool items, staged approval and question handling, exact-turn cancellation, durable exact-session recovery.
- Existing canonical thread-tool MCP bridge with per-session configuration and ownership/token cleanup; ordinary native coding tools remain Muse-owned.
- Additive settings/contracts, canonical event mapping, persistent identity/admission records, desktop/web UI and mobile selection compatibility, tests and redacted qualification report.

### Explicitly out of scope

- Remote provider execution or local runtime against a remote workspace, a new Rust transport, a separate inference/agent loop, importing arbitrary native sessions or attaching to the user's running TUI session.
- Programmatic sign-in/logout/payment/subscription management; reading native credential files; rewriting native global permissions, workspace trust, Contributor mode, plugins or model defaults.
- First-release fork (including automatic fork fallback), rewind, native steering, automated sleep continuation, autonomous goals/workflow control, subagent-control UI, native computer use, voice/video/image-generation support, learning jobs and unattended git-text generation.
- Attachment upload/delivery for the initial milestone. Explicitly reject attachments rather than pretending Meta model multimodality proves harness delivery. Adding text/image delivery requires a follow-up qualification/plan update.
- Native session-file deletion. bigbud thread deletion removes its own resources and fences activity, but retains native history; disclose this retention boundary.
- Separate unsend/queue-management UI or automatic composer restoration. The existing Stop gesture must safely handle the adapter's accepted queued submission; it does not add native steering or another submission flow.
- Upstream-proven features that remain out of this milestone unless the user explicitly reopens scope with new evidence: native steering (`turn/steer`), native queued turns beyond the Stop/reclaim path, native subagent projection and controls, image attachments, `session/compact` as a user action, unattended text generation (including upstream's read-only `--disable-shell --disable-write` host), native usage/subscription accounting, custom (non-catalog) models, multi-instance provider registration, and launcher self-update checks. Upstream shipping them [S21] proves feasibility only; it does not amend AC1–AC8 or the settled decisions in §11.

### Unchanged behavior

Do not change global default provider/model/access settings, existing provider ordering rules, canonical thread/turn identities, WebSocket transport, other providers' auth/capabilities, historical OpenCode read-only behavior, or unrelated worktree edits. No blanket provider refactor, new validation framework, or package-manager change.

- **Pre-1.0/experimental drift:** pin SDK, document CLI range and handshake/capability evidence; warn on fingerprints but block required incompatibilities. Account/profile experimental APIs must not silently disappear behind an apparently ready snapshot.
- **Durability gaps:** existing runtime cursor updates happen around start/send and do not make every streamed cursor a durable checkpoint. Start with authoritative snapshot reconstruction and stable publication identities, not cursor-only resume. Runtime-directory rollback must not erase native session-creation ownership; use the separate binding table. Native refusals require proven failed settlement, not false accepted states. Outer dispatch/recovery records and retained explicit-Stop state must stay correlated without authorizing replay. A native terminal row or shared liveness terminal claim is not a durable canonical-delivery receipt; Phase 3.15 must recover the missing-delivery window without weakening deduplication.
- **Resource pressure:** per-thread processes trade memory for clear ownership. Spawn on use, bound startup/probe concurrency and buffers, release idle/closed children only when no pending work, and test multiple threads. Never pool hosts across safety/workspace boundaries merely to reduce memory.
- **MCP and trust:** session-local config is a supported wire surface but not yet in the SDK facade. Request the actual capability, require startup success, use existing per-thread authentication and deny cross-thread actions. Never serialize bridge secrets into resume cursors or browser data.
- **Moving worktree:** OpenCode v2/tool bridge/UI edits are active. Rebase the plan's exact seams against accepted changes; do not copy obsolete registrations or revert concurrent fixes.
- **Rollout:** new provider default off; first expose honest setup status, then permit turns only after all required native checks pass. No automatic CLI update/install and no global defaults changed. Diagnostics include stage, version, schema warning, native error kind, request/turn identity and recovery disposition, with redaction.
- **Rollback:** disable Muse routing and stop only owned processes/bridges; retain canonical history, native history, exact cursors and admission identities. Keep serialized provider kind/schema compatibility so old Muse threads remain readable. Never downgrade by reinterpreting a Muse thread as another provider. SDK/CLI rollback must respect native session compatibility; do not downgrade native storage in place.
