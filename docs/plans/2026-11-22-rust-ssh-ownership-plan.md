# One Rust owner for SSH

- **Date:** 22 November 2026
- **Status:** S0 closed for contracts and local baselines by explicit approval. Release qualification and final Linux/Windows build tests are deferred, not passed. Continue S1–S4 implementation on isolated profiles without waiting for release runners; production activation and transfer M0 remain gated. The dev-only testing exception is not a release selector or phase acceptance.
- **Owner:** Local runtime / SSH, with terminal, provider, remote-backend and release owners at cutover.
- **Inspected baseline:** `dev` at `9102a63611`. Recheck actual call sites, packaging and owner overlaps before implementation.

## Summary

Rust is the sole owner and executor of **bigbud-managed SSH**. It manages the system OpenSSH client; this is not a new SSH protocol implementation. TypeScript conveys authorized user intent, displays native status and trust prompts, and retains non-SSH product authority. It cannot prepare SSH argv or environment, cache a target password, launch a master, select another SSH runtime, or independently reconnect or disconnect. If the owner is unavailable, SSH is unavailable. Local-only work continues.

Prove trust → authenticate → perform a real read → reconnect → explicit disconnect through Rust **before** migrating the rest. Build and exercise all consumer adapters off the production path, then activate all together and remove the legacy execution path. There is no per-target rollout, hot fallback or period with competing owners. The downstream transfer plan starts only after **S4 accepted**; its own data-plane and publication proofs remain to be done.

## Problem

Today a shared TS argument builder is not a shared process owner. Connection guards, trust checks, password masters, provider children, PTYs, relay pipes and health probes have different lifetimes and spawn paths. Giving transfers another way to start SSH would make a disconnected host reachable through a second path. A migration that only changes `sshCommand.ts` cannot close that gap.

## Goals

- One fenced Rust authority per local backend/profile ownership domain; all clients of the same domain share it. Bind target identity to the existing execution target (including auth mode, user, port and transport), never just hostname. Preserve intentional isolation between profiles.
- Preserve currently supported key/password, alias/config, workspace, PTY, provider, forwarding, agent and disconnect behavior. Keep qualified versus unqualified Windows password support explicit.
- Preserve data paths and latency: control requests are separate from bounded byte streams. A future transfer worker can consume an admitted stream directly, without either a JS chunk relay or permission to open SSH itself.

## Non-Goals

- No change to application authorization, file picker grants, public provider protocols, remote agent ownership of running remote jobs, or the contents of user SSH config and keys. No replacement SSH library.
- No transfer engine, rsync bundle, recursive transfer, or drag UI in this prerequisite. No managed-SSH policy imposed on a human typing `ssh` in a local terminal or unrelated software using SSH. Commands deliberately launched by bigbud on behalf of managed SSH operations **are** in scope, including indirectly launched children.

#### Private owner protocol v1: who can do what

`Exec`, `Pty` and `Stream` are internal Rust response/transport shapes, **not** wire requests. Use a closed, versioned request union. The trusted backend authorization dispatcher binds an already-approved product action to a dedicated adapter session and an opaque owner-issued grant (profile, adapter class, target, generation, resource, allowed verb, expiry and, for a one-shot launch, normalized operand digest). Derive class and rights from the authenticated channel/grant record, never a caller-supplied role or activity label. Only the dispatcher can request grants, and only within its profile and existing product permissions; the renderer, providers and remote agent never get the issuer channel. In-process adapters are not a sandbox against a compromised backend. A distinct native client must authenticate separately and receive only a delegated lease.

### S1 — Build the owner and prove one complete path in isolation

1. Add one authenticated, local-only control channel: inherited private handles for bootstrap; where attachment is required use a per-profile protected Unix socket or owner-only Windows named pipe with peer identity verification. #### Effective OpenSSH configuration: v1 compatibility contract

Evaluate only local configuration first, without invoking OpenSSH on unchecked input (`ssh -G` can itself evaluate `Match exec`). The **same immutable descriptor** supplies destination, port, user, host-key name, route/hop identities, known-hosts sources and auth policy for inspection and live use. Launch with an explicit owner-generated private `-F` configuration for every SSH child, including hops; do not reread ambient configuration or inherit shell/askpass overrides. Use native OpenSSH defaults for absent values except the owner overrides below. Apply this table to active user/system settings, **not** the expanded list of OpenSSH built-in defaults. Pinned peers use their isolated descriptor and ignore ordinary user configuration entirely.

### S2 — Port trust, credentials, transport lifecycle and platform gates

#### Durable disconnect: schema, transaction and rollback

**Keep one source of truth.** Membership in `remote_execution_target_disconnects(target_id TEXT PRIMARY KEY, disconnected_at INTEGER NOT NULL)` alone means disconnected. Do not change its layout, clear it, or backfill a duplicate boolean. The current [store](../../apps/server/src/persistence/Layers/RemoteExecutionTargetDisconnects.ts) creates it lazily and uses unconditional writes. The [downgrade guard](../../apps/server/src/persistence/Migrations.downgradeGuard.ts) refuses a database above a binary's latest known migration ID even if every change is additive. Do not bypass that guard.

1. **Prepare the rollback build A before activating build B.** Ship A with the existing TS executor only and a numbered additive migration in `apps/server/src/persistence/Migrations/`, imported and registered in `Migrations.ts` at the next free ID. In one migration create the existing disconnect table if absent (identical DDL for fresh installs), plus the two metadata tables below. Leave legacy rows and timestamps byte-for-byte unchanged. A's old writer ignores metadata. B uses the same migration and schema ceiling as A; no B-only migration, trigger on legacy writes, or destructive down-migration. Record the exact A/B artifact pair, schema ceiling and DB ownership domain per profile. A predating the migration is **not** the rollback build.
2. **Metadata in that same database.** `ssh_owner_writer(singleton INTEGER PRIMARY KEY CHECK(singleton=1), writer_epoch TEXT NOT NULL)`; `ssh_target_transition(target_id TEXT PRIMARY KEY, seq INTEGER NOT NULL CHECK(seq>0), last_request_id TEXT NOT NULL, last_digest TEXT NOT NULL)`. No foreign key to the disconnect row: Connect removes that row, not the sequence. Absent target metadata means sequence zero, including for already-disconnected legacy rows. The random writer epoch identifies an owner plus a storage binding; rotating it does not change live PTY identity. The singleton covers the whole existing disconnect store: profiles sharing a DB must share its fenced writer, not compete for independent epochs.
3. **Takeover and hydration.** With admission closed, take exclusive ownership of the domain and retire all A launchers/writers (S4). On B startup or authorized storage rebind, rotate the writer token with a compare-and-swap on the expected previous token in a SQLite write transaction (`BEGIN IMMEDIATE` or equivalent); install the first token only when absent. Read the authoritative disconnect set and sequences under that transaction before admitting after commit. Installation is a separate privileged operation available only to the current lock holder, never an automatic response to a stale mutation. An old callback cannot acquire a fresh epoch. Loss of the lock or DB binding closes admission.
4. **Transition.** Send `(writerEpoch, targetId, expectedSeq, requestId, desiredState)`; digest the canonical version/target/expected sequence/desired state. Under one immediate write transaction, check epoch first. An identical last ID/digest is a receipt for its already-committed sequence, not another write; same ID with different digest is a conflict. Otherwise require `seq == expectedSeq` (missing = 0); reject stale requests without side effects. On Disconnect insert the flag only if absent, preserving its first timestamp; on Connect delete it. Upsert `seq=expectedSeq+1`, ID and digest even for an already-satisfied state; commit before replying. A delayed request older than the retained receipt is stale, not replayable. Never retry a stale ID with a newly read sequence. Publishing status, teardown and target generation changes are fenced to this committed transition; a duplicate receipt must not run them twice. TS may execute this transaction as a private storage adapter; B has no other writer API.
5. **Offline rollback and re-upgrade.** Drain B, revoke its storage binding, close its DB handles, and verify retirement of every B launcher/owner under the release fence before starting A. Keep the live DB, including WAL-committed writes; do not restore a pre-upgrade snapshot or edit migration history. A reads and can change the original flags normally. Re-upgrading rotates to a fresh epoch and hydrates **current flag membership**, not the last B request; old-epoch receipts cannot hide changes made by A. If artifact/schema compatibility or exclusive retirement cannot be verified, refuse the switch and leave the database intact.

**Required executable fixture:** create a DB with the pre-migration build, disconnect X and leave Y connected; start the actual A build and then B on the same disposable DB. Assert X's original timestamp and zero background connections to X after each start. In B, clear X, disconnect Y, lose the commit reply, then inject a stale writer after rotation; assert rows, sequences and exactly-once effects. Stop B offline and boot A with its downgrade guard enabled: X is connected, Y is disconnected. Change both in A; start B again, verify X stays disconnected and Y stays connected, and reject delayed pre-rollback requests. Also cover a fresh DB and a deliberately too-old rollback binary (startup refused, no DB edits). A mock store or a raw SQL read from an old schema is not rollback proof.

- Rust serializes target transitions, blocks admission while a durable write is pending, and acknowledges only durable success. On confirmed failure retain the prior durable state. On timeout or lost acknowledgement do not treat a read of the old value as proof that a write cannot still commit: wait for the transaction to settle or transactionally supersede its writer epoch before rehydrating and admitting. If the storage/control adapter is unavailable, fail closed for new admission.
- A committed Disconnect revokes the target generation, closes only its owned local transports, and emits one authoritative state. A later Connect starts a new generation only after durable clear. Fence late prompts, callbacks and cleanup from the old generation; keep TS domain teardown hooks bounded, idempotent and scoped to the acknowledged generation. Test delayed old-epoch Connect after a newer Disconnect, delayed old-epoch Disconnect after a newer Connect, crash after commit before reply, and backend/owner restart. In each case assert the actual SQLite state, post-restart admission and zero stale transport teardown. S4 must quiesce pre-fence legacy writers and verify the existing rows remain readable by the supported offline rollback build.

**Recovery.** One Rust reconnect controller per target: bounded exponential backoff with jitter and cancellation, coalesce concurrent opens, no background unlock dialogs. Separate unavailable/paused, deliberate disconnect, transient loss, auth-required, changed host key, and ambiguous operation outcome. Backend clients reattach using a fresh authorized session and owner epoch. Owner restart wipes passwords, reconciles live handles/owned children before new admission, and never infers a remote job died because a local SSH process vanished. If exclusive ownership cannot be proved, report unavailable. No TS timer, monitor or fallback may reopen a disconnected target.

**Windows and POSIX authentication (absorbs transfer-plan U2, U4–U8 and former W2):**

- POSIX password unlock may establish one Rust-owned ControlMaster using a private short socket path; subsequent admitted callers reuse it. Apply the same effective trust policy as for direct opens; never retain a POSIX password after unlock. Rust owns creation, invalidation and closing of all product masters, including keys, regardless of consumer.
- On qualified Windows builds, use native askpass for each direct `ssh.exe`, no ControlMaster. Hold only a verified password in zeroizable Rust memory keyed by target; do not cache if authentication succeeded without requesting the password. Wipe on explicit Disconnect, owner exit or 10 minutes without **user** activity. Terminal input/open, browse/read, turn, transfer start and explicit connect/unlock count; polling, cleanup and askpass do not. On expiry, pause probes and inspection with existing leases intact; next user operation may prompt; unlock resumes polling. Use fake time and real monitor/relay sessions.
- Register and acknowledge a random single-use target/role grant before spawn; bind the direct SSH PID, retained handle, resolved image and creation time. Handle a helper arriving early with a bounded wait (≤2 s and never past grant expiry); reject late/foreign requests without consuming the real grant. Native helper verifies the pipe server PID; owner verifies client image/identity, immediate SSH parent, role, target and generation. Use an owner-only DACL, random per-session pipe, first-instance semantics and rejection of remote clients. Revoke on exit/cancel/restart. No passwords in argv, env, logs, journal, telemetry or progress. UI submission is transient; neither TS nor Electron may cache or return secrets. Document the same-user-malware limitation; this prevents accidental retrieval, not deliberate same-user compromise.
- Distinct trust and password roles: respond only to the exact approved key challenge or eligible password prompt, never crossed roles or OTP/passcodes. Bind password release to a qualified destination authentication flow, not to a guess from prompt text. `ssh -G` is advisory; key-only jump hops may work where proven, but refuse inner-hop password prompts at runtime without consuming the destination grant. Expire unused grants at 20 s; bound a stuck helper request separately and never kill a valid silent SSH child merely because no prompt occurred. No output heuristics for authentication.
- **Password verification and parity gate.** For caching, require both a single credential release to the verified destination process and positive evidence of acceptance. Qualify a dedicated owner-run unlock probe: a fresh, strictly host-verified connection with no master/agent reuse, password as the sole eligible destination authentication method after OpenSSH's initial `none` request, no method fallback, and successful completion of a fixed authenticated probe on that same child. A consumed grant, generic command exit, connection state alone, or diagnostic/prompt text is not evidence. Until both probe conditions hold, retain only the pending zeroizable secret; wipe it on failure, cancellation, timeout or generation change. A successful no-prompt command remains usable without populating the cache. Test wrong password, no-prompt success, rejected password with another method available, partial authentication, lost transport after release, and stale-generation success.
- Inventory password and keyboard-interactive separately in S0. The existing keyboard-interactive allowance does not make an arbitrary challenge eligible for a cached password: do not qualify it unless the supported client can prove the challenge type and acceptance without prompt heuristics, including tests that OTP/MFA challenges receive no password. Missing evidence means the combination stays unqualified. If a shipped combination is already supported, an unqualified result blocks S4 unless an explicit compatibility decision changes that requirement; it is not a silent removal.
- Gate Windows password support on real Win10 22H2/inbox 8.1p1 and Win11/inbox: prove `DISPLAY` + `SSH_ASKPASS` on 8.1p1, `SSH_ASKPASS_REQUIRE=force` where supported, ConPTY, silent no-prompt command, exact-key approval and changed-key rejection, no visible console, no leaking helper environment to unrelated children. Qualify native helper availability in dev and packaged deployments separately. An unqualified build returns `windowsPasswordUnsupported` **before credential collection** with “Use an SSH key for this host.” Qualified build missing helper: `askpassUnavailable`; expired secret: unlock required. Owner absent: `sshOwnerUnavailable`, not a credential prompt. Never substitute TS. Windows key auth is independently qualified; unqualified password is an explicit capability denial, not a partial owner migration.

**Exit:** native and integration tests prove the auth/lifecycle matrix; no previously supported combination is silently dropped. Publish redacted evidence by profile/OS/auth mode in the implementation handoff. The future transfer E2E rows are downstream, not a requirement for S2 or S4.

### S3 — Complete the adapters; stage one cutover, not two owners

Implement each S0 row against the private owner in the integration build. Delegate product SSH for bounded commands, PTY resize/EOF/cancel, agent proxy, forwarding and streaming to typed handles with target generation and lease identity. Return explicit signal/exit/partial-stream outcomes. Do not close a shared session when one consumer cancels. Priority and session budgets belong to the owner; reserve interactive capacity, block or refuse excess work, and keep `MaxSessions`/quota failures distinct from authentication.

**Direct SSH PTY ownership and reattachment (freeze before S3).** The Rust SSH owner hosts the local SSH PTY and its bounded screen/spool/replay, reusing existing Rust terminal-host machinery rather than introducing a second screen authority. The existing terminal host retains non-SSH PTYs; the remote agent retains its remote PTYs. The backend retains pane identity, user authorization, lifecycle preferences and the durable pane binding. Extend the existing durable ownership records rather than maintaining a second pane registry. Reserve before dispatch and bind an authorized pane to a specific owner epoch, target generation and opaque PTY lease. Reattach is lookup and replay from a cursor or bounded cold snapshot, not `openTerminal`; close/restart cannot release a possibly live reservation on transport loss alone. Restore the terminal-policy adapter to target that exact lease for idle expiry, Forget, thread deletion, default quit and Disconnect.

- **Backend loss without a quit signal:** the owner and eligible live PTYs outlive the backend; a staged owner starts independently of Electron and does not die with the backend process group or job. Detach clients, preserve bounded replay and apply native idle-close policy while detached; do not admit new SSH work until the authorized backend and durable-store binding are restored. Reattach the same pane and PTY without a second SSH spawn in the eligible survival cases; test key and qualified password paths and existing intentional fallback limitations.
- **App quit, restart, and update (user-approved compatibility decision):** when the backend receives an app quit signal, close Rust-owned direct SSH PTYs by exact lease even if “keep terminals running after quit” is enabled. Local terminals remain eligible for keep mode. Direct SSH terminals are explicitly excluded. Remote-agent terminals still follow the setting today; whether that exception stays is an open user decision. A stop without a quit signal still detaches. If close is unconfirmed, retain the reservation; do not infer that a remote job ended. Use remote `tmux` or `screen` for work that needs to survive an intentional app quit, restart, or update.
- **Owner crash:** report `sshOwnerUnavailable` during recovery. Without verified live ownership and replay state, mark the pane host-lost and retain the durable fence until termination or safe release is proved; never simulate survival by opening a new SSH connection. Confirmed local SSH exit does not prove that an execution-host shell or job died. No automatic remote replacement.
- **Upgrade:** a compatible native owner may continue serving existing panes when the new backend verifies its identity and negotiates the existing protocol. For an incompatible native owner, drain owned panes or block activation; do not run two owner epochs. The initial TS-to-Rust cutover cannot adopt legacy managed SSH PTYs into this binding: notify users of the interruption, let them close/save their work or explicitly approve draining the identified panes, and mark drained panes closed with no auto-respawn. If local ownership or exit cannot be established, block cutover rather than clearing the fence or starting replacements. A required upgrade-survival guarantee that conflicts with drain requires an explicit compatibility decision before S4.

Define the **downstream handoff** without building transfers: a private Rust client obtains a scoped operation/stream lease, authenticated target capability snapshot, cancellation and per-generation lifecycle events. Direct SSH pipes/data endpoints stay between native processes (protected FD/handle or private bounded native channel); no file bytes in TypeScript. For rsync's child-launched SSH, the future worker requests a bounded packaged-rsync operation: the owner checks target/auth mode, controls the exact `-e` executable, SSH arguments and environment, launches/supervises the local process tree and charges its session lease. The transfer worker supplies validated transfer operands and consumes progress/exit; neither the worker nor TS gets a generic SSH launch escape hatch. Validate the interface with a disposable native stream and child-process fixture before S4; actual rsync/throughput proof belongs to transfer M2/M3.

Prepare packaging inputs for all initiating profiles. Verify clean install and upgrade with actual signed/verified native artifacts and an incompatible/missing helper at Pre-cutover qualification. The approved dev-only exception below does not permit a shipped per-consumer runtime selector, dual-write credential state, or masters on a real target just for shadow comparison.

Update the [terminal lifecycle setting](/Users/youpele/DevWorld/bigbud/apps/web/src/components/settings/TerminalLifecycleSettings.tsx) to explain the direct SSH exclusion when the behavior is available. Do not label it “local only” while remote-agent terminals still honor it.

**Exit:** all consumer and deployment inventory rows map to adapters with parity evidence or existing intentional denials; no unclassified SSH path, no unbounded byte channel and no adopted orphan with unverified identity. Local adapter evidence does not satisfy deployment parity in the release lane.

### S4 — Atomic activation, failure behavior and dependency handoff

- One release/composition change cuts **all** product SSH consumers over, including standalone entry points. For each S0 profile, document which old launchers are excluded by the existing backend state lock, which outlive it (including detached terminal hosts), and how each is disabled before activation. Hold the backend fence where applicable, quiesce legacy persistence writers, and drain verified legacy masters, relays and SSH PTYs before Rust hydrates and opens admission. Verify exit or acknowledged retirement of SSH admission, not just a process snapshot or the absence of an old socket; a retained terminal host may serve non-SSH panes only if its managed SSH launch path is fenced out. Build A is the required rollback floor and ships first. Where launchers lack a shared lock, require an offline upgrade from A that retires their managed launch paths before B activation. If exclusion cannot be proved, block activation; never kill unrelated user SSH or blindly delete sockets. Preserve sticky flags, known hosts and remote durable jobs.
- Exercise upgrade with a live relay, terminal and monitor, plus an attempted restart through each legacy entry point in the supported upgrade path. Verify user-visible PTY drain, no pane respawn, no late SQLite mutation, and zero legacy managed spawns after activation. The guarantee is for shipped managed launch paths, not arbitrary manual execution of old binaries outside the supported upgrade procedure.
- Delete old launch builders/executors, TS askpass/master/credential caches, reconnect and teardown authority. Keep only typed client adapters, product auth checks and presentation. Enforce with a focused structural checker plus process traces: no direct or indirect managed `ssh`/`ssh.exe` launches outside owner-controlled process trees, including config/status probes, node-pty and command wrappers. Maintain negative fixtures that would catch bypasses. No change to global process-runner quoting defaults.
- On owner crash or incompatible version, stop SSH admission and report unavailable. Recover only by restarting/reattaching the **Rust** owner under the exclusive fence. Release rollback means stop/drain the whole new release, verify no native ownership remains, then restore a compatible previous release offline; never silently switch a running profile to TS. Do not remove, replay or widen durable disconnects to make rollback succeed.
- **S4 accepted** means the signed/package/profile matrix, lifecycle proof and zero-bypass consumer evidence are recorded against the build and reviewed together. Record owner protocol version, supported capabilities including Windows password, typed errors, session limits and tested artifact IDs for the transfer implementer. A missing required row blocks acceptance. Do not mark complete because the Rust crate compiles or because S1 passed.

## Risks And Decision Gates

A TS adapter that accepts an executable/env, or a Rust transfer worker that launches SSH independently, reintroduces the second owner. Reject both in API review. The highest-risk compatibility rows are persistent PTYs across backend restarts, standalone relay lifetimes, SSH config/known-hosts parity and Windows credential binding. Run their real-process fixtures before activation. No cutover that weakens host trust, provider approval, lease isolation or local/remote role checks. If parity cannot be preserved, stop and report the specific profile/caller, not a fallback implementation.

## Acceptance Criteria

1. One real Rust lifecycle proof passed before broad migration; isolated proof never shared a production target with the old implementation.
2. Every currently supported initiating runtime and managed caller has cut over together; no TS SSH policy, executor, standby, hidden monitor or alternate reconnect loop remains. Intentionally unsupported combinations return documented errors.
3. No stale owner or disconnect can resurrect or close a newer session. No ambiguous mutation is replayed. A missing owner leaves local features available and causes zero new SSH launches.
4. The transfer plan references **S4 accepted** and consumes only the native owner contract; the prerequisite can be accepted without implementing transfers, and a transfer test cannot pass in place of SSH ownership evidence.
