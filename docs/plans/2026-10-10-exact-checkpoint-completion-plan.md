### E1 — Schema3 row layout that can actually be adopted

**Choose uncompressed interleaved row payloads for the first dense proof.** A row is its own ordinary fixed ArrayBuffer of `cols*3*4` bytes, zero offset, [content,fg,bg] Uint32 words in **little-endian wire order**. At max width that is12,000 bytes, below existing48 KiB page ceiling. Separate metadata pages carry kind/row ordinal/buffer index/length/isWrapped, combined strings, graph refs and digests. Do not put headers into a row backing, pack rows together, or create a row spanning multiple buffers. Metadata pages remain <=48 KiB; rows are typed variable-length pages, so `ceil(total/PAGE_BYTES)` is no longer the page-count rule. Validate declared exact row/metadata inventories and total physical bytes instead.

Use a schema3 manifest `{schema,pairedBuild,fieldMapDigest,optionsDigest,sourceGeneration,cutOrdinal,metadataPageCount,rowDescriptors,totalBytes,sectionDigests}` with fixed typed fields, canonical field order/LE integers, no payload-selected constructor/method/path. Row descriptors reference unique row-page IDs and byte lengths exactly matching geometry; reject overlaps/duplicate backing IDs, unknown kinds, invalid endian/stride, count/index overflow, digest/cross-reference failure before adoption. Source rows may have oversize capacity after shrink: encode only logical cell words, but charge the source's **actual full backing** until released. Spare source capacity is allocator state, not visible continuation state; re-expansion initializes cells per pinned source.

Little-endian runtime: instantiate receiver `Uint32Array` over the entire validated row AB, with no content copy. Big-endian runtime: after full validation, byte-swap words **in receiver-exclusive buffer in place** before creating the view; preserve manifest wire digest separately. No swap is permitted on committed checkpoint/caller/source memory. Test endian path artificially on supported hosts; do not silently view LE bytes as native-endian elsewhere.

`BufferLine` gains an owned factory/adoption hook using trusted local prototype/constructors but **no allocating `new Uint32Array(cols*3)` then overwrite**. It accepts only branded internal row custody and creates metadata/maps under reservation. Existing resize/clone/copy/reflow/cleanup allocations acquire/transfer/release backing ownership through instrumentation. A row may shrink to a subarray offset0; accounting charges its full remaining AB. Never share mutable row backing between two live lines or terminals; preserve repeated source line-object references only if the audited source graph can legitimately contain them, with explicit IDs and no accidental alias expansion.

### E3 — Fit staging, then enforce restorable-state growth

Define restore staging `R = unique receiver row backings + receiver metadata pages + decoded non-row graph/strings + bounded validation/transport/commit scratch`; **never add the adopted row bytes again as decoded cells**. All source/old-target/committed snapshots remain charged in the512 MiB pool. Distinct committed checkpoint bytes are not removed from global accounting just because they are outside the receiver's R. Incoming transferred/copy row bytes remain **inside R** until adoption retags them to active state.

Dense forecast:66MB normal rows +~8.2MB metadata/state under comparable previous estimates is~74.2MB, with~60MB staging room before134.2MB. With populated alternate use72MB raw and remeasure metadata/graph overhead; no reliance on compressibility. Reserve exact manifest totals and conservative bounded graph/scratch **before** allocating. A valid schema can still refuse before effect when total exceeds limits; it cannot manufacture room by releasing old state/snapshot early.
