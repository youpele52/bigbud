## Summary

Let a user, or an agent acting for them, install or replace the bigbud remote agent without
depending on the in-app consent dialog succeeding. Three routes are planned, sharing one
server-side install transaction:

1. **Remote-side manual placement.** The user downloads the agent on the remote machine with a
   published script. bigbud then registers and activates those bytes without uploading anything.
2. **Local CLI.** `bigbud remote-agent install <target> [--replace]` runs the existing install
   transaction through the running backend.
3. **Agent tool.** The same operation is exposed as a bigbud capability so agents can request it.

A static Linux build and honest error reporting are included because they remove the most likely
reasons the automatic install fails today.

Subsequent phases harden persistent terminals, add a remote-owned TypeScript backend using
shared bigbud services, and then add remote orchestration. They do not block independent delivery
of the installation phases. No implementation or provider compatibility is implied by this roadmap.

## Problem

The automatic install often fails, and the user cannot tell why or work around it.

Observed facts:

- The published release is healthy. `remote-agent-install-source.json` for v0.3.3 downloads,
  parses and verifies its signature with the current shared artifact module. Both Linux binaries
  are present.
- The published x86_64 agent is dynamically linked and requires `GLIBC_2.34`. It cannot run on
  Ubuntu 20.04, Debian 11, RHEL/Rocky/Alma 8, Amazon Linux 2 or Alpine. The release job builds
  glibc targets on `ubuntu-22.04` (`.github/workflows/release.yml:144-147`).
- The install uploads the whole binary as base64 through one SSH command with a 60 second limit
  and truncated output (`apps/server/src/remote-agent/remoteAgentInstall.ts:174`, `:231-233`).
- The install script needs GNU `stat -c`, `sha256sum`, `flock`, `readlink -f`, `sync -f` and
  `install -d`. It aborts when an existing directory under `~/.bigbud/agent` is not mode 700.
- Every SSH failure becomes "The SSH setup command failed (exit N)" and remote stderr is dropped
  (`apps/server/src/remote-agent/remoteAgentFailure.ts:4-6`).
- The remote keeps at most two build payloads. When both slots are occupied and the predecessor
  cannot be safely retired, installation stops with a capacity error
  (`apps/server/src/remote-agent/remoteAgentInstall.capacity.ts:22`, `:42`).
- Install is reachable only from the UI dialog through the `server.installRemoteAgent` RPC
  (`apps/server/src/ws/wsExecutionTargetVerification.ts:99`). It stages the build only; activation
  happens on the next connection (`:125`).
- No supported manual route exists. An undocumented legacy adoption path accepts an executable at
  `~/.bigbud/agent/bin/current` on a remote with no registered current build. It pins the adopted
  build to `unknown-legacy-owner` (`apps/server/src/remote-agent/remoteAgentLegacyBinding.ts:169`),
  which can block later retirement. It must not be documented as the manual route.

Hypothesis, not yet proven: the glibc floor is the most common failure on real servers. Phase 1
must capture real error output to test this hypothesis; static-build work does not depend on
proving it is the most common cause.

## Goals

- A failed install reports the real remote cause in the app and the CLI.
- A user can place the agent on the remote by hand and bigbud adopts it as a normal managed build,
  with signature-backed trust, no upload, and no legacy pin.
- A user or agent can run one command that installs, or replaces, the agent for a target.
- Replacing an existing install retires the old build when it is safe, and reports clearly when
  retirement is deferred because live work still uses it.
- The released agent runs on any supported Linux distribution regardless of glibc version.

- Later phases: remote terminal work and supported provider turns survive laptop disconnection,
  and the normal bigbud UI catches up when reconnected.
- Eventually, explicitly enabled remote workflows continue without the laptop.

## Non-Goals

- macOS or Windows remote hosts.
- Installing an agent whose bytes do not match a signed release manifest, except through the
  existing explicit development-artifact setting.
- A remote-side download script that writes the installation registry. Authorized desktop
  backends coordinate installation-registry mutations through remote CAS. TypeScript is the only
  writer of its backend state root; Rust owns PTY/process state only.
- Killing live remote terminals or processes to force a replacement.

## Decisions

These were agreed with the user on 13 November, 2026. They follow herdr's design, which was
checked against herdr-core's `docs/security.md` and `docs/machines.md` and its published
`releases.herdr.dev/core/install.sh` and `releases.herdr.dev/app/install.sh`.

### D1: The CLI reaches the backend through an owner-only local socket

- The backend opens a dedicated Unix domain socket inside a mode 700 directory under the state
  directory. On Windows it uses a named pipe whose access rules allow only the current account.
- No secret is written to disk. The trust boundary is the user's OS account, as in herdr, whose
  core uses an account-only socket and has "no separate API password or per-client permission
  check".
- The socket accepts only remote-agent operations: `status`, read-only `doctor`, `install` and `install --replace`.
  It is deliberately separate from the backend lock's existing control port and secret, which
  can shut the backend down.
- Agents running inside bigbud threads do not use the CLI. They call a capability tool, which
  already has per-thread authentication through `ThreadOrchestrationToolAuth.ts`. The CLI serves
  people and agents running outside bigbud.
- Rejected: reusing the lock file's control secret, because it grants shutdown authority. Rejected:
  a token file for the WebSocket RPC, because it puts a full-access credential on disk.

### D2: A `bigbud` launcher is placed on PATH the herdr way

- The launcher goes into `~/.local/bin/bigbud` on macOS and Linux. It is created only when no
  other `bigbud` command exists, matching how herdr creates `hc` only when none exists.
- Shell startup files are never edited. When `~/.local/bin` is not on PATH, the user is told to
  add it, as herdr's installers do.
- Two entry points create it: a Settings action named "Install command-line tool", and the
  existing desktop install script.
- The launcher runs the server CLI already bundled in the app, so nothing extra is downloaded.
  On Windows the installer adds it to the user's PATH.

### D3: The remote install script lives on bigbud.app and pins the selected artifact

- The script is served from `https://bigbud.app/remote-agent.sh`. Binaries and the signed manifest
  stay on GitHub releases. The same script is also attached to every release so older app
  versions keep a matching copy.
- The remote agent must satisfy negotiated protocol/capability compatibility; exact app-version
  equality is not required for every connected client. The script takes `BIGBUD_AGENT_VERSION`
  from the verified selected artifact. When
  an install fails or a user chooses manual install, the app shows the exact command with the
  version already pinned and a copy button, the way herdr shows "what to run in your own
  terminal" for steps that need a person.
- Like herdr's installer, the script reads the release manifest, verifies the download's SHA-256,
  stages bytes in a private inbox, and reports failures plainly. The app verifies signature-backed
  identity before executing the candidate; the script does not execute downloaded bytes.
- The website's install button stops fetching scripts from the repository's `main` branch on
  raw.githubusercontent.com and points at bigbud.app instead.

### D4: glibc builds are dropped after one transition release

- The first release with static musl builds also ships the glibc builds, so app versions that only
  recognise glibc targets still find a match.
- The following release ships musl builds only. Its manifest, release workflow stop producing glibc triples. The shared parser retains historic triple
  compatibility for pinned releases and cleanup, while new selection prefers musl.
- Remotes still running a glibc build are moved to musl by the normal automatic update, because
  the new build has a different digest.

### D5: The CLI skips consent for hosts already approved in the app

- No per-host consent record exists today. The in-app dialog asks before the first install, and
  the automatic update coordinator then upgrades known hosts without asking again.
- "Already approved" is derived from existing state, without new storage. A host counts as
  approved when it is a saved remote project whose connection method is the bigbud remote agent,
  or when its remote registry already holds a managed build.
- For an approved host, `bigbud remote-agent install` and `--replace` run without a prompt.
- For any other host, the CLI asks interactively. In a non-interactive shell it refuses unless
  `--yes` is passed, matching herdr's `--install` flag for scripts.
- The capability tool follows the same rule, so an agent never installs on an unapproved host
  without the user's consent in the thread.

### D6: The app owns clean installation and replacement, with a manual VPS fallback

- The app must offer Install, Update/Replace and Copy remote command actions for a remote VPS.
  Manual commands are available proactively as well as after a failed automatic operation.
- App installation and replacement use the same transaction as the CLI: verify, stage, connect,
  activate, then retire unused builds. Repeating an operation for the same build is safe.
- The copyable command runs in the VPS terminal and pins the artifact version selected by the
  app. It supports both a fresh install and staging an update to an existing managed install.
- Under the coordinated desktop-writer design, the remote script stages bytes only. Its output and
  the app must explicitly say to return to bigbud and choose Finish install/update to register
  and activate them. Downloaded or staged must never be presented as an active update.
- Failed downloads, verification failures and interrupted staging preserve the working build.
  Concurrent script and app operations must not overwrite a running binary or publish partial
  bytes; use temporary files and coordinated publication of verified immutable build paths.
- Report separately whether the new build is active and whether old-build cleanup is deferred.
  Live work is never killed to make replacement succeed.

### D7: Hybrid runtime with remote-owned state — supersedes Rust-heavy design

- Rust manages base installation, launch/probe/proxy, terminals and filesystem/process facilities.
- A remote deployment composition of the existing TypeScript backend owns provider semantics,
  canonical conversations/SQLite, approvals, receipts and applicable services on the VPS.
- The UI connects to each remote backend through SSH; it does not duplicate canonical remote
  conversation state in the laptop backend. One backend/state-root authority serves multiple clients.
- Package the existing headless backend as a measured control before trimming its composition.
  There is no commitment to a tiny extracted microservice, Rust provider drivers, Rust canonical
  reducers, per-provider helper ABI or second Rust workflow scheduler.
- Support OpenCode v2; remove legacy OpenCode selectable registration/capability claims and
  investigate stored state/text-generation consumers before removing remaining implementation.
- Install the optional backend for persistent chat and only selected vendor tools on each VPS.
  New remote threads use this ownership; existing paths are not silently migrated.

### D8: Boot startup is an opt-in account service — agreed

- Offer automatic backend startup after VPS reboot during setup; install/enable it only when
  the user opts in. Explain systemd user-service and lingering prerequisites and give exact
  remediation when unavailable. No silent privilege escalation or root-owned installation.
- Without boot startup, explicit backend launch/re-adoption remains supported and the Rust-only
  terminal/filesystem tier stays usable. Enabling a service does not resume interrupted turns
  automatically or imply that processes survived a reboot.

### D9: Updates preserve live work unless interruption is explicitly confirmed — agreed

- Automatic runtime updates defer activation while turns, valid pending approvals or other
  blocking work remain. Staging is allowed within capacity limits; a generic update request is
  not consent to terminate work.
- An explicitly requested interrupting update needs a separate confirmation naming affected work.
  Record that consent against the update operation ID; agents and unattended calls cannot infer
  it. Cancellation/drain must settle or report uncertain outcomes before replacement proceeds.
- Independent Rust user terminals stay alive across TS runtime updates; interruption consent for
  backend work does not authorize killing those terminals.

### D10: Update requests require authenticated setup authority — agreed

- Any client with authenticated setup authority may request the shared serialized drain/update
  operation. Ordinary viewers cannot stage, activate or interrupt an update.
- Enforce authority on the backend/control boundary, not only UI controls. Concurrent authorized
  clients observe the same operation/result; conflicting requests reconcile instead of launching
  another updater. Setup authority alone does not supply D9 interruption consent.
- Within SSH account trust, client identity is for audit/coordination; viewer restrictions govern
  application sessions and cannot revoke a user's independent OS/SSH authority.

### Phase 1: Report the real failure

Goal: make every install failure diagnosable before changing behaviour.

- Capture a bounded, control-character-stripped tail of remote stderr for install, check and
  platform probe commands. Changed `outputMode` for those commands so stderr is retained.
- Map known failures to plain messages: glibc version too old, missing GNU tool, directory
  permission mismatch, upload timeout, capacity deferred, unsupported platform.
- Add a pre-flight probe that reports `ldd --version`, required tool presence and existing
  directory modes before uploading.
- Keep scripts and tokens out of user-visible messages, as the current sanitiser intends.

Files: `remoteAgentFailure.ts`, `remoteAgentInstall.ts`, `remoteAgentPlatform.ts`, new
`remoteAgentInstall.preflight.ts`.

Exit: a failing install against a glibc 2.31 container shows a message naming the glibc floor.

### Phase 2: Static Linux build

Goal: remove the glibc floor.

- Add `x86_64-unknown-linux-musl` and `aarch64-unknown-linux-musl` to the release build and the
  signed manifest. Kept the glibc assets for one transition release so older clients still find a
  match, then removed them in the next release, as decided in D4.
- Extend the shared target triple type, resolver and validator to prefer musl when present.
- Verify in CI that the agent builds, passes its Rust tests, and runs `--check` on Alpine,

Decision gate: the agent's file locking, PTY and process code must pass its existing Linux tests
under musl before the manifest prefers musl.

### Phase 3: Adopt pre-placed bytes

Goal: make manual placement a first-class install route that reuses the managed transaction.

- Before uploading, probe the managed build path. When an owned, mode 700 file with the expected
  size and SHA-256 exists, skip the download and upload. Otherwise inspect the manual inbox
  before downloading. Reserve capacity and publish trusted bytes before the normal identity check.
- Publish `remote-agent.sh` on bigbud.app and as a release asset, as decided in D3. It
  detects the architecture, reads the release manifest for `BIGBUD_AGENT_VERSION`, downloads the
  matching binary, verifies its SHA-256, and places it in the private inbox specified in the implementation contract below with
  mode 700. The app performs trusted promotion and `--check`. It prints the next step. It never touches the registry or the `current` link.
- Add Install, Update/Replace and Copy remote command actions in the app, including failure
  recovery. Commands are version-pinned and usable on fresh and previously installed VPS hosts.
  Provide Finish install/update for manual staging, with the explicit activation boundary in D6.
- Trust is unchanged: bigbud only promotes bytes whose hash matches the signed manifest.

Exit: on a fresh container, running the script and then the app's Install performs no upload and
reaches a ready connection.

### Phase 4: Install and replace from the CLI

Goal: one command for users and agents.

- Add `bigbud remote-agent status <target>` and `bigbud remote-agent install <target>
[--replace] [--yes]`.
- The command talks to the running backend through the owner-only socket from D1, so the
  registry mutations coordinate across backends and each local connection pool has one owner. If no backend is running, it fails
  with a clear message instead of writing state.
- Add the PATH launcher from D2 through a Settings action and the desktop install script.
- Install performs stage, connect and activation in one call, rather than stopping at "staged".
- `--replace` retires non-current builds through the existing retirement flow after activation.
  When the new build is active but old work pins the predecessor, report active with cleanup
  deferred. Report replacement deferred only when activation itself cannot complete.
- Consent follows D5. Approved hosts install without a prompt. Unapproved hosts are asked, and
  non-interactive runs need `--yes`.

Decision gate: the launcher must be proven to start the bundled server CLI from the packaged app
on macOS, Linux and Windows before the Settings action ships.

### Phase 5: Agent capability

Goal: let agents request install or replacement.

- Apply the D5 approval rule. Unapproved hosts require explicit user consent in the thread.

- Bound output, logs, retained sessions and disk consumption; report replay gaps explicitly.

- Preserve live work during updates by deferring activation or retirement when necessary.

Likely modules: `crates/bigbud-remote-agent/src/supervisor`, `src/pty`,

### Phase 8: TypeScript-owned remote orchestration and peer connections

Goal: remote workflows continue across multiple VPSs without a laptop relay. Depends on phase 7
proving remote ownership/recovery; reuse the same TS scheduler and coordination services.

- Keep one authoritative remote coordinator per workflow and ordinary remote child threads on
  worker backends. Persist dispatch IDs, destination identity, child receipts and completion
  delivery. Retry status/follow operations, never launch duplicate children on an uncertain send.
- Introduce a peer-connection abstraction carrying host identity, scoped authority and namespaced
  idempotency keys. SSH is an initial transport option, not an inherent workflow requirement.
  Reuse existing authenticated reachability where possible; paired application transport needs
  its own reviewed authentication and endpoint design before enablement.
- Require coordinator-to-worker reachability only for cross-host autonomous workflows. Ordinary
  multi-VPS sessions need laptop-to-VPS access only. Preflight each hop from the coordinator,
  verify host identity and grant scopes, and provide exact manual setup if unavailable.
- For SSH setup prefer existing configuration. An optional dedicated key is generated on the
  coordinator after approval; only the public key is authorized on workers. Do not copy private
  keys, forward laptop agents, disable host verification or silently grant unrestricted access.
- Scope delegated tools to approved hosts/workspaces/providers, propagate the caller's narrower
  permissions, and preserve origin identity. Revoke peer access independently from deleting a
  local saved connection. Account-level SSH access remains the outer trust boundary.
- Persist cancellation intent, display cancel-pending during partitions, and resume following
  durable child records after coordinator restart. No automatic coordinator failover; permanent
  host loss needs explicit worker inspect/stop recovery. Do not infer cancellation from silence.
- Transfer bounded result summaries and explicit attachments; do not assume shared filesystem
  paths or automatically synchronize repositories. Keep credentials on the execution host.

Likely modules: existing TS orchestration/tools, new server peer transport/follower services,
contracts, backend-scoped UI and SSH setup. Rust supplies transport/process primitives without
becoming a second workflow scheduler.

Exit: two VPS workers and two clients; disconnect both clients and observe completion or explicit
approval wait. Inject partition before/after acceptance, lost results, coordinator restart,
revocation and cancellation; verify one child launch and one result delivery per durable identity.

## Phases 1–6 Implementation Contract (Restored After Architecture Rewrite)

- Preflight/install/check diagnostics retain at most 8 KiB sanitized stderr, with secret redaction
  and terminal-control stripping. A missing `ldd` is informational for musl; report required GNU
  tool prerequisites explicitly rather than claiming static linking removes shell dependencies.
- Manual script publishes verified-size/hash bytes only to an owner-only
  `~/.bigbud/agent/inbox/<sha256>/` using private temporary files and atomic publication. Never
  execute the download or write registry/current selectors. The app verifies signature trust
  before identity execution and promotes through managed capacity/reservation checks.
- Keep inbox outside managed `bin`: `remoteAgentInstall.orphan.ts` can reclaim unregistered
  managed payloads. Allow one completed candidate plus one bounded in-progress download; reuse
  identical candidates and report conflicts instead of deleting unknown content. Interrupted
  adoption preserves the candidate and working build. Lock order: inbox publication/claim first,
  short registry CAS second; never hold a registry lock during download or reverse that order.
- Share `remoteAgentInstall.operation.ts` across app/CLI/tools. Results: staged, active, deferred,
  failed, uncertain; include operation ID and separate cleanupDeferred. Poll accepted operations
  after lost replies before retrying. CLI JSON mode and exit codes: 0 active, 2 consent required,
  3 deferred, 4 failed, 5 uncertain, 6 backend unavailable.
- Local-control framing: 64 KiB request cap, 16 concurrent clients, 5-second admission deadline,
  allow-list install/status/read-only doctor. Return operation IDs for long work. Resolve saved
  target IDs or unambiguous SSH aliases; reject arbitrary command fragments.
- Consent is bound to verified host/account identity, not a registry from another target.
  Agent installation consent never grants backend-runtime or vendor-tool installation consent.
  Phase-5 install capability installs only the Rust base; expose separate explicit setup actions.
- Reconnect transient failures with jittered 1/2/4/8/16/30-second delays, ten attempts/episode;
  stop for authentication/host-key failures. Manual retry/network recovery starts a new episode.
  Reattach by epoch/generation/resource identity; never repeat an uncertain launch.
- Extend paginated PTY inventory (100/page) and output cursors with explicit gaps, bounded by the
  existing 4 MiB output suffix. Decide owner-store placement with phase 7 before extending schema:
  laptop-executed projects use existing ownership; remote-owned threads store ownership remotely.
  Any Rust-resident inventory remains authoritative for actual live PTYs.

## Phase 7 Detailed Boundaries And Acceptance Additions

- **Work order:** packaging baseline; remote composition/lifecycle; multi-backend client;
  selected-provider provisioning; complete provider conformance. An internal prototype slice
  does not reduce the nine-provider release scope.
- **Terminal independence:** baseline may include node-pty as a measurement control, but final
  remote composition delegates all user-visible PTYs to the local Rust supervisor socket and
  excludes node-pty if no other verified consumer requires it. Remote backend owns thread-terminal
  bindings; any attached laptop can discover them. Backend update AND backend kill/restart leave
  user terminals alive and reattachable from another laptop. Provider SDK children remain governed
  separately by the TS process ledger; never reap independent Rust terminals with those children.
- **Stable backend lifecycle:** launch detached outside Rust process-operation/PTY accounting.
  Place lock/socket/start-token records outside rotating generation directories. Do not pin a
  Rust generation forever merely because it launched the backend. Remote startup does not need
  desktop fd-5 lifecycle hints or fd-6/7 handoff. Only one process owns backend.lock/state root.
  Prototype an account-scoped service supervisor with at most five crash restarts in five minutes,
  then needs-repair; do not restart provider turns. A restart-disabled path must still reap dead
  backend children safely. Boot startup follows the opt-in account-service policy in D8.
- **Tunnel owner:** laptop backend owns SSH tunnels and exposes authenticated per-host WebSocket
  and HTTP byte-relay endpoints to the UI. Reuse host-key validation and SSH reconnect. Relay
  stores no canonical remote events and cannot dispatch provider work itself. Attachments/assets
  and HTTP origins must route by host as well as WS. Browser/mobile clients require access to
  this relay; they cannot establish SSH themselves. Keep this limitation visible.
- **Authentication:** remote Unix account is trust unit. Client IDs identify/audit connections,
  not credentials. Authenticate client RPC even on loopback fallback; scoped per-thread callback
  credentials are not full client credentials. Application revocation cannot revoke SSH access.
- **Workspace modes:** reserve canonical host/account/realpath identity for one runtime mode.
  Refuse creating a remote-owned project on an existing laptop-runtime workspace until explicit
  conversion while idle. Add shared remote reservation evidence; two laptop databases alone
  cannot establish exclusivity. Test aliases/symlink paths and concurrent conversion attempts.
- **Handshake:** add a minimal pre-command descriptor returning host identity, backend version,
  RPC schema revision and capabilities. Each client declares a supported revision range; refuse
  incompatible clients with update guidance (do not promise read-only compatibility without its
  own schema tests). Updates never downgrade automatically to match an older client.
- **Safe update drain:** first reject new turns/commands and pause scheduler admission globally.
  Drain in-flight commands, tool callbacks, turns, queued deliveries that can dispatch work and
  provider children before activation. Independent Rust user terminals do not block TS activation.
  Held scheduled/queued work stays durable for the new runtime; it must not deadlock drain.
  Pending approvals block automatic activation. Explicit interruption follows D9; update
  authorization and cross-client serialization follow D10.
- **Writers/retention:** authorized desktop installer publishes backend archives through shared
  remote CAS; remote TS backend is the single writer for managed provider provisioning. Runtime
  archive retention is separate from the agent two-build bound: retain active, previous rollback
  and any pending/in-use runtime; prune only unreferenced completed versions after durable commit.
- **Provisioning tiers:** backend signed archive (runtime/native workers), optional backend
  externals (e.g. Copilot/Pi closure), vendor programs. Each provider gets a versioned recipe with
  OS/arch/libc, integrity/provenance, auth, path discovery and manual fallback. No uncontrolled
  lifecycle scripts during backend setup. If a vendor requires an installer script, make that a
  reviewed provider-specific action with separate consent and provenance, not a hidden exception.
- **Daemon discovery gate:** prove login-shell PATH/version-manager tools are found under
  noninteractive SSH and service startup; report missing prerequisites and preserve explicit paths.
- **Migration disk gate:** while old backend is stopped, require available space for DB+WAL,
  consistent backup, staged runtime, temporary migration/restore files and a configured reserve
  (initially max(256 MiB, 20% of DB+WAL)). Refuse before outage if the estimate cannot be satisfied;
  recheck under maintenance lock before migration. Test insufficient space and interrupted restore.
- **Peer endpoint:** phase 8 uses a separate narrow authenticated endpoint for allow-listed
  delegation/status/follow/cancel operations; peer credentials never authorize full client RPC.
- **Live release matrix:** dated provider/version/OS/arch/libc/account test results, with secrets
  excluded. All nine must pass advertised combinations; one failing required provider blocks
  persistent-chat release. CI mocks do not substitute for vendor-runtime acceptance.

## Risks And Decision Gates

- Phases 1–6 are independent of the backend architecture and can ship first. Their existing
  installation trust, CAS, capacity and retirement guarantees remain mandatory.
- Runtime tiers have separate compatibility: static Rust portability does not certify the
  private JS runtime, native addons or provider tools on Alpine/older Linux/ARM64.
- Full-backend packaging is the control experiment. A small extracted service is not promised;
  extract only if measured size, memory or startup costs justify it.
- Verify Node/Bun/runtime choice against current server APIs and native dependency ABI. Package
  signed per-platform archives with recorded versions, dependency/license review and trust roots.
- Rust and TypeScript artifacts have independent immutable versions. Base replacement must not
  kill chat; runtime activation defers while live work exists. Session pins must be visible to
  every controller, not just one laptop's owner store. Preserve remote registry CAS.
- One backend version/state-root lock at a time. Before migrations record a consistent offline
  database backup or prove backward schema compatibility. An incompatible downgrade refuses
  startup; no rollback that silently loses acknowledged data or duplicates provider effects.
- Mixed clients use negotiated capability/protocol support. Incompatible clients get update
  guidance; do not oscillate the remote backend to match whichever laptop connects last.
- Legacy OpenCode cleanup requires consumer/state migration evidence; do not break legacy text
  generation or silently alias old sessions. Runtime support inventory must match actual adapters.
- Detached launch does not by itself prove logout survival, restart ownership or orphan cleanup.
  Verify systemd user/linger policies and restricted-host behavior; show targeted recovery steps.
- Offline approvals depend on provider request validity. Backend restart does not reconstruct
  live SDK callbacks just because an approval row is durable.
- Resource limits and minimum VPS/distro claims must be measured. Provider process memory is
  separate from backend overhead. Include global bounds, slow consumers, logs, disk-full and
  temporary migration/compaction/rollback space; reject unbounded queues at busy ingestion seams.
- New persistent remote threads first; existing sessions retain current semantics. No automatic
  production migration is authorized by this plan. Broader history migration needs its own design.

## Acceptance Criteria

- App, CLI and capability paths share safe install/replace with truthful staged/active/deferred/
  uncertain results. Manual pinned VPS command works on fresh and existing managed installations.
- Static Linux base passes advertised platform checks; old glibc assets stop after the transition
  release while historic manifests/installed builds remain readable.
- Interrupted installation preserves working state. Live work pins old versions; a third build
  request defers rather than evicting either live build. Active-with-cleanup-deferred is distinct
  from activation-deferred. Missing supervisor evidence is never proof work is idle.
- Local launcher reports PATH remediation and respects existing commands; packaged launch works
  on macOS/Linux/Windows without bootstrapping a second backend.
- Persistent terminals survive client disconnect and have explicit Stop and bounded replay.
- One remote TS backend owns its DB/services per state root and serves multiple clients through
  backend-scoped UI connections. No laptop canonical conversation import or Rust duplicate store.
- All nine supported providers, including OpenCode v2, pass real conformance on advertised tuples.
  Legacy OpenCode is removed from selectable registration; existing data/consumers handled safely.
- Only selected providers are provisioned; existing compatible tools and managed installs are
  reused across reconnects, restarts and switching. Unselected dependencies do not break bootstrap.
- Closing a laptop preserves remote work and valid approval waits. Backend death reports
  interruption/uncertainty with no blind turn replay. Existing receipt/event semantics are shared.
- Rust base updates preserve chat or defer. TS runtime activation waits for safe idle unless
  separately confirmed interruption follows D9; schema
  rollback/downgrade tests pass. Credentials and user-managed tools are never overwritten.
- Cross-host workflows continue independently of laptops with scoped peer connections, durable
  child receipts, truthful pending cancellation and restart-follow recovery.
- Boot startup is disabled unless selected; enabling it survives a VPS reboot under supported
  account-service conditions. Disabling/removing startup preserves data and explicit launch.
- Automatic updates leave active turns and valid approval waits intact; an interrupting update
  requires operation-bound confirmation, rejects stale/reused consent and preserves Rust terminals.
- Viewers are denied update operations server-side; authorized clients share one serialized
  update result and cannot bypass separate interruption confirmation.
- Measurements and platform limits are published before footprint/minimum-VPS promises.
