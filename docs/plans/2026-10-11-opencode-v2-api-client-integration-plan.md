## Intended implementation contract

### 1. Borrowed transport, not owned runtime

- Keep `@opencode/client@2.0.26`; no new dependency or lockfile churn is expected.
- Preserve literal-loopback origin allowlist, no redirects/URL credentials, bounded response decode, deadlines and registration privacy checks. Do not expand to remote/DNS/wildcard origins.
- Registration identity/auth are transport-only; not DB identity, binary attestation, native physical-exit proof or exclusive ownership.
- Health is typed `client.server.info`; OpenAPI capability inspection remains a finite raw GET. Reject generation/version/capability conflict before Location activation or session mutation.
- Before every request recheck original secure registration; changed registration/auth invalidates transport. Retain current explicit bigbud restart/reconnect requirement for changed service generations. Same-generation SSE repair may resubscribe after authoritative reconciliation only.
- `Service.headers` owns auth encoding. No credentials in web contracts, logs, cache keys, durable bindings or diagnostics.
- Production imports/calls must not use ensure/start/stop/config-admin/plugin-register/provider-auth/runtime install. Fixture-only native processes retain explicitly disposable ownership.

### 2. Explicit native trust boundary

- Add optional `nativeServiceTrust: "host-user-v1"` setting; absent/unrecognized is not acknowledged. Defaults remain sparse/backward-compatible; do not silently opt existing enabled users into new weaker guarantees.
- Explanatory UI: this attaches to existing native accounts/configuration; Location activation can run/install **already-configured** native plugins; chat writes ordinary native session history; native tools/plugins run as the user, not in bigbud's sandbox; logical history cannot distinguish identical copies.
- The user acknowledges these effects explicitly. Native service-file/mode edits and reset clear acknowledgement in UI; imported settings preserve explicit serialized acknowledgement but never manufacture one for old exports.
- Before consent, background refresh reports checked service/version/capability and a consent-required warning; it must not call Location catalog or start a native session. Use the existing provider snapshot contract and severity semantics.
- Gate queued start/send/catalog after settings are rechecked, not just on UI state. Revocation blocks new work synchronously with backend acceptance of changed settings; original-owner interrupt/cleanup remains available without native daemon control. Re-enabling cannot discharge pending quarantine.
- Retain known default native data/config/state/registration directory denies with cross-platform normalization. Retain additional restrictive denies on verified legacy sessions where their policy grammar is valid. Do not invent custom DB/config roots or promise all plugin writes are contained.

#### Executable backend revision/cancellation fence

**State owner and settings propagation:** extend the existing server-authoritative `ServerSettingsService`, not a UI-owned flag or independent settings cache. Extract a small provider-neutral `ws/serverSettings.snapshot.ts` concern with a synchronous accepted snapshot, monotonic revision and synchronous change listeners. Expose a synchronous snapshot reader/listener on the internal service; initialize only from a successfully loaded/validated settings snapshot. An unavailable snapshot fails closed. Keep `Cache`, write semaphore, atomic persistence, `ready` and `streamChanges` for their existing roles.

- Route accepted initialization, `persistSettings` and `revalidateAndEmit` through one snapshot-accept operation. After a successful persisted write/validated external reload, update the synchronous snapshot/revision and notify cancellation listeners in one synchronous step **before** any cache/publication await or update-RPC acknowledgement. No provider refresh or `streamChanges` consumer must run before revocation takes effect. Settings writes are still serialized by the existing semaphore; validate before admission and preserve unrelated settings. Listener failure must not prevent the revision from advancing or remaining listeners being invalidated.
- Existing WebSocket settings RPCs already call `updateSettings`; keep that path and UI settings change propagation. The async stream schedules UX refresh/cleanup only, never owns authority. Mirror the same snapshot transition in `layerTest` and settings fixtures, including those whose change stream is empty. External disk edits take effect when the existing watcher accepts a validated reload; do not promise immediate detection before its debounce/read latency. No instantaneous external-filesystem or crash atomicity guarantee is added.

**V2 permit owner:** add `Application.consent.ts` under the existing application registration scope. It subscribes synchronously to accepted snapshots and keeps a V2-specific monotonic config/consent revision derived from enabled state, resolved mode, selected service file, native-trust version and active mode's configuration key. Unrelated greeting/terminal changes do not revoke V2 permits. A relevant transition advances the revision, aborts all prior disposable request/publication permits and invalidates pending bootstrap/snapshot generations synchronously; scope finalization unsubscribes and invalidates them too. Regrant creates a new revision and cannot make an old permit valid again. No native lifecycle signal, uncertain-admission release or mutation-quarantine reset is allowed in this callback.

**Capture, dispatch and publication:** capture a permit `{ revision, signal, assertCurrent, release }` when each catalog/bootstrap/start/send/reply/repair operation is admitted, after initial settings readiness and before its first await. Combine its signal with existing deadline/owner cancellation; check its revision synchronously after every awaited preparation/registration/ownership/SQL stage and immediately before each native invocation. Reuse `authorizeExecution`, `beforeDispatch`, owner queues and `v2ReplyGuard`, but return a validator that checks **both** captured permit and existing exact owner/epoch/transport generation. In particular, revocation during `Runtime.replies.ts:107-108` must be rejected by the returned dispatch validator, not just the earlier async authorization read.

At `Client.ts`'s guarded fetch boundary add a synchronous per-operation validation **after** the awaited `beforeRequest` registration check and directly before calling fetch in the same synchronous turn. Implement a scoped shared-transport request context in `Client.guard.ts` using Node's existing `AsyncLocalStorage` (no new dependency): operation entrypoints run their queued Promise chain under the captured immutable permit, and guarded fetch retrieves/validates that exact context for this transport. Missing or mismatched context rejects a shared request. Do not overwrite a mutable client-global 'current permit' shared by concurrent callers. Existing `v2Request` deadlines combine the context's signal; the long-lived hub starts/consumes `event.subscribe` under its separately captured SSE permit so lazy iteration/source setup inherits the correct context. Health-only context admits just the two allowed GET routes; cleanup context admits only its explicit exact-owner routes/IDs. Isolated clients keep their existing authorization model.

Validate responses after decode and again at the actual snapshot/event publication boundary, not only before awaiting an emit. Pass the captured publication validator into the existing snapshot store/runtime emit path so validation occurs directly at the queued PubSub enqueue, after any earlier awaits. Reject stale native results, buffered events, interaction opens and model/auth status from revoked revisions. Carry the capture through event-hub owner delivery and queued publication; asynchronous callback context alone is not a replacement for the explicit revision check. An old operation cannot publish on behalf of a regranted/new owner. Cancellation stops only bigbud's disposable requests/subscriptions; it never proves native mutation settlement, terminal completion or safe resend.

**Preconsent connection path:** `Application.composition` branches before `ensure`/execution initialization. Call secure health/contract discovery directly, create no manager lease, and never enter `Development.provider` acquisition. `ServerManager.acquire` currently starts the hub at lines 180-187; do not use it even for preconsent status. The typed health client is lazy and must not consume `event.subscribe`. Publish only version/capability plus consent-required status under a captured config revision. After consent, manager acquisition itself requires a valid permit before acquisition and again before opening SSE; a revoked late acquisition is disposed locally, never replaced or interpreted as daemon exit. Health-only probes remain separately authorized to run without trust, but their results still require the matching enabled/config revision before publication.

**Cleanup exception:** use an explicit original-owner cleanup intent, not a trust bypass on the ordinary execution client. After revocation, only exact-owner interrupt with `resume:false`, owned-inbox cancellation/interaction cancellation and already-established lease/resource release are permitted, following existing ownership/uncertainty fences. Permission/form replies that may resume execution (even a decline) require the ordinary current consent permit; do not classify them as harmless cleanup. Cleanup may publish exact-owner stop/unknown status through a separate lifecycle publication gate, never late transcript/model/permission-open results. Cleanup failure, aborted request or a new healthy transport leaves existing journal/create intent/mutation/teardown quarantine intact.

### 3. Durable logical binding and legacy adoption

Implement a narrowly scoped `OpencodeV2SharedBindings` persistence service using existing Effect SQL/repository conventions. As of this baseline the next migration is `127`; recheck for concurrent migration additions immediately before choosing its ID. Register the migration in `Migrations.ts` and provide the live service beside `ProviderTurnAdmissionsLive` in optional-provider composition.

The binding record is keyed by the durable foreground or hidden-learning thread ID and stores immutable native session ID, opaque storage token, exact canonical Location, local runtime/workspace targets, identity kind/version (`shared-api-v1` or adopted legacy), revision, creation state and initial model/creation-material fingerprint. No service password, native database pathname, native credentials, prompts or native config contents are stored. Preserve records/tombstones independently of ephemeral runtime-directory cleanup and avoid cascade deletion of replay evidence.

- **Fresh binding:** deterministic namespace token derived from the canonical registration file and a versioned shared-API discriminator; native ID still hashes token+thread ID. Transport generation/PID/password/version never enters durable token. Persist the binding before native mutation.
- **Creation state:** reserve immutable material; CAS to `dispatch-intent` before calling `session.create`; mark verified only after exact API verification. A retained dispatch intent with missing native session is unknown and **never** resubmits create. An existing verified binding never creates missing history. #### Rollout, interruption and rollback boundary

The new binding repository is safety-critical durable data, not a reversible cache. Rollout is default-unconsented: migrate bigbud's schema without automatically adopting/rekeying native history, then enable shared execution only through the consent/revision fence. Reserve creation intent before native mutation; leave native and local evidence intact after interruption. An app interruption may leave **only** a new `dispatch-intent` record, with no old cursor or admission journal; startup/recovery checks the new repository first and never derives a different physical-ID session or retries create.

**Safe rollback:** either retain the new binding/recovery fences in any rollback build, or disable shared execution using the persisted common `providers.opencodeV2.enabled:false` setting **before** running an older build. Use the existing settings RPC/service, wait for its acknowledged durable write, invalidate/drain bigbud-owned requests/owners without clearing uncertainty, then stop the bigbud application. Keep the new table/rows, creation intents, cursors, journal/tombstones and immutable attachments unchanged; never drop the migration, restore a pre-intent database snapshot over current state, delete/rekey records, or 'repair' by creating fresh history. Native daemon shutdown/restart is not part of rollback. Return to an API-aware build to inspect/reconcile retained bindings before re-enabling; re-enabling on an older build that ignores the records is prohibited.

**Limit of enforcement:** a downgraded binary can ignore every new marker/table and `nativeServiceTrust`; the new build cannot technically prevent that binary or a user from re-enabling the old shared path. The compatible `enabled:false` setting is the explicit operational rollback boundary, not a claimed universal downgrade interlock. Add a prominent downgrade warning in provider docs/validation and a warning exposed by this build when shared logical records exist: do not run shared execution in a build lacking `OpencodeV2SharedBindings` recovery. If a rollback cannot preserve the fence or keep shared disabled, it is unsupported; preserve state and report the blocker instead of suggesting an unsafe code/data reversal.

**Compatibility evidence:** fixture an interrupted create with only a dispatch intent, zero cursor and zero prompt journal, then restart: verify zero create/prompt dispatch and byte-identical retained record. Test the older-compatible disabled setting gates acquisition/dispatch independently of the new repo/consent fields; document that this tests the known old enabled gate, not an untested old binary or universal downgrade enforcement. Re-enable only through the API-aware reader and prove exact native recovery/missing-history quarantine remains. Include a negative compatibility fixture showing that a reader which ignores the new record would otherwise derive/recreate a different session; this is evidence why enabled shared downgrade is unsupported, not a production fallback.
