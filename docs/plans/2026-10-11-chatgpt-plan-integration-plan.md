## Summary

Offer **Continue with ChatGPT** in bigbud so eligible users can explicitly authorize their ChatGPT plan for coding-agent requests, without first configuring a Codex CLI login. Keep the existing Codex CLI, API-key, custom-provider, other-provider, and speech-to-text paths intact. Show the account registration and billing route actually used by each conversation, and link to ChatGPT's usage controls.

**Confirmed scope of this task:** research and save this plan only. The recommended implementation is optional, server-owned OAuth plus the existing Codex app-server adapter, initially for a provider runtime on the user's local computer, including a local runtime working in a remote workspace. A genuinely remote provider runtime, managed binary installation, and centrally hosted/paid offerings are separate gates, not implicitly authorized extensions.

bigbud is an MIT open-source downloadable desktop/local app. The documented OSS/local integration is applicable to that distribution model; no commercial-partner approval blocker follows merely from bigbud.app saying “freemium forever.” Offering this in a paid or centrally hosted product would require revisiting OpenAI's separate interest/approval path. Eligibility for an individual user/workspace and successful use of a particular model remain runtime-dependent.

## Problem

Current Codex setup tells users to manage a CLI installation/login. Its discovery and plan display read native Codex account state. That does not provide official bigbud-owned consent, per-app usage management, multiple managed account registrations, revocation, or a browser sign-in lifecycle.

Adding only an OAuth button and saving a refreshed token is unsafe: app-server captures `ACCESS_TOKEN` at launch. Reusing the process can continue sending an expired token, while blindly restarting it can interrupt approvals, background tools, and partially executed turns. A global “active account” consulted during every retry can also bill a different account or resume its native history after switching. This plan treats routing, durable history ownership, refresh, and safe process replacement as prerequisites, not follow-up cleanup.

## Goals

1. Use O3's official public-client flow, with validated identity and explicit granted plan permission, without an API key or client secret.
2. Support separately labeled saved user/workspace registrations, reuse their issued clients and host ID, and capture immutable account ownership for every admitted workload.
3. Keep secrets server-side; provide protected cross-platform storage and cross-process refresh safety in packaged and Bun/local-server modes.
4. Use the existing local Codex runtime with a fixed public Responses route; replace stale launch credentials safely and resume the same owner-bound native thread.
5. Preserve drafts, attachments, local conversation history, approvals, session epochs, cancellation, reconnects, remote-workspace bridges, and all legacy billing paths.
6. Show permission, current account/route, model-catalog provenance, real failures, and external usage controls without inventing entitlements, balances, reset times, or success.
7. Ship behind an opt-in rollout with additive persistence and reversible runtime routing; do not import ChatGPT chats or reuse SIWC tokens for STT.

## Non-Goals

- Replacing bigbud's own local/server authorization with an OpenAI identity, adding a SaaS login, billing service, app credits, or paid subscription.
- Removing the CLI path, changing the default provider, importing native CLI credentials into managed registrations, or overwriting `~/.codex/auth.json`/configuration.
- Generic provider-instance/auth infrastructure copied from t3code, its new orchestrator, or its Effect 4.0.1 upgrade. bigbud currently uses Effect `4.0.0-beta.43`.
- Device-code auth for the OSS dynamic SIWC flow or an API-key exchange for it. O13 documents native Codex device code/API-key login, **not** O3's dynamic integration; leave those native paths alone.
- Fetching/importing ChatGPT conversations, account context, API keys, or undocumented workspace claims; using `chatgpt.com/backend-api` for inference.
- SIWC audio/video, transcription, hosted file search/Code Interpreter/image generation/native computer use/hosted MCP, or Responses `tool_search`.
- Automatic remote secret transfer or managed Codex downloads in the initial baseline; those require separately approved phases.
- Unrelated worktree fixes or broad formatting/refactoring.

### Exact official flow to implement

- Persist host identity before sign-in. Recommendation: supported `urn:uuid:<UUIDv4>` once per canonical credential-store/runtime host; dev/prod separate stores are separate hosts. Restart, logout, reauth, account switch and upgrade do not rotate it. O2 recommends a JWK thumbprint URI, but currently no key-possession proof; choose that instead only with an explicit lifecycle/key-storage decision. Copying a data directory to a new machine must not silently clone host identity.
- Initial authorization uses `client_id=dynamic_agent_client`, `agent_name_hint=bigbud`, stable `ext_agent_host_id`, `response_type=code`, `resource=https://api.openai.com/v1`, and scopes **`openid profile email offline_access resource.invoke chatgpt.tokens.use.direct`**. There is no client secret or partner API key.
- Start `http://127.0.0.1:<available-port>/auth/callback` **before** opening the system browser. Only the port can vary for returning sign-ins. No `localhost` substitution; code exchange uses the exact URI chosen for that attempt.
- Generate fresh unpredictable state, nonce and PKCE verifier/challenge (`S256`). On callback validate state before consuming the attempt; reject duplicates/ambiguous query parameters, supplied client mismatch, missing required **success** fields as distinguished below, wrong method/path and expired/cancelled attempts. An invalid unsolicited callback must not consume the legitimate pending attempt.
- For a successful **new registration**, require code and an issued `client_id` (never `dynamic_agent_client`); without the issued ID, registration is incomplete. For **returning sign-in**, O3 permits the callback to omit `client_id`: use the exact saved issued client captured in the pending attempt. If supplied, it must match that client; reject mismatch rather than replace the selected registration. OAuth errors are handled after state validation and before requiring success fields.
- Exchange form-encoded `grant_type=authorization_code`, resolved issued `client_id` (new callback or returning pending attempt), `code`, `code_verifier`, exact `redirect_uri`, `resource` at O14's token endpoint. Never use the dynamic sentinel for exchange or refresh. On code `invalid_grant`, abandon code and preserve only a **pending, unverified** issued-client mapping for fresh auth; it is not an authenticated account.
- Verify ID token signature with discovered JWKS; issuer exactly `https://auth.openai.com`, audience issued client, expiry, saved nonce, nonempty `sub` and advertised algorithm policy. O14 currently advertises RS256. Do not accept arbitrary `jku`, embedded keys, algorithms or redirects; allow only approved HTTPS OpenAI discovery/JWKS endpoints, bounded fetch/cache and key-rotation behavior. Test any algorithm change before broadening policy.
- Account key is local opaque registration ID plus verified **issuer/client/sub** association. Email is a recognition hint, not uniqueness or workspace identity; do not merge registrations with the same email. Do not infer workspace or plan from opaque encrypted access-token metadata. Reauth under the same issued client requires the same verified identity.
- Token-response scopes, not callback scope or ID-token validity alone, determine plan permission. Missing direct permission retains verified sign-in with `planPermission=disabled`; no inference. Explicit Enable plan usage repeats full scopes with `prompt=consent`; `force_reconsent=true` only if OpenAI confirms deployment for this integration (O9). Do not force consent on ordinary login.
- Save the whole protected token generation: access/refresh/retained ID token, token type, granted scopes, receipt time/expiry and earliest refresh. Refresh form is `grant_type=refresh_token`, saved issued client, refresh token, resource; **omit scope**. O8 gives lifetimes, but schedule from response and verified expiry, not a hardcoded countdown. Token metadata is opaque; no assumed `chatgpt_account_id` for this route.
- Reauth omits `agent_name_hint`; retained `id_token_hint` (may be expired) and optional email `login_hint` must belong to the selected registration. Never expose/log the hinted authorization URL. Signout clears retained hints/tokens but retains mapping/label/host ID.
- `GET https://api.openai.com/v1/models` uses the selected generation's token. Parse `models`, keep server ordering and `visibility="list"`, use `display_name` and `slug`. App-server `model/list` is capability/catalog evidence, **not** account entitlement or plan permission. Only a completed real inference verifies that request's access; do not perform hidden billed test inference at login.
- O6's managed provider uses `model_provider="openai_chatgpt_plan"`, `name="ChatGPT plan"`, `base_url="https://api.openai.com/v1"`, `env_key="ACCESS_TOKEN"`, `wire_api="responses"`, `requires_openai_auth=false`, `supports_websockets=false`. Pass token in child env only. Initialize then initialized, start/resume native thread, save native ID; success requires `turn/completed` with `turn.status="completed"`.
- O13's experimental `account/login/start {type:"chatgptAuthTokens",...}` and `account/chatgptAuthTokens/refresh` are **not** a hot-update mechanism proven for O6's custom env-key provider. Do not use them to avoid documented restart, decode an unsupported account ID, or claim native `account/read`/rate limits represent SIWC. A command-backed bearer provider is also a different, qualification-gated design, not the baseline.
- **Credential-bearing HTTP policy:** server token exchange, refresh, revocation and account-model requests must reject all redirects at the HTTP transport before any follow-up request, not merely inspect the final URL or rely on cross-origin Authorization stripping. Never replay code/verifier/refresh-token form bodies or bearer headers to a `Location`, including same-origin, cross-origin, downgrade and 307/308 redirects. Record a sanitized integration error; a dispatched refresh still follows uncertain-rotation recovery. This is a proposed bigbud security requirement, not an assertion that O3 mandates a particular HTTP library option. Codex owns inference HTTP independently: app fetch redirect settings do **not** control it. Phase 0 separately proves the chosen Codex transport does not redirect credentials; if not configurable/provable, block managed qualification rather than claim protection.
