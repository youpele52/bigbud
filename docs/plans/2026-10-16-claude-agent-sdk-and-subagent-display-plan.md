## Summary

This plan upgrades `@anthropic-ai/claude-agent-sdk` from 0.3.293 to the latest stable release, 0.3.301, with no behavior change. It then extends bigbud's **provider subagent** display so that, for every provider exposing the data, users see what each subagent is doing: status, model, current tool, recent steps, elapsed time, tokens and cost, and the result or failure. It fixes three Claude defects: real subagents are classified as ordinary tasks, a subagent's cumulative tokens overwrite the thread's context meter, and most SDK subagent fields are dropped.

OpenCode V2 shows no subagents because bigbud denies native subagents for security. This plan builds a read-only observer and display path now and enables native subagents only after gate G4 proves children inherit the parent's permissions.

"Subagent" means a provider-native subagent or task inside one provider session. bigbud's parent/child thread delegation (`create_thread`, `DelegatedChildrenCard`, `ThreadOrchestrationTools`) is out of scope and unchanged.

## Problem

Observed facts:

1. **Claude subagents are misclassified.**
   - bigbud marks a Claude task as `providerSubagent` only when `subagentType === "agent"` (`apps/server/src/provider/Layers/Claude/Adapter.tasks.ts:87`; correlation at `Adapter.stream.handlers.messages.ts:185`).
   - The CLI's actual task type is `local_agent`. Both the SDK 0.3.301 declarations ("Agent type of a local_agent task") and the strings in the native CLI 2.1.293 show this; the CLI also uses `local_bash`, `local_workflow`, `remote_agent`, `in_process_teammate`, `monitor_mcp` and `dream`.
   - The only places `"agent"` appears are a synthetic 0.3.219 fixture (`fixtures/sdk-0.3.219-task-messages.json:23`) and tests.
   - The reducer also merges `subagent_type` and `task_type` into one field (`Adapter.tasks.reducer.ts:157-163`).
   - Result: subagents end up in the plan checklist (`claudeTaskPlanPayload`, `Adapter.tasks.ts:39-63`). Confidence is high, based on the code and the type declarations. Real output will be checked manually by the user after delivery.
2. **The context meter is corrupted.** The `task_progress` and `task_notification` handlers turn the subagent's cumulative `usage.total_tokens` into a thread-level `thread.token-usage.updated` event and overwrite `context.lastKnownTokenUsage` (`Adapter.stream.system.ts:175-200, 226-250`; `Adapter.utils.ts:145-185`).
3. **Subagent data is dropped.**
   - The `task_started` decoder keeps only `task_id`, `description` and `tool_use_id` (`Adapter.sdk.messages.tasks.ts:15-23`), and the handler passes on only `description` (`Adapter.stream.system.ts:156-174`).
   - The SDK also provides `task_type`, `subagent_type`, `prompt`, `is_backgrounded`, `spawn_depth`, `parent_task_id`, `run_id`, `ambient`, `skip_transcript` and `workflow_name`.
   - Subagent messages carry `agent_id` (from SDK 0.3.292) and `message.model`, and their `tool_use` blocks arrive even without `forwardSubagentText`. bigbud reads only their text (`Adapter.stream.handlers.messages.ts:173-219`).
   - `AgentOutput` (`sdk-tools.d.ts:102`) carries `resolvedModel`, `totalTokens`, `totalToolUseCount`, `totalDurationMs` and `toolStats`. bigbud ignores all of them.
4. **Subagent partial messages are not guarded.** `SDKPartialAssistantMessage.parent_tool_use_id` exists, but `handleStreamEvent` (`Adapter.stream.handlers.ts:56-282`) never checks it. If such a partial arrives, its block indexes could collide with the parent's text-block and tool maps.
5. **OpenCode V2 shows no subagents.**
   - The native `subagent` action is denied in both policies: shared (`OpencodeV2/Runtime.policy.shared.ts:28-29`) and local (a deny-all base, `Runtime.policy.ts:18-57`).
   - Sessions with a `parentID` are rejected as owners (`Runtime.ownership.ts:22`, `Runtime.sessions.ts:284`).
   - `EventHub` routes events only to the session IDs of registered owners (`EventHub.ts:162-171`).
   - V2 does expose child data that a read-only observer could use: `SessionInfo` (`parentID`, `agent`, `model`, `tokens`, `cost`, `outcome`, `time`), `session.created.parentID`, `session.list({parentID})`, `session.active` and `session.execution.*` (from the `@opencode/client@2.0.26` generated types).
6. **Display gaps.**
   - `SubagentsCard` shows only the subject, status, elapsed time and `progressSummary ?? lastToolName` (`apps/web/src/components/chat/agents/SubagentsCard.tsx:44-110`). It shows no model, metrics, steps, result or status colors.
   - The web store appends agents without bound (`events.store.threads.runtime.ts:41-57`).
   - Task upserts are not throttled. Each Claude progress update causes two upserts, and each upsert is a persisted orchestration event.
   - The elapsed-time clock (`nowTick`) ticks only while the main turn is working (`chat-view-effects.hooks.ts:301-309`), so a background subagent's elapsed time freezes once the parent turn ends.

## Goals

1. Run Claude on SDK 0.3.301 with no regressions.
2. For every provider with documented subagent data, show each subagent's identity, status, model, current activity, recent steps, elapsed time, metrics, nesting and result through one provider-neutral model.
3. Make Claude subagents classify correctly. They must never distort thread usage or leak into the parent's text or plan steps.
4. Observe and display OpenCode V2 child sessions read-only. Enable native V2 subagents only after G4 passes.
5. Adopt the Claude SDK capabilities that give real user value, in shippable slices, including a per-subagent Stop control.
6. Keep subagent event volume and memory bounded.

## Non-Goals

- Changing bigbud thread delegation, `create_thread` model choice, `DelegatedChildrenCard` or origin links.
- Changing the turn-level Stop. It still interrupts the turn, and Claude still kills background tasks on interrupt because bigbud never declares `perTaskStopAffordance`.
- Changing dead-thread recovery, fork, the no-resend and no-replay rules, or approval semantics.
- Upgrading other provider SDKs. Copilot 1.0.22, Pi 1.3.0 and `@opencode/client` 2.0.30 exist but are not needed.
- Editing the frozen OpenCode V2 thread-tool files: `Orchestration.plugin*.ts`, `Orchestration.implementation*.ts` (including `.manifest.generated.ts`), `PluginSetup*.ts` and `NativeCompatibility.qualification.registry.ts`.
- Subagent mappings for Cursor, Devin, KiloCode and CLIProxyAPI. These remain evidence-gated.
- Rust changes and SQLite migrations. `task_json` is schemaless JSON (migrations `046_ProjectionThreadTasks.ts` and `082_ProjectionThreadTasksOwnership.ts`).

**Must remain unchanged:**

- Main-agent status takes precedence over subagent status (`chat-view-agent-activity.logic.ts`, `Sidebar.logic.status.ts:83`).
- No toasts or OS notifications for subagents.
- Todo items and plans never appear as agents.
- Stale `running` rows are demoted to "Last seen" after a restart or epoch change.
- The violet child-only indicator (`agentActivity.presentation.ts:3`).
- CLIProxy tasks stay `kind: "task"`. This is enforced by the `context.providerSubagentsSupported` gate (`Adapter.session.ts:330`, `Adapter.stream.tasks.ts:95`, `Adapter.stream.handlers.messages.ts:189`).

1. **Adapter:** emits `task.updated` with `kind: "providerSubagent"` (`providerRuntime.payloads.tasks.ts:35-77`).

   - `task.*` events also produce work-log activities (`ProviderRuntimeIngestion.helpers.activities.ts:136-140`).

5. **UI:**
   - `ChatAgentActivityFeed` (`ChatViewChatBody.tsx:235`) shows active subagents.
   - `subagents-history` timeline rows (`MessagesTimeline.logic.ts:203-230`) show past ones.
   - `SubagentsCard` plus its hierarchy helper nests rows by `parentAgentId` only.
   - Chat and sidebar status come from `chat-view-agent-activity.logic.ts` and `Sidebar.logic.status.ts:83`.

### Phase 2: Provider-neutral subagent model and display

1. **Contracts (schema only).**
   - Move the task schemas (`orchestration.thread.ts:166-246`) to a new `orchestration.thread.tasks.ts`, and re-export them from `orchestration.thread.ts`. If the Effect language service flags the re-export, update the importers instead.
   - Add these optional fields to both `OrchestrationTask` and `TaskUpdatedPayload`:

   ```ts
   model?; effort?; prompt?; depth?: NonNegativeInt; endedAt?: IsoDateTime; resultSummary?;
   metrics?: { totalTokens?; toolUses?; durationMs?; costUsd? /* >= 0 */ };
   recentSteps?: Array<{ toolName; label?; status: "running" | "completed" | "failed"; at }>; // max 5
   ```

   - Keep `usage` for compatibility. The UI stops rendering it.
   - Add tests to `providerRuntime.payloads.tasks.test.ts`: decoding a legacy row, the new fields, and rejecting more than 5 steps.

2. **Shared module.** Add `packages/shared/src/providerSubagents.ts` and export it as the `./providerSubagents` subpath.
   - It holds the field bounds: subject 120, model 120, prompt 1,000, summaries 500/1,000, tool name 80, label 160.
   - It runs strings through `toBoundedRedactedText` (`providerRuntime.ts:139`).
   - It exports `appendSubagentStep`, a ring of 5 deduplicated by tool-use ID, and `normalizeSubagentMetrics`.
   - Adapters send the full bounded `recentSteps` list on each update, and ingestion replaces the stored list. This keeps updates idempotent.
3. **Ingestion.**
   - Split first: move the task-event branch of `ProviderRuntimeIngestion.processor.runtime.ts:378-400` into `ProviderRuntimeIngestion.processor.tasks.ts`.
   - Move the `task.updated` mapping (`.processor.events.ts:153-221`) into `ProviderRuntimeIngestion.tasks.map.ts`. Carry the new fields over, falling back to the previous values, and set `endedAt` on the first terminal status.
   - Add `ProviderRuntimeIngestion.subagentThrottle.ts`. It applies only to `providerSubagent` tasks, and works as follows:
     - **Never throttled:** the first update for a task; any change of `status`, `kind` or `model`; and every terminal status (completed, failed or stopped). Terminal and completed states are always persisted immediately (user-confirmed, D10).
     - **Otherwise:** at most one persisted upsert per task per 1,000 ms. A suppressed update is kept as the pending latest value for that task, merged with any newer one.
     - **Opportunistic flush:** whenever ingestion processes _any_ runtime event for the thread, it first flushes every pending entry whose 1,000 ms window has elapsed. It then processes the event. Order is preserved because this runs synchronously, with no timers.
     - **Bounded flush:** on `turn.completed`, `turn.aborted`, `session.state.changed`, `session.exited`, on adapter stop or session teardown, and on ingestion shutdown, it flushes all pending entries for that thread.
     - **Capacity:** up to 256 tasks per thread and 256 threads, evicted least-recently-used. An eviction flushes the evicted entry first.
     - **Worst-case staleness:** a non-terminal progress snapshot is persisted after at most max(1 s, time until the next runtime event of the same thread, time until a flush boundary). A Claude background subagent keeps producing its own events (heartbeats, and progress summaries roughly every 30 s), so in practice staleness is about 30 s or less.
     - **Crash loss:** a crash can lose only the latest non-terminal progress snapshot. Status changes and terminal results are never held back.
4. **Web state.**
   - Move the provider-agent upsert and remove logic into `events.store.providerAgents.ts`.
   - Cap each thread at 100 agents: keep all active ones and drop the oldest terminal ones. Apply the same cap in `mappers.lazy.store.ts:225-227`.
5. **Clock.** Verified: `nowTick` ticks only while `thread.isWorking` (`chat-view-effects.hooks.ts:301-309`). ### Phase 7 — Prompt suggestions (added 2026-10-16 by the user)

User requirements: a provider-agnostic pipeline so any provider with native prompt suggestions plugs in, starting with the Claude Agent SDK; when a provider has none, bigbud generates one. The suggestion is the logical next message (a question or an instruction), always related to what was discussed, 15–150 characters. Text generation always uses the thread's current model; the fallback is the text-generation model.

1. **Contracts.**
   - Runtime event `turn.prompt-suggestion` with payload `{ suggestion, source: "native" | "generated" }`; `threadId`, `turnId` and `provider` come from the event envelope.
   - `orchestration.promptSuggestion.ts`: activity kind `prompt.suggestion`, payload `{ suggestion, source, provider }`, and the length bounds.
   - Server settings `promptSuggestions` (default on) and `generatedPromptSuggestions` (default on), with patch keys. Older saved settings decode to the defaults.
2. **Normalizer** (`@bigbud/shared/promptSuggestion`): trim; collapse to one line; strip control, zero-width and bidi characters; keep 15–150 characters after normalization and drop anything outside the range (never truncate); drop a suggestion equal to the last user message.
3. **Ingestion** projects the latest suggestion onto the thread as a `prompt.suggestion` activity bound to its turn. It attaches only when the setting is on, the turn is the thread's latest and completed, no turn is running, nothing is queued, and the thread is not archived or deleting. The activity is hidden from the work log.
4. **Clearing.** The web shows only the newest suggestion, and only while it belongs to the latest settled turn with no later user message (new turn, send and queue clear it). Revert and rollback drop suggestion activities in every projector (in-memory, SQL and web). Forks never copy them. A suggestion is never sent automatically and never touches recovery or the queued-prompt path.
5. **Claude native.** `promptSuggestions: true` in the query options when the setting is on (not for the CLIProxy harness). The stream keeps iterating after `result`; `prompt_suggestion` maps to `turn.prompt-suggestion` with `source: "native"` for the turn that just completed. This replaces the 6.1 no-op.
6. **Generated fallback** for adapters without `capabilities.nativePromptSuggestions`, when both settings are on.
   - Runs after a successful turn. Skipped on the first turn, after failed or interrupted turns, in plan mode, while approvals or user input are pending, and when the thread is archived, deleting or has a pending delegated model choice.
   - Model: the thread's `modelSelection` when bigbud's text generation can run it, otherwise `textGenerationModelSelection`. A failure yields no suggestion and is logged at debug level.
   - Input: a bounded transcript of user and assistant message text only (no tool output, attachments or terminal context) with common secret patterns redacted.
   - One in-flight generation per thread (a new turn, user message, queue, revert, archive or deletion cancels it), a ~15 s timeout and a global concurrency cap. It never blocks a turn and attaches only if the turn is still the latest.
7. **Settings UI.** Two toggles in Settings → AI (text generation), with a one-line note that the generated fallback makes an extra model call.
8. **Web composer.** Ghost text only when the composer is empty and the suggestion belongs to the latest settled turn. Tab or → accepts it; typing hides it; Enter never sends an unaccepted suggestion. An aria hint announces it. The slash and mention menus are unaffected (they need typed text). On touch devices a tap chip accepts it.
9. **Tests:** normalizer bounds (14/15/150/151, multi-line, bidi); Claude mapping after `result`; clearing on new turn, send, fork and revert; fallback model order; cancellation; no auto-send; a composer browser test.

## Implementation Deviations

Recorded during implementation; the validation ledger is [claude-sdk-subagent-display-2026-10-16.md](../validation/claude-sdk-subagent-display-2026-10-16.md).

- **2026-10-16, pre-flight:** every split-first line count and the SDK pin matched at HEAD `4a1661223b`. No deviation.
- **2026-10-16, Phase 2.1:** `OrchestrationSubagentStep` gained an optional `id`, the native tool-use ID. The plan requires the step ring to be deduplicated by tool-use ID, and the listed step shape had no field to carry it. The field is additive and has no user-facing effect.
- **2026-10-16, Phase 2.3:** `upsertTask` moved into `ProviderRuntimeIngestion.processor.tasks.ts` together with the task branch, because the throttle and the flushes need it in one place. To bring `ProviderRuntimeIngestion.processor.runtime.ts` from 401 to 385 lines, the session-status switch also moved into `ProviderRuntimeIngestion.lifecycle.ts` as `lifecycleSessionStatus`. Behavior is unchanged.
- **2026-10-16, Phase 2.3:** projections merge with `mergeTaskPatch`, which can never clear a field. That made the 3.9 rule ("a newer run reopens the task and clears `endedAt` and `resultSummary`") impossible to implement. A shared `mergeTaskSnapshot` (`@bigbud/shared/providerSubagents`) now drops stale end data when a terminal task reopens. It is used by the in-memory projector, the SQL projector and ingestion. For every other transition it behaves exactly like `mergeTaskPatch`.
- **2026-10-16, Phase 2.3:** the throttle measures time with Effect `Clock` (wall time), not provider timestamps. "Adapter stop or session teardown" is flushed through the `session.exited` and `session.state.changed` events that adapters emit on stop. Ingestion shutdown is flushed by a scope finalizer.
- **2026-10-16, Phase 2.4:** the 100-agent cap also applies to snapshot hydration (`mappers.store.ts`), not only to `mappers.lazy.store.ts`. This keeps the bound true on every path into the store.
- **2026-10-16, Phase 3.5:** a notification `summary` now maps to `resultSummary` for every Claude task, no longer to `progressSummary`. `task_type` no longer feeds `subagentType`; the two are stored separately (3.3).
- **2026-10-16, Phase 3.6:** a subagent `stream_event` is dropped entirely, and no separate in-memory heartbeat exists. Subagent liveness comes from `tool_progress` (3.7), `task_progress` and the subagent's own messages.
- **2026-10-16, Phase 3.7:** a `tool_progress` heartbeat updates the task only when the tool name changes, to bound event volume. Every emitted update still carries `activityFresh: true`.
- **2026-10-16, Phase 3.10:** the Claude adapter now emits each task snapshot (`task.updated`) before its lifecycle copy. Without that, a brand-new task had no owner yet, so the skip could not apply to its first lifecycle event, and a duplicate `task` row resulted. Lifecycle events still drive work-log activities.
- **2026-10-16, Phase 3 tests:** `FakeClaudeQuery` moved to `Adapter.test.helpers.query.ts`; `makeHarness` gained `serverSettings` and `resolveHarness` options.
- **2026-10-16, Phase 4 (G4):** G4 is not passed, so V2 native subagents stay denied (D1, item 5). Every G4 item needs frames from a paid live native probe, which D2 forbids, and no recorded child frames exist. Evidence and per-item status: [opencode-v2-subagent-evidence-2026-10-16.md](../validation/opencode-v2-subagent-evidence-2026-10-16.md); known limitation in `docs/reports/providers-opencode-v2.md`.
- **2026-10-16, Phase 4.1:** the observer runs at the end of a successful reconcile (`Runtime.recovery.ts`, after the hub restarts), so it covers both stream-triggered and repair-triggered reconciles. Observer events carry no top-level `turnId`: `ProviderTurnLiveness.observeEvent` only records events with one, so observer output is never turn liveness evidence. Forks (`SessionInfo.fork`) are excluded. Zero tokens or cost are shown as absent. A failed read keeps the last native revision and raises the ordinal, so the "last seen" demotion orders after the last observation.
- **2026-10-16, Phase 4.2:** child hints do not enqueue events, so they cannot consume the per-owner queue bounds. A hint sets a flag and goes through the existing coalesced repair queue (`scheduleRepair(owner, false)`, one queued repair per owner). Child text and reasoning deltas never hint. A child already bound to one owner is never rebound to another.

The async widget reports only the current tool, so a step starts when `currentTool` changes and the previous step is marked finished; "completed" there means the step ended, not that it succeeded.
