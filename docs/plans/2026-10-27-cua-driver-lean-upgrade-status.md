### M3 addendum: private Driver state, `--pid-file`, and the HOME decision

Decision: do **not** override `HOME`; move Driver-owned state with the two upstream overrides both versions honour, and pass `--pid-file` only to 0.38.

Evidence (upstream 0.38 `85e2b13…`, 0.9.1 `683e8b7…`, paths under `libs/cua-driver/rust/crates/`):

- `HOME` is needed by the allowed tools: `list_apps` and `launch_app` discover `~/Applications` through it (0.38 `platform-macos/src/apps/mod.rs:190-193,672-680,826-827`; 0.9.1 `apps/mod.rs:282-288,380-381`). A private `HOME` would hide user-installed apps on both versions, so the private-HOME option is rejected (a `<home>/Applications` symlink would work around it; not applied). TCC is by code identity and unaffected; the direct-capture consent check reads `~/Library/Group Containers/...ScreenCaptureApprovals.plist` only for an `.app` bundle (`capture_consent.rs:52-56,197-210`), which bigbud's bare binary is not.
- `CUA_DRIVER_RS_HOME` relocates the 0.38 Computer History root, so the persisted `admission.json` that can force installed-product verification before bind is read from the private dir (`history_runtime.rs:396-398,424-429`; startup `main.rs:601-606`), plus skills/extensions/release-channel state. 0.9.1 reads it for skills only (`skills.rs:145,165`): safe.
- `CUA_DRIVER_TELEMETRY_HOME` relocates telemetry config and install markers (0.38 `telemetry.rs:48,2240-2244`; 0.9.1 `telemetry.rs:46,1718-1722`). Set for both versions (trivial, verified).
- `--pid-file`: 0.38 honours it (`cli.rs:56`, `main.rs:671,1056`; written after bind, removed on shutdown, `serve.rs:969-976,1405-1408`; only a log hint in `serve.rs:2246-2257`, so it does not interact with the stale-socket fix). 0.9.1 parses it as a value flag (`cli.rs:181`) but `Command::Serve` has no field (`cli.rs:45-57,605-610`) and always uses `default_pid_file_path()` (`main.rs:340,453,644,660`), so 0.9.1 argv is kept byte-identical. `status`/`stop` stay socket-directed and unchanged.
- Telemetry: `CUA_DRIVER_TELEMETRY_HOME` moves telemetry's own `config.json` and install markers out of `~/.cua-driver` on both versions (0.38 `telemetry.rs:2253-2254`, 0.9.1 `telemetry.rs:1731-1732`). A 0.9.1-visible change, practically nil: telemetry is already forced off by env, so only marker locations move.
- Still shared by design (the real `HOME` stays): the Driver config `~/.cua-driver/config.json` is still **read** by `load_driver_config`, PiP and cursor motion defaults on both versions (0.38 `platform-macos/src/tools/mod.rs:725-735,915`, `pip-preview/src/lib.rs:21-25`, `cursor-overlay/src/motion_defaults.rs:78-80`; 0.9.1 `tools/mod.rs:216-219,388`), and never written (`set_config` is not allowed); the cursor-theme directory; `run_script`'s HOME read (`script_tool.rs:85-91`, a denied tool).

### 0.9.1-visible changes (all deliberate, all practically nil)

- Telemetry markers and telemetry's own `config.json` move to the private state home (#10). Telemetry is already forced off by env.
- A managed generation that **records** another version is skipped: with only such a generation, status is `missing` (Install offered) instead of `incompatible` (#11). Under pin 0.9.1 that only happens after a 0.38 install plus a pin rollback, where `previous.json` normally resolves first. Unknown-version pointers resolve exactly as before.
- When the endpoint holds a non-socket file, the daemon is not respawned and `lastError` says so (#12). Before, 0.9.1 unlinked whatever was there and bound. The endpoint lives in bigbud's private 0700 run dir, so this needs a foreign file planted there; Settings Repair (stop and start) creates a fresh run dir and recovers.
- Reinstalling the pin keeps the other version's rollback slot instead of making `previous.json` the last active (#7). Under 0.9.1 with no other-version generation this is the old behaviour.
