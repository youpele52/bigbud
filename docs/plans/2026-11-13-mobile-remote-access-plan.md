## Summary

Make mobile web a reliable, lightweight client of a selected desktop or VPS backend. Share a Rust mobile gateway between host deployments, while the owning TypeScript backend retains provider execution, authentication policy, command receipts and conversation persistence. A phone connects directly to a VPS without routing through a sleeping laptop. Refresh the mobile interface to match the current desktop experience using the React implementation in `apps/web`, with touch-appropriate layouts.

This plan depends on the remote runtime. Implementation is authorized by the subsequent user instructions recorded in the current checkpoint. Network diagnostics and UI work proceed in parallel; laptop-independent VPS chat needs the remote authority/lifecycle and optional mobile composition handoff.

## Problem

The user reports mobile works on the same network but fails outside it despite Tailscale. This has not been reproduced on a cellular-connected phone. Changing language cannot establish network reachability or wake a sleeping laptop.

The existing architecture also couples mobile access to a desktop-owned backend and stores one mobile session. VPS access must target the VPS authority itself. A small command payload still needs authentication, receipts, event catch-up and bounded flow control; a packet relay alone cannot guarantee safe execution.

## Goals

**Agreed network policy:** Tailscale is required on the phone and the target desktop or VPS. The phone must be signed in, connected and authorized to reach the target through the tailnet. Mobile access uses private HTTPS through Tailscale Serve, plus bigbud pairing and application scopes. Public access without Tailscale is out of scope.

- Pair and control an authorized host from cellular or another Wi-Fi network through verified HTTPS access.
- Connect directly to a running VPS while the laptop is powered off.
- Preserve uncertain-command reconciliation, approval scopes and bounded recovery.
- Use one Rust gateway implementation on desktop and VPS without duplicating conversation logic.
- Support multiple explicitly paired hosts with isolated drafts, credentials, cursors and UI caches.
- Match current desktop typography, surfaces, icons, transcript and composer, retaining mobile accessibility.

## Non-Goals

- Rewrite provider adapters, mobile React UI or orchestration in Rust.
- Create a custom VPN, hosted public relay or implicit public exposure.
- Guarantee phone background execution, wake sleeping desktops, or migrate desktop-owned conversations automatically.
- Proxy arbitrary URLs, full desktop RPC, provider callbacks, shell commands or cross-host orchestration through the mobile gateway.
- Treat Tailscale membership as sufficient application authorization.

### Phase 2: Specify And Prototype Shared Rust Gateway

Dependencies: phase 1 evidence; remote plan transport/identity contracts. Proposed new focused crate `crates/bigbud-mobile-gateway`, shared by desktop native deployment and VPS agent deployment. Keep it optional so terminal-only installations do not acquire mobile dependencies.

**Locked architecture decision:** Rust owns the mobile HTTP/WebSocket entry point, mobile asset serving, narrow route forwarding and bounded connection handling. TypeScript retains pairing authorization, provider execution, approvals and conversation storage, including existing command receipts and recovery semantics. Rust forwards requests to the private backend interface; it does not duplicate these state machines or grant authority independently. The same Rust component serves desktop and VPS deployments.

A separate TypeScript mobile-only listener and a Rust-versus-TypeScript comparison prototype are not requirements. The TS listener alternative was considered and rejected in favor of the user's explicit Rust transport preference. Validate the selected Rust design for protocol compatibility, security, resource limits and lifecycle behavior; measurements guide improvements rather than reopening the language decision.

Ownership:

| Component              | Responsibility                                                                                                                                     |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Rust gateway           | Narrow HTTP/WS routing, bounded streaming, connection health, local authenticated upstream attachment and diagnostics                              |
| Tailscale daemon/Serve | Tailnet reachability and TLS termination; configure explicitly, do not reimplement                                                                 |
| Owning TS backend      | Pairing/session issuance and revocation, authorization on each operation, command receipts, approvals, canonical conversation events and snapshots |
| Mobile React client    | Host selection, drafts, presentation, reconnect and catch-up through existing contracts                                                            |

Use the existing mobile RPC protocol unchanged in the first prototype. Rust must not decode and reimplement orchestration business rules. Expose only mobile static assets, pairing routes, `/mobile-ws` and narrowly reviewed mobile asset routes. Reject `/ws`, full client RPC, provider tool endpoints and arbitrary upstream destinations. Strip untrusted forwarding headers; use a configured external origin and trusted proxy boundary. Upstream endpoints are local, fixed and identity-checked.

Prefer host-served `/mobile/` assets on the same tailnet HTTPS origin. This reduces cross-origin browser dependencies. Keep the hosted mobile site as an explicitly tested compatibility path, not an assumed fix for private-network browser restrictions. No automatic Funnel/public exposure. Preserve other users' Serve routes; mutate only configuration owned by bigbud and support rollback.

Use owner-only local sockets on Unix and restricted pipes on Windows where supported; otherwise authenticated loopback with a startup-generated private credential and no unauthenticated fallback. The browser cannot open SSH or Unix sockets; Serve reaches the gateway, which reaches the local backend. Verify Windows transport support in the prototype rather than assuming Unix behavior transfers.

Start with explicit configurable budgets: 1 MiB inbound WS message, 4 MiB queued bytes per connection, 16 active connections, 10-second upstream connect deadline. Align with existing recovery envelopes before freezing these values; legitimate larger results need pagination, not unbounded buffering. Backpressure or close a slow connection with resumable recovery; never accumulate unbounded output. Rate-limit pairing attempts and authenticate before expensive subscriptions. Retain redaction and immediate backend revocation enforcement on existing sockets.

Exit: desktop and Linux VPS prototypes show protocol parity, rejection of broad routes, bounded memory under slow readers and safe failure when backend stops. Measure incremental archive size/RSS/latency before making footprint claims. Gateway contains no durable command queue or chat database.

### Phase 4: Reliable Delivery And Recovery Across Network Changes

Dependencies: phase 3 for multi-host coverage; existing-host fixes can ship earlier.

Preserve command IDs and backend receipts across disconnects. An acknowledgement lost after dispatch becomes uncertain; query outcome with the same authority and ID. Never generate a fresh turn on reconnect. Reconcile before allowing an ambiguous resend. The Rust gateway does not retry mutation requests.

Use one client reconnect controller with jittered bounded retries and explicit user retry, plus visibility/online resumption. Clear terminal auth failures until re-pairing; distinguish transport-connected from caught-up. Reuse atomic baseline-plus-event recovery and server epochs. Snapshot/replay gaps trigger bounded refresh, not repeated full-history downloads. Keep drafts through suspension without treating them as submitted work.

Validate revocation, expired sessions, server restart, gateway restart, stale approvals, two simultaneous clients and host switching. A backend death follows the remote plan's interrupted/unknown-outcome semantics; gateway recovery cannot promise live SDK continuation.

Exit: repeated Wi-Fi/cellular transitions, a 30-minute suspension and lost acknowledgements produce one accepted execution per command, no cross-host leakage and an accurate pending/uncertain/interrupted UI.
