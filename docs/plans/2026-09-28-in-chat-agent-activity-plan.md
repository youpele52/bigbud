## Summary

Show work delegated by an agent in its parent chat. Provider subagents use the existing tool-call card pattern from the supplied first screenshot: `SUBAGENTS (4)`, one visible agent row, and `SHOW 3 MORE` to expand the rest. Each row reveals who is working, its assignment, current status, latest observable action, and elapsed time. The view must represent parallel, sequential, and nested work, retain completed and failed work after reload, and let the user inspect the detail the integration actually provides. Subagent activity must not generate a bigbud toast or OS notification.

This covers two different execution mechanisms: **provider subagents** within a provider session and **bigbud delegated child threads** with their own conversations. They share a presentation surface but retain distinct identities, lifecycle rules, and detail views. Delegated children must be clickable from their parent chat. Prompts sent between threads, including handoffs, must show their true source thread as a clickable link so an agent-originated prompt cannot be mistaken for one written by the user. Pi support is required for both its supported extension-based subagent path and its bigbud `create_thread` delegation path.

## Problem

Providers can delegate work, sometimes in parallel or in a chain, yet bigbud's parent chat does not consistently show the child agents or their progress. The user may have to ask the parent whether an implementer is still working. A prose status reply is neither timely nor an authoritative lifecycle source.

The existing server already stores provider-neutral task records with optional agent relationships. The web model drops them. The selected-thread detail API returns only active tasks, so sequentially completed agents disappear after reload. The same task projection also contains ordinary plans and todos; treating every task as an agent would mislabel them. bigbud also persists standalone delegations, but current parent-chat watch links do not provide a complete, live account of delegated work. Messages submitted by one thread to another currently appear as ordinary user-role prompts without durable sender provenance. Initial delegation hides parent information inside prompt text, and handoff seeds carry a file path without a structured link to the source conversation.

## Goals

1. Show an Agents control in the parent chat for bigbud-delegated children and provider subagents whose actual integration has an explicit, documented source of subagent identity and activity. Show assignment, status, latest available action, elapsed time, and parent relationship only to the extent the source supplies them; expose further detail on demand.
2. Represent parallel, sequential, and nested agents individually. Retain recent terminal agents when the thread is reopened and restore accurate state after reconnect or restart.
3. Make Pi a required implementation path: consume structured progress from the installed Pi subagent extension when that extension is active, and show Pi-created bigbud child threads through durable delegation data. The same delegated-thread behavior applies to other providers that call `create_thread`.
4. Implement only evidence-backed mappings through each provider's actual integration. Do not make universal provider coverage an acceptance criterion. An unsupported provider keeps its existing parent chat without a fabricated Agents card.
5. Keep child output isolated from the parent assistant response and keep ordinary plans/todos out of the Agents view.
6. Never send a bigbud toast or OS notification for subagent lifecycle or progress.
7. Make each bigbud-delegated child clickable from the parent thread. For every parent-to-child or child-to-parent prompt, visibly identify that an agent in a named source thread sent it, with the source name linking to that thread. Apply the same source-link treatment to handoff prompts, including sequential handoffs between sibling threads. Preserve ordinary user prompts as visibly distinct.
8. Show in-provider subagent activity separately from main-agent activity. The main agent's status and blue indicator always take precedence, including when a child is also active. A child-only indicator requires fresh evidence; a persisted `running` record alone cannot keep it lit after restart or lost contact. If the main agent is available while a subagent continues, a new prompt is admitted under today's server rules. Subagent activity alone never adds a queue hold; existing approval, input, reservation, and recovery safeguards remain authoritative. Preserve today's Stop behavior, with no new cancellation cascade for provider subagents or standalone delegated bigbud threads.
9. Preserve existing queued-prompt merging. When a merged turn contains instructions from different source threads or the user, retain attribution for each source segment; never label the whole merged text as one agent's prompt. Existing completion-watch prompts are marked as automation and link to their contributing child threads. Automatic completion reports for delegated threads are optional; navigating to each clickable child is sufficient.

## Non-Goals

- Replacing bigbud's separate thread orchestration, sidebar, plan card, todo list, or existing whole-thread completion notifications.
- Changing provider selection, enabling delegation, or creating a new provider-independent subagent runtime.
- Adding child stop, message, or other controls without verified targeted support and authorization for that provider.
- Claiming a full transcript exists when an integration supplies only lifecycle or summary data.
- Treating an arbitrary Pi tool whose name contains “agent” as a structured subagent source.
- Inferring subagents from generic tool calls, background-process counts, session titles, model prose, parent busy status, or undocumented/private protocol shapes. Do not build a fallback adapter merely to claim coverage for every provider.
- Changing the provider-facing `user` role needed to execute a prompt merely to make an agent-sent message look different in the UI; message origin and execution role are separate concepts.
- Changing Stop/interrupt semantics or adding automatic cancellation of provider subagents. Standalone delegated bigbud threads remain separate entities.
- Adding a new automatic completion report from a delegated bigbud thread. Preserve any existing completion-watch behavior and label its injected prompt accurately.

## Risks And Decision Gates

- **Misclassification and scope:** Require both explicit provider documentation and matching installed event/read evidence. Default legacy and unknown records to ordinary tasks. Validate Pi extension `details` rather than trusting a name-based heuristic. Unsupported providers keep the existing parent-only view.
- **False lifecycle:** A delegation's creation state is not its child's workflow state. Do not silently mark active children done on parent turn completion, transport loss, or an empty progress update.
- **Availability and color:** A provider may hold the parent turn open while a child works, or may leave child work alive after parent interruption. Main-agent status always wins in the sidebar and chat. Preserve the main-turn dispatch lock and all current non-turn safety gates, plus current Stop semantics. Separate display activity from prompt admission; show child-only state only on fresh, authoritative child evidence and demote stale persisted `running` entries to last-seen/unknown. Use a semantic subagent activity token and a visible label/count, with contrast verified in both themes, so the distinction never depends on hue alone.
- **Mixed streams:** Preserve parent/child boundaries in included Copilot, Codex, OpenCode, Claude, and Pi mappings. Leave ACP parent behavior intact at this baseline. Keep the current parent message-coalescing fix and test its interaction with task-event delivery.
- **Load and size:** Bound recent history, detail fields, and query results. Inspect query plans before adding indexes or exposing child transcripts. Avoid full per-child transcripts in global snapshots.
- **Access and cleanup:** Check cross-project authorization, deletion, archived children, and links to unavailable threads. Reuse canonical deletion/projection behavior; do not create a separate lifecycle for delegated threads.
- **Origin integrity:** Use stable source thread IDs from trusted execution context, not display text or a supplied title. Validate client-built seed provenance against server-known lineage or handoff jobs; reject or omit unverified origin rather than accepting a forged link. Preserve origin through queueing, idempotent retries, thread-create seeds, orchestra assignments, and projection replay. Keep historical messages decodable and leave unverifiable old origins unlinked rather than guessing.
- **Compatibility and rollback:** Additive task fields must decode older events and projections. If one provider mapping fails validation, disable that mapping while preserving existing parent chat, tools, approvals, and turn completion. No provider upgrade or migration is assumed without its own evidence gate.
- **External/version gate:** Verify public provider documentation and installed SDK/CLI wire shapes before enabling each mapping. Pi extension subagents are visible when that documented extension is loaded; arbitrary third-party Pi extensions need their own documented, validated mapping. Newly documented ACP child activity can be planned later, not guessed into this release.
