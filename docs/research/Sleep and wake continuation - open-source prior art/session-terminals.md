# Session terminals: Mosh, Eternal Terminal, tmux, Zellij and WezTerm mux

Research date: 2026-10-22. Sources: mobile-shell/mosh at decd9b7 (2026-03-22), latest release mosh-1.4.0; MisterTea/EternalTerminal at 7ee361a (2026-10-19), latest release et-v7.0.0; tmux/tmux at 1c418f0 (2026-10-22), latest release 3.8; zellij-org/zellij at c7c4ce4 (2026-10-22), latest release v0.45.1; wezterm/wezterm at e2a98e1 (2026-10-10), latest release 20240203-110809-5046fc22. bigbud paths are at `main` a16a6a2. Tags: **[V]** verified in source at that commit, **[D]** from the repo's docs or man pages, **[I]** inferred.

## Answer

All five keep the remote shell in a process that does not depend on the client's connection, so a closed lid costs nothing on the remote side. That confirms D7. They split on how the client catches up. Mosh, tmux, Zellij and WezTerm send the current screen state (a diff against what the client is known to hold, or a full redraw) and never replay history. Eternal Terminal (ET) replays a sequence-numbered gap from a bounded buffer, and when the gap is too big it applies back-pressure to the shell rather than dropping bytes. bigbud's remote agent already has ET's model: sequence numbers, acks, a retained window and a replay-gap error. Two gaps stand out. A process whose unacknowledged output overflows 8 MiB during sleep cannot be reattached at all, because the attach fails before it returns the exit code. Results are also kept for only 600 s after the process ends. Zellij gives the clearest "never blindly replay" precedent: a resurrected session shows each command as "Waiting to run" until the user presses ENTER.

## Mosh (C++): state sync, not a byte stream

**What survives.** `mosh-server` owns the PTY and keeps running when the client vanishes. By default it waits for the client forever. `MOSH_SERVER_NETWORK_TMOUT` (seconds) makes it exit after that long without a client update, and `SIGUSR1` kills it, optionally only after `MOSH_SERVER_SIGNAL_TMOUT` seconds of silence. A server that never hears from any client exits after 60 s. [V: [mosh-server.cc#L394-L418](https://github.com/mobile-shell/mosh/blob/decd9b705eb81626f694335b8d5940538beb06da/src/frontend/mosh-server.cc#L394-L418), [#L717](https://github.com/mobile-shell/mosh/blob/decd9b705eb81626f694335b8d5940538beb06da/src/frontend/mosh-server.cc#L717), [#L886-L908](https://github.com/mobile-shell/mosh/blob/decd9b705eb81626f694335b8d5940538beb06da/src/frontend/mosh-server.cc#L886-L908), [#L943-L948](https://github.com/mobile-shell/mosh/blob/decd9b705eb81626f694335b8d5940538beb06da/src/frontend/mosh-server.cc#L943-L948); D: [mosh-server.1#L96-L122](https://github.com/mobile-shell/mosh/blob/decd9b705eb81626f694335b8d5940538beb06da/man/mosh-server.1#L96-L122)]

**How the client resyncs.** Each side holds a state object (screen for the server, keystroke list for the client). Every datagram carries `old_num`, `new_num`, `ack_num` and `throwaway_num` plus a diff from `old_num` to the current state. [V: [transportsender-impl.h#L306-L316](https://github.com/mobile-shell/mosh/blob/decd9b705eb81626f694335b8d5940538beb06da/src/network/transportsender-impl.h#L306-L316)] The sender diffs against the newest state it assumes the receiver has: a state sent within one timeout counts, otherwise it falls back to the last acknowledged one. [V: [transportsender-impl.h#L152-L156](https://github.com/mobile-shell/mosh/blob/decd9b705eb81626f694335b8d5940538beb06da/src/network/transportsender-impl.h#L152-L156), [#L255-L278](https://github.com/mobile-shell/mosh/blob/decd9b705eb81626f694335b8d5940538beb06da/src/network/transportsender-impl.h#L255-L278)] After a long cut, the first packet that gets through is one diff from the last acknowledged screen to the current one. Intermediate frames are never sent. The receiver drops a packet whose `new_num` it already has, or whose `old_num` it does not hold; the source comment calls this "part of how we enforce idempotency". [V: [networktransport-impl.h#L80-L109](https://github.com/mobile-shell/mosh/blob/decd9b705eb81626f694335b8d5940538beb06da/src/network/networktransport-impl.h#L80-L109)] Keystrokes are an ordered event list, and the diff carries only events past the acknowledged prefix, so input is applied exactly once. [V: [user.cc#L44-L71](https://github.com/mobile-shell/mosh/blob/decd9b705eb81626f694335b8d5940538beb06da/src/statesync/user.cc#L44-L71)]

**Roaming.** The server adopts the source address of any authenticated packet ("only client can roam"). The client switches to a new local port after 10 s without a round trip. The server stops sending after 40 s of silence ("Server now detached from client"), but keeps the session. [V: [network.cc#L388-L399](https://github.com/mobile-shell/mosh/blob/decd9b705eb81626f694335b8d5940538beb06da/src/network/network.cc#L388-L399), [#L523-L543](https://github.com/mobile-shell/mosh/blob/decd9b705eb81626f694335b8d5940538beb06da/src/network/network.cc#L523-L543), [network.h#L145-L146](https://github.com/mobile-shell/mosh/blob/decd9b705eb81626f694335b8d5940538beb06da/src/network/network.h#L145-L146)]

**Limits.** At most 32 sent states, with the middle ones dropped first. The receiver refuses new states beyond 1024 queued instead of acking and later discarding them. Empty acks go every 3 s. After 10 s without contact the sender stops retransmitting at frame rate. [V: [transportsender.h#L49-L54](https://github.com/mobile-shell/mosh/blob/decd9b705eb81626f694335b8d5940538beb06da/src/network/transportsender.h#L49-L54), [transportsender-impl.h#L211-L222](https://github.com/mobile-shell/mosh/blob/decd9b705eb81626f694335b8d5940538beb06da/src/network/transportsender-impl.h#L211-L222), [networktransport-impl.h#L111-L132](https://github.com/mobile-shell/mosh/blob/decd9b705eb81626f694335b8d5940538beb06da/src/network/networktransport-impl.h#L111-L132)] The session key reaches `mosh-client` only through `MOSH_KEY` and is not stored anywhere else, so a client process that dies cannot reattach. The server lives on with no way back in. [V: [mosh-client.cc#L167-L183](https://github.com/mobile-shell/mosh/blob/decd9b705eb81626f694335b8d5940538beb06da/src/frontend/mosh-client.cc#L167-L183), [mosh-server.cc#L450](https://github.com/mobile-shell/mosh/blob/decd9b705eb81626f694335b8d5940538beb06da/src/frontend/mosh-server.cc#L450)]

**What the user sees.** A blue bar across the top of the screen: "mosh: Last contact N seconds ago." after 6.5 s without hearing from the server, or "Last reply" when only the uplink is late (10 s). The counter ticks every second, then every 3 s after 60 s to save power. The client gives up only before the first contact ("Timed out waiting for server...", 15 s); after that it never times out. [V: [terminaloverlay.h#L159-L161](https://github.com/mobile-shell/mosh/blob/decd9b705eb81626f694335b8d5940538beb06da/src/frontend/terminaloverlay.h#L159-L161), [terminaloverlay.cc#L204-L245](https://github.com/mobile-shell/mosh/blob/decd9b705eb81626f694335b8d5940538beb06da/src/frontend/terminaloverlay.cc#L204-L245), [#L316-L322](https://github.com/mobile-shell/mosh/blob/decd9b705eb81626f694335b8d5940538beb06da/src/frontend/terminaloverlay.cc#L316-L322), [stmclient.cc#L536-L547](https://github.com/mobile-shell/mosh/blob/decd9b705eb81626f694335b8d5940538beb06da/src/frontend/stmclient.cc#L536-L547), [stmclient.h#L83-L86](https://github.com/mobile-shell/mosh/blob/decd9b705eb81626f694335b8d5940538beb06da/src/frontend/stmclient.h#L83-L86)]

## Eternal Terminal (C++): ack-by-reconnect, replay the gap

**What survives.** The shell runs under `etterminal`, and `etserver` routes client connections to it. The server's comment on the disconnected path reads "Disconnected: today's 64MB BackedWriter path, so a job keeps running after the laptop closes." `--disconnect-timeout` defaults to 0, meaning no timeout. [V: [TerminalServer.cpp#L494-L500](https://github.com/MisterTea/EternalTerminal/blob/7ee361a75fbb3e0900445b110188996fbe950823/src/terminal/TerminalServer.cpp#L494-L500), [#L650-L666](https://github.com/MisterTea/EternalTerminal/blob/7ee361a75fbb3e0900445b110188996fbe950823/src/terminal/TerminalServer.cpp#L650-L666), [TerminalServerMain.cpp#L82-L85](https://github.com/MisterTea/EternalTerminal/blob/7ee361a75fbb3e0900445b110188996fbe950823/src/terminal/TerminalServerMain.cpp#L82-L85)]

**How the client resyncs.** `BackedWriter` encrypts every packet, pushes it into a backup deque and increments `sequenceNumber`, whether or not a socket is attached. [V: [BackedWriter.cpp#L16-L46](https://github.com/MisterTea/EternalTerminal/blob/7ee361a75fbb3e0900445b110188996fbe950823/src/base/BackedWriter.cpp#L16-L46)] There are no per-packet acks while connected. The backup is trimmed only by size. On reconnect each side writes a `SequenceHeader` with the count of packets it has read. The peer answers with a `CatchupBuffer` of the packets after that count, and the reader queues them before reading the socket again. [V: [Connection.cpp#L141-L210](https://github.com/MisterTea/EternalTerminal/blob/7ee361a75fbb3e0900445b110188996fbe950823/src/base/Connection.cpp#L141-L210), [BackedWriter.cpp#L86-L114](https://github.com/MisterTea/EternalTerminal/blob/7ee361a75fbb3e0900445b110188996fbe950823/src/base/BackedWriter.cpp#L86-L114), [BackedReader.cpp#L116-L122](https://github.com/MisterTea/EternalTerminal/blob/7ee361a75fbb3e0900445b110188996fbe950823/src/base/BackedReader.cpp#L116-L122)] Errors that sleep produces are listed as reconnectable, with comments: `ENETDOWN` "Laptop woke up with the network down", `ENETUNREACH` "Network still coming up after a wake". [V: [Connection.cpp#L31-L49](https://github.com/MisterTea/EternalTerminal/blob/7ee361a75fbb3e0900445b110188996fbe950823/src/base/Connection.cpp#L31-L49)]

**Limits.** The backup holds 64 MiB while connected, plus 64 MiB written while disconnected. When the disconnected buffer is full, writes return `SKIPPED` and the server stops reading the PTY. The job blocks on its own output. No bytes are dropped. [V: [BackedWriter.hpp#L31-L34](https://github.com/MisterTea/EternalTerminal/blob/7ee361a75fbb3e0900445b110188996fbe950823/src/base/BackedWriter.hpp#L31-L34), [BackedWriter.cpp#L20-L25](https://github.com/MisterTea/EternalTerminal/blob/7ee361a75fbb3e0900445b110188996fbe950823/src/base/BackedWriter.cpp#L20-L25), [TerminalServer.cpp#L494-L503](https://github.com/MisterTea/EternalTerminal/blob/7ee361a75fbb3e0900445b110188996fbe950823/src/terminal/TerminalServer.cpp#L494-L503)] If the requested gap is older than the backup, `recover` throws "Client is too far behind server" and that reconnect fails. [V: [BackedWriter.cpp#L113](https://github.com/MisterTea/EternalTerminal/blob/7ee361a75fbb3e0900445b110188996fbe950823/src/base/BackedWriter.cpp#L113), [Connection.cpp#L211-L215](https://github.com/MisterTea/EternalTerminal/blob/7ee361a75fbb3e0900445b110188996fbe950823/src/base/Connection.cpp#L211-L215)]

**Identity for reattach.** The client sends a client id and proves it holds the passkey. The server answers `RETURNING_CLIENT` (catch up), `NEW_CLIENT`, `INVALID_KEY` (session gone, so the client stops) or `RETRY_LATER`. `RETRY_LATER` covers the 60 s after an `etserver` restart, while terminals re-register. [V: [ServerConnection.cpp#L83-L160](https://github.com/MisterTea/EternalTerminal/blob/7ee361a75fbb3e0900445b110188996fbe950823/src/base/ServerConnection.cpp#L83-L160), [ServerConnection.hpp#L134](https://github.com/MisterTea/EternalTerminal/blob/7ee361a75fbb3e0900445b110188996fbe950823/src/base/ServerConnection.hpp#L134), [ClientConnection.cpp#L210-L277](https://github.com/MisterTea/EternalTerminal/blob/7ee361a75fbb3e0900445b110188996fbe950823/src/base/ClientConnection.cpp#L210-L277)] When the shell survived but the buffers did not (an `etserver` restart, or a fresh client resuming a named session), both sides reset to sequence 0 under a new salt with an empty catchup. The gap is dropped, not guessed at. [V: [ServerConnection.cpp#L161-L201](https://github.com/MisterTea/EternalTerminal/blob/7ee361a75fbb3e0900445b110188996fbe950823/src/base/ServerConnection.cpp#L161-L201), [Connection.cpp#L159-L177](https://github.com/MisterTea/EternalTerminal/blob/7ee361a75fbb3e0900445b110188996fbe950823/src/base/Connection.cpp#L159-L177)] Named sessions save id and passkey to `~/.et/sessions`, written atomically with owner-only permissions. A separate control-session scrollback keeps a byte cursor and returns `truncated = true` when the reader fell behind the retained window. [V: [SessionStore.hpp#L12-L33](https://github.com/MisterTea/EternalTerminal/blob/7ee361a75fbb3e0900445b110188996fbe950823/src/terminal/SessionStore.hpp#L12-L33), [SessionScrollback.hpp#L11-L38](https://github.com/MisterTea/EternalTerminal/blob/7ee361a75fbb3e0900445b110188996fbe950823/src/terminal/SessionScrollback.hpp#L11-L38)]

**What the user sees.** Little. The client sends a keepalive every 5 s at most and drops the socket after one missed reply. The server's keepalive is 11 s. The client retries every second with no limit; only `INVALID_KEY` ends it, with "Session terminated". [V: [TerminalClient.cpp#L686-L697](https://github.com/MisterTea/EternalTerminal/blob/7ee361a75fbb3e0900445b110188996fbe950823/src/terminal/TerminalClient.cpp#L686-L697), [Headers.hpp#L225-L227](https://github.com/MisterTea/EternalTerminal/blob/7ee361a75fbb3e0900445b110188996fbe950823/src/base/Headers.hpp#L225-L227), [TerminalClient.cpp#L814](https://github.com/MisterTea/EternalTerminal/blob/7ee361a75fbb3e0900445b110188996fbe950823/src/terminal/TerminalClient.cpp#L814)]

## tmux (C): the server owns the session

On `SIGHUP` an attached client sets exit reason "lost tty" and tells the server it is exiting. [V: [client.c#L536-L541](https://github.com/tmux/tmux/blob/1c418f0b62d131b57d2e113362c2911867102652/client.c#L536-L541)] The server marks the client dead and removes it. The session and its panes keep running. [V: [server-client.c#L375-L392](https://github.com/tmux/tmux/blob/1c418f0b62d131b57d2e113362c2911867102652/server-client.c#L375-L392)] `destroy-unattached` defaults to off. [V: [options-table.c#L902-L909](https://github.com/tmux/tmux/blob/1c418f0b62d131b57d2e113362c2911867102652/options-table.c#L902-L909)] Reattach is `tmux attach -t <name>`. The server redraws the client from its own grid, so this is a full snapshot with no byte replay. [V: [server-client.c#L360-L366](https://github.com/tmux/tmux/blob/1c418f0b62d131b57d2e113362c2911867102652/server-client.c#L360-L366)] tmux has no network layer. Over SSH, the SSH session dies and the user reattaches by hand.

## Zellij (Rust): detach is free; resurrection does not re-run commands

**What survives.** The native client maps `SIGHUP` (like `SIGTERM`, `SIGINT` and `SIGQUIT`) to quit and sends `ClientExited`. [V: [os_input_output_unix.rs#L40-L43](https://github.com/zellij-org/zellij/blob/c7c4ce42b8663dad464c03b92a7949ad58c68c55/zellij-client/src/os_input_output_unix.rs#L40-L43), [lib.rs#L1518-L1520](https://github.com/zellij-org/zellij/blob/c7c4ce42b8663dad464c03b92a7949ad58c68c55/zellij-client/src/lib.rs#L1518-L1520)] The server removes that client and keeps the session. Only `KillSession` breaks the server loop. [V: [zellij-server/src/lib.rs#L4387-L4440](https://github.com/zellij-org/zellij/blob/c7c4ce42b8663dad464c03b92a7949ad58c68c55/zellij-server/src/lib.rs#L4387-L4440)] The web client reconnects with delays of 1, 2, 4, 8 and then 16 s, shown in a modal with a cancel button. When the server answers, it reloads the page and gets a fresh render, not a replay. ## WezTerm mux (Rust): re-list, then pull current lines

**Reconnect.** Only TLS domains reconnect automatically. Unix domains do not ("respawning it would not preserve the set of tabs"). SSH domains do not either, because the client cannot yet tell a network drop from the user closing the last shell. [V: [client.rs#L632-L646](https://github.com/wezterm/wezterm/blob/e2a98e1b8af156988ad0ac778658ac27b60a55fb/wezterm-client/src/client.rs#L632-L646)] The TLS loop opens a "wezterm: Reconnecting..." window. It retries with backoff from 1 s doubling to 10 s, with no attempt limit, and passes `no_auto_start` so a reconnect never starts a fresh server. A clean EOF stops it. [V: [client.rs#L1049-L1108](https://github.com/wezterm/wezterm/blob/e2a98e1b8af156988ad0ac778658ac27b60a55fb/wezterm-client/src/client.rs#L1049-L1108)] The same `ClientId` is sent again after each connect. [V: [client.rs#L1046](https://github.com/wezterm/wezterm/blob/e2a98e1b8af156988ad0ac778658ac27b60a55fb/wezterm-client/src/client.rs#L1046), [#L1166-L1170](https://github.com/wezterm/wezterm/blob/e2a98e1b8af156988ad0ac778658ac27b60a55fb/wezterm-client/src/client.rs#L1166-L1170)]

**Resync is a snapshot.** The PDU `serial` is only a request/response id. In-flight requests are failed on a decode error, not resent. [V: [codec/src/lib.rs#L96-L101](https://github.com/wezterm/wezterm/blob/e2a98e1b8af156988ad0ac778658ac27b60a55fb/codec/src/lib.rs#L96-L101), [client.rs#L404-L427](https://github.com/wezterm/wezterm/blob/e2a98e1b8af156988ad0ac778658ac27b60a55fb/wezterm-client/src/client.rs#L404-L427)] `ClientDomain::reattach` calls `list_panes` because "another client connected and adjusted the set of tabs since we were connected, so we need to re-sync". [V: [domain.rs#L462-L473](https://github.com/wezterm/wezterm/blob/e2a98e1b8af156988ad0ac778658ac27b60a55fb/wezterm-client/src/domain.rs#L462-L473)] The server tracks a `seqno` per pane in a `PerPane` that belongs to the connection's `SessionHandler`, and sends the lines changed since that seqno. A new connection starts from zero, so the first response marks the whole viewport dirty. [V: [sessionhandler.rs#L39-L50](https://github.com/wezterm/wezterm/blob/e2a98e1b8af156988ad0ac778658ac27b60a55fb/wezterm-mux-server-impl/src/sessionhandler.rs#L39-L50), [#L87-L95](https://github.com/wezterm/wezterm/blob/e2a98e1b8af156988ad0ac778658ac27b60a55fb/wezterm-mux-server-impl/src/sessionhandler.rs#L87-L95), [#L209-L233](https://github.com/wezterm/wezterm/blob/e2a98e1b8af156988ad0ac778658ac27b60a55fb/wezterm-mux-server-impl/src/sessionhandler.rs#L209-L233), [dispatch.rs#L59](https://github.com/wezterm/wezterm/blob/e2a98e1b8af156988ad0ac778658ac27b60a55fb/wezterm-mux-server-impl/src/dispatch.rs#L59); I that seqno 0 yields all lines] The response has `dirty_lines`, `bonus_lines` and `seqno`, and the client fetches the rest with `GetLines`. [V: [codec/src/lib.rs#L914-L929](https://github.com/wezterm/wezterm/blob/e2a98e1b8af156988ad0ac778658ac27b60a55fb/codec/src/lib.rs#L914-L929)]

**What the user sees.** "wezterm: Ns⏳since last response", in white on blue at the top right of the pane. It appears when nothing has arrived for 3 s (or the poll interval, if longer) and the client has sent since. ## Comparison

## For bigbud

The remote agent already has most of ET's machinery. `OperationSnapshot` has `next_sequence` and `first_retained_sequence`, and `replay_from` returns `ReplayGap`. Clients acknowledge to trim, a same-id, same-digest re-accept returns the existing operation's output and result without starting it again, and after an agent restart every non-terminal operation is marked `Expired` with `AGENT_RESTARTED` instead of being re-run (`crates/bigbud-remote-agent/src/operations/core.rs`, `operations/registry.rs` `accept`, `replay_from`, `expire_non_terminal`, `session/process_handlers.rs` duplicate path, `session/core.rs` journal restore). PTY input uses a sequence and digest ledger (`pty/input.ledger.rs`), the same exactly-once property as Mosh's keystroke stream.

1. **Confirms D7 (Rust).** Every tool keeps the work in a server process that outlives the link, and none restarts work on reconnect. WezTerm passes `no_auto_start` on reconnect, and ET resets an unknown gap instead of guessing. The agent's `AGENT_RESTARTED` expiry and the TypeScript "missing or expired history does not authorize replay" error (`apps/server/src/remote-agent/remoteAgentProcessClient.ts`) are the same rule.
2. **Adds to D7: process attach should degrade like PTY attach, not fail (Rust).** `handle_pty_attach` returns the snapshot with `replay_gap = true` when the cursor is too old (`session/pty_handlers.rs`). `handle_process_attach` calls `replay_from` first and returns an error on `ReplayGap`, so the snapshot and `ProcessCompleted` (exit code) are never sent (`session/process_handlers.rs:292`). Retained output is evicted oldest-first above 8 MiB per operation (`operations/registry.rs:99`, `session/core.rs`), and nothing acks during sleep. So a chatty build on a sleeping laptop will most likely come back as `PROCESS_REPLAY_ERROR`, which the TypeScript client maps to a connection error. [I from source; not run] Raising an error on purpose is already the TypeScript rule: a test expects `PROCESS_OUTPUT_GAP` even when the operation completed (`remoteAgentProcessClient.reconnect.test.ts`). The missing part is evidence. Return the snapshot, the tail and the terminal result with `output_truncated`, the way ET's `SessionScrollback` returns data plus `truncated`. Then the prompt can say "finished with exit 0, output partly lost" instead of "unknown". ET's other option, pausing the producer when the buffer is full, does not suit an agent's tool runs.
3. **Adds to D7: the retention horizon is shorter than a sleep (Rust).** Mosh and ET keep sessions forever by default. bigbud keeps process and PTY results for 600 s after the process ends (`PROCESS_RESULT_RETENTION`, `PTY_RESULT_RETENTION` in `session/core.rs`). The Retention journal record carries the same deadline, so a lid closed for 30 minutes after a command finished leaves "unknown or expired", which becomes the uncertain prompt. Phase 6's exit test uses a 10-minute sleep, which is right at this edge. Keep the terminal result (state and exit code, a few bytes) much longer than the output bytes, for example 24 h or until acknowledged.
4. **Adds to D4: Zellij is the UI precedent for "ask, don't re-run".** Resurrected commands are held, named on screen, and run only on ENTER. The other choices are a shell or exit, and the bypass is an explicit flag. Phase 6's resolution prompt should likewise name the exact command and offer run again, skip, or stop. Any future rerun allowlist should be an explicit opt-in, like `--force-run-commands`. TypeScript and the UI own this.
5. **Adds to D1: replay is safe only where the receiver deduplicates.** Mosh and ET replay freely because sequence numbers make the receiver idempotent. Model providers and tool executors do not deduplicate, which is why D1's `may-have-been-sent` marker is needed for them. Inside bigbud's own protocol, keep using sequence-plus-digest (process accept, PTY input) so transport retries stay safe.
6. **Adds to D3 (Rust transport, TypeScript classification).** ET treats `ENETDOWN`, `ENETUNREACH` and similar errors as reconnectable, with comments naming laptop wake. All four network tools use short application keepalives (Mosh 3 s acks and a 6.5 s banner, ET 5 s and 11 s, WezTerm 3 s) instead of TCP timeouts. Classify these errno values near a resume as `interrupted-by-sleep`, and detect a dead SSH link with the agent's heartbeat, not TCP. WezTerm will not auto-reconnect SSH domains because it cannot tell a network drop from a closed shell. bigbud can tell, because the agent reports a terminal state, so base the decision on that and not on the SSH exit.
7. **Adds to D5: keep the transport reconnect loop separate from recovery attempts.** Mosh, ET and WezTerm retry the link forever (ET every 1 s; WezTerm 1 to 10 s). Zellij's web client keeps retrying until the user cancels. Parking after 3 attempts should count failed continuation decisions, not reconnect attempts, or a 20-minute network outage will park a turn that would have reattached fine.
8. **Adds to reattach identity (D4, D7).** ET separates "known client, catch up", "server restarted, resync from zero", "retry later (grace window)" and "session gone". The agent already exposes `agent_instance_id` (`agent-<pid>`, `session/core.rs`). The TypeScript side should map it the same way: same instance and operation known means attach; same instance and operation unknown means result lost, so prompt; new instance means operations expired, so prompt; unreachable means keep the intent and retry.
9. **Confirms D8.** Every resync engine here is native and has fixed bounds (state queues, 64 MiB buffers, per-pane seqno). bigbud's journal (64 MiB cap, `operations/journal.rs`) and registries are already in Rust. The decision about what to do with a gap or an uncertain result stays in TypeScript.
