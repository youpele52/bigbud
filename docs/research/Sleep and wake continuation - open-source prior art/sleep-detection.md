# Detecting sleep and wake: Electron, OS clocks, Rust and Tauri

Research date: 2026-10-22. Sources: electron/electron at 3b24d8f (2026-10-22), latest release v45.0.0. Also chromium/chromium at e1b5da7 (2026-10-22), libuv/libuv at e36964a (2026-10-21, latest release v1.53.0), nodejs/node at 1c12ff1 (2026-10-22), rust-lang/rust at c303e41 (2026-10-22), tauri-apps/tao at 9977d58 (2026-10-20), tailscale/tailscale at f8ad538 (2026-10-22, latest release v1.104.2), microsoft/vscode at 171a964 (2026-10-22). bigbud at a16a6a2a96.

## Answer

Trust `resume`, not `suspend`. On macOS and Windows, Electron delivers `suspend` to JavaScript through a posted task after Chromium has already let the OS sleep, and on Linux it releases its logind delay lock as soon as the synchronous emit returns. Chromium also drops a `resume` that was not preceded by a `suspend`, so a missed suspend hides the resume too. A server-side gap detector is therefore needed on every OS, not only on Linux without logind. The detector must account for a clock fact that bigbud's current code gets wrong: Node's `performance.now()` keeps counting through sleep on macOS (libuv uses `mach_continuous_time`), as it does on Windows. Only on Linux does it stop. The most robust native signal is a per-OS "time spent suspended" counter. It is a few lines of Rust, works without logind or a window, and is immune to wall-clock changes.

## How Electron implements suspend and resume

- **macOS.** Suspend and resume come from Chromium's `base::PowerMonitor`, which calls `IORegisterForSystemPower`. On `kIOMessageSystemWillSleep` it posts a suspend event and then immediately calls `IOAllowPowerChange`. On `kIOMessageSystemWillPowerOn` it posts resume ([power_monitor_device_source_mac.mm#L107-L130](https://github.com/chromium/chromium/blob/e1b5da71892a0825f7f0987ae2e073116099c2be/base/power_monitor/power_monitor_device_source_mac.mm#L107-L130)). Electron's own macOS code adds only lock, unlock and session events through `NSDistributedNotificationCenter` and `NSWorkspace` ([electron_api_power_monitor_mac.mm#L30-L59](https://github.com/electron/electron/blob/3b24d8f7f6246b6899cf594b0969c4087a3cd301/shell/browser/api/electron_api_power_monitor_mac.mm#L30-L59)).
- **Windows.** Chromium creates a hidden message window and maps `WM_POWERBROADCAST` `PBT_APMSUSPEND` to suspend and `PBT_APMRESUMEAUTOMATIC` to resume. It ignores `PBT_APMRESUMESUSPEND` ([power_monitor_device_source_win.cc#L28-L56](https://github.com/chromium/chromium/blob/e1b5da71892a0825f7f0987ae2e073116099c2be/base/power_monitor/power_monitor_device_source_win.cc#L28-L56)). It calls `RegisterSuspendResumeNotification` because "on machines with modern standby" that is "required in order to get the PBT_APMSUSPEND message" ([#L117-L120](https://github.com/chromium/chromium/blob/e1b5da71892a0825f7f0987ae2e073116099c2be/base/power_monitor/power_monitor_device_source_win.cc#L117-L120)). Lock and unlock come from WTS session notifications ([electron_api_power_monitor_win.cc#L16-L41](https://github.com/electron/electron/blob/3b24d8f7f6246b6899cf594b0969c4087a3cd301/shell/browser/api/electron_api_power_monitor_win.cc#L16-L41)). Microsoft documents that an app gets "approximately two seconds" to handle `PBT_APMSUSPEND` ([docs](https://learn.microsoft.com/en-us/windows/win32/power/pbt-apmsuspend)).
- **Linux.** Chromium has no desktop Linux source, so Electron subscribes to logind's `PrepareForSleep` on the system bus. When logind appears, Electron takes an `Inhibit("sleep", <exe name>, "Application cleanup before suspend", "delay")` lock ([power_observer_linux.cc#L68-L90](https://github.com/electron/electron/blob/3b24d8f7f6246b6899cf594b0969c4087a3cd301/shell/browser/lib/power_observer_linux.cc#L68-L90)). On `PrepareForSleep(true)` it calls `OnSuspend()` and then releases the lock at once. On `false` it takes a new lock and then calls `OnResume()` ([#L144-L160](https://github.com/electron/electron/blob/3b24d8f7f6246b6899cf594b0969c4087a3cd301/shell/browser/lib/power_observer_linux.cc#L144-L160)). On Linux the emit is synchronous, but anything asynchronous started in the handler is not waited for. logind caps any delay lock at `InhibitDelayMaxSec`, which "Defaults to 5" seconds ([logind.conf](https://www.freedesktop.org/software/systemd/man/latest/logind.conf.html)).
- **Without logind.** If there is no system bus, Electron logs "Failed to get system bus connection". If login1 never appears, it logs "not available" and emits nothing ([#L42-L46](https://github.com/electron/electron/blob/3b24d8f7f6246b6899cf594b0969c4087a3cd301/shell/browser/lib/power_observer_linux.cc#L42-L46), [#L68-L72](https://github.com/electron/electron/blob/3b24d8f7f6246b6899cf594b0969c4087a3cd301/shell/browser/lib/power_observer_linux.cc#L68-L72)). elogind implements the same `org.freedesktop.login1` interface standalone (per its README), so non-systemd distributions that ship elogind should behave the same. I did not test this.
- **Lazy start.** The native monitor, and with it the Linux delay lock, is created only when the first `powerMonitor` listener is added ([power-monitor.ts#L15-L19](https://github.com/electron/electron/blob/3b24d8f7f6246b6899cf594b0969c4087a3cd301/lib/browser/api/power-monitor.ts#L15-L19)). bigbud registers at startup, so this is fine.

### Why `suspend` is late, and why `resume` can go missing

- Chromium delivers suspend and resume through `ObserverListThreadSafe::Notify`. Its own docs say that notifications "will always be done via PostTask()" and that "You cannot assume that at the completion of the Notify call that all Observers have been Notified" ([observer_list_threadsafe.h#L54-L57](https://github.com/chromium/chromium/blob/e1b5da71892a0825f7f0987ae2e073116099c2be/base/observer_list_threadsafe.h#L54-L57), [#L225-L230](https://github.com/chromium/chromium/blob/e1b5da71892a0825f7f0987ae2e073116099c2be/base/observer_list_threadsafe.h#L225-L230)). On macOS, `IOAllowPowerChange` runs straight after the post, so the JavaScript `suspend` handler can run after wake.
- `PowerMonitor::NotifyResume` notifies only if `is_system_suspended_` is set, and only `NotifySuspend` sets it ([power_monitor.cc#L196-L231](https://github.com/chromium/chromium/blob/e1b5da71892a0825f7f0987ae2e073116099c2be/base/power_monitor/power_monitor.cc#L196-L231)). On macOS and Windows, a lost suspend also means a lost resume. The Linux path calls Electron's observer directly and skips this guard.

## Clocks during sleep

| Clock                                                    | macOS                                     | Linux                                | Windows                                  |
| -------------------------------------------------------- | ----------------------------------------- | ------------------------------------ | ---------------------------------------- |
| Node `performance.now()`, `process.hrtime`, libuv timers | **counts sleep** (`mach_continuous_time`) | stops (`CLOCK_MONOTONIC`)            | counts sleep (`QueryPerformanceCounter`) |
| Node `Date.now()`                                        | wall clock, includes sleep, can jump      | same                                 | same                                     |
| Node `os.uptime()`                                       | wall-based boot time                      | `/proc/uptime`, **includes suspend** | not checked                              |
| Rust `Instant`                                           | stops (`CLOCK_UPTIME_RAW`)                | stops (`CLOCK_MONOTONIC`)            | counts sleep (QPC)                       |

- On macOS, `uv__hrtime` returns `mach_continuous_time()` ([darwin.c#L60-L63](https://github.com/libuv/libuv/blob/e36964a094fadba7926e88fe333dd1d6a6baf13c/src/unix/darwin.c#L60-L63)). That clock increments "including while the system is asleep", while `mach_absolute_time` "does not increment while the system is asleep" (Apple documentation). The switch landed in libuv commit 4685be2 in 2020 (fixing libuv#2891, closed), so it is in every Node bundled with current Electron. bigbud uses Electron 40.6.0, and the server runs as `ELECTRON_RUN_AS_NODE`.
- Linux uses `CLOCK_MONOTONIC`, or `CLOCK_MONOTONIC_COARSE` for loop time ([linux.c#L1661-L1695](https://github.com/libuv/libuv/blob/e36964a094fadba7926e88fe333dd1d6a6baf13c/src/unix/linux.c#L1661-L1695)). Windows uses QPC ([win/util.c#L464-L483](https://github.com/libuv/libuv/blob/e36964a094fadba7926e88fe333dd1d6a6baf13c/src/win/util.c#L464-L483)). The loop time that drives `setTimeout` comes from the same `uv__hrtime` ([unix/internal.h#L471-L475](https://github.com/libuv/libuv/blob/e36964a094fadba7926e88fe333dd1d6a6baf13c/src/unix/internal.h#L471-L475), [win/core.c#L329-L333](https://github.com/libuv/libuv/blob/e36964a094fadba7926e88fe333dd1d6a6baf13c/src/win/core.c#L329-L333)). Node's `performance.now()` is `uv_hrtime()` ([node_perf.cc#L375-L378](https://github.com/nodejs/node/blob/1c12ff166756c8ddd830cb4742953314065fcacc/src/node_perf.cc#L375-L378)).
- On Linux, `os.uptime()` reads `/proc/uptime`, which `proc_uptime(5)` describes as uptime "including time spent in suspend". If that read fails, it falls back to `CLOCK_BOOTTIME` ([linux.c#L1733-L1750](https://github.com/libuv/libuv/blob/e36964a094fadba7926e88fe333dd1d6a6baf13c/src/unix/linux.c#L1733-L1750), [node_os.cc#L172-L182](https://github.com/nodejs/node/blob/1c12ff166756c8ddd830cb4742953314065fcacc/src/node_os.cc#L172-L182)).
- Rust documents the platform calls and says that "it is also not specified whether system suspends count as elapsed time" ([time.rs#L56-L57](https://github.com/rust-lang/rust/blob/c303e414dd813ab090055754d0be647054fce70a/library/std/src/time.rs#L56-L57), [#L111-L119](https://github.com/rust-lang/rust/blob/c303e414dd813ab090055754d0be647054fce70a/library/std/src/time.rs#L111-L119)). The related issues are rust-lang/rust#87906 (open) and #79462 (open; it quotes Microsoft: QPC counts "sleep... standby, hibernate, or connected standby"). Two PRs to switch to `CLOCK_BOOTTIME`, #87907 and #88714, were closed unmerged, partly because Go chose the opposite approach (golang/go#24595 closed, #36141 open).
- Practical consequence: on macOS and Windows, every pending Node timer in the server fires right at wake once the sleep is longer than the timer. On Linux, timers are pushed back by the sleep length. Provider SDK timeouts behave the same way.

### The wall-versus-monotonic technique in practice

- Tailscale polls wall time every 15 s and strips Go's monotonic reading with `time.Now().Round(0)`. It reports a jump when wall time advanced more than 1.5 times the interval. It treats only jumps of 10 minutes or more as major, because macOS "DarkWake maintenance cycles of ~55s" are common ([netmon.go#L28-L42](https://github.com/tailscale/tailscale/blob/f8ad538a3ba0b905c87688c3bc881d20e232a644/net/netmon/netmon.go#L28-L42), [#L703-L741](https://github.com/tailscale/tailscale/blob/f8ad538a3ba0b905c87688c3bc881d20e232a644/net/netmon/netmon.go#L703-L741)). This is the same design as bigbud's Electron-main poll (10 s interval, 30 s gap).
- VS Code exposes `onDidSuspendOS` and `onDidResumeOS` ([nativeHostMainService.ts#L137-L138](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/platform/native/electron-main/nativeHostMainService.ts#L137-L138)). In this checkout their only consumer is telemetry ([app.ts#L1731-L1737](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/code/electron-main/app.ts#L1731-L1737)). Remote reconnection relies on socket timeouts, not on power events.

## Tauri

tao's `Event::Suspended` and `Event::Resumed` are mobile app-lifecycle events, documented as "Linux / macOS / Windows: Unsupported" ([event.rs#L300-L317](https://github.com/tauri-apps/tao/blob/9977d585ba364d1812db37218c0d9e6a953a7db4/src/event.rs#L300-L317)). A code search of the tauri-apps organisation for `PBT_APMSUSPEND`, `PrepareForSleep` and `IORegisterForSystemPower` returned nothing. Tauri, tao and wry expose no system suspend or resume.

## Native options, Linux without logind, and Rust crates

- Without logind or elogind, an unprivileged desktop app has no suspend event that I could find. Hooks in `/usr/lib/systemd/system-sleep/` need root and systemd. I found no notification mechanism on `/sys/power`. NetworkManager's sleep state is itself fed by logind (from documentation; not verified in NetworkManager source). What remains is clock comparison and network transitions.
- **Per-OS "time suspended so far" counters** grow only while the machine sleeps. They need no subscription, no window and no logind, and they ignore NTP or manual clock changes:
  - Linux: `CLOCK_BOOTTIME` minus `CLOCK_MONOTONIC`. In pure Node, this is the `os.uptime()` delta minus the `performance.now()` delta, at 10 ms resolution.
  - macOS: `mach_continuous_time` minus `mach_absolute_time`. This is native only, because Node exposes only the first.
  - Windows: `QueryInterruptTime` minus `QueryUnbiasedInterruptTime`. Microsoft says the unbiased count does "not include time the system spends in sleep or hibernation" ([docs](https://learn.microsoft.com/en-us/windows/win32/api/realtimeapiset/nf-realtimeapiset-queryunbiasedinterrupttime)). This is native only.
- **Verified crates on crates.io** (2026-10-22):
  - `zbus` 6.0.0; `logind-zbus` 5.3.2, whose `ManagerProxy` has `receive_prepare_for_sleep` and `inhibit`; `zbus_systemd`.
  - `windows-sys` 0.61.2, which has `RegisterSuspendResumeNotification`, `PowerRegisterSuspendResumeNotification` (callback form, needs no window), `QueryUnbiasedInterruptTime` and `QueryInterruptTime`.
  - `objc2-io-kit` 0.3.2, which has `IORegisterForSystemPower`.
  - `keepawake` 0.6.1, which prevents sleep but does not detect it.
  - `system_shutdown` 4.1.0, which performs shutdowns and does not detect them.
  - No crate named `power-events` or `sleep-monitor` exists.
  - bigbud's `bigbud-desktop-supervisor` and `bigbud-system` depend on none of these today.

## Network signals

- `net.isOnline()` is `!NetworkChangeNotifier::IsOffline()` ([electron_api_net.cc#L25-L27](https://github.com/electron/electron/blob/3b24d8f7f6246b6899cf594b0969c4087a3cd301/shell/common/api/electron_api_net.cc#L25-L27)). The docs say that `false` "is a pretty strong indicator" of being offline, but `true` "is inconclusive" ([net.md#L125-L133](https://github.com/electron/electron/blob/3b24d8f7f6246b6899cf594b0969c4087a3cd301/docs/api/net.md#L125-L133)). It always returned `true` in utility processes until #48100 (closed 2025-08-22). Calling it from main, as bigbud does, is the supported path. Electron main has no network-change event, so polling is needed.
- MDN on `navigator.onLine`: LAN, or "virtual ethernet adapters that are always connected", counts as online, while on Windows a blocked Microsoft probe can read as offline. The property is "inherently unreliable".

## For bigbud

- **Confirms D2, with a change in emphasis.** Treat `resume` as the anchor and `suspend` as an optional hint. A missed suspend also suppresses resume on macOS and Windows ([power_monitor.cc#L215-L231](https://github.com/chromium/chromium/blob/e1b5da71892a0825f7f0987ae2e073116099c2be/base/power_monitor/power_monitor.cc#L215-L231)), so the gap detector is a backup on every OS, not only Linux. Today the hints reach only renderer windows ([connectivitySignals.main.ts#L20-L24](../../../apps/desktop/src/connectivity/connectivitySignals.main.ts)), and nothing in `apps/server` consumes them. Sending them straight to the server is still to be built. On Linux, write the suspend hint synchronously inside the handler, because the delay lock is released when the handler returns. TypeScript.
- **Adds to D2 (bug).** The server's `EventLoopLagMonitor` defaults `monotonicIncludesSleep` to Windows only ([EventLoopLagMonitor.ts#L55](../../../apps/server/src/connection-diagnostics/Layers/EventLoopLagMonitor.ts)). Its comment says the macOS monotonic clock stops during sleep ([EventLoopLagMonitor.logic.ts#L48-L59](../../../apps/server/src/connection-diagnostics/EventLoopLagMonitor.logic.ts)). Under Electron-as-Node it does not, so a macOS lid-close will be reported as a `stalled` event lasting the whole sleep, with no `system-sleep` record. I verified this by reading the source; I did not run it. Fix: treat `darwin` like `win32`. On Linux, add the missing branch, where sleep shows as wall delta minus monotonic delta and is not seen at all today. Better still, on Linux compare `os.uptime()` with `performance.now()` so that wall-clock steps cannot fake a sleep. TypeScript.
- **Adds to D2: thresholds and debounce.**
  - Keep the 250 ms sampler.
  - Classify as sleep when the suspended-time delta is at least 5 s on Linux (precise).
  - On macOS and Windows, classify as sleep when the gap is at least 30 s, CPU is under 5 %, and the wall and monotonic clocks agree (the existing rule).
  - Collapse duplicate `resume` events and detector hits into one "sleep epoch", keyed by the estimated sleep start (`now - gap`), instead of a fixed 1 s window. Windows and Debian double fires (#44252) can be further apart than that.
  - Tailscale's DarkWake note argues against starting recovery for gaps under about 60 s unless a turn actually failed.
- **Adds to D3.** On macOS and Windows, provider and heartbeat timeouts fire all at once at wake, so the `interrupted-by-sleep` window must also include timeout errors raised in the first seconds after the epoch, not only socket errors. Anchor the window on the epoch's estimated start and end, not on receiving `suspend`. TypeScript.
- **Adds to D4.** Use `net.isOnline()` only to trigger a retry on an offline-to-online transition. Gate the actual continuation on a real probe of the provider endpoint or SSH host, because `true` is inconclusive.
- **Adds to D8.**
  - A small "suspended time" reader is a good bounded Rust piece. It suits `bigbud-desktop-supervisor`, which the server already runs as a sidecar. Use `libc::clock_gettime(CLOCK_BOOTTIME/MONOTONIC)` on Linux, `mach_continuous_time`/`mach_absolute_time` on macOS, and `QueryInterruptTime`/`QueryUnbiasedInterruptTime` via `windows-sys` on Windows. The server reads it on each sampler tick or on any transport error. TypeScript still decides.
  - Native event subscriptions (logind through `logind-zbus`, `PowerRegisterSuspendResumeNotification`, `IORegisterForSystemPower`) only duplicate Electron. They are worth adding only for a headless or web-only server.
  - Tauri offers nothing here.
  - Note that the supervisor's `Instant`-based ack timeouts ([main.rs#L115](../../../crates/bigbud-desktop-supervisor/src/main.rs)) will expire at wake on Windows, because QPC counts sleep, but not on macOS or Linux.
