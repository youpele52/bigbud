# Sleep and wake continuation: open-source prior art

Research date: 2026-10-22. No code was changed. Each linked note gives the commit SHA, the latest release and line permalinks for every claim. Nothing was run across a real sleep; all behaviour comes from reading source, docs and changelogs, and each note labels which is which.

This folder adds to [Durable connections - OpenCode, Pi and a Rust layer](../Durable%20connections%20-%20OpenCode,%20Pi%20and%20a%20Rust%20layer/README.md). It does not repeat OpenCode's service resume, Pi Durable or the Rust socket proxy. The plan it serves is Phase 6 (and Phase 2) of the [connection resilience plan](../../plans/2026-10-21-connection-resilience-plan.md).

## Answer

The decided design holds. No project studied does better than "reconcile, continue only when no tool may have run, otherwise ask." Several do worse, and the ones that do worse show why.

The closest prior art is Claude Code. It detects sleep itself, re-asks the model only when no text block or tool call has finished, and answers an unrecorded tool call with "outcome is unknown, check before running it again" ([claude-code.md](claude-code.md)). Codex, Zed, Goose and current Cline also never re-run a started tool. They differ in what they tell the model. Roo Code and classic Cline resend after a mid-stream failure even when a tool may have run. That is the replay bigbud's invariant forbids ([cline-roo-code.md](cline-roo-code.md)).

Three findings change details of the plan rather than its shape:

1. **The server's sleep detector is wrong on macOS.** Node's `performance.now()` keeps counting through sleep on macOS, as it does on Windows. Only on Linux does it stop. bigbud's `EventLoopLagMonitor` assumes the opposite, so a macOS lid close will be logged as a server stall the length of the sleep ([sleep-detection.md](sleep-detection.md)).
2. **`suspend` is not reliable on any OS, so the gap detector is a backup everywhere, not only on Linux.** Chromium posts `suspend` after it has let macOS sleep, and drops a `resume` that had no `suspend` before it.
3. **The remote agent can lose a finished result during a normal sleep.** Results are kept for 600 s after a process ends, and an attach whose cursor fell behind the 8 MiB output window fails before it returns the exit code ([session-terminals.md](session-terminals.md)).

## Top lessons, by plan item

Phase numbers refer to the connection resilience plan. D-numbers refer to the decided design (listed in the next section).

1. **Phase 2, Phase 6 item 4. Anchor on `resume`, treat `suspend` as a hint, and run the gap detector on every OS.** On macOS, Chromium posts the suspend task and then calls `IOAllowPowerChange` at once, so the JavaScript handler can run after wake. On macOS and Windows, a missed `suspend` also hides `resume`. On Linux, Electron releases its logind delay lock as soon as the synchronous handler returns. Write the suspend hint synchronously. Electron issues #47739, #44252 and #42050 show late, doubled and missing events. Source: [power_monitor.cc#L196-L231](https://github.com/chromium/chromium/blob/e1b5da71892a0825f7f0987ae2e073116099c2be/base/power_monitor/power_monitor.cc#L196-L231), [power_observer_linux.cc#L144-L160](https://github.com/electron/electron/blob/3b24d8f7f6246b6899cf594b0969c4087a3cd301/shell/browser/lib/power_observer_linux.cc#L144-L160). Note: [sleep-detection.md](sleep-detection.md).

2. **Phase 6 item 4. Fix the clock assumption before using the drift sampler to classify sleep.** libuv's `uv__hrtime` on macOS is `mach_continuous_time()` ([darwin.c#L60-L63](https://github.com/libuv/libuv/blob/e36964a094fadba7926e88fe333dd1d6a6baf13c/src/unix/darwin.c#L60-L63)), and Node's `performance.now()` is `uv_hrtime()` ([node_perf.cc#L375-L378](https://github.com/nodejs/node/blob/1c12ff166756c8ddd830cb4742953314065fcacc/src/node_perf.cc#L375-L378)). bigbud sets `monotonicIncludesSleep` only for `win32` (`apps/server/src/connection-diagnostics/Layers/EventLoopLagMonitor.ts:55`), and its comment in `EventLoopLagMonitor.logic.ts` says the macOS clock stops. On Linux the sampler has no sleep branch at all. The same wrong statement is in the [Sleep and wake provider conformance](../Sleep%20and%20wake%20provider%20conformance/README.md) README ("On macOS and Linux the monotonic clock stops during sleep"), so the probe's drift correction should be checked on macOS before its rows are trusted. A side effect of the macOS clock: every pending Node timer fires at once at wake, so `interrupted-by-sleep` must include timeout errors in the first seconds after wake, not only socket errors.

3. **Phase 6 item 4. Use the provider's own sleep evidence where it exists.** Claude Code compares wall and monotonic time when its idle watchdog fires and labels the error "Connection lost while your computer was asleep". These strings are in the 2.1.301 CLI that bigbud's SDK 0.3.301 bundles (checked with `strings`). bigbud's Claude adapter maps `api_retry` to a generic warning (`apps/server/src/provider/Layers/Claude/Adapter.stream.system.ts:168-177`). Codex and Goose have no sleep awareness, and a dead socket after wake can sit for 300 s (Codex `stream_idle_timeout_ms`) or 600 s (Goose read timeout) before it errors. So the wake signal, not a provider timeout, must start reconciliation, with a deadline after which bigbud interrupts and reconciles. Notes: [claude-code.md](claude-code.md), [codex.md](codex.md), [goose.md](goose.md).

4. **Phase 6 item 5. The line "no completed block or tool call yet" is the industry's safe-retry line.** Claude Code retries only before any text block or tool call completes ([errors docs](https://code.claude.com/docs/en/errors)). Current Cline retries only when the failed attempt produced no content and ran no tools, at most 3 times ([agent-runtime.ts#L1282-L1314](https://github.com/cline/cline/blob/c441897f11f658f978a00678f045670c1ab2b60d/sdk/packages/agents/src/agent-runtime.ts#L1282-L1314)). Gemini CLI re-asks up to 3 times mid-stream, and that is safe only because its tools run after the stream ends. This confirms D4's "model request cut and no tool in flight" rule.

5. **Phase 6 items 3 and 5. A tool call recorded without its result is the "may have been mid-flight" evidence, and several providers already write it.** Codex writes the call item to the rollout before dispatch and the output after ([stream_events_utils.rs#L325-L371](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/core/src/stream_events_utils.rs#L325-L371)). Goose and current Cline save the assistant message with its tool requests before running tools. Gemini CLI writes a tool call only after it completes, so a crash mid-tool leaves no trace there. Zed does not persist a streaming step at all. bigbud's own `may-have-been-sent` row is still required, because not every provider records the call first. The provider record is a useful second input to D4's check.

6. **Phase 6 item 5. Word the uncertain case as "unknown", never as "failed" or "cancelled by the user".** Claude Code's synthetic result is "the session ended before this call's result was recorded, so its outcome is unknown. Check whether it took effect before relying on it or running it again." It once reported a shutdown-interrupted call as a user rejection and fixed it (changelog 2.1.296). Codex inserts a bare `"aborted"` output ([normalize.rs#L21-L66](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/core/src/context_manager/normalize.rs#L21-L66)). Zed says "Tool canceled by user". Roo says "Task was interrupted before this tool call could be completed", which can be false. Use the "unknown" form in bigbud's linked continuation and in the resolution prompt. Codex's daemon continuation adds a good instruction for the safe case: "Check the current state before repeating actions that may already have completed." Claude Code adds "Re-verify anything time-sensitive (branch state, running processes, prior partial work)".

7. **Phase 6 item 5 and the resolution prompt. Zellij is the UI precedent for "ask, do not re-run".** A resurrected session holds every command as "Waiting to run: `<cmd>`" with ENTER to run, ESC for a shell, Ctrl-c to exit. The only bypass is an explicit `--force-run-commands` flag ([session_serialization.rs#L570-L578](https://github.com/zellij-org/zellij/blob/c7c4ce42b8663dad464c03b92a7949ad58c68c55/zellij-utils/src/session_serialization.rs#L570-L578), [terminal_character.rs#L1299-L1340](https://github.com/zellij-org/zellij/blob/c7c4ce42b8663dad464c03b92a7949ad58c68c55/zellij-server/src/panes/terminal_character.rs#L1299-L1340)). VS Code's agent host fails a tool whose executing client vanished for 30 s with an explicit error naming the tool and client, and never re-runs it ([protocolServerHandler.ts#L2009-L2039](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/platform/agentHost/node/protocolServerHandler.ts#L2009-L2039)).

8. **Phase 6 items 5 and 7. Count only bigbud's own recovery attempts toward the park limit, keep the count durable, and measure budgets in awake time.** Codex waits for the network with no limit while the turn stays in progress ("Reconnecting... waiting for network", [responses_retry.rs#L93-L118](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/core/src/responses_retry.rs#L93-L118)). Mosh, ET and WezTerm retry the link forever. Those waits are not failed recoveries. Restate stores its attempt count durably so a restart does not reset it, and pauses (not kills) on exhaustion with the last error and the failing step's name ([lib.rs#L1389-L1450](https://github.com/restatedev/restate/blob/e410013917885a4a7561be80fbbbbdf00c0f5759/crates/invoker-impl/src/lib.rs#L1389-L1450)). VS Code's grace timers count 1 s ticks of process time, and its agent-host client pauses its reconnect deadline on suspend ([async.ts#L1265-L1335](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/base/common/async.ts#L1265-L1335)). Otherwise a long sleep spends the budget the moment the machine wakes. Notes: [durable-execution.md](durable-execution.md), [vscode-remote.md](vscode-remote.md).

9. **Phase 6 item 6. Reattach mode must refuse to spawn, and must still deliver the exit code when output was lost.** Zed's `proxy --reconnect` never starts a server and returns a distinct "server not running" exit ([server.rs#L980-L1012](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/remote_server/src/server.rs#L980-L1012)). WezTerm reconnects with `no_auto_start`. ET separates "returning client", "server restarted, resync from zero", "retry later" and "session gone". bigbud's remote agent already refuses to re-run (`AGENT_RESTARTED` expiry). Two gaps, read from source and not reproduced:
   - `handle_process_attach` calls `replay_from` first and returns `ProcessReplay` on `ReplayGap`, so the snapshot and `ProcessCompleted` are never sent (`crates/bigbud-remote-agent/src/session/process_handlers.rs:292-306`). Output is capped at 8 MiB per operation and nothing acknowledges during sleep. The PTY path already returns a snapshot with `replay_gap = true`. Do the same for processes, so the prompt can say "finished with exit 0, output partly lost" instead of "unknown".
   - `PROCESS_RESULT_RETENTION`, `ACCEPTED_OPERATION_RETENTION` and `PTY_RESULT_RETENTION` are 600 s (`session/core.rs:63-70`). The remote host does not sleep, so a 30-minute lid close after a command finished turns a known result into "unknown". The Phase 6 exit test uses a 10-minute sleep, right at this edge. Keep the small terminal result (state, exit code) much longer than the output, for example 24 h or until acknowledged.
     Zed adds a warning: its remote daemon exits after 10 idle minutes, and its remote terminals and ACP agents ride separate ssh sessions the daemon does not own ([server.rs#L517-L560](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/remote_server/src/server.rs#L517-L560)). bigbud's remote agent must own provider and tool processes and must not idle-exit while an operation is open.

10. **Phase 6 item 5, D6. Do not let a provider CLI auto-continue after a restart while bigbud also continues.** `CLAUDE_CODE_RESUME_INTERRUPTED_TURN` makes the Claude CLI continue an interrupted turn by itself. Its changelog lists repeated fixes for re-running finished turns (lines 522, 617, 1548, 2741, 4101 at [5ed799e](https://github.com/anthropics/claude-code/blob/5ed799e5cc56bea9efff57398ca43e31d82784ff/CHANGELOG.md)). Leave it unset. Codex's daemon continuation runs only on the Unix-socket managed daemon, not on bigbud's stdio `codex app-server`, but if bigbud ever uses that transport the same rule applies. Within one request, Codex and Claude Code retry by themselves after wake. bigbud should observe those (`willRetry: true`, `api_retry`) as "the provider continued on its own".

11. **Phase 6 item 7. Delay the visible state and give one action.** VS Code shows nothing for the first 40 s after data stops, offers "Reconnect Now" during backoff, and parks on one modal with "Reload Window". Mosh shows a quiet "Last contact N seconds ago" bar. Zed shows "Retrying. Next attempt in N seconds." and then one Retry button. bigbud's blue "Resuming after sleep" state can stay hidden for the first few seconds after resume if the turn is already progressing.

## What fits in Rust

- **A "time spent suspended" reader** in `crates/bigbud-desktop-supervisor`, which the server already runs as a sidecar. Linux: `CLOCK_BOOTTIME` minus `CLOCK_MONOTONIC`. macOS: `mach_continuous_time` minus `mach_absolute_time`. Windows: `QueryInterruptTime` minus `QueryUnbiasedInterruptTime` (`windows-sys`). It needs no logind, no window and is immune to wall-clock changes. The server reads it on each sampler tick or on a transport error. TypeScript still decides. On Linux, pure Node can approximate it with `os.uptime()` against `performance.now()`. Detail: [sleep-detection.md](sleep-detection.md).
- **Native suspend subscriptions** (logind via `logind-zbus`, `PowerRegisterSuspendResumeNotification`, `IORegisterForSystemPower`) only duplicate Electron. Add them only for a headless or web-only server. gpui shows a full set in Rust ([zed.md](zed.md)). Tauri and tao expose no desktop suspend events.
- **Remote agent changes** (lesson 9): process attach that returns a snapshot plus terminal result on a replay gap, longer retention for terminal results, no idle exit while an operation is open, and distinct "instance restarted" versus "operation unknown" answers. This is bigbud's existing `crates/bigbud-remote-agent`, which already has ET-style sequence numbers, acks and a replay-gap error.
- **A consume-once recovery snapshot**, written atomically and deleted before serving, as Codex's daemon does ([codex.md](codex.md)). Useful if the Rust background-service plan ever owns provider restarts.
- **Note on Rust `Instant`:** it stops during sleep on macOS and Linux but counts sleep on Windows. The supervisor's `Instant`-based acknowledgement timeouts (`crates/bigbud-desktop-supervisor/src/main.rs`) will therefore expire at wake on Windows only.
- Decisions about intents, classification, continuation and prompts stay in TypeScript, matching `docs/plans/2026-08-25-rust-systems-core-plan.md`.

## Projects dropped or found irrelevant

- **Roo Code** is archived (read-only since 2026-05-15, last release v3.54.0). It is kept as a counterexample only.
- **Goose** moved from `block/goose` to `aaif-goose/goose`.
- **Tauri** has nothing to offer for desktop suspend.
- **tmux** has no network layer; it only shows that the server owning the session is enough.

## Could not verify

- Real behaviour across a lid close for any project. The conformance kit in [Sleep and wake provider conformance](../Sleep%20and%20wake%20provider%20conformance/README.md) is the place to measure it.
- How the Claude CLI decides a streamed tool call "completed", and when it flushes the `tool_use` line. The source is closed; only docs, changelog and bundle strings were read.
- Whether Windows Modern Standby (S0ix) delivers `suspend` and `resume` reliably, and whether macOS DarkWake emits `resume`.
- Whether a Codex websocket connect failure after wake gets the unlimited network wait or the counted retries.
- Whether Zed replays a handled but unacknowledged request twice at runtime, and what happens to its remote terminal and agent processes when their ssh session drops.
- The two remote-agent gaps in lesson 9. There is no session-level test that attaches a process after more than 8 MiB of unacknowledged output.
- Restate's docs say an unset retry policy retries forever; the code says 70 attempts then pause. Not resolved.
- How the Copilot extension retries a cut chat request in VS Code. Its code was not checked out.
