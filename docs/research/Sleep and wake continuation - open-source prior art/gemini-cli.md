# Gemini CLI: retries, checkpoints and interrupted tool calls

Research date: 2026-10-22. Sources: google-gemini/gemini-cli at c690b9d (2026-10-22), latest release v0.65.0 (2026-10-20). Paths are relative to the repo root. Tags: **[V]** verified in source at that commit, **[D]** from the repo's docs, **[I]** inferred.

## Answer

Gemini CLI retries hard inside one model request and never continues across a process restart. Opening a request retries up to 10 attempts (5 s doubling to 30 s, 429, 499, 5xx and a list of socket errors such as `ECONNRESET` and `ETIMEDOUT`), and a stream that breaks after it started is re-requested from the same history up to 3 more times, 1 s, 2 s, 4 s apart. That re-request is safe only because tools never run while the model is streaming: they are scheduled after the stream ends. If every attempt fails, the user's prompt is rolled back out of history and the turn ends with an error. A restart loses any tool that was running, and the transcript does not show it, because a tool call is written to the session file only when it completes or is cancelled. The `/restore` checkpoint is a recovery tool for the user, not for the agent: a shadow-git commit taken when an edit tool is waiting for approval.

## What happens when the connection is cut mid-turn

- **Connection phase.** `retryWithBackoff` wraps the call that opens the stream. Default 10 attempts (config caps it at 10), 5000 ms initial, 30 000 ms cap, plus or minus 30% jitter. It retries 429, 499, 5xx, never 400, and the codes `ECONNRESET`, `ETIMEDOUT`, `EPIPE`, `ENOTFOUND`, `EAI_AGAIN`, `ECONNREFUSED`, `UND_ERR_*_TIMEOUT`, `ERR_STREAM_PREMATURE_CLOSE` and SSL bad-record-MAC. With `retryFetchErrors` (default on) it also retries "fetch failed" and "incomplete json segment". [V: [retry.ts#L20](https://github.com/google-gemini/gemini-cli/blob/c690b9df153f74202c0c5b13cc197790f3c7f92f/packages/core/src/utils/retry.ts#L20), [#L42-L62](https://github.com/google-gemini/gemini-cli/blob/c690b9df153f74202c0c5b13cc197790f3c7f92f/packages/core/src/utils/retry.ts#L42-L62), [#L170-L209](https://github.com/google-gemini/gemini-cli/blob/c690b9df153f74202c0c5b13cc197790f3c7f92f/packages/core/src/utils/retry.ts#L170-L209); [config.ts#L1391-L1395](https://github.com/google-gemini/gemini-cli/blob/c690b9df153f74202c0c5b13cc197790f3c7f92f/packages/core/src/config/config.ts#L1391-L1395); [geminiChat.ts#L1211-L1229](https://github.com/google-gemini/gemini-cli/blob/c690b9df153f74202c0c5b13cc197790f3c7f92f/packages/core/src/core/geminiChat.ts#L1211-L1229)]
- **Mid-stream.** Errors after the first chunk are handled by a second loop: retryable network errors and every `InvalidStreamError` (no finish reason, empty text, malformed function call and others) start a new request with the same `requestHistory`, at most 4 attempts in total, waiting 1 s, 2 s, 4 s. Connection-phase errors that reach this loop are not retried again. [V: [geminiChat.ts#L105-L109](https://github.com/google-gemini/gemini-cli/blob/c690b9df153f74202c0c5b13cc197790f3c7f92f/packages/core/src/core/geminiChat.ts#L105-L109), [#L664-L810](https://github.com/google-gemini/gemini-cli/blob/c690b9df153f74202c0c5b13cc197790f3c7f92f/packages/core/src/core/geminiChat.ts#L664-L810)]
- **Partial output.** Thoughts and usage from a failed attempt are buffered and dropped; the model message is recorded only after a successful attempt. [V: [geminiChat.ts#L1749-L1781](https://github.com/google-gemini/gemini-cli/blob/c690b9df153f74202c0c5b13cc197790f3c7f92f/packages/core/src/core/geminiChat.ts#L1749-L1781)] The UI is told `Retry` and ignores it ("handled transparently"). [V: [useGeminiStream.ts#L1749-L1751](https://github.com/google-gemini/gemini-cli/blob/c690b9df153f74202c0c5b13cc197790f3c7f92f/packages/cli/src/ui/hooks/useGeminiStream.ts#L1749-L1751)] Whether streamed text already on screen is cleared on retry I did not check.
- **Exhausted.** On a non-abort failure the history is rolled back to before the user's prompt, and the session file is synced to match. On abort it rolls back to the start of the whole prompt sequence. [V: [geminiChat.ts#L812-L840](https://github.com/google-gemini/gemini-cli/blob/c690b9df153f74202c0c5b13cc197790f3c7f92f/packages/core/src/core/geminiChat.ts#L812-L840)]
- **Sleep awareness.** None found: no suspend, resume, offline or `navigator.onLine` handling in `packages/core` or `packages/cli`. No stream idle timeout found either; a dead socket after wake is caught by undici's body timeout (`UND_ERR_BODY_TIMEOUT` is in the retry list) or by the OS. [V by search; I for the timeout value]

## In-flight tool calls

- **Tools run after the stream.** Tool requests are collected during the stream and scheduled once it ends. A mid-stream retry therefore never repeats a tool. [V: [useGeminiStream.ts#L1694](https://github.com/google-gemini/gemini-cli/blob/c690b9df153f74202c0c5b13cc197790f3c7f92f/packages/cli/src/ui/hooks/useGeminiStream.ts#L1694), [#L1762-L1772](https://github.com/google-gemini/gemini-cli/blob/c690b9df153f74202c0c5b13cc197790f3c7f92f/packages/cli/src/ui/hooks/useGeminiStream.ts#L1762-L1772)]
- **User cancel.** Every unsubmitted call, including function calls that only exist in the last model turn, is recorded as cancelled with the error "[Operation Cancelled] Reason: User cancelled operation". [V: [useGeminiStream.ts#L895-L970](https://github.com/google-gemini/gemini-cli/blob/c690b9df153f74202c0c5b13cc197790f3c7f92f/packages/cli/src/ui/hooks/useGeminiStream.ts#L895-L970), [useAgentStream.ts#L47-L48](https://github.com/google-gemini/gemini-cli/blob/c690b9df153f74202c0c5b13cc197790f3c7f92f/packages/cli/src/ui/hooks/useAgentStream.ts#L47-L48)]
- **Repair before the next prompt.** If history ends with a model turn whose function calls have no responses, a synthetic user turn answers each with `{error: "Response was lost or interrupted."}`. If history ends with tool responses and no model reply (the stream that carried the results failed), a model turn "[The previous response was interrupted before it completed.]" is added. Both run only when the next real user message is sent, are recorded to the session file, and never resend the tool. [V: [geminiChat.ts#L113-L131](https://github.com/google-gemini/gemini-cli/blob/c690b9df153f74202c0c5b13cc197790f3c7f92f/packages/core/src/core/geminiChat.ts#L113-L131), [#L525-L536](https://github.com/google-gemini/gemini-cli/blob/c690b9df153f74202c0c5b13cc197790f3c7f92f/packages/core/src/core/geminiChat.ts#L525-L536), [#L854-L935](https://github.com/google-gemini/gemini-cli/blob/c690b9df153f74202c0c5b13cc197790f3c7f92f/packages/core/src/core/geminiChat.ts#L854-L935), [#L1896-L1908](https://github.com/google-gemini/gemini-cli/blob/c690b9df153f74202c0c5b13cc197790f3c7f92f/packages/core/src/core/geminiChat.ts#L1896-L1908)]
- **Process restart.** The model message is recorded with its text only; the call's name, args and result are attached by `recordCompletedToolCalls` after the tool finishes. I found no earlier write of the call. A crash while a tool runs leaves a transcript with no trace of the call, and `--resume` rebuilds function calls only from recorded `toolCalls`. [V: [geminiChat.ts#L1762-L1773](https://github.com/google-gemini/gemini-cli/blob/c690b9df153f74202c0c5b13cc197790f3c7f92f/packages/core/src/core/geminiChat.ts#L1762-L1773), [#L1801-L1831](https://github.com/google-gemini/gemini-cli/blob/c690b9df153f74202c0c5b13cc197790f3c7f92f/packages/core/src/core/geminiChat.ts#L1801-L1831); [sessionUtils.ts#L196-L215](https://github.com/google-gemini/gemini-cli/blob/c690b9df153f74202c0c5b13cc197790f3c7f92f/packages/core/src/utils/sessionUtils.ts#L196-L215); I for "no earlier write"]

## What is persisted, and when

- **Session file.** One JSONL file per session in `~/.gemini/tmp/<project_hash>/chats/`, written with `appendFileSync` and no fsync. Disk full turns recording off with a warning. [V: [chatRecordingService.ts#L814-L820](https://github.com/google-gemini/gemini-cli/blob/c690b9df153f74202c0c5b13cc197790f3c7f92f/packages/core/src/services/chatRecordingService.ts#L814-L820), [#L942-L958](https://github.com/google-gemini/gemini-cli/blob/c690b9df153f74202c0c5b13cc197790f3c7f92f/packages/core/src/services/chatRecordingService.ts#L942-L958); D: `docs/cli/session-management.md:9-20`]
- **Order within a turn.** User prompt before the request [V: [geminiChat.ts#L545-L566](https://github.com/google-gemini/gemini-cli/blob/c690b9df153f74202c0c5b13cc197790f3c7f92f/packages/core/src/core/geminiChat.ts#L545-L566)]; model text after a successful stream; tool call plus result after the tool; tool results sent back to the model as a synthetic user record [V: [#L591-L596](https://github.com/google-gemini/gemini-cli/blob/c690b9df153f74202c0c5b13cc197790f3c7f92f/packages/core/src/core/geminiChat.ts#L591-L596)].
- **File checkpoint.** With `general.checkpointing.enabled` (off by default), when an edit tool (`EDIT_TOOL_NAMES`) enters `AwaitingApproval`, the CLI commits the project to a shadow git repo in `~/.gemini/history/<project_hash>` and writes a JSON file with the UI history, the client history, the tool call and the commit hash. This is fire-and-forget inside a React effect. [V: [useGeminiStream.ts#L2351-L2400](https://github.com/google-gemini/gemini-cli/blob/c690b9df153f74202c0c5b13cc197790f3c7f92f/packages/cli/src/ui/hooks/useGeminiStream.ts#L2351-L2400), [checkpointUtils.ts#L84-L158](https://github.com/google-gemini/gemini-cli/blob/c690b9df153f74202c0c5b13cc197790f3c7f92f/packages/core/src/utils/checkpointUtils.ts#L84-L158); D: `docs/cli/checkpointing.md:10-35`] So the snapshot is taken before execution and before approval. A tool allowed by policy without asking never enters `AwaitingApproval` and so gets no checkpoint. [V: approval state set only in [confirmation.ts#L162-L165](https://github.com/google-gemini/gemini-cli/blob/c690b9df153f74202c0c5b13cc197790f3c7f92f/packages/core/src/scheduler/confirmation.ts#L162-L165) when `decision === ASK_USER`, [scheduler.ts#L720-L727](https://github.com/google-gemini/gemini-cli/blob/c690b9df153f74202c0c5b13cc197790f3c7f92f/packages/core/src/scheduler/scheduler.ts#L720-L727); I for YOLO and auto-edit behavior]
- **`/restore`** reverts files to the snapshot, restores both histories and proposes the original tool call again for the user to run, edit or ignore. [D: `docs/cli/checkpointing.md:23-29`]
- **`/chat save <tag>`**, now `/resume save <tag>`, saves only the conversation history as a named checkpoint, no files. [V: [chatCommand.ts#L91-L150](https://github.com/google-gemini/gemini-cli/blob/c690b9df153f74202c0c5b13cc197790f3c7f92f/packages/cli/src/ui/commands/chatCommand.ts#L91-L150); D: `docs/cli/session-management.md:84-97`]

## What the user sees

- During retries the loading line reads "Trying to reach <model> (Attempt n/m)". [V: [useLoadingIndicator.ts#L87-L92](https://github.com/google-gemini/gemini-cli/blob/c690b9df153f74202c0c5b13cc197790f3c7f92f/packages/cli/src/ui/hooks/useLoadingIndicator.ts#L87-L92)]
- After failure, an error item; the prompt is gone from history and must be sent again.
- `gemini --resume` and `/resume` load the session and wait. Nothing continues on its own. [V: [client.ts#L355-L375](https://github.com/google-gemini/gemini-cli/blob/c690b9df153f74202c0c5b13cc197790f3c7f92f/packages/core/src/core/client.ts#L355-L375); D: `docs/cli/session-management.md:26-52`]

## Retry limits and parking

- Connection: 10 attempts. Mid-stream: 4 attempts. Persistent 429 can trigger a model fallback callback. No turn-level retry, no parked state.

## For bigbud

- **Confirms D4 (TypeScript).** "Model request cut, no tool in flight, re-ask once" is what Gemini CLI does, three times, inside the request. It is safe there because tool execution is strictly after the stream. bigbud's continuation should keep the same rule: continue automatically only when the transcript shows the stream ended before any tool was dispatched.
- **Adds to D1.** Gemini CLI's gap is the mirror of D1: the tool call is durable only after it finishes, so a crash mid-tool is invisible. bigbud's `prepared` and `may-have-been-sent` states written before dispatch are what make the D4 "ask the user" branch possible at all.
- **Adds to D4 (TypeScript).** When a call has no result, answer it with an explicit error result ("Response was lost or interrupted.") and, if a tool result has no model reply, add a model placeholder before the next turn. bigbud's linked continuation can carry the same two markers so the model knows what is uncertain.
- **Adds to D4 and D7.** A pre-tool file snapshot, taken before approval, is a cheap way to make "a file edit may have happened" recoverable. A shadow git commit could back the resolution prompt with an "undo to before this action" choice. Out of scope for this phase; noted as a candidate.
- **Adds to D3.** Rolling the user's prompt out of history on failure hides that the turn was ever accepted. bigbud's intent should keep the accepted turn and mark it `interrupted-by-sleep` rather than erase it.
- **Adds to D2.** No sleep or network signal is used; recovery depends on errors arriving. Same lesson as Goose: the wake hint must drive reconciliation, not a socket timeout.
