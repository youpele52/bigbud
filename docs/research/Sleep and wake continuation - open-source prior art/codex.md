# OpenAI Codex CLI (codex-rs): stream retry, tool calls and resume

Research date: 2026-10-22. Sources: openai/codex at a3d93e1 (2026-10-22), latest release rust-v0.163.0 (published 2026-10-15). Line citations are at `main` a3d93e1. The key files (`responses_retry.rs`, `normalize.rs`, `turn_suspension.rs`, `daemon_continuation.rs`) and the `unbounded_connection_retries` default were also checked at the rust-v0.163.0 tag via `gh api`.

## Answer

Codex handles a cut model stream inside the turn. It does not resend the original request bytes. It rebuilds the request from the in-memory history, which already holds every output item that completed before the cut and the outputs of any tools that ran. Only the partial, not-yet-completed item is dropped. Tool calls start as soon as their item completes, before `response.completed`. A stream cut does not cancel them: they run to completion and their outputs are recorded before the retry. Any call that ends up without an output, for example after a crash or kill, gets a synthetic `"aborted"` output when the next prompt is built, so a tool is never re-run by replay. When the network is down, a turn-level loop (on by default) waits for the network with no upper bound and emits "Reconnecting... waiting for network". bigbud sees this as `error` notifications with `willRetry: true` while the turn stays in progress. Codex has no sleep or suspend awareness. Its only automatic continuation after a process restart is the managed-daemon (Unix socket) path. It reconciles against the rollout, closes the old turn and starts a linked turn with a "check the current state before repeating actions" instruction, even if a tool was in flight. That path does not apply to bigbud's stdio `codex app-server`.

## What happens when the connection is cut mid-turn

- **Two retry layers.** The HTTP layer retries failed requests `request_max_retries` times (default 4, cap 100). It retries on transport errors and 5xx, not 429, with a 200 ms doubling backoff and ±10% jitter. ([`lib.rs#L67-L76`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/model-provider-info/src/lib.rs#L67-L76), [`lib.rs#L455-L461`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/model-provider-info/src/lib.rs#L455-L461); [`retry.rs#L22-L51`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/codex-client/src/retry.rs#L22-L51))
- **Turn-level stream retry.** `stream_max_retries` (default 5, cap 100) counts reconnects of a dropped streaming response. The delay is server `Retry-After` if present, otherwise `backoff(n)`: 200 ms doubling with ±10% jitter. ([`lib.rs#L500-L519`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/model-provider-info/src/lib.rs#L500-L519); [`backoff.rs#L7-L17`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/async-utils/src/backoff.rs#L7-L17); [`error.rs#L413-L460`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/protocol/src/error.rs#L413-L460))
- **Idle timeout.** `stream_idle_timeout_ms` defaults to 300 000 ms. An SSE or websocket read that sees nothing for that long becomes `Stream("idle timeout waiting for SSE")` or `"... websocket"`. A clean close before `response.completed` becomes `Stream("stream closed before response.completed")`. ([`responses.rs#L553-L588`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/codex-api/src/sse/responses.rs#L553-L588); [`responses_websocket.rs#L744-L748`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/codex-api/src/endpoint/responses_websocket.rs#L744-L748); [`turn.rs#L2860-L2887`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/core/src/session/turn.rs#L2860-L2887))
- **`Stream` errors are meant to be retried.** The doc comment says the session loop "will automatically retry the turn". ([`error.rs#L108-L113`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/protocol/src/error.rs#L108-L113))
- **Unbounded wait for the network.** With feature `unbounded_connection_retries` (Stable, on by default), a `ConnectionFailed` error during sampling does not use the retry budget. It shows "Reconnecting... waiting for network", sleeps 5 s, then doubles up to 60 s, and loops until the network returns or the turn is interrupted. Internal sessions and Amazon Bedrock are excluded. A mid-stream cut is `Stream` and uses the counted budget. The reconnect attempts that fail to connect are `ConnectionFailed`, so a laptop that is offline stays in this loop. ([`responses_retry.rs#L23-L24`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/core/src/responses_retry.rs#L23-L24), [`responses_retry.rs#L93-L118`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/core/src/responses_retry.rs#L93-L118); [`lib.rs#L220-L221`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/features/src/lib.rs#L220-L221), [`lib.rs#L1477-L1482`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/features/src/lib.rs#L1477-L1482); [`api_bridge.rs#L266-L269`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/codex-api/src/api_bridge.rs#L266-L269))
- **Counted retries.** Each counted retry emits "Reconnecting... n/m". The first websocket retry is hidden in release builds. When the budget is used up on websockets, Codex falls back to HTTPS once, warns "Falling back from WebSockets to HTTPS transport.", and resets the counter. ([`responses_retry.rs#L120-L167`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/core/src/responses_retry.rs#L120-L167))
- **The retry rebuilds the request from history.** Only the first attempt uses the prepared input. Later attempts use `sess.clone_history().for_prompt(...)`. ([`turn.rs#L1775-L1782`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/core/src/session/turn.rs#L1775-L1782))
- **What survives a cut.** Output items that completed before the cut, such as reasoning, messages and function calls, are kept. Text deltas of the item that was still streaming are lost from history, because items are recorded only on `OutputItemDone`. ([`stream_events_utils.rs#L325-L371`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/core/src/stream_events_utils.rs#L325-L371))
- **Loose end in the client view.** A comment notes that items already shown to the client are not reconciled on one break path: "TODO: Reconcile any response item already being presented to the client." ([`turn.rs#L2844`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/core/src/session/turn.rs#L2844))
- **`previous_response_id` only follows a completed response.** It is used on the websocket transport only when the previous response completed, because `LastResponse` is sent only on `Completed`. After a cut, the retry is a full, non-incremental request. No idempotency key is sent on model requests: there was no hit for `idempotenc` outside project creation in `state/`. ([`client.rs#L1577-L1597`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/core/src/client.rs#L1577-L1597), [`client.rs#L2620-L2627`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/core/src/client.rs#L2620-L2627))

## In-flight tool calls

- **Tools start before the response completes.** On `OutputItemDone` for a tool call, Codex writes the call item to history first, then dispatches it ("handle_tool_call dispatches immediately"), and pushes the future onto `in_flight`. ([`stream_events_utils.rs#L325-L371`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/core/src/stream_events_utils.rs#L325-L371); [`turn.rs#L3012-L3014`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/core/src/session/turn.rs#L3012-L3014))
- **A stream error does not cancel running tools.** The tool's cancellation token comes from the turn's token, not the stream. When the stream loop breaks with an error, `drain_in_flight` still awaits every running tool and records its output. Only then does the error go back to the retry loop. ([`turn.rs#L3421-L3430`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/core/src/session/turn.rs#L3421-L3430), [`turn.rs#L2601-L2629`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/core/src/session/turn.rs#L2601-L2629))
- **What the next attempt sends.** The next request carries the call and its real output, so the model continues from the result and nothing is re-executed. This is verified from code flow. I did not run it.
- **Cancelled tools get explicit "aborted" outputs.** These come only from turn cancellation (user interrupt or preempt). Shell calls get "Wall time: Xs / aborted by user". Other tools get "aborted by user after Xs". A call cancelled before dispatch gets "aborted before dispatch". ([`parallel.rs#L258-L320`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/core/src/tools/parallel.rs#L258-L320), [`parallel.rs#L365-L385`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/core/src/tools/parallel.rs#L365-L385))
- **History repair at prompt time.** `ensure_call_outputs_present` inserts a synthetic `FunctionCallOutput("aborted")` for any call without an output. It runs every time history is prepared for a prompt, not when it is persisted. This is what covers a resumed session whose process died mid-tool. ([`normalize.rs#L21-L66`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/core/src/context_manager/normalize.rs#L21-L66); [`history.rs#L603-L617`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/core/src/context_manager/history.rs#L603-L617), [`history.rs#L964-L980`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/core/src/context_manager/history.rs#L964-L980))
- **Model-visible note after a user interrupt.** Codex appends a `<turn_aborted>` note: "If any tools/commands were aborted, they may have partially executed." It flushes the rollout before emitting `TurnAborted`. ([`turn_aborted.rs#L12`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/core/src/context/turn_aborted.rs#L12); [`mod.rs#L990-L1007`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/core/src/tasks/mod.rs#L990-L1007))

## What is persisted, and when

- **Rollout is an append-only JSONL file**, one per thread, under `~/.codex/sessions/...`. A background writer task writes each `AddItems` batch at once, with `write_all` and `flush` per line. There is no `fsync`; `sync_all` appears only in compression. Failed writes keep the unwritten suffix and retry on the next barrier. ([`recorder.rs#L1810-L1815`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/rollout/src/recorder.rs#L1810-L1815), [`recorder.rs#L1993-L1996`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/rollout/src/recorder.rs#L1993-L1996), [`recorder.rs#L2141-L2147`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/rollout/src/recorder.rs#L2141-L2147))
- **Order of writes.** The tool call item is persisted before the tool runs. The tool output is persisted after it finishes, during the drain. So the durable record has a "may have been sent" state for tools for free: a call line with no output line. ([`stream_events_utils.rs#L348-L349`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/core/src/stream_events_utils.rs#L348-L349); [`turn.rs#L2601-L2629`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/core/src/session/turn.rs#L2601-L2629))
- **No retry or attempt state is persisted.** The retry counters live in `ResponsesStreamRetryState` in memory. ([`responses_retry.rs#L32-L46`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/core/src/responses_retry.rs#L32-L46))
- **Resume of a session that ended mid-turn.** `thread/resume` (also `codex resume` and `codex exec resume`) reloads history. A turn with no terminal event is shown as `Interrupted` once the thread is not active. There is no automatic continuation; the user sends the next message, and the missing call output becomes `"aborted"`. ([`thread_processor.rs#L6286-L6300`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/app-server/src/request_processors/thread_processor.rs#L6286-L6300); [`thread_lifecycle.rs#L1074-L1088`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/app-server/src/request_processors/thread_lifecycle.rs#L1074-L1088))
- **Resume of a thread that is still loaded** attaches to the running thread (`RunningThreadResumeResult::Handled`) instead of starting it again. ([`thread_processor.rs#L3936-L3954`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/app-server/src/request_processors/thread_processor.rs#L3936-L3954))

## Managed-daemon recovery (the one automatic continuation)

- **Only on the Unix-socket managed daemon.** It is active only when the transport is a Unix socket and `managed_daemon` is set. bigbud's stdio app-server does not get it. ([`lib.rs#L532-L533`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/app-server/src/lib.rs#L532-L533))
- **Snapshot on shutdown.** On shutdown, Codex snapshots each persistent root thread and, if a regular turn is running and its input is recorded, the turn id and settings. Only local, thread-configured environments qualify. The file is written atomically. ([`daemon_recovery.rs#L22-L55`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/core/src/session/daemon_recovery.rs#L22-L55); [`daemon_snapshot.rs#L15-L55`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/app-server/src/request_processors/daemon_snapshot.rs#L15-L55); [`app-server-transport/src/daemon_recovery.rs`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/app-server-transport/src/daemon_recovery.rs))
- **Consume once.** On start the snapshot file is read and deleted before serving requests, so each interrupted turn gets at most one automatic continuation per restart. ([`daemon_thread_recovery.rs#L32-L50`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/app-server/src/daemon_thread_recovery.rs#L32-L50))
- **Reconcile before continuing.** Recovery continues only if the last `TurnStarted` in the rollout is that turn and no `TurnComplete` or `TurnAborted` follows. The environment must still match, and the permission profile must not have changed. ([`daemon_continuation.rs#L40-L87`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/app-server/src/request_processors/daemon_continuation.rs#L40-L87))
- **How it continues.** It appends `TurnAborted(Interrupted)` for the old turn, then starts a new turn under the same `root_turn_id` with a hidden instruction: "The server restarted and interrupted the previous turn. Continue the unfinished work from the saved conversation. Check the current state before repeating actions that may already have completed." The thread shows a warning, "Resuming interrupted work". There is no check for an in-flight tool. ([`daemon_continuation.rs#L88-L130`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/app-server/src/request_processors/daemon_continuation.rs#L88-L130))
- **Graceful handoff.** `Op::SuspendTurnAndShutdown` flushes the rollout before cancelling. It stops the turn without writing a terminal event, so a replacement worker can recover it, and it closes the writer before announcing `ShutdownComplete`. ([`turn_suspension.rs#L13-L111`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/core/src/session/turn_suspension.rs#L13-L111))

## What the user sees

- **app-server.** `EventMsg::StreamError` becomes `error` with `willRetry: true` and `codexErrorInfo: responseStreamDisconnected`. The protocol comment says that a `willRetry: true` error "will not interrupt a turn". Both "Reconnecting... n/m" and "Reconnecting... waiting for network" use this notification; only the message text tells them apart. ([`bespoke_event_handling.rs#L1069-L1086`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/app-server/src/bespoke_event_handling.rs#L1069-L1086); [`notification.rs#L59-L69`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/app-server-protocol/src/protocol/v2/notification.rs#L59-L69); [`mod.rs#L5425-L5441`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/core/src/session/mod.rs#L5425-L5441))
- **TUI.** The TUI puts the retry message in the status row and restores the previous header on the next non-retry event. ([`protocol.rs#L206-L214`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/tui/src/chatwidget/protocol.rs#L206-L214); [`streaming.rs#L424-L434`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/tui/src/chatwidget/streaming.rs#L424-L434))
- **Turn status.** `TurnStatus` is `completed | interrupted | failed | inProgress`. A turn that ended with an error is `failed`. A `TurnAborted` turn is `interrupted`. ([`turn.rs#L33-L38`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/app-server-protocol/src/protocol/v2/turn.rs#L33-L38); [`bespoke_event_handling.rs#L1571`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/app-server/src/bespoke_event_handling.rs#L1571))

## Retry limits and parking

- **When the budget is used up**, the error goes up from `run_sampling_request`. `run_turn` emits `EventMsg::Error` (in app-server, `willRetry: false`) and ends the turn: "let the user continue the conversation". The turn becomes `failed`. Codex does not park it or retry it later; the user must send a new message. ([`responses_retry.rs#L169-L175`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/core/src/responses_retry.rs#L169-L175); [`turn.rs#L903-L918`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/core/src/session/turn.rs#L903-L918))
- **Network-down is not limited** while `unbounded_connection_retries` is on. The turn stays `inProgress` until the network returns or the user interrupts.

## For bigbud

- **Confirms D4 (model cut, no tool):** for Codex the model-cut case is already handled inside the provider. A short cut is retried with the same history and completed items kept. bigbud should observe (`willRetry: true`), not continue, and treat it like D6 ("the provider continued on its own"). TypeScript, in the Codex adapter.
- **Adds to D3:** after wake, a dead socket may not error at once. Detection can wait up to `stream_idle_timeout_ms` (300 s), and I found no client-side ping or keepalive. bigbud cannot tell "Codex will retry soon" from "hung" by events alone. Pair the wake hint with a deadline, and if no `willRetry` or progress arrives, interrupt the turn and reconcile from the rollout or `thread/read`. TypeScript.
- **Confirms D1 and adds to it:** Codex writes the call item before dispatch and the output after. bigbud can derive "tool may have been mid-flight" from the provider's own record, a call item with no `ItemCompleted` or output, instead of guessing. Use it as input to D4's tool check. TypeScript.
- **Contradicts D4 (tool in flight), as a design difference:** Codex's daemon recovery continues automatically even with a tool in flight. It relies on a synthetic `"aborted"` output plus a "check the current state before repeating actions" instruction. bigbud's stricter "ask the user" rule is a deliberate choice. Codex's wording is worth reusing in bigbud's linked continuation prompt. TypeScript.
- **Adds to D4 (unreachable):** Codex already waits for the network with no limit, and the turn stays `inProgress`. bigbud should not also retry or count those as failed recovery attempts toward D5. Count only bigbud-initiated attempts. TypeScript.
- **Adds to D5:** Codex's daemon snapshot is consumed once per restart, its implicit limit. Codex has no parking. The Retry button is bigbud's own.
- **Adds to D8:** worth emulating in Rust-native pieces: an atomic, consume-once recovery snapshot read and deleted before serving, and "flush before cancel, close writer before announcing completion" so a successor cannot double-write. ([`turn_suspension.rs#L30-L33`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/core/src/session/turn_suspension.rs#L30-L33), [`turn_suspension.rs#L92-L110`](https://github.com/openai/codex/blob/a3d93e1e692f1144cf8685175a5d1f6bf7294f57/codex-rs/core/src/session/turn_suspension.rs#L92-L110))
- **Adds to D3 (classification):** both retry kinds arrive as the same `codexErrorInfo` (`responseStreamDisconnected`). Telling "waiting for network" apart needs the message text, which is fragile. Prefer bigbud's own network and wake signals. bigbud already maps `willRetry` to a warning in `apps/server/src/provider/Layers/Codex/Adapter.stream.handlers.misc.ts:116-123`.

## Could not verify

- **Clock behaviour during sleep.** Whether tokio timers (idle timeout, backoff) pause during system sleep. They use the monotonic `Instant`.
