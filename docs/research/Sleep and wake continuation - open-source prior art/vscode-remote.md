# VS Code remote: PersistentProtocol, grace periods, and sleep handling

Research date: 2026-10-22. Sources: microsoft/vscode at 171a964 (2026-10-22), latest release 1.143.0.

## Answer

VS Code Remote keeps everything on the remote host alive for a long reconnection grace period: 3 hours by default. That covers the extension host, the management connection and persistent terminals. A reconnecting window replays unacknowledged messages from both sides, keyed by message id. Delivery is exactly-once and in order, because the receiver drops anything that is not the next id. Sleep is handled mostly by not counting it. Every grace timer is a `ProcessTimeRunOnceScheduler` that counts 1 s interval ticks, so time spent suspended does not use up the budget on the side that slept. A load estimator stops a frozen or just-woken event loop from being read as a dead link. The classic remote stack does not listen to OS suspend or resume at all. The newer agent-host protocol for chat agent sessions does: it pauses its reconnect deadline across suspend, replays from a server sequence number, and fails a client-owned tool call with an explicit error after 30 s instead of re-running it.

## What happens when the connection is cut mid-turn

**Detection.** Both sides send a keepalive every 5 s (`KeepAliveSendTime`). A timeout fires when nothing has been received for 20 s (`TimeoutTime`), or when an unacknowledged message is 20 s old and no data arrived in that window. Acks are batched within 2 s ([ipc.net.ts#L289-L313](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/base/parts/ipc/common/ipc.net.ts#L289-L313), [#L1123-L1213](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/base/parts/ipc/common/ipc.net.ts#L1123-L1213)). Neither timeout fires while `LoadEstimator.hasHighLoad()` is true. The estimator records a tick every second and reports high load when half of the last 10 ticks are missing ([#L742-L787](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/base/parts/ipc/common/ipc.net.ts#L742-L787)). Right after wake, every tick is stale, so the check is suppressed for a few seconds. This is my reading of the code. The code comment only says the check guards against "the event loop being busy".

**Message ids, ack and replay.** Each regular message carries a monotonically increasing `id` and an `ack` of the highest id received. The sender keeps `_outgoingUnackMsg` until it is acked. The receiver accepts only `id === _incomingMsgId + 1`. On a gap it sends a `ReplayRequest`, at most once every 10 s, and the peer resends the whole unacked queue ([#L1014-L1030](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/base/parts/ipc/common/ipc.net.ts#L1014-L1030), [#L1045-L1052](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/base/parts/ipc/common/ipc.net.ts#L1045-L1052)). On reconnect, `beginAcceptReconnection` swaps in the new socket. `endAcceptReconnection` then re-sends an Ack for everything received, followed by every unacked message ([#L952-L990](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/base/parts/ipc/common/ipc.net.ts#L952-L990)). Duplicates and out-of-order messages are dropped, so delivery at this layer is exactly-once while both processes stay alive. The queue is in memory only.

**Client reconnect loop.** The loop starts on a socket close or timeout. The waits before attempts are `[0, 5, 5, 10, 10, 10, 10, 10, 30]` seconds, then 30 s for every later attempt. Each attempt has a 30 s connect timeout (`RECONNECT_TIMEOUT`). Network errors (`ETIMEDOUT`, `ENETUNREACH`, `ECONNREFUSED`, `ECONNRESET` on connect), "temporarily not available" and cancellations retry. A server rejection (`VSCODE_CONNECTION_ERROR`), a resolver error, an unknown error, or an expired grace time is a permanent failure ([remoteAgentConnection.ts#L24](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/platform/remote/common/remoteAgentConnection.ts#L24), [#L652-L746](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/platform/remote/common/remoteAgentConnection.ts#L652-L746)). The client's grace timer is a `ProcessTimeRunOnceScheduler`. Its own comment says a 3 h timer followed by an 8 h sleep fires "3hrs after waking" ([async.ts#L1265-L1335](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/base/common/async.ts#L1265-L1335)). A management-connection failure is fatal for the whole window. An extension-host failure only affects that connection (`reconnectionFailureIsFatal`, [#L748-L759](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/platform/remote/common/remoteAgentConnection.ts#L748-L759), [#L772-L791](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/platform/remote/common/remoteAgentConnection.ts#L772-L791)).

**Server grace period.** When the socket closes, the server's `ManagementConnection` waits `ReconnectionGraceTime`. The default is 3 h, and `--reconnection-grace-time` overrides it. If another client connects in the meantime, the server takes that as proof the owner has connectivity and shortens the wait to `ReconnectionShortGraceTime` (5 min). When the wait expires, the connection is disposed ([remoteExtensionManagement.ts#L51-L125](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/server/node/remoteExtensionManagement.ts#L51-L125), [remoteExtensionHostAgentServer.ts#L383-L391](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/server/node/remoteExtensionHostAgentServer.ts#L383-L391)). The remote extension host process enforces the same two timers on itself, read from `VSCODE_RECONNECTION_GRACE_TIME`, and terminates with "renderer disconnected for too long" (`src/vs/workbench/api/node/extensionHostProcess.ts` lines 215-262, read through the GitHub API). After disposal, a reconnect with the old token gets "Unknown reconnection token (seen before)" ([remoteExtensionHostAgentServer.ts#L415-L436](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/server/node/remoteExtensionHostAgentServer.ts#L415-L436)). The client turns that into a permanent failure ([remoteAgentConnection.ts#L813-L817](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/platform/remote/common/remoteAgentConnection.ts#L813-L817)). The only way out is to reload the window, which starts a fresh extension host. VS Code does not reattach to the old host.

**Terminals.** Persistent terminals live in the remote pty host. Each one has the same pair of grace timers, also process-time based, built from the server's grace values ([ptyService.ts#L804-L811](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/platform/terminal/node/ptyService.ts#L804-L811), [serverServices.ts#L236-L241](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/server/node/serverServices.ts#L236-L241)). `attach` cancels the timers. `detach` arms them only if the terminal has had interaction. A terminal is orphaned if no renderer answers an "orphan question" within 4 s ([#L830-L846](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/platform/terminal/node/ptyService.ts#L830-L846), [#L980-L1012](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/platform/terminal/node/ptyService.ts#L980-L1012)). A command running in a remote terminal keeps running through a laptop sleep of up to about 3 h. The scrollback (default 100 lines) is replayed on reattach.

## In-flight tool calls

The classic remote stack has no notion of a tool call. Extension-host RPCs simply wait while the protocol reconnects and replays. In the agent-host protocol, a transport loss rejects the client's pending requests, because the new transport has a separate request-id space. The client then sends `reconnect` with `lastSeenServerSeq`. The server replays from a 1000-entry buffer if that sequence is still in range. Otherwise it sends snapshots ([agentHostProtocolClient.ts#L915-L960](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/platform/agentHost/browser/agentHostProtocolClient.ts#L915-L960), [#L1111-L1112](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/platform/agentHost/browser/agentHostProtocolClient.ts#L1111-L1112), [protocolServerHandler.ts#L123-L127](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/platform/agentHost/node/protocolServerHandler.ts#L123-L127), [#L1344-L1349](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/platform/agentHost/node/protocolServerHandler.ts#L1344-L1349)). Some tool calls are executed by the client: their contributor is that client, and they are still pending. If that client stays disconnected for `CLIENT_TOOL_CALL_DISCONNECT_TIMEOUT = 30 s`, the server completes the call with `success: false` and the error "Client X disconnected before completing Y". Only when another connected client offers the same tool does the result add "You may try calling the tool again" ([#L1660-L1684](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/platform/agentHost/node/protocolServerHandler.ts#L1660-L1684), [#L2009-L2039](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/platform/agentHost/node/protocolServerHandler.ts#L2009-L2039)). The server never re-runs the tool on its own. That timer is wall-clock (`disposableTimeout`) on the server side.

## What is persisted, and when

- The `PersistentProtocol` queues and the agent-host replay buffer exist only in memory.
- Local chat (`workbench/contrib/chat`) serializes a response that is still `Pending` or `NeedsInput` as `Cancelled`, and does the same when loading old data. An interrupted request reloads as a cancelled response. It does not resume ([chatModel.ts#L2011](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/workbench/contrib/chat/common/model/chatModel.ts#L2011), [#L3378-L3381](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/workbench/contrib/chat/common/model/chatModel.ts#L3378-L3381)).
- A network error in a chat request shows "Sorry, there was a network error. Please try again later." ([chatErrorMessages.ts#L305-L306](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/workbench/contrib/chat/common/chatErrorMessages.ts#L305-L306)). Any automatic retry would live in the Copilot extension's networking code, which I did not check out.

## What the user sees

The window reports progress only once more than 40 s have passed since the last incoming data (`DISCONNECT_PROMPT_TIME`), so short blips stay silent ([remote.ts#L785](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/workbench/contrib/remote/browser/remote.ts#L785)). The states and messages are ([remote.ts#L775-L777](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/workbench/contrib/remote/browser/remote.ts#L775-L777), [#L886-L1016](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/workbench/contrib/remote/browser/remote.ts#L886-L1016)):

- "Connection Lost"
- "Attempting to reconnect in N seconds...", with "Reconnect Now" (which calls `ReconnectionWaitEvent.skipWait()`) and "Reload Window"
- "Disconnected. Attempting to reconnect..."
- On permanent failure, a modal error: "Cannot reconnect. Please reload the window." with "Reload Window"

## Retry limits and parking

- Classic remote has no attempt cap. It retries until the grace time expires (3 h of client process time), then parks on the reload modal.
- The agent host's default policy is exponential backoff from 1 s up to 30 s, with `maxAttempts: 10`. An optional `maxElapsedTimeMs` total budget is "excluding reported OS sleep" ([reconnectPolicy.ts#L6-L48](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/platform/agentHost/common/reconnectPolicy.ts#L6-L48)).
- When suspend fires, the client saves the remaining deadline. On resume it re-arms the deadline from that remainder ([agentHostProtocolClient.ts#L744-L790](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/platform/agentHost/browser/agentHostProtocolClient.ts#L744-L790)). The cloud sandbox wires `powerService.onDidSuspend/onDidResume` into this, with a 120 s budget for user-local hosts ([cloudSandboxAgentHostService.ts#L65-L70](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/workbench/contrib/chat/browser/remoteAgentHost/cloudSandboxAgentHostService.ts#L65-L70), [#L329-L331](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/workbench/contrib/chat/browser/remoteAgentHost/cloudSandboxAgentHostService.ts#L329-L331)).
- After exhaustion, automatic restore stops and recovery waits for a user action ([agentHostProtocolClient.ts#L1050-L1067](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/platform/agentHost/browser/agentHostProtocolClient.ts#L1050-L1067)).

## Sleep and resume detection

- Electron main exposes `powerMonitor` `suspend` and `resume` as `onDidSuspendOS` / `onDidResumeOS` ([nativeHostMainService.ts#L137-L138](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/platform/native/electron-main/nativeHostMainService.ts#L137-L138)). Main itself only logs `power.suspend` and `power.resume` telemetry ([app.ts#L1731-L1737](https://github.com/microsoft/vscode/blob/171a964de3b81209b9748b4b3561428a8b6ee409/src/vs/code/electron-main/app.ts#L1731-L1737)).
- In the checked-out tree, the only workbench consumer of `onDidResume` is the agent-host client described above. `remoteAgentConnection.ts` does not use it.
- The classic stack avoids needing a hint through two mechanisms: process-time grace timers, and the load estimator suppressing timeouts after a long gap.

## For bigbud

1. **Adds to D2. TypeScript.** Count recovery budgets in time the process was awake, not wall-clock time. Use either a 1 s tick counter like `ProcessTimeRunOnceScheduler`, or pause on the suspend hint and resume from the remainder like `_suspendReconnectDeadline`. Otherwise a long sleep exhausts D5's attempts or a grace window the moment the machine wakes. The tick-gap trick behind `LoadEstimator` doubles as the wall-clock-gap backup D2 already names.
2. **Confirms D4. Adds to D4.** The agent host fails a tool call whose owner disappeared with an explicit `success: false` result naming the tool. It does not re-run the tool. It invites a retry only when an equivalent executor is live. That matches "a tool may have been mid-flight: ask, do not continue". The explicit failed result is a good shape for what the model sees on a linked continuation.
3. **Adds to D7. Rust.** VS Code's remote survival comes from server-side grace windows: 3 h, shortened to 5 min when another client connects. Terminals are kept alive and reattached with replayed scrollback. bigbud's remote agent should have an explicit, configurable grace window for unattended operations. It should also return a distinct "operation gone" answer, like "Unknown reconnection token (seen before)", so the client can tell "expired" apart from "never existed".
4. **Adds to D1.** Exactly-once delivery in `PersistentProtocol` holds only while both processes survive. Its queues are in memory. Chat reloads an in-flight response as Cancelled. Neither replaces a durable intent written before dispatch. Use the protocol pattern (ids, acks, replay of the unacked queue, server sequence cursor) for transport reattach. Keep D1's durable states for crashes and restarts.
5. **Adds to the UX (Phase 6 item 7).** Delay the visible "reconnecting" state for 40 s after data stops. Offer "Reconnect Now" during backoff waits. Park on a single modal or banner with one action. bigbud's blue "Resuming after sleep" state could similarly stay hidden for the first few seconds after resume.
