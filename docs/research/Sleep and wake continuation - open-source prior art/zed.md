# Zed: SSH remote reconnect, collab reconnect, agent retries, and sleep hooks

Research date: 2026-10-22. Sources: zed-industries/zed at cfb894a (2026-10-22), latest release v1.25.2 (v1.26.1-pre is the newest pre-release).

## Answer

Zed's SSH remote keeps a detached `remote_server` daemon on the host. After a cut, the client starts a new `proxy --reconnect` process that attaches to the same daemon through its pid file and Unix sockets, then replays unacknowledged messages from an in-memory buffer keyed by message id. That is close to what D7 asks for. The daemon exits after 10 minutes without a client, though, and terminals and external ACP agents on a remote project are separate `ssh` children that the daemon does not own, so they do not survive a long sleep. The native agent retries a cut model stream a small, error-specific number of times with a visible countdown, then stops with a Retry button. Retry sends "Continue where you left off". It never re-runs a tool call that was already sent. gpui now reports sleep and wake on macOS, Windows and Linux (logind). The only caller outside gpui is the auto-updater, which restarts a stalled download on wake. Remote, collab and agent code ignore it.

## What happens when the connection is cut mid-turn

**SSH remote detection.** The client pings every 5 s with a 5 s timeout. Any incoming traffic counts as a heartbeat. After 5 missed heartbeats it reconnects ([remote_client.rs#L161-L170](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/remote/src/remote_client.rs#L161-L170), [#L799-L895](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/remote/src/remote_client.rs#L799-L895)). By that arithmetic a silent dead TCP connection is detected after about 50 s. If the local `ssh` proxy process exits instead, `monitor` starts a reconnect at once ([#L897-L940](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/remote/src/remote_client.rs#L897-L940)). Zed does not set `ServerAliveInterval`. The only ssh timeout option it passes is `ConnectTimeout` ([ssh.rs#L1979](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/remote/src/transport/ssh.rs#L1979)).

**Reconnect.** `MAX_RECONNECT_ATTEMPTS = 3`. A failed attempt goes straight into the next attempt, with no backoff delay ([remote_client.rs#L591-L797](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/remote/src/remote_client.rs#L591-L797), limit at [#L642-L650](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/remote/src/remote_client.rs#L642-L650)). Each attempt kills the old ssh master, opens a new connection through the pool, and runs `proxy --identifier <id> --reconnect` ([ssh.rs#L643-L676](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/remote/src/transport/ssh.rs#L643-L676)). The handshake and the resync each have a 15 s timeout (debug builds use 5 s).

**Reattaching to the same server.** The identifier names a state directory holding `server.pid`, `stdin.sock`, `stdout.sock` and `stderr.sock` ([server.rs#L884-L904](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/remote_server/src/server.rs#L884-L904)). With `--reconnect`, the proxy refuses to spawn a server. If the pid is gone it exits with a special code, which the client maps to `ServerNotRunning`. Without `--reconnect`, it kills any existing server and starts a fresh one ([server.rs#L980-L1012](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/remote_server/src/server.rs#L980-L1012)). This "reconnect never spawns" rule is the safety property D7 wants. On Windows the daemon is detached from sshd's job object so that closing the session does not kill it ([server.rs#L1186-L1195](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/remote_server/src/server.rs#L1186-L1195)).

**Server lifetime during the gap.** After a client connection ends, the daemon goes back to `accept` with `IDLE_TIMEOUT = 10 min`. If nothing connects in that time, it shuts down ([server.rs#L517-L560](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/remote_server/src/server.rs#L517-L560)). Language servers and the agent-server store live inside that daemon ([headless_project.rs#L231](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/remote_server/src/headless_project.rs#L231), [#L254-L262](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/remote_server/src/headless_project.rs#L254-L262)). If a sleep lasts more than about 10 minutes after the proxy dies, reattach ends in `ServerNotRunning`. The user then gets a fresh server that has lost all of that state.

**Message resync.** `ChannelClient` gives every envelope an increasing `id`. Each buffered send carries `ack_id = max_received` and is kept in a `VecDeque` until the peer acks it ([remote_client.rs#L1943-L1956](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/remote/src/remote_client.rs#L1943-L1956)). On reconnect the client sends `FlushBufferedMessages` unbuffered, so the peer trims everything already received and replays the rest. The client then resends its own buffer ([#L1628-L1664](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/remote/src/remote_client.rs#L1628-L1664), [#L1816-L1836](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/remote/src/remote_client.rs#L1816-L1836)). The daemon uses the same `ChannelClient`, so its outgoing messages are buffered as well ([server.rs#L645](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/remote_server/src/server.rs#L645)). The buffer exists only in memory and has no size cap. I found no duplicate check on the receive path: `handle_message` stores `max_received = incoming.id` without comparing it to the previous value. A request the server handled but never acked could therefore be handled twice after a reconnect. This comes from reading the code. I did not test it.

**Collab (`crates/client`).** Collab is a different stack. On `ConnectionLost` the client reconnects with exponential backoff from 500 ms to a 30 s cap, with jitter, and never stops ([client.rs#L87-L88](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/client/src/client.rs#L87-L88), [#L695-L740](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/client/src/client.rs#L695-L740)). The peer keepalive is 1 s with a 10 s receive timeout ([peer.rs#L94-L96](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/rpc/src/peer.rs#L94-L96)). The collab server keeps a lost connection's room membership for `RECONNECT_TIMEOUT = 30 s`, then removes it ([collab rpc.rs#L1362-L1366](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/collab/src/rpc.rs#L1362-L1366)). Any sleep longer than 30 s drops the user from the call. Collab has no sleep hint.

## In-flight tool calls

- **Native agent.** A stream error breaks the event loop, and Zed drops any tool input that was still streaming ("Dropping partial tool inputs because the stream ended"). Tools that had already started are awaited to completion, and their results are recorded before the retry ([thread.rs#L3159-L3180](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/agent/src/thread.rs#L3159-L3180), [#L3239-L3262](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/agent/src/thread.rs#L3239-L3262)). When the pending message is flushed, any tool use without a result gets a synthetic error result, "Tool canceled by user" ([#L4280-L4317](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/agent/src/thread.rs#L4280-L4317)). A tool is never re-run. The model sees either the real result or the canceled marker.
- **Remote terminals** are separate `ssh -t` commands from `build_command`, not children of the daemon ([ssh.rs#L2034-L2160](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/remote/src/transport/ssh.rs#L2034-L2160), [terminals.rs#L99-L112](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/project/src/terminals.rs#L99-L112)). **External ACP agents** on a remote project are local child processes whose stdio runs through `build_stdio_command`, which is also an ssh session ([agent_servers acp/transport.rs#L30-L80](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/agent_servers/src/acp/transport.rs#L30-L80)). Neither has any reattach code. A network cut breaks their pipes. I did not verify what happens to the remote process when that happens.

## What is persisted, and when

`Thread::to_db` serializes only completed `messages`. The streaming `pending_message` is left out on purpose, and saves are skipped while a message streams ([thread.rs#L1945-L1981](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/agent/src/thread.rs#L1945-L1981), [agent.rs#L398-L408](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/agent/src/agent.rs#L398-L408)). If Zed dies mid-step, the in-flight assistant text and any tool call issued in that step are lost from the saved thread, and so is the fact that the tool was called. Zed has no intent record and no "may have been sent" marker. The SSH resend buffer is also in memory only.

## What the user sees

- SSH title bar: "Connecting to", "Connected to", "Connection attempt to {host} missed. Retrying..." in warning colour, "Lost connection to {host}. Reconnecting..." in warning colour, and "Disconnected from {host}" in error colour ([title_bar.rs#L634-L656](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/title_bar/src/title_bar.rs#L634-L656)). Once attempts are exhausted or the server is gone, a "Disconnected" modal says the server is "not responding" or "process exiting unexpectedly". It offers "Reconnect" and "Close Window" ([disconnected_overlay.rs#L145-L210](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/recent_projects/src/disconnected_overlay.rs#L145-L210)).
- Agent: a callout reads "Retrying. Next attempt in N seconds." while the backoff runs ([thread_view.rs#L3813-L3860](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/agent_ui/src/conversation_view/thread_view.rs#L3813-L3860)). After the last attempt the error shows with a "Retry" button ([#L12538-L12542](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/agent_ui/src/conversation_view/thread_view.rs#L12538-L12542)). Retry calls `thread.resume`, which appends a `Resume` message that the model receives as the user text "Continue where you left off" ([thread.rs#L256-L261](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/agent/src/thread.rs#L256-L261), [#L2600-L2609](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/agent/src/thread.rs#L2600-L2609), [agent.rs#L3489](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/agent/src/agent.rs#L3489)).

## Retry limits and parking

`retry_strategy_for` sorts errors into classes ([thread.rs#L4825-L4877](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/agent/src/thread.rs#L4825-L4877)):

| Error class                                                           | Retry policy                                                                   |
| --------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| `HttpSend`, `ApiReadResponseError`, `DeserializeResponse` (transport) | fixed 5 s, 3 attempts                                                          |
| `StreamEndedUnexpectedly`, `SerializeRequest`, `BuildRequestBody`     | fixed 5 s, 1 attempt                                                           |
| `Other` (mid-stream mapping)                                          | fixed 5 s, 2 attempts                                                          |
| Transient provider rejections                                         | provider `retry_after`, or exponential backoff, up to `MAX_RETRY_ATTEMPTS = 4` |
| Auth, model unavailable, consent, non-transient rejections            | none                                                                           |

Delays get up to 10% jitter ([agent.rs#L77-L82](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/agent/src/agent.rs#L77-L82)). If the last agent message has no tool results, an automatic retry also appends `Resume`. Otherwise it resends the tool results ([thread.rs#L3279-L3302](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/agent/src/thread.rs#L3279-L3302)). Cancelling during the wait stops the turn ([#L3322-L3346](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/agent/src/thread.rs#L3322-L3346)). Zed Cloud models retry automatically only when the user has a plan ([#L3601-L3609](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/agent/src/thread.rs#L3601-L3609)). The retry timer is a normal executor timer, so a sleep during the countdown just shortens the wait.

## Sleep and wake in gpui

- macOS observes `NSWorkspaceWillSleepNotification` and `NSWorkspaceDidWakeNotification` ([gpui_macos platform.rs#L1304-L1323](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/gpui_macos/src/platform.rs#L1304-L1323)).
- Windows handles `WM_POWERBROADCAST` with `PBT_APMSUSPEND` and `PBT_APMRESUMEAUTOMATIC` ([gpui_windows platform.rs#L1383-L1394](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/gpui_windows/src/platform.rs#L1383-L1394)).
- Linux subscribes to logind `PrepareForSleep` over the system D-Bus ([gpui_linux platform.rs#L245-L269](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/gpui_linux/src/linux/platform.rs#L245-L269)).
- The app-level API is `cx.on_system_sleep` / `cx.on_system_wake` ([gpui app.rs#L1680](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/gpui/src/app.rs#L1680), [#L1747](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/gpui/src/app.rs#L1747)).
- The one consumer I found outside gpui is `auto_update`. Its comment says an in-flight download "is almost certainly riding a TCP connection that silently died during suspend". On wake it restarts only the network phases (`Checking` or `Downloading`), never `Installing` ([auto_update.rs#L452-L460](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/auto_update/src/auto_update.rs#L452-L460), [#L474-L488](https://github.com/zed-industries/zed/blob/cfb894a5dde8ccf3fba1659164f47fdd1c024e2e/crates/auto_update/src/auto_update.rs#L474-L488)).
- A `git grep` of the whole tree at this commit finds no other caller of `on_system_wake`, so `remote`, `remote_server`, `client`, `agent`, `acp_thread` and `agent_ui` ignore these hooks. After wake, SSH still waits for heartbeats to fail.

## For bigbud

1. **Confirms D7. Rust.** The reattach key in Zed is a stable identifier mapped to a pid file and sockets, plus a `--reconnect` mode that refuses to spawn and returns a distinct "server not running" exit code. bigbud's remote agent should have the same split: reattach mode either attaches to the journaled process or reports it gone, and never starts a new run.
2. **Adds to D7.** Zed's daemon exits after 10 idle minutes, and its terminals and ACP agents ride separate ssh sessions. Both break "remote work keeps running during sleep" for sleeps of 10 minutes or more. The bigbud remote agent must own the provider and tool processes itself, and its idle shutdown has to be longer than any realistic sleep, or tied to the journal (no idle exit while an operation is open).
3. **Adds to D1. Rust or TypeScript.** Zed's ack/replay buffer is in memory and appears to have no duplicate suppression on receive. Replay gives at-least-once delivery. A side-effecting request needs an idempotency key or journal entry that the receiver checks. This supports writing `may-have-been-sent` before dispatch rather than relying on transport replay.
4. **Confirms D2. Adds to D2.** gpui shows the full native set, including logind `PrepareForSleep` on Linux. Zed also shows the cost of not wiring it: SSH can take about 50 s to notice a dead link after wake. bigbud should start the reconnect and the probe on resume rather than wait for heartbeats. The auto-updater's "restart network phases only, never the install phase" rule is the same split as D4.
5. **Confirms D4. Adds to D5.** Zed never re-runs an already started tool. Unanswered tool uses get an explicit canceled result, and the model is told "Continue where you left off". bigbud's linked continuation can use the same framing. Zed's limits are per error class (1 to 4 attempts) with a visible countdown and a final Retry button, which is consistent with D5's "3 then park". Classifying first, so that auth or consent errors are never retried, is worth copying.
6. **Contradicts nothing, but warns on D1.** Zed does not persist a streaming step at all. A crash or kill mid-tool loses the record that the tool was called. bigbud's durable intent written before dispatch is strictly stronger and should stay.
