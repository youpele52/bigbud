# Durable execution: Restate and Temporal

Research date: 2026-10-22. Sources: restatedev/restate at e410013 (2026-10-22, `main`, version 1.8.2-dev), latest release v1.8.1 (defaults below re-checked at the v1.8.1 tag); restatedev/sdk-typescript at b1080a1 (`main`, 2026-10-22) for one doc comment; temporalio/sdk-typescript at f4c92a5 (2026-10-22), latest release v1.24.0. DBOS and Inngest from docs only.

## Answer

Neither Restate nor Temporal has a "this side effect may have run, ask a person" state. Both run the side-effecting step at least once and make the step's author responsible for idempotency. Restate makes the uncertain window as small as possible: it journals a named `Run` command, keeps the result only after the server acknowledges it, and lets at most one un-journaled run happen at a time. After a crash, at most the latest run executes again. When retries run out, Restate pauses the invocation by default instead of killing it. The pause records the last error and the name of the command involved, and a person resumes it from the CLI or UI. That is the closest prior art for D5's park-with-Retry and for D4's prompt that names the action. bigbud's D4 is stricter than both systems for a good reason: bigbud does not write the tools. A shell command or file edit run by a provider has no idempotency key, so the at-least-once retry these systems use is not available to bigbud.

## What happens when the connection is cut mid-turn

**Restate.** The invoker in the server streams the journal to the SDK over HTTP. If the stream breaks, the invoker raises a transient `InvokerError`. Almost every invoker error counts as transient ([error.rs#L225-L231](https://github.com/restatedev/restate/blob/e410013917885a4a7561be80fbbbbdf00c0f5759/crates/invoker-impl/src/error.rs#L225-L231)). `handle_task_error` then schedules a retry timer from the retry iterator. When the iterator is exhausted, or the error is not transient, it applies `on_max_attempts`: `Pause` or `Kill` ([invocation_state_machine.rs#L535-L616](https://github.com/restatedev/restate/blob/e410013917885a4a7561be80fbbbbdf00c0f5759/crates/invoker-impl/src/invocation_state_machine.rs#L535-L616)). A retry is a new attempt that replays the journal. If the SDK sends nothing for the inactivity timeout, the invoker closes the stream and the invocation suspends ([service_protocol_runner_v4.rs#L683-L688](https://github.com/restatedev/restate/blob/e410013917885a4a7561be80fbbbbdf00c0f5759/crates/invoker-impl/src/invocation_task/service_protocol_runner_v4.rs#L683-L688)). The defaults are 60 s inactivity and 600 s abort ([worker.rs#L391-L393](https://github.com/restatedev/restate/blob/e410013917885a4a7561be80fbbbbdf00c0f5759/crates/types/src/config/worker.rs#L391-L393)). Nothing in Restate is specific to sleep. A host that sleeps and wakes looks the same as a broken stream or an inactive one.

**Temporal.** The TS SDK documents that the server "doesn't detect Worker process failures directly". Instead, the server uses `startToCloseTimeout` for each attempt and `heartbeatTimeout` for long activities ([activity-options.ts#L110-L122](https://github.com/temporalio/sdk-typescript/blob/f4c92a5f43873a0e80f98b9cb138253df541cdd3/packages/common/src/activity-options.ts#L110-L122)). An attempt that never reports back times out and is retried under the retry policy. `scheduleToCloseTimeout` caps the total time across all retries ([activity-options.ts#L132-L141](https://github.com/temporalio/sdk-typescript/blob/f4c92a5f43873a0e80f98b9cb138253df541cdd3/packages/common/src/activity-options.ts#L132-L141)). A cut connection therefore surfaces only as a timeout, followed by another attempt.

## In-flight tool calls (side effects)

**Restate.** The protocol journals a `RunCommandMessage` that carries the run's `name` ([protocol.proto#L638-L646](https://github.com/restatedev/restate/blob/e410013917885a4a7561be80fbbbbdf00c0f5759/service-protocol/dev/restate/service/protocol.proto#L638-L646)). After the closure finishes, the SDK sends `ProposeRunCompletionMessage`. That message is "not written to the journal immediately"; the SDK waits for an ack meaning "stored and replicated" ([protocol.proto#L214-L226](https://github.com/restatedev/restate/blob/e410013917885a4a7561be80fbbbbdf00c0f5759/service-protocol/dev/restate/service/protocol.proto#L214-L226), [#L241-L264](https://github.com/restatedev/restate/blob/e410013917885a4a7561be80fbbbbdf00c0f5759/service-protocol/dev/restate/service/protocol.proto#L241-L264)). The invoker records the run name with the command ([service_protocol_runner_v4.rs#L1109-L1114](https://github.com/restatedev/restate/blob/e410013917885a4a7561be80fbbbbdf00c0f5759/crates/invoker-impl/src/invocation_task/service_protocol_runner_v4.rs#L1109-L1114)). The TS SDK states the guarantee directly ([context.ts#L390-L406](https://github.com/restatedev/sdk-typescript/blob/b1080a11984b35419e0e825a0e82bc17c656a22d/packages/libs/restate-sdk/src/context.ts#L390-L406)):

> There is a small window where an action may be re-run, if a failure occurred between a successful run and persisting the result. No second action will be run while a previous run's result is not yet durable ... at most one run will be re-executed on replay.

So a journal with a `Run` command and no completion is Restate's "may have run" state. Restate does not show it to anyone. It runs the action again. The protocol also lets the SDK say it is "executing side effects" while it waits (`AwaitingOnMessage`, [protocol.proto#L228-L236](https://github.com/restatedev/restate/blob/e410013917885a4a7561be80fbbbbdf00c0f5759/service-protocol/dev/restate/service/protocol.proto#L228-L236)). The server does not act on that flag yet; the handler ends in `todo(azmy): Handle awaiting on message` ([service_protocol_runner_v4.rs#L1449-L1476](https://github.com/restatedev/restate/blob/e410013917885a4a7561be80fbbbbdf00c0f5759/crates/invoker-impl/src/invocation_task/service_protocol_runner_v4.rs#L1449-L1476)).

**Temporal.** The docs say: "Because Activities may be retried, these functions may be executed more than once." They also name the exact gap: "The Activity function completes successfully, but the Worker crashes just before it notifies the Temporal Service." Their remedy is to make activities idempotent and to "use a combination of the Workflow Run ID and the Activity ID as an idempotency key" ([docs: activity definition](https://docs.temporal.io/activity-definition)). The SDK's `activityId` defaults to a sequence number and "does not need to be unique" ([activity-options.ts#L83-L90](https://github.com/temporalio/sdk-typescript/blob/f4c92a5f43873a0e80f98b9cb138253df541cdd3/packages/common/src/activity-options.ts#L83-L90)).

**Heartbeats.** `heartbeat(details)` records progress. On the next attempt, `activityInfo().heartbeatDetails` holds the last recorded value, "a periodic checkpoint mechanism for the progress of an Activity". If the final attempt times out, the workflow gets `TimeoutFailure.lastHeartbeatDetails` ([activity/src/index.ts#L397-L420](https://github.com/temporalio/sdk-typescript/blob/f4c92a5f43873a0e80f98b9cb138253df541cdd3/packages/activity/src/index.ts#L397-L420), [#L254-L259](https://github.com/temporalio/sdk-typescript/blob/f4c92a5f43873a0e80f98b9cb138253df541cdd3/packages/activity/src/index.ts#L254-L259)). An activity receives cancellation only if it heartbeats ([index.ts#L23-L45](https://github.com/temporalio/sdk-typescript/blob/f4c92a5f43873a0e80f98b9cb138253df541cdd3/packages/activity/src/index.ts#L23-L45)). The cancellation reasons are `notFound`, `cancelRequested`, `paused`, `timedOut`, `workerShutdown` and `reset` ([activity-cancellation-details.ts#L3-L10](https://github.com/temporalio/sdk-typescript/blob/f4c92a5f43873a0e80f98b9cb138253df541cdd3/packages/common/src/activity-cancellation-details.ts#L3-L10)). The activity's own code decides how to resume. Temporal only carries the checkpoint value.

**DBOS (docs only).** "If a workflow fails while executing a step, it retries the step during recovery." "Steps should be idempotent." A checkpointed step is never run again ([docs](https://docs.dbos.dev/architecture)).

**Inngest (docs only).** Completed steps are memoized and failed steps are retried. The docs warn that a refund "can succeed before Inngest saves the step result and retries the step", so the step must be idempotent ([docs](https://www.inngest.com/docs/learn/how-functions-are-executed)).

## What is persisted, and when

- **Restate.** The invocation status is durable: `Scheduled`, `Inboxed`, `Invoked`, `Suspended { awaiting_on }`, `Paused`, `Completed` ([invocation_status_table/mod.rs#L144-L157](https://github.com/restatedev/restate/blob/e410013917885a4a7561be80fbbbbdf00c0f5759/crates/storage-api/src/invocation_status_table/mod.rs#L144-L157)). The user-facing status is derived from it: `pending`, `scheduled`, `completed`, `suspended`, `paused`, `running` (an attempt is in flight), `backing-off` (invoked with `retry_count > 0`), otherwise `ready` ([context.rs#L113-L122](https://github.com/restatedev/restate/blob/e410013917885a4a7561be80fbbbbdf00c0f5759/crates/storage-query-datafusion/src/context.rs#L113-L122)). The same view also stores `last_failure_related_command_name` and its index and type.
- **Restate.** The attempt count survives task recreation. A new invoker task calls `retry_iter.fast_forward(...retry_attempts)` from stored metadata ([invoker-impl/src/lib.rs#L543-L553](https://github.com/restatedev/restate/blob/e410013917885a4a7561be80fbbbbdf00c0f5759/crates/invoker-impl/src/lib.rs#L543-L553)), so restarting the server does not reset the limit.
- **Restate idempotency keys.** Ingress accepts an `idempotency-key` header ([service_handler.rs#L437-L441](https://github.com/restatedev/restate/blob/e410013917885a4a7561be80fbbbbdf00c0f5759/crates/ingress-http/src/handler/service_handler.rs#L437-L441)). Completed results are kept for deduplication for a default of 24 h ([invocation.rs#L132](https://github.com/restatedev/restate/blob/e410013917885a4a7561be80fbbbbdf00c0f5759/crates/types/src/config/invocation.rs#L132)).
- **Temporal.** The server keeps the last heartbeat details and the attempt number. The worker keeps nothing durable.

## What the user sees

- **Restate.** On pause, the invoker emits a `PausedEvent` with `last_failure`: the error code, message, stack trace, and `related_command_index`, `related_command_name` and `related_command_type` ([invoker-impl/src/lib.rs#L1389-L1450](https://github.com/restatedev/restate/blob/e410013917885a4a7561be80fbbbbdf00c0f5759/crates/invoker-impl/src/lib.rs#L1389-L1450)). An operator therefore sees which named step was failing. Resume uses `restate invocations resume <id>` or the UI, and can also move a `backing-off` invocation forward. `pause`, `cancel` and `kill` exist too, and kill "may leave your service in an inconsistent state" ([docs: managing invocations](https://docs.restate.dev/services/invocation/managing-invocations)).
- **Temporal.** The workflow sees an `ActivityFailure` only after retries are exhausted. With the default `maximumAttempts` of `Infinity` ([retry-policy.ts#L26-L32](https://github.com/temporalio/sdk-typescript/blob/f4c92a5f43873a0e80f98b9cb138253df541cdd3/packages/common/src/retry-policy.ts#L26-L32)), that never happens unless a timeout ends it. An operator can run `temporal activity pause`. That stops new retries, but it is manual and does not fire on exhaustion. A running attempt that heartbeats is interrupted at its next heartbeat; one that does not heartbeat keeps running ([docs: pause](https://docs.temporal.io/activity-operations/pause)).

## Retry limits and parking

- **Restate defaults** ([invocation.rs#L151-L242](https://github.com/restatedev/restate/blob/e410013917885a4a7561be80fbbbbdf00c0f5759/crates/types/src/config/invocation.rs#L151-L242)): 500 ms initial interval, factor 2.0, 60 s maximum interval, 70 attempts, and `on_max_attempts = Pause` (`#[default]`). These values are the same at the v1.8.1 tag. The SDK can ask for `Pause`, `Fail` or a retry with an interval override, and that request takes precedence over the policy. A user-requested pause short-circuits everything else. `ctx.run` has its own policy (`maxRetryAttempts`, `maxRetryDuration`); when that policy is exhausted, the run throws `TerminalError` ([docs: TS durable steps](https://docs.restate.dev/develop/ts/durable-steps.md)).
- **Temporal defaults:** 1 s initial interval, coefficient 2, maximum interval 100 times the initial, unlimited attempts ([retry-policy.ts#L8-L41](https://github.com/temporalio/sdk-typescript/blob/f4c92a5f43873a0e80f98b9cb138253df541cdd3/packages/common/src/retry-policy.ts#L8-L41)). Nothing parks automatically.

## Concept mapping to bigbud

| Restate / Temporal concept                                        | bigbud design                                                 | Relation                                                                    |
| ----------------------------------------------------------------- | ------------------------------------------------------------- | --------------------------------------------------------------------------- |
| Restate `RunCommand` journaled with a name, no completion yet     | D1 `may-have-been-sent` on the dispatch attempt               | Same idea: durable "started, outcome unknown" marker                        |
| Restate `ProposeRunCompletion` acked as stored                    | D1 `provider-acknowledged`                                    | Same: outcome known only after a durable write                              |
| Restate SDK: no second run until the previous one is durable      | One dispatch attempt in flight per intent                     | Confirms the single-attempt rule                                            |
| Restate retries the un-journaled run (at least once)              | D4: tool may have been mid-flight, so ask                     | bigbud is deliberately stricter                                             |
| Temporal: retry the attempt; activity must be idempotent          | D4 ask; no rerun allowlist yet                                | Contrast: bigbud cannot add idempotency keys to provider tools              |
| Restate `on_max_attempts = pause`, durable attempt count          | D5 park after 3 with Retry                                    | Confirms; Restate's default is 70 because its retries are cheap and safe    |
| Restate `PausedEvent.related_command_name`                        | D4 prompt naming the uncertain action                         | Confirms the prompt content                                                 |
| Restate status `running` / `backing-off` / `paused` / `suspended` | Intent recovery status, including `interrupted-by-sleep` (D3) | Adds: derive the shown status from stored facts                             |
| Temporal `heartbeatDetails` (checkpoint read on the next attempt) | Remote agent output sequence and ack (D7)                     | Different purpose: replay cursor for reattach, not a resume point for rerun |
| Restate idempotency key, 24 h retention                           | Remote agent `operation_id` + `request_digest` with retention | Confirms D7 deduplication                                                   |

## For bigbud

1. **Confirms D1.** Restate writes a named command before the side effect and treats the outcome as unknown until a stored ack exists. That is the same shape as `prepared` → `may-have-been-sent` → `provider-acknowledged`. Keep these rows in TypeScript with the canonical intent state (D8).
2. **Adds to D1.** Restate never allows a second un-journaled run while one is unresolved. bigbud should enforce the same rule: at most one dispatch attempt per intent may be in `may-have-been-sent`. A new attempt is created only after the previous one is resolved or explicitly given up by the user. This keeps the uncertain set at size one, which keeps the D4 prompt simple.
3. **Confirms D4, with the contrast stated.** Restate, Temporal, DBOS and Inngest all rerun the uncertain step and rely on the author's idempotency. bigbud does not write the tools and has no idempotency key for a provider's shell command, so asking is the only safe choice. If the rerun allowlist is revisited, Temporal's rule applies: rerun only what is idempotent by construction.
4. **Confirms D5, and adds two details.** Restate pauses by default, not kill, and stores the attempt count durably so a restart does not reset it ([lib.rs#L543-L553](https://github.com/restatedev/restate/blob/e410013917885a4a7561be80fbbbbdf00c0f5759/crates/invoker-impl/src/lib.rs#L543-L553)). bigbud's 3-attempt counter should live on the intent row, not in memory. A parked intent should keep the last failure and the name of the related action, as `PausedEvent` does, so the Retry card can say what failed. A user Stop should short-circuit to revoke, the way `requested_pause` short-circuits Restate's policy.
5. **Adds to D3.** Restate derives `running` and `backing-off` from stored facts (an attempt in flight, and the retry count) instead of storing them separately. bigbud can derive "Resuming after sleep" the same way, from the intent's recovery status plus whether an attempt is live. No extra state is needed.
6. **Confirms D7 (Rust).** bigbud's remote agent journal records `Accepted` (operation ID plus request digest), `Started`, sequenced `Output`, `Acknowledged`, `OutputWatermark`, `Retention` and `Completed`, with `sync_all` after each append (`crates/bigbud-remote-agent/src/operations/journal.rs`). The registry returns `Duplicate` for the same ID and digest, and `OperationIdConflict` if the digest differs (`crates/bigbud-remote-agent/src/operations/registry.rs`, `core.rs`). That is an idempotency key with payload checking, which is stronger than a bare key. When the agent itself restarts, every non-terminal operation becomes `Expired` with `AGENT_RESTARTED` (`registry.rs` `expire_non_terminal`, called from `crates/bigbud-remote-agent/src/session/core.rs`). It is never rerun. That is the same "do not rerun" choice as D4, made inside Rust. Temporal heartbeats are a different tool: a checkpoint that a retry uses to skip completed work. bigbud never retries the remote process, so it needs a replay cursor (sequence and ack), which it already has.
