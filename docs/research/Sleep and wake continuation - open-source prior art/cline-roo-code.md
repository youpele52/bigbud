# Cline and Roo Code: resuming an interrupted task

Research date: 2026-10-22. Sources: cline/cline at c441897 (2026-10-21), latest release v4.1.25 (2026-10-16); the classic pre-SDK Cline `Task` at tag v3.85.0 (9ee6181, 2026-05-25); RooCodeInc/Roo-Code at b867ec9 (2026-05-15), latest release v3.54.0. The Roo Code GitHub repository is archived (read-only) as of 2026-05-15, and v3.54.0 is its last release.

## Answer

Neither project detects sleep or network loss. Both treat an interrupted task the same way: when the task is reopened, they load the saved conversation, show a "Resume Task" ask, and wait for the user to click. On resume they fill in any tool call that has no result with a made-up result, then let the model decide what to redo. The useful parts for bigbud are in Cline's current SDK runtime and its cloud client. A failed model request is retried automatically only if it produced nothing visible and ran no tools, at most 3 times. The assistant message is saved before its tools run. After a dropped connection, the cloud client checks whether the server already accepted a prompt before it sends it again. Roo Code and classic Cline get this wrong: they resend after a mid-stream failure even when a tool may already have run, and they leave reconciling it to the model. That is the replay bigbud's invariant forbids.

Cline was restructured between v3.85.0 and v3.86.0. The classic `src/core/task/index.ts` with `resumeTaskFromHistory` is gone, and its job is now done by `apps/vscode/src/sdk/*` on top of `sdk/packages/agents` and `sdk/packages/core`. Roo Code still uses the classic design, forked from Cline. Neither has a `resumePausedTask`. Roo's equivalent for subtasks is `resumeAfterDelegation`, which is unrelated to crashes.

## What happens when the connection is cut mid-turn

**Cline today (SDK runtime).** A model turn that fails is retried only when all of these hold: it failed with a retryable provider error, it produced no content, it ran no provider-side tools, and it was not an auth or context-window error ([agent-runtime.ts#L1282-L1314](https://github.com/cline/cline/blob/c441897f11f658f978a00678f045670c1ab2b60d/sdk/packages/agents/src/agent-runtime.ts#L1282-L1314)). The code comment says why: re-streaming would show output twice, and "re-issuing the request could run those side effects again". There are at most 3 retries, with backoff that doubles from 1 s and is capped at 15 s ([#L87-L91](https://github.com/cline/cline/blob/c441897f11f658f978a00678f045670c1ab2b60d/sdk/packages/agents/src/agent-runtime.ts#L87-L91), [#L1242-L1280](https://github.com/cline/cline/blob/c441897f11f658f978a00678f045670c1ab2b60d/sdk/packages/agents/src/agent-runtime.ts#L1242-L1280)). When a turn ends with an unknown finish reason and has no tool calls, the runtime saves the partial message, adds "Previous turn ended unexpectedly. Continue from where you left off." as a user-role reminder, and continues once ([#L1202-L1233](https://github.com/cline/cline/blob/c441897f11f658f978a00678f045670c1ab2b60d/sdk/packages/agents/src/agent-runtime.ts#L1202-L1233)). Any other failure ends the turn with an `api_req_failed` ask ([message-translator.ts#L1322-L1346](https://github.com/cline/cline/blob/c441897f11f658f978a00678f045670c1ab2b60d/apps/vscode/src/sdk/message-translator.ts#L1322-L1346)).

**Classic Cline (v3.85.0).** If the first chunk fails, it retries automatically 3 times after 2, 4 and 8 s, then shows `api_req_failed` ([index.ts#L2100-L2175](https://github.com/cline/cline/blob/9ee618111d58630fea30b27439216448225458e0/src/core/task/index.ts#L2100-L2175)). If the stream fails partway, it saves the partial text to the API history with `[Response interrupted by API Error]` appended ([#L2723-L2757](https://github.com/cline/cline/blob/9ee618111d58630fea30b27439216448225458e0/src/core/task/index.ts#L2723-L2757)). It then cancels the task, rebuilds it from disk, and after the same backoff presses Resume itself (`handleWebviewAskResponse("yesButtonClicked")`). That happens even though the code's own comment says some tools may already have run ([#L3016-L3060](https://github.com/cline/cline/blob/9ee618111d58630fea30b27439216448225458e0/src/core/task/index.ts#L3016-L3060)).

**Roo Code.** First-chunk failure behaves like classic Cline: with auto-approval on, it retries automatically; otherwise it shows `api_req_failed` with Retry ([Task.ts#L4217-L4253](https://github.com/RooCodeInc/Roo-Code/blob/b867ec9145750d0ae1ff7f02d35406e9bf2a0b16/src/core/task/Task.ts#L4217-L4253)). A mid-stream failure marks the UI row "Provider ended the request" and pushes the same user content back onto the request stack. The request is sent again with no attempt cap. With auto-approval on, it waits first. Without it, it resends immediately ([#L3145-L3198](https://github.com/RooCodeInc/Roo-Code/blob/b867ec9145750d0ae1ff7f02d35406e9bf2a0b16/src/core/task/Task.ts#L3145-L3198)). Roo's `abortStream` no longer writes an "interrupted" marker to the API history ([#L2672-L2694](https://github.com/RooCodeInc/Roo-Code/blob/b867ec9145750d0ae1ff7f02d35406e9bf2a0b16/src/core/task/Task.ts#L2672-L2694)). The i18n string "Response interrupted by API error" still exists, but no code under `src/` or `webview-ui/` uses it.

## In-flight tool calls

Both classic designs run a tool **during** the stream, as soon as its block is complete ([Roo Task.ts#L2896-L2900](https://github.com/RooCodeInc/Roo-Code/blob/b867ec9145750d0ae1ff7f02d35406e9bf2a0b16/src/core/task/Task.ts#L2896-L2900)). Roo's own comment says tools "execute during streaming via presentAssistantMessage, BEFORE the assistant message is saved" ([#L1042-L1050](https://github.com/RooCodeInc/Roo-Code/blob/b867ec9145750d0ae1ff7f02d35406e9bf2a0b16/src/core/task/Task.ts#L1042-L1050)). The "save assistant message BEFORE executing tools" step at [#L3439-L3444](https://github.com/RooCodeInc/Roo-Code/blob/b867ec9145750d0ae1ff7f02d35406e9bf2a0b16/src/core/task/Task.ts#L3439-L3444) only covers blocks still partial when the stream ends. So when a stream fails after a tool ran, the API history has no record of that tool. The mid-stream retry then resends the same request, and the model may issue the tool again. This is an inference from the code; I did not reproduce it.

Cline's SDK runtime saves the assistant message, including its tool calls, before running tools: `recordAssistantMessage` runs at [agent-runtime.ts#L906](https://github.com/cline/cline/blob/c441897f11f658f978a00678f045670c1ab2b60d/sdk/packages/agents/src/agent-runtime.ts#L900-L906) and `executeToolCalls` at [#L974](https://github.com/cline/cline/blob/c441897f11f658f978a00678f045670c1ab2b60d/sdk/packages/agents/src/agent-runtime.ts#L974). The VS Code host writes the transcript to disk on that `assistant-message` event ([local-runtime-host.ts#L957-L975](https://github.com/cline/cline/blob/c441897f11f658f978a00678f045670c1ab2b60d/sdk/packages/core/src/runtime/host/local-runtime-host.ts#L957-L975)). Event hooks are awaited ([agent-runtime.ts#L2772-L2773](https://github.com/cline/cline/blob/c441897f11f658f978a00678f045670c1ab2b60d/sdk/packages/agents/src/agent-runtime.ts#L2772-L2773)). After a crash, a `tool_use` with no `tool_result` is therefore reliable evidence that a tool may have been in flight.

On resume, every project fills each unmatched `tool_use` with a placeholder result so the provider accepts the history:

- Roo: `"Task was interrupted before this tool call could be completed."` ([Task.ts#L2061-L2125](https://github.com/RooCodeInc/Roo-Code/blob/b867ec9145750d0ae1ff7f02d35406e9bf2a0b16/src/core/task/Task.ts#L2061-L2125)). A second repair pass uses `"Tool execution was interrupted before completion."` ([validateToolResultIds.ts#L184-L190](https://github.com/RooCodeInc/Roo-Code/blob/b867ec9145750d0ae1ff7f02d35406e9bf2a0b16/src/core/task/validateToolResultIds.ts#L184-L190)). Both texts can be false: the tool may have finished.
- Cline today: `"[migration] Tool result missing in legacy conversation history."` ([initial-message-sanitizer.ts#L48-L57](https://github.com/cline/cline/blob/c441897f11f658f978a00678f045670c1ab2b60d/apps/vscode/src/sdk/initial-message-sanitizer.ts#L48-L57), [#L88-L112](https://github.com/cline/cline/blob/c441897f11f658f978a00678f045670c1ab2b60d/apps/vscode/src/sdk/initial-message-sanitizer.ts#L88-L112)). It is applied to SDK-saved history as well as legacy history ([sdk-session-history-loader.ts#L6-L21](https://github.com/cline/cline/blob/c441897f11f658f978a00678f045670c1ab2b60d/apps/vscode/src/sdk/sdk-session-history-loader.ts#L6-L21)).

The text sent to the model on resume:

- Classic Cline: `[TASK RESUMPTION] This task was interrupted {ago}. It may or may not be complete ... Be aware that the project state may have changed since then ... If you previously attempted a tool use that the user did not provide a result for, you should assume the tool use was not successful and assess whether you should retry.` Within 30 s it adds that an interrupted `replace_in_file`/`write_to_file` "was reverted back to its original state" ([responses.ts#L239-L245 at v3.85.0](https://github.com/cline/cline/blob/9ee618111d58630fea30b27439216448225458e0/src/core/prompts/responses.ts#L239-L245), used at [index.ts#L1343-L1384](https://github.com/cline/cline/blob/9ee618111d58630fea30b27439216448225458e0/src/core/task/index.ts#L1343-L1384)). The function is still in current Cline ([responses.ts#L230-L256](https://github.com/cline/cline/blob/c441897f11f658f978a00678f045670c1ab2b60d/apps/vscode/src/core/prompts/responses.ts#L230-L256)), but `git grep` finds no caller.
- Cline today: only `"[TASK RESUMPTION] Please continue where you left off."`, hidden from the transcript. Per the code comment, the original task text is deliberately left out because "the model treats it as new instructions and redoes already-completed work (#12975)" ([sdk-followup-coordinator.ts#L20-L27](https://github.com/cline/cline/blob/c441897f11f658f978a00678f045670c1ab2b60d/apps/vscode/src/sdk/sdk-followup-coordinator.ts#L20-L27)).
- Roo: placeholder tool results, plus the user's typed text if any. Otherwise only `"[TASK RESUMPTION] Resuming task..."` ([Task.ts#L2155-L2178](https://github.com/RooCodeInc/Roo-Code/blob/b867ec9145750d0ae1ff7f02d35406e9bf2a0b16/src/core/task/Task.ts#L2155-L2178)). Roo still computes the "ago" text but never sends it ([#L2135-L2153](https://github.com/RooCodeInc/Roo-Code/blob/b867ec9145750d0ae1ff7f02d35406e9bf2a0b16/src/core/task/Task.ts#L2135-L2153)).

## What is persisted, and when

- Roo, UI messages: the whole `ui_messages.json` is rewritten when a message is added and when a partial message is completed. Streaming updates to a partial message are not saved ([Task.ts#L1727-L1776](https://github.com/RooCodeInc/Roo-Code/blob/b867ec9145750d0ae1ff7f02d35406e9bf2a0b16/src/core/task/Task.ts#L1727-L1776)). Writes go through `safeWriteJson`: a temp file, a backup, and a `proper-lockfile` advisory lock.
- Roo, API history: the user message is written before the request, on the first attempt only ([#L2588-L2599](https://github.com/RooCodeInc/Roo-Code/blob/b867ec9145750d0ae1ff7f02d35406e9bf2a0b16/src/core/task/Task.ts#L2588-L2599)). The assistant message is written after the stream ends. Classic Cline is the same ([index.ts#L2626-L2630](https://github.com/cline/cline/blob/9ee618111d58630fea30b27439216448225458e0/src/core/task/index.ts#L2626-L2630), [#L3157-L3162](https://github.com/cline/cline/blob/9ee618111d58630fea30b27439216448225458e0/src/core/task/index.ts#L3157-L3162)).
- Cline today: the transcript is written on each assistant message (before tools) and again at each iteration end (after tools). The second write is fire-and-forget ([agent-events.ts#L312-L318](https://github.com/cline/cline/blob/c441897f11f658f978a00678f045670c1ab2b60d/sdk/packages/core/src/services/agent-events.ts#L312-L318), [local-runtime-host.ts#L427-L435](https://github.com/cline/cline/blob/c441897f11f658f978a00678f045670c1ab2b60d/sdk/packages/core/src/runtime/host/local-runtime-host.ts#L427-L435)).
- Checkpoints (shadow git). Roo takes one before the first file-editing tool of each response (`write_to_file`, `apply_diff`, `edit_file`, `apply_patch` and others; not `execute_command`) ([presentAssistantMessage.ts#L651-L654](https://github.com/RooCodeInc/Roo-Code/blob/b867ec9145750d0ae1ff7f02d35406e9bf2a0b16/src/core/assistant-message/presentAssistantMessage.ts#L651-L654), [#L957-L967](https://github.com/RooCodeInc/Roo-Code/blob/b867ec9145750d0ae1ff7f02d35406e9bf2a0b16/src/core/assistant-message/presentAssistantMessage.ts#L957-L967)), and another on each user message ([Task.ts#L1464-L1469](https://github.com/RooCodeInc/Roo-Code/blob/b867ec9145750d0ae1ff7f02d35406e9bf2a0b16/src/core/task/Task.ts#L1464-L1469)). Classic Cline takes one **after** all tools in a response have finished ([index.ts#L3204-L3205](https://github.com/cline/cline/blob/9ee618111d58630fea30b27439216448225458e0/src/core/task/index.ts#L3204-L3205)). Current Cline takes a `git stash create` snapshot at most once per user turn ([checkpoint-hooks.ts#L504-L519](https://github.com/cline/cline/blob/c441897f11f658f978a00678f045670c1ab2b60d/sdk/packages/core/src/hooks/checkpoint-hooks.ts#L504-L519)). None of these is tied to resuming after an interruption.

## What the user sees

Resume is always a click. On reopen, Roo trims stale resume asks and drops an `api_req_started` row with no cost and no cancel reason, then asks `resume_completed_task` if the last message was `completion_result`, and `resume_task` otherwise ([Task.ts#L1956-L2023](https://github.com/RooCodeInc/Roo-Code/blob/b867ec9145750d0ae1ff7f02d35406e9bf2a0b16/src/core/task/Task.ts#L1956-L2023)). On cancel, both projects abort, wait up to 3 s, and rebuild the task from disk, so the Resume button appears ([Roo ClineProvider.ts#L2663-L2714](https://github.com/RooCodeInc/Roo-Code/blob/b867ec9145750d0ae1ff7f02d35406e9bf2a0b16/src/core/webview/ClineProvider.ts#L2663-L2714); [Cline sdk-task-control-coordinator.ts#L107-L116](https://github.com/cline/cline/blob/c441897f11f658f978a00678f045670c1ab2b60d/apps/vscode/src/sdk/sdk-task-control-coordinator.ts#L107-L116)). Current Cline picks the ask from the saved session status. If the status is unknown, it shows Resume, because "hiding Resume on an interrupted one is the data-loss illusion this exists to prevent" ([#L293-L311](https://github.com/cline/cline/blob/c441897f11f658f978a00678f045670c1ab2b60d/apps/vscode/src/sdk/sdk-task-control-coordinator.ts#L293-L311)). Retrying shows a status line, "provider error — retrying (attempt n/3)" in current Cline and a seconds countdown in Roo. The `api_req_failed` buttons are "Retry" and "Start New Task" ([buttonConfig.ts#L30-L37](https://github.com/cline/cline/blob/c441897f11f658f978a00678f045670c1ab2b60d/apps/vscode/webview-ui/src/components/chat/chat-view/shared/buttonConfig.ts#L30-L37)).

## Retry limits and parking

- Cline today: 3 automatic retries (1 s, 2 s, 4 s, capped at 15 s), only for empty, side-effect-free attempts; then `api_req_failed`, and only a click retries.
- Classic Cline: 3 automatic retries (2 s, 4 s, 8 s) for first-chunk and mid-stream failures; then a Retry button.
- Roo: with auto-approval, **no cap**. The delay is `requestDelaySeconds` (default 5) × 2^attempt, capped at 600 s, or a 429 `RetryInfo` delay if one is given ([Task.ts#L4268-L4299](https://github.com/RooCodeInc/Roo-Code/blob/b867ec9145750d0ae1ff7f02d35406e9bf2a0b16/src/core/task/Task.ts#L4268-L4299), [#L132](https://github.com/RooCodeInc/Roo-Code/blob/b867ec9145750d0ae1ff7f02d35406e9bf2a0b16/src/core/task/Task.ts#L132)). The countdown is a series of 1-second `delay` calls ([#L4319-L4327](https://github.com/RooCodeInc/Roo-Code/blob/b867ec9145750d0ae1ff7f02d35406e9bf2a0b16/src/core/task/Task.ts#L4319-L4327)), so during sleep it simply stops and carries on after wake.

## Remote work: Cline cloud sessions

Cline's cloud client has the closest match to bigbud's reconciliation rules:

- Before creating a sandbox, it writes the start to a per-process journal, `<pid>-<uuid>.json`. A later window cleans up abandoned starts, but never takes over a journal whose process is still alive, since "the owner may only be paused" ([cloud-pending-starts.ts#L32-L42](https://github.com/cline/cline/blob/c441897f11f658f978a00678f045670c1ab2b60d/apps/vscode/src/sdk/cloud-pending-starts.ts#L32-L42)).
- If sending a prompt hits a transport error or timeout, it reloads the remote transcript and compares how many times the prompt appears before and after. If it cannot prove the prompt was accepted, it does not resend. It reports "Cline could not confirm whether this message was accepted. Check the cloud session before resending it." ([controller.ts#L1484-L1530](https://github.com/cline/cline/blob/c441897f11f658f978a00678f045670c1ab2b60d/sdk/packages/core/src/cloud/controller.ts#L1484-L1530), [#L171-L180](https://github.com/cline/cline/blob/c441897f11f658f978a00678f045670c1ab2b60d/sdk/packages/core/src/cloud/controller.ts#L171-L180)).
- Because the API has no idempotency, a stable request id is stored in the session title ([api.ts#L582-L585](https://github.com/cline/cline/blob/c441897f11f658f978a00678f045670c1ab2b60d/sdk/packages/core/src/cloud/api.ts#L582-L585)).
- On reopen, it attaches to a remote session that is still running and only watches it. Otherwise it shows the resume ask ([sdk-cloud-session-coordinator.ts#L1338-L1366](https://github.com/cline/cline/blob/c441897f11f658f978a00678f045670c1ab2b60d/apps/vscode/src/sdk/sdk-cloud-session-coordinator.ts#L1338-L1366)).

## For bigbud

1. **Confirms D4** (TypeScript). Cline's SDK retries automatically only when the cut attempt produced nothing and ran no tools, and continues once after an unknown finish only when there were no tool calls. That matches "model request cut and no tool in flight → continue once". Copy the check itself: no content, no tool activity, error not auth or context-window.
2. **Confirms D4 and the invariant, by counterexample.** Roo resends without limit after a mid-stream failure, and classic Cline presses Resume itself, even when a tool may already have run. Both rely on prompt text ("assume the tool use was not successful") to sort it out. bigbud should not.
3. **Adds to D1** (TypeScript). Save the assistant turn, with its tool calls, before running any tool, as Cline's SDK does and Roo does not. A `tool_use` with no `tool_result` then reliably means "tool may have been in flight", which D4 needs to decide whether to ask the user.
4. **Adds to D1 and D7.** Cline cloud's "count the prompt in the remote transcript before resending, otherwise say we could not confirm it" is the `may-have-been-sent` reconciliation in practice. A stable request id stands in for idempotency. The per-pid journal treats a live but paused owner as alive, which is exactly the state after sleep. Attach-if-running then resume-ask matches D6 and D7.
5. **Adds to D4 wording.** Placeholder tool results such as Roo's "interrupted before this tool call could be completed" claim the tool did not run. bigbud's linked continuation should say the outcome is unknown, or carry the user's answer, and should not repeat the original objective as fresh instructions (Cline #12975).
6. **Confirms D5.** Two of the three designs stop after 3 automatic attempts and show a Retry button. Roo's unlimited retries are the case D5 avoids.
7. **Adds to D2 and D3.** Neither project listens for power or network events (`powerMonitor`, `online`, suspend), and neither classifies errors around sleep. Their timer-based backoff just freezes during sleep. There is nothing here to copy for D2, D3 or D8.
