# bigbud requirements against the OpenCode V2 HTTP API

## 1. Is existing-service, API-first integration sensible, and what maps natively?

### Takeaway

**Yes: API-first is the appropriate default for borrowing the user's already-running OpenCode V2 service. It is not a replacement for bigbud's adapter, durable admission journal, ownership checks, recovery, or execution-target orchestration.** The existing implementation already uses `@opencode/client` against the shared HTTP service; the remaining Windows database-handle qualification problem is an additional bigbud storage invariant, not evidence that the HTTP API or client cannot work on Windows. [B-client] [B-borrow] [B-storage]

Scope/provenance: read-only research, no service calls or qualification probes. bigbud task code was read with `git show` at published task commit **420f0c83f59eb87158679881c0c96c572dd23f3b**, not from concurrent dirty task files. OpenCode minimum source is **e7a34f09bfd9134dfade5a8ddb843f7030bc9a69 (2.0.24)**, identified by the existing source archive root; the current session HTTP handler was independently fetched at **9b4ec5714d481559990db0a816d5dec19541a814 (2.0.26)**. The table distinguishes available upstream operations from currently exposed bigbud capabilities. V2 official docs and Context7 `/websites/opencode_ai_v2` were consulted; no V1 endpoint assumptions were used. [U-session-current] [D-api] [D-client]

### Inferences

- API-first can reduce private-process/profile/plugin scaffolding for the **borrowed-service path**, but “just call the API” would discard safety requirements currently implemented above it. Existing `makeV2Client`, ownership checks, bounded native reads, canonical projections, interaction guards and the durable admission journal are reusable rather than reasons to start over. [B-client] [B-owner] [B-admission] [B-recovery]
- **Cross-provider compatibility is bigbud's adapter contract**, with explicitly differing fork/rewind/recovery/turn-control capabilities. OpenCode's common model/provider API does not make Codex app-server, Claude SDK, Copilot SDK, etc. share universal OpenCode session semantics or auth/tool guarantees. [B-adapter] [B-caps]

### Gaps

- Current research did not run macOS/Linux/Windows runtime qualification. The assignment says the current metadata probe failed qualification; that remains a release blocker if that invariant is retained. Existing tests/docs/plans are background evidence, not endpoint authority or proof of the current unfinished prototype. [B-storage] [B-version]

## 2. Which guarantees does HTTP actually supply, and which invariants remain unsolved?

### Takeaway

Native durable IDs/history/admission provide useful recovery primitives, **not exactly-once end-to-end execution, exclusive app ownership, storage identity, sandbox isolation, or future-version stability**. The transport can be portable across OSes while an extra storage-isolation admission rule remains unqualified on one OS. [U-session-contract] [U-inbox] [U-server-info] [B-storage] [D-permissions]

### Cited Findings

1. **No durable SSE replay/reconnect.** Official client docs explicitly say subscriptions are live-only, source failure terminates subscribers, and callers must subscribe again. Server SSE frames contain `data:` JSON, start with `server.connected`, heartbeat every 15 seconds, and use a bounded queue whose overflow terminates a subscriber. It does not implement a `Last-Event-ID` replay cursor. **Important qualification:** there _is_ a separate experimental `/api/experimental/session/{sessionID}/log?after=…&follow=…` backed by the durable session bus log. This is not replay of transient text/reasoning deltas or automatic reconnect of `/api/event`; do not claim that V2 has no durable log at all. [D-client] [U-events] [U-event-feed] [U-session-contract] [U-session-core]

2. **Durable prompt ID is not request-body equality or universal exactly-once.** Minimum core `Session.prompt` reconciles an existing ID, prepares only when absent, admits durably and wakes execution unless `resume:false`. Inbox reconciliation checks session/type and returns the first existing payload; it does **not** compare new text/model/attachments for equality. A repeated prompt call can also wake the session. bigbud's immutable fingerprint, model/media/policy binding and “absence never permits resend” journal remain necessary. Native hooks can modify the canonical admitted payload and run more than once before one admission wins; app fingerprints are ownership/correlation evidence, not proof arbitrary plugins left prompts unchanged. [U-prompt-core] [U-inbox] [D-plugins] [B-admission]

3. **Create IDs aid recovery, but must be verified.** Core create returns an already-recorded session for that ID and resolves concurrent create races to the existing identity; it does not verify that this call's requested metadata/model/location equals the recorded values. bigbud's post-create/get checks are essential. The native fork route, unlike create/prompt, has no caller-supplied deterministic destination ID in its contract; a lost fork acknowledgment therefore needs read-only reconciliation/manual recovery, not automatic retry. [U-session-core] [U-session-contract] [B-sessions]

4. **Metadata ownership is advisory, not exclusive authorization.** Session metadata and permissions are mutable via PATCH; session operations identify a session ID and authenticate to the service, with no client-owner token/CAS condition in these endpoint payloads. bigbud can verify its metadata on every mutation and fail closed on drift, but GET-then-mutate has a race with another authenticated client and cannot prove exclusive control if the same session is opened/modified from a native UI. This is a real shared-service guarantee gap, not solved by switching from SDK to raw HTTP. [U-session-contract] [U-session-current] [B-owner]

5. **Physical storage identity is not exposed by current server.info.** Minimum `/api/info` returns version, PID, URLs, `paths` supplied by ServerInfo (only tmp), and persistent-PTY capability; no canonical database path/inode/store-instance identifier. Session info identifies native session/location/project, not physical storage. Current bigbud `SharedService.storage.ts:18–66` separately probes process-open-file metadata, verifies database path/device/inode and generation, then hashes them. **Windows probing failure is this extra bigbud policy's failure**. It neither proves native HTTP incompatibility nor grants permission to guess HOME/XDG paths, read process environment/secrets, modify SQLite, or add a hidden marker/plugin. [U-server-info] [U-server-info-service] [B-storage]

6. **Directory is authoritative server location, not database namespace.** Location-scoped endpoints choose explicit location query/header, then server cwd. Session middleware loads the _stored session location_ through `instances.provide(session)`; passing a different directory header does not relocate an existing session. Native `/move` is a separate operation at a delivery boundary; it changes project placement, not the service's SQLite storage directory. Directory hashes must not be advertised as proof of a physical store. [U-location] [U-session-location] [U-session-contract] [B-binding]

7. **“GET/read-only HTTP” can initialize native runtime with side effects.** Ordinary `/api/info` and session list/get are not equivalent to Location-scoped catalogs/config/MCP/tool endpoints. Location middleware obtains the Location service graph; it contains filesystem config, plugins/supervisor, MCP, shell, model/provider and watchers. Plugin activation starts locally available modules and installs missing configured packages when needed. Existing project/global configuration is discovered upward to filesystem root and `.opencode/plugins` can autoload. Session PATCH/prompt/model operations also have session-location middleware. Thus “bigbud sends no config writes” is achievable; “any allowed request has zero native config/plugin/MCP bootstrap effects” is **not** guaranteed merely by HTTP method or session deny-all permissions. [U-location] [U-instance] [U-plugin-supervisor] [U-session-contract] [D-config] [D-plugins]

8. **Permissions are not a sandbox and do not govern arbitrary plugin setup.** Native shell has the host user's filesystem/process/network authority; path inference is best effort. Session rule arrays can deny tools; they cannot stop arbitrary already-trusted native plugin code from executing on setup or guarantee that a custom tool requests permission correctly. Saved `always` grants are project-scoped, and native subagents inherit/create native session state rather than automatically gaining canonical bigbud thread ownership. Retain narrow policies and explicit trust boundaries; do not promise strict app-storage protection once arbitrary shell is allowed. [D-permissions] [D-plugins] [B-shared-policy] [B-interactions]

9. **Cancellation addresses a session/current execution, not an atomic expected turn.** Native interrupt reports whether this process interrupted an active drain; idle is a no-op. `resume:true` can resume steering/control inputs while queued prompts remain parked. Cancel inbox affects undelivered items only. Disconnecting an HTTP/SSE client does not stop already-owned server work; tool executors must cooperate with cancellation signals. bigbud must retain local turn/epoch/generation fences, call interrupt with `resume:false`, reconcile persisted state and keep uncertain cleanup quarantined. [U-session-contract] [U-prompt-core] [D-plugins] [B-replies] [B-cleanup] [B-recovery]

10. **Transfer is explicit history restore, not transparent continuation.** Export filters incomplete assistant/running shell/compaction records; import retains the supplied session ID, rejects collisions, resolves the requested destination project and requires parents to exist first. It installs transcript rows and selected metadata/totals, not runtime fibers, pending inbox/tools, credential/config state, physical database identity, complete event log or workspace snapshots. Unsanitized export contains sensitive text/tool content; sanitized export is not execution-equivalent context. Fork uses a newly generated child ID and latest instruction values. [U-transfer] [U-session-core] [U-session-contract]

11. **Runtime/schema qualification is a gate, not a future guarantee.** Official API calls itself experimental. bigbud's published policy accepts stable V2 `>=2.0.24`, excludes V3 and supplements it with exact consumed-operation/schema checks; release qualification currently names 2.0.24 and 2.0.26 only. Shape checks cannot establish semantic safety of every future V2 patch (hooks, prompt/retry semantics, platform behavior, provider availability). Catalog/config/plugin startup can settle asynchronously. [D-api] [B-version] [B-required] [B-native-catalog]

12. **Authentication/model/tool availability remains native and vendor-controlled.** `Service.headers` uses the discovered service authentication context, not vendor credential portability. Native integration/provider/model registries depend on active connections, policy and plugin sources; importing a plugin RPC definition does not install its server implementation. bigbud should present unavailable/setup-needed choices without writing credentials/config or pretending that a public model catalog guarantees provider execution, reasoning support, cost accuracy or tools. [D-client] [D-plugins] [B-public-catalog] [B-model]

### Inferences

- There are two different ownership promises: **bigbud will mutate only its verified sessions** (app-enforceable) versus **no other authenticated OpenCode client can mutate those sessions** (not currently server-enforceable). The integration must state the weaker implemented guarantee, serialize its own writes and refuse unsafe drift. Hard exclusion requires an upstream session lease/CAS capability, not a hidden plugin. [B-owner] [U-session-contract]
- If “no installs/config/DB mutation” means **no direct administrative writes by bigbud**, owned-session HTTP persistence is compatible. If it means **no database writes at all** or **no native bootstrap/plugin effects whatsoever**, session creation/prompting on the native service cannot satisfy it. Do not redefine this invariant silently; separate authorized session-record persistence from prohibited administrative state mutation and ask the parent/user to settle the strict interpretation if necessary. [U-prompt-core] [U-instance] [U-plugin-supervisor]

### Gaps

- No documented native API provides an attested physical store ID/path, per-client exclusive session lease, or a per-request “load this Location without config/plugins/MCP/install discovery” flag. Core has `Instance.Options.discovery:false`/replacement layers for a host, but those are not existing HTTP create/location parameters. [U-server-info] [U-instance] [U-session-contract] [U-location]
- Current HTTP controls do not prove all background tools stopped across a daemon restart or interruption of uncooperative plugin work. Absence from `session.active` specifically means no current foreground drain, not universal process/task absence. [U-session-contract] [D-plugins]

## 3. What bounded redesign preserves the requirements instead of hiding gaps?

### Takeaway

**Recommend a borrowed-service API adapter with logical session identity and explicit native bindings; keep physical storage-directory enforcement as a separate, named admission policy.** This is an architectural proposal, not authorization to remove the current database protection/identity invariant: strict storage policy must remain fail-closed on Windows until qualified or an explicitly approved equivalent exists. [B-storage] [B-binding] [B-required]

### Cited Findings

- Existing reusable boundaries already separate adapter capability declarations, client transport, ownership, deterministic admissions, immutable attachments, recovery/projections and application target preparation. Shared mode avoids private-profile/plugin initialization. The existing design is therefore partly API-first already; redesign should target physical/native identity coupling and clearly scoped missing capabilities, not replace all orchestration with SDK convenience methods. [B-adapter] [B-client] [B-owner] [B-admission] [B-attachments] [B-recovery] [B-targets] [B-shared-config]
- Embedded SDK creates and owns a host, opens no HTTP listener and supports runtime plugin registration/customization; it does not simply attach to the user's native shared service. Embedding is a different execution mode and cannot be an invisible fallback when borrowing fails. [D-sdk] [D-client]

### Inferences / recommended proposal

1. **Borrow only.** Discover an already healthy service or accept an explicitly user-configured endpoint/auth context; create a client with existing service headers. Never call ensure/start/stop/restart/update/install/provider-connect/credential CRUD/config PATCH/plugin update/MCP mutation. Closing bigbud stops only its owned session work and subscriptions/tunnel handles, not the daemon. Preserve origin/redirect/decode/deadline controls. Missing or incompatible service gives actionable setup instructions, not fallback provisioning. [D-client] [B-client] [B-borrow] [B-cleanup]

2. **Admission gate: minimum version AND consumed capabilities AND qualified behavior.** Keep stable V2 >=2.0.24, V3/pre-release exclusion, native `/api/info` and `/openapi.json` read-only checks, exact request/response/events used by the adapter, and OS-specific qualification. Gate optional fork/revert/log/background capabilities separately instead of assuming version alone supplies semantic parity. Do not promote the failed metadata prototype into a guarantee. [B-version] [B-required] [D-api]

3. **Logical identity independent of physical/native identity.** Proposal: retain stable bigbud thread/session identity in bigbud persistence; store a binding record with native session ID, user-visible connection identity, runtime/workspace targets, stored Location, ownership tag, capability evidence, admission journal generation and transfer provenance. A service restart is a transport generation change, not automatically a new logical chat. Never rebind to another store merely because a path or session ID matches. Keep existing storage attestation in the separate policy below. The present `hash(storageIdentity, threadId)` native-ID derivation is convenient for duplicate create prevention but unnecessarily conflates logical conversation identity with a database inode. [B-binding] [B-sessions] [B-borrow]

4. **Explicit resume vs copy vs restore.** Resume means use the verified existing native binding and read history/inbox; missing session is not permission to create/replay. Native fork makes a new binding/child with documented boundary semantics; lost acknowledgment cannot silently retry the fork. Restore/import is an explicit user action with settled-only transcript expectations, parent order/collision handling and new binding provenance. It does not resume in-flight tools or reconstruct credentials/config/workspace snapshots. No hidden sentinel session/instruction/plugin as an attestation trick. [B-sessions] [U-session-core] [U-transfer] [U-session-contract]

5. **Storage-dir policy remains separate and fail-closed.** Preserve the requirement that app-owned storage and native service storage are identified/protected as required. HTTP lacks the physical store attestation today; keep qualified non-content OS metadata probing if that remains the agreed method, without DB reads/writes or process environment inspection. On unqualified Windows, mark strict shared mode blocked, not “SDK unsupported.” Logical binding is not a substitute for this invariant. If redesign needs different trust/protection semantics, obtain explicit user approval or an upstream documented API first; neither native client nor embedded SDK can magically attest another daemon's database. [B-storage] [U-server-info] [U-server-info-service]

6. **Persist intent and reconcile, never uncertain replay.** Retain bigbud's reserved/dispatch-intent/accepted/terminal admission journal, native message IDs, complete fingerprints and immutable attachment preparation. Use SSE only for low-latency invalidation/deltas; on loss resubscribe under backoff, then bounded/paginated read repair of messages, inbox, active state and interactions. Experimental durable session log can assist future repair but not replace correlation or reconstruct every live delta. Keep unknown admission/cancellation/cleanup blocked until reconciled; absence alone cannot authorize re-execution. Native internal vendor retries belong to the same owned admission. [B-admission] [B-recovery] [B-attachments] [D-client] [U-session-core]

7. **Keep native trust and bigbud orchestration distinct.** Native catalogs/config/plugins/MCP are user-owned, may initialize on Location access and cannot be made sandboxed by session permissions. Strict remote-tool visibility/custom bigbud hooks are not native HTTP defaults. Permit only independently qualified native tools and supported forms; unsupported hidden/conditional/external forms need truthful fallback/cancellation, never guessed answers. Preserve canonical bigbud learning/delegation/scheduling ownership rather than interpreting native subagents/background tools as equivalent. [U-instance] [U-plugin-supervisor] [D-permissions] [B-forms] [B-interactions] [B-learning] [B-targets]

8. **Remote support must borrow an existing remote service, not reuse auto-provisioning.** A separately qualified future path can forward HTTP/SSE through a bigbud-owned authenticated SSH tunnel to an already-running, user-installed V2 service, with native paths on that host and inline attachment transfer. The app may own its tunnel lifecycle while not owning daemon lifecycle. Current shared target admission rejects remote outright, so do not advertise end-to-end SSH parity until ownership/cancellation/recovery/storage policy is qualified for that path and all required macOS/Linux/Windows clients. No mixed-host path guessing, injected MCP/plugin, local execution fallback or remote installation. [D-client] [D-attachments] [B-targets] [B-remote]

### Gaps / decision points for the report writer

- Whether absolute prevention of native plugin/config-bootstrap side effects is intended. HTTP on the existing service cannot currently disable them per request; an app-owned embedded host changes ownership/trust and conflicts with the requested default rather than solving it transparently. [U-instance] [U-plugin-supervisor] [D-sdk]
- Whether hard concurrent-client exclusion is required. Metadata verification is a useful fail-closed app guard, not atomic server-enforced ownership; strengthen upstream or document exclusive-use prerequisites explicitly. [B-owner] [U-session-contract]
- Whether physical DB path/inode attestation is non-negotiable. Assignment says preserve it; Windows failure remains a release gate. Do not quietly trade it for a directory tag, deterministic session ID or service registration identity. [B-storage] [B-binding] [U-server-info]
