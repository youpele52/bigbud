# Resolving the Home Directory of a Selected WSL Distribution

Research notes current to October 2026. **Documented facts** are separated from **inferences/recommendations** below. Microsoft’s public WSL documentation describes the CLI and supported file access, but does not specify every detail of environment construction for a non-interactive command; those limits are called out rather than assumed.

> Implementation policy: commit `93e43aa7492c77550d778e9f82448fdc90bd1217` deliberately chose the selected distro default user's **process `HOME`**, captured together with username/UID inside that distro and pinned for subsequent probes and PTY startup. It did not choose NSS account-home semantics or add a specific-account selector. The alternatives recommended below remain research, not changes to that policy. The [2026-10-12 follow-up](../../validation/wsl-terminal-followup-2026-10-12.md) repairs bounds and malformed-input handling without changing Home semantics.

## Documented behavior and approach comparison

### Takeaway

Always launch the explicitly selected distribution with WSL’s distribution selector. For a selected Linux account, also pass that account explicitly; for a distro-default account, let WSL select its configured default and inspect the identity from inside that process. `$HOME` and `getent passwd` answer related but different questions: process environment home versus account-database home.

### Cited findings

- Microsoft documents `wsl --distribution <Distribution Name> --user <User Name>` to run a named distro as a named existing user; a nonexistent user produces an error. It documents `wsl -d Ubuntu-22.04 -- cat /etc/os-release` as a command in a specific distro. These are the target-binding mechanisms; omitting the distro selector invokes the default-distro behavior instead. [Basic commands for WSL](https://learn.microsoft.com/en-us/windows/wsl/basic-commands); [WSL interop](https://learn.microsoft.com/en-us/windows/dev-environment/wsl-interop)
- `wsl --list --verbose` reports installed distributions and whether each is running or stopped; `--quiet` lists names only. The same command reference documents `--terminate <Distribution Name>` for stopping a particular distro and warns that `--unregister` permanently removes that distro’s data. [Basic commands for WSL](https://learn.microsoft.com/en-us/windows/wsl/basic-commands)
- WSL’s per-distro `/etc/wsl.conf` `[user] default=...` setting determines the default user for a distro. Microsoft’s custom-distro guide says imported distributions start as root by default unless configured otherwise. Therefore, a distro’s default account should not be inferred from its label, the Windows account name, or a conventional `/home/<name>` path. [Advanced settings configuration in WSL](https://learn.microsoft.com/en-us/windows/wsl/wsl-config); [Import any Linux distribution to use with WSL](https://learn.microsoft.com/en-us/windows/wsl/use-custom-distro)
- The Linux `getent` utility queries databases configured through Name Service Switch (NSS), including the `passwd` database. The passwd record’s fields include the account name, UID, and home-directory field. Thus `getent passwd <key>` can query the account database rather than trusting the shell’s current `HOME` value. [getent(1)](https://man7.org/linux/man-pages/man1/getent.1.html); [passwd(5)](https://man7.org/linux/man-pages/man5/passwd.5.html); [nsswitch.conf(5)](https://man7.org/linux/man-pages/man5/nsswitch.conf.5.html)
- `HOME` is an environment variable, not a separate NSS lookup. Bash’s documented non-interactive startup behavior is to read `BASH_ENV` when set; it does not ordinarily read interactive `.bashrc`, and it reads login startup files only when invoked as a login shell. This means a non-interactive query should not depend on interactive shell startup customizations to define or repair `HOME`. The documentation does not establish a universal guarantee for what environment WSL assigns to every non-interactive command across distro types/configurations. [Linux environ(7)](https://man7.org/linux/man-pages/man7/environ.7.html); [Bash startup files](https://www.gnu.org/software/bash/manual/html_node/Bash-Startup-Files.html)
- Microsoft documents WSL command examples using `wsl -d <distro> -- <command>` and says commands passed to `wsl.exe` are forwarded to WSL; it also documents `wslpath` for translating Linux and Windows paths. The interop page’s Linux-to-Windows example produces a `\\wsl.localhost\<distro>\...` path. [WSL interop](https://learn.microsoft.com/en-us/windows/dev-environment/wsl-interop); [Working across file systems](https://learn.microsoft.com/en-us/windows/wsl/filesystems)
- The supported Windows-facing route to Linux files is `\\wsl$\<distro>\...` or `\\wsl.localhost\<distro>\...`. Microsoft notes that `\\wsl$` is only available while the distro is running; the current interop guidance says `wsl.localhost` can auto-start a distro on Windows 11. Microsoft also documents that access through `\\wsl$` uses the distro’s **default user**, a distinct consideration if the app selected a non-default Linux user. [WSL interop](https://learn.microsoft.com/en-us/windows/dev-environment/wsl-interop); [File permissions for WSL](https://learn.microsoft.com/en-us/windows/wsl/file-permissions)
- Directly opening a WSL distro’s backing files under `%LOCALAPPDATA%\Packages\...\LocalState` is not a supported general path strategy. Microsoft warns not to modify, move, or access WSL-related files in AppData with Windows tools/editors because this can corrupt the distro. WSL supports imported distributions with caller-selected install locations; current config also documents a configurable default distribution install path. [How to manage WSL disk space](https://learn.microsoft.com/en-us/windows/wsl/disk-space); [Basic commands for WSL](https://learn.microsoft.com/en-us/windows/wsl/basic-commands); [Advanced settings configuration in WSL](https://learn.microsoft.com/en-us/windows/wsl/wsl-config)
- Microsoft’s `WslLaunch` API takes a `distributionName` and launches a process in that particular distro. The API’s command parameter is a command string, rather than a structured argv list in the documented signature; its docs say a null command launches the default shell. [WslLaunch function](https://learn.microsoft.com/en-us/windows/win32/api/wslapi/nf-wslapi-wsllaunch)
- OWASP recommends separating command structure from untrusted data (parameterization) and validating inputs for OS command execution. [OS Command Injection Defense Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/OS_Command_Injection_Defense_Cheat_Sheet.html)

### Inferences

- Prefer `getent passwd` when the product means “the home directory recorded for this Linux account.” Prefer `$HOME` only when the product specifically means “the home path advertised to this launched process.” They are not interchangeable if `HOME` is overridden or differs from the passwd entry.
- `getent` is generally safer than guessing `/home/<username>` because it follows the distro’s NSS account lookup and returns the passwd home field, which may be `/root`, a nonstandard path, or an account provided by a configured NSS source. This is an inference from the documented lookup and record semantics, not a Microsoft WSL guarantee.
- If `getent` is unavailable, a narrowly scoped fallback may parse `/etc/passwd` for the already-selected local account. That only covers local passwd-file entries and does not reproduce arbitrary NSS sources. If the account is not found or the file cannot be parsed safely, report “unable to resolve” rather than guessing. No universal `getent` availability guarantee was found for all imported/minimal/custom distros.
- Explicitly passing `--user` removes ambiguity when the user is known. When the user is not specified, WSL’s configured distro default is the target identity; query the effective user from within the same command invocation before looking up its account record. Do not silently substitute the Windows username.
- `wslpath` is a conversion tool, not a home-directory discovery mechanism. Keep the discovered value as a Linux path unless a particular Windows API needs a Windows-facing path. If conversion is required, use WSL’s supported conversion/UNC route rather than discovering or manufacturing an internal VHD/Store backing path.
- A distro name containing spaces is data, not shell syntax. Passing the name and username as individual process arguments avoids shell word-splitting and metacharacter interpretation; if a shell is unavoidable, keep the shell program fixed and pass values as positional parameters rather than interpolating them into `-c` text. An argv interface prevents shell injection but does not by itself solve option parsing: select a name from the current installed-distro list and pass it only as the value of `--distribution`.

### Gaps

- Microsoft’s public documentation reviewed here does not promise that every non-interactive WSL invocation will have `HOME` set to the passwd home, nor does it specify all environment inheritance/override behavior. Treat `$HOME` as a value to query and validate, not as a cross-distro invariant.
- The docs establish the named-distro selector and examples, but do not formally specify behavior for every malformed/unusual registered name (for example, labels beginning with option-like characters). Exact-list validation plus argument-array process creation is the conservative approach.

## Recommended target-bound design

### Takeaway

Model the resolution request and result with an explicit distro identity and Linux-user identity. Invoke `wsl.exe` for that exact distro on every query; obtain the account home inside that distro; retain it as a Linux path. Never recover from a target error by retrying against WSL’s default distro or by reading a guessed Windows backing-store location.

### Cited findings

- WSL’s documented CLI supports selecting a named distro and, optionally, a named existing Linux user. `--list --quiet` provides installed names, while verbose listing distinguishes running and stopped states. [Basic commands for WSL](https://learn.microsoft.com/en-us/windows/wsl/basic-commands)
- WSL config defines the per-distro default user, and imported distros may default to root. [Advanced settings configuration in WSL](https://learn.microsoft.com/en-us/windows/wsl/wsl-config); [Import any Linux distribution to use with WSL](https://learn.microsoft.com/en-us/windows/wsl/use-custom-distro)
- Linux NSS and passwd documentation define `getent` account lookups and the passwd home-directory field. [getent(1)](https://man7.org/linux/man-pages/man1/getent.1.html); [passwd(5)](https://man7.org/linux/man-pages/man5/passwd.5.html)
- Microsoft documents WSL UNC paths and `wslpath` conversion, and warns against direct manipulation/access of distro backing files in AppData. [WSL interop](https://learn.microsoft.com/en-us/windows/dev-environment/wsl-interop); [How to manage WSL disk space](https://learn.microsoft.com/en-us/windows/wsl/disk-space)

### Inferences

1. **Resolve target before launch.** Store the selected distro’s registered name/identifier (not display text alone if the product has a separate stable ID). Refresh the installed list when resolving, require an exact match, and fail as stale/unregistered if it is absent. Do not choose the default distro as a fallback.
2. **Choose identity policy explicitly.**
   - For an explicit Linux user, invoke the distro with `--distribution <selected-name> --user <selected-user>` and fail if WSL reports that user does not exist.
   - For “use distro default,” omit `--user` intentionally, but query the effective account from inside that same execution and label it as the distro-default identity. Do not infer it from the distro name or Windows account.
3. **Execute without interpolating data into a shell.** Use a process API that accepts an argument list where available. A query can be made with a fixed executable/command in the selected distro (for example, `getent passwd <account-key>`), passing the distro label and user/key as separate values. If using `sh -c` to read `$HOME`, make the script a fixed literal and pass any dynamic values as positional arguments; never concatenate distro labels or usernames into shell source. Use exact-list validation because argument separation is not a substitute for validating a target name.
4. **Prefer account lookup for account-home semantics.** For an explicit account, look up that exact passwd/NSS entry. For distro-default identity, determine the effective UID/name in the launched process and query the corresponding passwd entry. Parse the passwd result’s home field and require a successful exit, one unambiguous record, nonempty absolute Linux path, and bounded output. If the application instead intentionally wants the process environment home, query `$HOME` inside the same target/user invocation and make that distinction visible in the API/UI.
5. **Fallback only within the same target.** If `getent` is missing, only try a documented local-file fallback for the same distro and same account; otherwise return an explicit resolution failure. Do not retry with no `--distribution`, omit a failed explicit `--user`, switch to a different username, assume `/home/<name>`, or use a Windows profile path. If falling back from NSS to `$HOME`, do so only under a documented policy: it returns process environment home, which may not be the account database’s canonical home.
6. **Return a typed Linux path.** Carry at least `{ distro, Linux identity (username and/or UID), linuxHomePath }` together. Keep Linux separators and semantics; do not canonicalize with Windows path APIs. Use `wslpath` only at the boundary of a specific Windows consumer that requires a Windows-form path. A `\\wsl.localhost\...` UNC path can be produced/accessed when needed, but UNC access has lifecycle and default-user permission caveats.
7. **Treat every process result as untrusted output.** Require zero exit status; distinguish stderr diagnostics from the path; reject empty/multiline/relative results where not allowed; cap stdout/stderr collection. Avoid logging unsanitized values if they can contain control characters.

### Gaps

- A fallback from `getent` to `/etc/passwd` cannot support NSS identities not present in that file. Whether to allow `$HOME` as a fallback is a product-semantics choice; the docs do not establish it as identical to the passwd account home.
- The specific app runtime/framework is not supplied, so the exact safe argv API and process-tree cancellation primitive should be selected for that runtime. Windows process creation ultimately needs correct Windows command-line serialization; avoid hand-built command strings where a structured argument-list API exists.

## UX, timeout, and failure policy

### Takeaway

Make distro startup and identity choice explicit; treat unregistered, inaccessible, ambiguous, and timed-out lookups as errors for the selected target. Apply one wall-clock deadline to each host-side operation from process start through output collection, and never let timeout recovery silently change distro or user.

### Cited findings

- Microsoft reports running/stopped state in `wsl --list --verbose`; launching a named distro is the documented way to run commands in it. The `\\wsl$` path depends on the distro running, while Windows 11 `\\wsl.localhost` may auto-start it. [Basic commands for WSL](https://learn.microsoft.com/en-us/windows/wsl/basic-commands); [WSL interop](https://learn.microsoft.com/en-us/windows/dev-environment/wsl-interop)
- WSL invocation has no timeout option documented on the WSL basic-command reference. WSL 2 config does document internal VM/distribution startup timeout settings, but those are host WSL configuration and not a substitute for bounding the app’s own subprocess/wait/output handling. [Basic commands for WSL](https://learn.microsoft.com/en-us/windows/wsl/basic-commands); [Advanced settings configuration in WSL](https://learn.microsoft.com/en-us/windows/wsl/wsl-config)
- `wsl --unregister` permanently loses all data, settings, and software associated with the distro; it is a destructive lifecycle operation, not a valid recovery action for a failed query. [Basic commands for WSL](https://learn.microsoft.com/en-us/windows/wsl/basic-commands)

### Inferences

- **Stopped distro:** Tell the user that resolving its home may start the selected distro, or provide a “do not start; show stopped” policy if startup is not acceptable. Do not treat “stopped” as “missing”; a named WSL launch is the supported way to run a command in it. A pre-check can improve UX, but state can change between check and launch, so the launch result is authoritative.
- **Unregistered/stale distro:** Show that the selected distro is no longer registered and ask the user to choose another. Never silently use the default distro. If a list check and launch race with unregister/re-register, surface the launch failure and require re-selection or explicit retry.
- **Default-user ambiguity:** Offer “distro default user” versus “specific Linux user” when that distinction matters. Show the effective Linux username (and ideally UID) resolved from the exact invocation before persisting the home result. Imported distros may default to root, so avoid implying “default” means a conventional non-root account.
- **Timeout boundary:** Put a monotonic wall-clock deadline around the entire Windows-side subprocess lifecycle: process creation, WSL startup/boot, guest command/NSS lookup, waiting for exit, and draining stdout/stderr. Also cap collected output bytes. This bounds delayed distro startup and stuck NSS lookups, not merely execution of the final `getent` command. If the deadline expires, report timeout/unresolved and do not return partial output as success.
- **Timeout cancellation:** Stop waiting and attempt to cancel/terminate the host-side WSL invocation using the runtime’s supported process cancellation mechanism. Do not automatically run `wsl --terminate <distro>` as timeout cleanup: Microsoft documents that it stops that distro, which can disrupt unrelated user work. The reviewed docs do not guarantee that killing a host wrapper always terminates the guest command, so avoid claiming stronger cancellation than the runtime/WSL behavior verifies.
- **Same-target fallback policy:** Preserve the exact selected distro name and effective/explicit Linux identity through all fallback attempts. Reasonable fallback order is NSS lookup → (optional, explicitly approved) local `/etc/passwd` lookup for the same account. If neither can establish the home, fail closed. Never fall through to the default distro or a different user; never infer a path from `%LOCALAPPDATA%\Packages`.

### Gaps

- The cited WSL documentation does not guarantee guest-process termination semantics when the Windows app times out/kills its `wsl.exe` process. Validate cancellation behavior in the chosen Windows runtime and supported WSL versions; until then, treat a timeout as “result unknown,” not proof that the guest command stopped.
- No universal WSL guarantee was found for `getent` being installed in all distros. Imported and custom minimal images may omit utilities. This justifies a controlled fallback or a clear “required account lookup tool unavailable” error, not a guessed home path.
