# Selecting WSL distro Home: repository architecture

> Historical repository snapshot, researched before commit `93e43aa7492c77550d778e9f82448fdc90bd1217`. The statements below that WSL selection is absent describe that earlier state, not current bigbud. Selected-distro manual terminals, target-bound process Home probing, identity pinning and file-operation guards are now implemented. General WSL workspace/provider execution remains outside scope. See the [2026-10-12 follow-up validation](../../validation/wsl-terminal-followup-2026-10-12.md) for current repairs and runtime limits.

## Current target model and where WSL appears

### Takeaway

The repository carries an execution target as a generic string, but the terminal runtime currently dispatches it as a binary choice: `local` or SSH-style nonlocal. There is no selected-WSL-distro execution target or WSL home resolver today; the existing `wsl` mentions are shell/path-format features, not a target identity.

### Cited Findings

- `ExecutionTargetId` is a trimmed nonempty string, `local` is the default, and `isRemoteExecutionTargetId` means simply “not local”; the base contract does not define target kinds or a WSL variant — [baseSchemas.ts:11-29](../../../packages/contracts/src/core/baseSchemas.ts#L11-L29).
- Server target classification is likewise equality against `local`; every other ID is treated as remote by `isLocalExecutionTarget` — [executionTargets.ts:3-11](../../../apps/server/src/executionTargets.ts#L3-L11).
- The SSH parser recognizes only IDs prefixed `ssh:` and parses host/user/port/auth/key/transport from them — [sshExecutionTarget.ts:20-64](../../../apps/server/src/ssh/sshExecutionTarget.ts#L20-L64). `assertSshExecutionTargetReady` rejects an ID that does not parse as SSH — [sshVerification.ts:109-123](../../../apps/server/src/ssh/sshVerification.ts#L109-L123).
- Workspace target resolution exposes only `location: "local" | "remote"`; its `remote` value is any non-`local` ID — [workspaceTarget.ts:5-31](../../../apps/server/src/workspace-target/workspaceTarget.ts#L5-L31). Project contracts persist generic `providerRuntimeExecutionTargetId`, `workspaceExecutionTargetId`, and legacy `executionTargetId` values — [orchestration.project.ts:29-38](../../../packages/contracts/src/orchestration/orchestration.project.ts#L29-L38).
- Web target utilities likewise expose provider runtime location as only `local | remote` — [providerExecutionTargets.ts:7-38](../../../apps/web/src/lib/providerExecutionTargets.ts#L7-L38). The remote-project form model and its ID builder are specifically SSH-shaped — [Sidebar.projects.logic.ts:9-33](../../../apps/web/src/components/sidebar/Sidebar.projects.logic.ts#L9-L33), [Sidebar.projects.logic.ts:50-90](../../../apps/web/src/components/sidebar/Sidebar.projects.logic.ts#L50-L90), [Sidebar.projects.logic.ts:116-139](../../../apps/web/src/components/sidebar/Sidebar.projects.logic.ts#L116-L139).
- `wsl` is present in the terminal drop-path mode contract, and Windows shell-name detection maps a local `wsl.exe` shell to that mode — [terminal.ts:94-95](../../../packages/contracts/src/workspace/terminal.ts#L94-L95), [Manager.shell.ts:79-109](../../../apps/server/src/terminal/Layers/Manager.shell.ts#L79-L109). The renderer converts dropped Windows drive paths to `/mnt/<drive>/...` for that shell mode — [TerminalViewport.drop.ts:77-101](../../../apps/web/src/components/terminal/TerminalViewport.drop.ts#L77-L101). This is path formatting, not distro selection or target dispatch. The other direct WSL-related code hit is telemetry reading `WSL_DISTRO_NAME` — [AnalyticsService.ts:110-123](../../../apps/server/src/telemetry/Layers/AnalyticsService.ts#L110-L123).
- No WSL-specific target parser, target schema, terminal route, or distro-selection field was found in the inspected target/terminal paths. The current contract's generic ID can carry a future identifier syntactically, but that alone does not implement routing.

### Inferences

- A hypothetical `wsl:<distro>` ID would currently enter the nonlocal branch, then fail SSH-target validation or be routed toward SSH. It would not mean “run in this WSL distro.” This follows from the generic nonlocal classification plus the SSH-only readiness/parser route cited above.
- Do not describe WSL as wholly unsupported: the repo recognizes a WSL shell for drop-path formatting. The unsupported capability in scope is selecting a WSL distro as an execution target and resolving that target's Home.

### Gaps

- Repository evidence does not establish which UI surface should own distro selection (terminal-only setting versus project/workspace target selection). A project-level WSL target would imply broader file/git/provider execution support than the terminal/Home request alone.

## Terminal cwd resolution, launch context, and safety

### Takeaway

`Manager.cwd.ts` resolves local paths against the server process's host Home and SSH paths by probing Home on the SSH target. It never queries Linux Home merely because a Windows shell is WSL; the selected target must be explicitly dispatched for both folder validation and terminal spawn to avoid crossing environments.

### Cited Findings

- `makeResolveTerminalFolder` decides `local` by `isLocalExecutionTarget`; for nonlocal targets it first calls `assertSshExecutionTargetReady`. The local branch gets Home from the injected `localHome` defaulting to Node `os.homedir()`, expands `~` using `process.platform`, and validates through the host filesystem callback — [Manager.cwd.ts:1-3](../../../apps/server/src/terminal/Layers/Manager.cwd.ts#L1-L3), [Manager.cwd.ts:89-126](../../../apps/server/src/terminal/Layers/Manager.cwd.ts#L89-L126). That callback uses Node `FileSystem.stat/access` and `fs.access(..., X_OK)` — [Manager.process.state.ts:100-129](../../../apps/server/src/terminal/Layers/Manager.process.state.ts#L100-L129). On a Windows server this is Windows host Home/filesystem behavior, not a WSL Linux-target lookup.
- The SSH probe runs `sh -lc` through `runSshCommand`, uses `$HOME` when probing Home, tests/cds into the folder, and returns `pwd -P`; its request carries the same `executionTargetId` — [Manager.cwd.ts:35-41](../../../apps/server/src/terminal/Layers/Manager.cwd.ts#L35-L41), [Manager.cwd.ts:43-86](../../../apps/server/src/terminal/Layers/Manager.cwd.ts#L43-L86). `Manager.cwd.ts` applies a 10-second bound and an 8 KiB output cap — [Manager.cwd.ts:13](../../../apps/server/src/terminal/Layers/Manager.cwd.ts#L13), [Manager.cwd.ts:52-64](../../../apps/server/src/terminal/Layers/Manager.cwd.ts#L52-L64).
- The resolver falls back to Home only after a `TerminalCwdError`; connection/readiness failures are `TerminalExecutionTargetError`, not “directory missing.” The remote probe also distinguishes a timeout before its ready marker from a folder timeout after connection confirmation — [Manager.cwd.ts:66-85](../../../apps/server/src/terminal/Layers/Manager.cwd.ts#L66-L85), [Manager.cwd.ts:101-110](../../../apps/server/src/terminal/Layers/Manager.cwd.ts#L101-L110), [Manager.cwd.ts:127-171](../../../apps/server/src/terminal/Layers/Manager.cwd.ts#L127-L171).
- `TerminalOpenInput` and `TerminalRestartInput` already carry optional `executionTargetId`, `cwd`, and optional worktree/environment context. `TerminalSessionSnapshot` carries `executionTargetId`, resolved `cwd`, worktree, and optional `directoryFallback: { requestedCwd, reason }` — [terminal.ts:43-52](../../../packages/contracts/src/workspace/terminal.ts#L43-L52), [terminal.ts:73-82](../../../packages/contracts/src/workspace/terminal.ts#L73-L82), [terminal.ts:97-117](../../../packages/contracts/src/workspace/terminal.ts#L97-L117). The server session state stores the target and fallback, and snapshot serialization returns them — [Manager.types.ts:31-60](../../../apps/server/src/terminal/Layers/Manager.types.ts#L31-L60), [Manager.process-lifecycle.ts:79-99](../../../apps/server/src/terminal/Layers/Manager.process-lifecycle.ts#L79-L99).
- On fallback, `Manager.session.ts` opens at the fallback cwd, clears the worktree and drops the runtime environment/setup values before spawn — [Manager.session.ts:67-99](../../../apps/server/src/terminal/Layers/Manager.session.ts#L67-L99), [Manager.session.ts:237-293](../../../apps/server/src/terminal/Layers/Manager.session.ts#L237-L293).
- Interactive process routing also uses local-versus-nonlocal: local starts the configured local shell in `session.cwd`; nonlocal uses `buildRemoteTerminalShellCandidate`, places the PTY wrapper in host `homedir()`, and sets remote cwd — [Manager.process-drain.ts:71-83](../../../apps/server/src/terminal/Layers/Manager.process-drain.ts#L71-L83), [Manager.process-drain.ts:195-206](../../../apps/server/src/terminal/Layers/Manager.process-drain.ts#L195-L206), [Manager.remote.ts:4-22](../../../apps/server/src/terminal/Layers/Manager.remote.ts#L4-L22). The default local Windows shell is `ComSpec`/`cmd.exe`; shell detection can label `wsl.exe` for dropped paths, but that does not pin a distro or change cwd resolution — [Manager.shell.ts:58-63](../../../apps/server/src/terminal/Layers/Manager.shell.ts#L58-L63), [Manager.shell.ts:79-116](../../../apps/server/src/terminal/Layers/Manager.shell.ts#L79-L116).
- `open` explicitly reattaches to a running terminal before interpreting new launch settings; it does not silently replace the session target. Explicit restart performs the new launch — [Manager.session.ts:48-66](../../../apps/server/src/terminal/Layers/Manager.session.ts#L48-L66), [Manager.session.ts:231-249](../../../apps/server/src/terminal/Layers/Manager.session.ts#L231-L249). Tests assert that an open with a different remote target reattaches to the old target, and only restart changes it — [Manager.remote.test.ts:62-94](../../../apps/server/src/terminal/Layers/Manager.remote.test.ts#L62-L94). The startup test also checks that later chat cwd/env/target changes do not mutate a running terminal — [Manager.startup.test.ts:21-60](../../../apps/server/src/terminal/Layers/Manager.startup.test.ts#L21-L60).
- `terminalCommandContextMatches` compares cwd, worktree, resolved target ID, and environment. `assertTerminalCommandContext` rejects any fallback or mismatched/non-running snapshot before a project command is written — [terminalCommand.ts:15-31](../../../packages/shared/src/terminalCommand.ts#L15-L31), [terminalCommand.ts:34-62](../../../packages/shared/src/terminalCommand.ts#L34-L62). `runBoundTerminalCommand` binds before opening, records the server snapshot, checks it, and only then writes — [terminalLaunchBinding.command.ts:24-56](../../../apps/web/src/lib/terminalLaunchBinding.command.ts#L24-L56).
- Current regression coverage includes local and SSH Home/fallback, target connection errors, stalled probes, and same-target SSH Home — [Manager.cwd.test.ts:25-107](../../../apps/server/src/terminal/Layers/Manager.cwd.test.ts#L25-L107), [Manager.cwd.test.ts:136-197](../../../apps/server/src/terminal/Layers/Manager.cwd.test.ts#L136-L197). Project setup tests verify no setup write after fallback and no write/restart into a retained terminal with a different target — [ProjectSetupScriptRunner.terminal.test.ts:62-141](../../../apps/server/src/project/Layers/ProjectSetupScriptRunner.terminal.test.ts#L62-L141), [ProjectSetupScriptRunner.terminal.test.ts:145-193](../../../apps/server/src/project/Layers/ProjectSetupScriptRunner.terminal.test.ts#L145-L193). Shared command tests explicitly reject mismatched execution target and fallback snapshots — [terminalCommand.test.ts:32-89](../../../packages/shared/src/terminalCommand.test.ts#L32-L89).
- One-shot subprocess handling already has timeout/kill support: `runProcess` spawns with bounded options, sends TERM on timeout, then force-kills after one second (Windows uses `taskkill /T /F`) — [processRunner.ts:82-99](../../../apps/server/src/utils/processRunner.ts#L82-L99), [processRunner.ts:129-179](../../../apps/server/src/utils/processRunner.ts#L129-L179). `buildSshCommandInvocation` separately quotes each remote-shell argument; this is relevant precedent because Windows `runProcess` uses `shell: true` — [sshCommand.ts:23-29](../../../apps/server/src/ssh/sshCommand.ts#L23-L29), [sshCommand.ts:56-90](../../../apps/server/src/ssh/sshCommand.ts#L56-L90), [processRunner.ts:129-144](../../../apps/server/src/utils/processRunner.ts#L129-L144).

### Inferences

- `os.homedir()` in the local resolver and outer PTY cwd is the Bigbud server process's host context. A `wsl.exe` shell label alone cannot make `Manager.cwd.ts`'s local `stat/access` or host Home refer to a chosen Linux distro.
- A WSL ID cannot safely be added as “just another nonlocal string”: both folder resolution and interactive spawn currently funnel nonlocal targets into SSH-specific validation/command construction. Both routes need an explicit WSL branch that consumes the same captured target ID.
- Since a WSL Linux path is not host-validated by the current local filesystem callback, WSL folder existence/access and Home lookup need to execute inside the selected distro (rather than checking the Windows host filesystem or substituting host `os.homedir()`). This is a design inference from current local/SSH implementations, not an existing WSL implementation.

### Gaps

- Current code does not specify whether WSL should support worktree runtime leases, agent identity detection, project file/git APIs, or provider runtime placement. `Manager.ts` currently skips local filesystem worktree leases for every nonlocal ID, and agent identity polling only inspects local IDs — [Manager.ts:28-49](../../../apps/server/src/terminal/Layers/Manager.ts#L28-L49), [Manager.process-drain.identity.ts:9-22](../../../apps/server/src/terminal/Layers/Manager.process-drain.identity.ts#L9-L22). Those are additional scope decisions if WSL becomes a general workspace target.

## Minimum additive design, tests, compatibility, and accurate deferral wording

### Takeaway

The narrowest safe addition is a terminal execution-target adapter for an explicit, stable WSL distro identity, used consistently by folder probing and PTY startup. Keep the current local/SSH behavior intact, preserve target identity in the existing launch request/snapshot, and fail closed on WSL target errors rather than falling back to host Home or another distro.

### Cited Findings

- No separate distro field is required merely to carry target identity through the current terminal contract: open/restart requests and snapshots already carry `executionTargetId`, and that ID is also captured in the terminal's server-side session state — [terminal.ts:43-50](../../../packages/contracts/src/workspace/terminal.ts#L43-L50), [terminal.ts:73-80](../../../packages/contracts/src/workspace/terminal.ts#L73-L80), [Manager.types.ts:31-40](../../../apps/server/src/terminal/Layers/Manager.types.ts#L31-L40).
- The current committed startup change is HEAD commit `79e2119689` (“Fixed terminal startup ownership and launch-context safety”). Its commit message states: “resolved origin/global-default directories with a bounded same-target Home fallback” and “Selected-distro WSL Home remains deferred.” The implementation and regressions are in `Manager.cwd.ts`, terminal startup/session code, and the tests cited above.

### Inferences

- **Target identity (proposal):** represent the chosen distro in a canonical explicit ID (for example, `wsl:<encoded-distro-name>`), parsed/validated by a WSL-specific helper. Treat the ID as immutable launch identity and pass it from request → session → snapshot → browser launch binding. The existing `ExecutionTargetId` accepts such a string, but a WSL parser/dispatcher and UI producer do not exist today. Avoid resolving “selected distro” from an ambient default at runtime; that would make a retained terminal's meaning mutable.
- **Same-target Home lookup (proposal):** add an explicit WSL adapter in the server terminal runtime and dispatch `Manager.cwd.ts`'s requested-folder and Home probes through the exact WSL target ID. Validate/canonicalize both folders inside that distro, return a bounded result, and set `directoryFallback` only when the requested path fails but that same distro's Home succeeds. On unavailable distro, probe timeout before target confirmation, or Home failure, return a target error; do not silently switch to local Windows Home, SSH, or a default WSL distro. This preserves the existing distinction between target/connection failures and ordinary cwd failures.
- **Process and command safety (proposal):** add a specific WSL PTY candidate/spawn path alongside the local/SSH paths, carrying the same target ID and launching explicitly into that distro. Use the existing 10-second folder-resolution budget and capped output for the one-shot probe, and process termination/timeout handling from `runProcess` for that probe. Build invocation arguments with a dedicated tested builder; do not interpolate distro names or requested paths into shell source, and account for Windows `shell: true` argument handling. The probe and interactive PTY must agree on the target, not merely invoke a generic `wsl.exe` shell.
- **Contracts/UI (proposal):** minimum terminal-only support can reuse `executionTargetId`; add a WSL target selection surface that emits the canonical ID and ensure terminal command launch inputs, restart inputs, and snapshots retain it. If distro is instead modeled as a separate property, it must be added consistently to open/restart contracts, session state/snapshots, UI launch binding, and project/thread persistence where selection is stored. Existing project target fields are generic enough to persist an ID, but current project remote-target UI is SSH-specific; project-level WSL selection would need its own UI and wider operation-routing audit.
- **Tests (proposal):** add resolver tests proving (1) requested cwd and Home probes use the identical explicit WSL ID, (2) WSL Home is returned rather than injected host `homedir()`, (3) a failed/missing target never falls back to host Home or a different distro, and (4) only a cwd error after target confirmation is eligible for same-distro Home fallback. Add invocation-builder adversarial cases for spaces, quotes, and shell metacharacters in distro/path inputs; process timeout/output-cap and late-result/no-spawn tests; and manager/PTy tests asserting selected distro identity survives open/snapshot/restart. Extend command-safety tests to ensure setup/project commands are not written on `directoryFallback`, target mismatch, or wrong retained terminal. These extend existing `Manager.cwd.test.ts`, `Manager.remote.test.ts`, and `ProjectSetupScriptRunner.terminal.test.ts` patterns.
- **Compatibility (proposal):** preserve omission/null of `executionTargetId` as `local` and leave all current `local` and `ssh:` routing unchanged. Make WSL routing opt-in only for the explicit WSL ID. Unknown/unsupported target schemes should fail as unsupported targets rather than being normalized to a host target. If project-level IDs are introduced, preserve legacy `executionTargetId` fallback behavior and keep the separate provider-runtime/workspace-target semantics already represented in project contracts.
- **Accurate deferral wording:** say “The committed terminal startup work adds bounded same-target Home fallback for local and SSH targets; selected-distro WSL Home lookup remains deferred.” Do not say “WSL support is entirely deferred/unsupported,” because WSL shell path formatting and drop-path conversion already exist. Also do not imply that setting a WSL drop-path mode selects a distro or makes Home lookup WSL-aware.

### Gaps

- The repo makes no explicit product decision about whether the WSL target applies only to terminal sessions or is a first-class project/workspace target. The proposal above is intentionally terminal-scoped; promoting it to a general workspace target needs explicit decisions and tests for filesystem/git operations, worktree leases, provider execution targets, and target verification.
