# Selecting a WSL distro's Home directory

Research checked 2026-10-11. Microsoft Learn page metadata showed these currentness markers when fetched: _Basic commands for WSL_ dated 2025-12-01 and updated 2026-06-02; _Advanced settings configuration in WSL_ dated 2026-04-15 and updated 2026-09-16; _Working across file systems_ dated 2021-09-27 and updated 2026-06-02. API reference pages for `WslGetDistributionConfiguration` and `WslLaunch` were updated 2024-02-22. Microsoft's basic-commands article recommends the Store-serviced WSL for receiving updates as available and says `wsl --help` is the full command list; CLI support can therefore vary with the installed WSL/Windows version.

## 1. Enumerating, selecting, and launching a distribution

### Takeaway

Use `wsl.exe --list --quiet` to enumerate installed distribution names, then pass the selected name explicitly with `--distribution` and, when needed, a Linux account with `--user`. `--exec` is the direct-command interface; `--shell-type` selects standard versus login shell behavior. The Microsoft Learn overview sends readers to the installed CLI's `wsl --help` for the complete option list, and does not itself define `--exec` or `--shell-type`, so check the target machine's help/version before depending on newer flags.

### Cited Findings

- **Installed list vs. online catalog:** `wsl --list --online` lists distributions available in the online store. `wsl --list --verbose` lists installed distributions with running/stopped state and WSL 1/2 version; list options include `--all`, `--running`, and `--quiet`, the latter showing only names. Therefore `--list --quiet` is a names-only view of the locally installed/registered set, not the online catalog and not a home-directory query. — [Basic commands for WSL | Microsoft Learn](https://learn.microsoft.com/en-us/windows/wsl/basic-commands) (dated 2025-12-01; page updated 2026-06-02)
- **Explicit distro selection:** `--distribution <Distribution Name>` (short form `-d`) is documented for running a specific distribution; `--set-default <Distribution Name>` is a separate operation that changes which distro unqualified WSL commands use. For a one-off query, pass `-d` rather than changing the default. — [Basic commands for WSL | Microsoft Learn](https://learn.microsoft.com/en-us/windows/wsl/basic-commands)
- **Explicit Linux user:** The documented form is `wsl --distribution <Distribution Name> --user <User Name>` (`--user`/`-u` in CLI help). The account must already exist in that distro; Learn says a nonexistent account produces an error and suggests `whoami` to print the current Linux username. — [Basic commands for WSL | Microsoft Learn](https://learn.microsoft.com/en-us/windows/wsl/basic-commands)
- **`--exec` / `-e`:** Microsoft's release notes include the CLI help text: `--exec, -e <CommandLine>` executes the specified command without using the default Linux shell. The current Basic commands article directs readers to run `wsl --help` for the complete command/option list; use the installed help as the version-specific reference. — [Release Notes for WSL | Microsoft Learn, Build 18305](https://learn.microsoft.com/en-us/windows/wsl/release-notes#build-18305); [Basic commands for WSL | Microsoft Learn](https://learn.microsoft.com/en-us/windows/wsl/basic-commands)
- **`--shell-type`:** The current WSL CLI help describes `--shell-type <Type>` as selecting how to run a shell, with `standard` and `login` types (standard is the default). The Learn pages reviewed do not define this option and refer readers to local `wsl --help`; this description was not runtime-verified on Windows for this research and is not a portable guarantee for older inbox WSL builds. `--shell-type` selects shell mode, not distro or user. — [Basic commands for WSL | Microsoft Learn](https://learn.microsoft.com/en-us/windows/wsl/basic-commands) (its stated full-option reference is the installed `wsl --help`)
- **Version differences:** The Learn page recommends updating to the Microsoft Store-serviced WSL for available updates and directs users to `wsl --version` and `wsl --help` to inspect the installed implementation. — [Basic commands for WSL | Microsoft Learn](https://learn.microsoft.com/en-us/windows/wsl/basic-commands)

### Inferences

- A names-only listing is useful for populating a selector, but Microsoft does not describe it as structured JSON or as including user/home metadata. Do not parse the human-oriented verbose table when the quiet listing is sufficient; keep the returned registration name as the value passed to `--distribution`.
- A suitable query shape is `wsl.exe --distribution <registered-name> --user <linux-user> --exec sh -c 'printf "%s\\n" "$HOME"'`. It explicitly selects the distro and account, then runs a shell only because the requested value is an environment variable. Use an argument array/process API in automation rather than interpolating untrusted names into a shell command string. The exact quoting wrapper depends on whether the Windows caller is PowerShell, CMD, or a programmatic process API.

### Gaps

- The Learn page does not publish the `--exec` and `--shell-type` help text or a minimum WSL build for these options. Confirm exact options with `wsl.exe --help` and `wsl.exe --version` on the target Windows machine; the host used for this research is macOS and cannot execute WSL locally.

## 2. Default-user configuration and obtaining that user's home path

### Takeaway

`/etc/wsl.conf` `[user] default=<name>` configures a distro's default login user; `--user <name>` selects a user for an individual invocation without changing that default. Microsoft's documented Win32 configuration API reports a default **UID**, not a home path. To retrieve the selected account's home value, launch a command in that distro as that account and print it from Linux; no direct home-path return field was found in the official API references reviewed.

### Cited Findings

- **Per-distro default user:** `wsl.conf` is stored at `/etc/wsl.conf` inside a distribution and applies to that distribution. Under `[user]`, `default` is a string specifying the user used when first starting a WSL session; the documented default is the initial username created on first run. These user settings are available starting with Windows Build 18980. — [Advanced settings configuration in WSL | Microsoft Learn](https://learn.microsoft.com/en-us/windows/wsl/wsl-config#user-settings) (dated 2026-04-15; page updated 2026-09-16)
- **Configuration timing:** WSL must stop and restart the distribution before configuration changes take effect; the article describes waiting until the subsystem has stopped (typically about eight seconds after closing all shells) and identifies `wsl --terminate <distroName>` or `wsl --shutdown` as ways to stop it. — [Advanced settings configuration in WSL | Microsoft Learn](https://learn.microsoft.com/en-us/windows/wsl/wsl-config#the-8-second-rule-for-configuration-changes)
- **Launcher configuration caveat:** The distro-launcher form `<DistributionName> config --default-user <Username>` requires an existing user, but Microsoft's Learn page warns it does not work for imported distributions because imported distributions have no executable launcher; use `/etc/wsl.conf` for those. — [Basic commands for WSL | Microsoft Learn](https://learn.microsoft.com/en-us/windows/wsl/basic-commands)
- **Invocation-time user selection:** `--user` runs WSL as a specified existing Linux user; combined with `--distribution`, Learn shows how to select a specific distro and user. — [Basic commands for WSL | Microsoft Learn](https://learn.microsoft.com/en-us/windows/wsl/basic-commands)
- **Documented WSL API fields:** `WslGetDistributionConfiguration` takes a registered distro name and returns distribution version, `defaultUID`, distribution flags, and default environment-variable strings/count. Its documented signature has no home-path output parameter. — [WslGetDistributionConfiguration function (wslapi.h) | Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/wslapi/nf-wslapi-wslgetdistributionconfiguration) (API reference updated 2024-02-22)
- **Documented process-launch API:** `WslLaunch` launches a process in a particular distribution, accepts an optional command, and returns a process handle. If no command is supplied it launches the default shell; if the caller does not inherit its current working directory, the process starts in the default user's home (`~`). It does not return that path. — [WslLaunch function (wslapi.h) | Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/wslapi/nf-wslapi-wsllaunch) (API reference updated 2024-02-22)
- **WSL `~` behavior:** `wsl ~` starts in the user's home directory, while `cd ~` returns to home inside a WSL prompt. This documents navigation behavior, not an API that outputs a home-path string. — [Basic commands for WSL | Microsoft Learn](https://learn.microsoft.com/en-us/windows/wsl/basic-commands)

### Inferences

- For the current session's home environment, `wsl.exe -d <name> -u <user> --exec sh -c 'printf "%s\\n" "$HOME"'` asks Linux to report `$HOME` after WSL has selected the requested distro and user. This is preferable to deriving `/home/<username>` because Linux accounts can use other home locations, and the root account's home is not normally under `/home`.
- `$HOME` reports the environment supplied to that process. If the requirement is specifically the account database's configured home field rather than the process environment, query the account record inside the distro (for example via `getent passwd <user>` where that utility/NSS source exists); Microsoft does not prescribe a cross-distro command for this.
- WSL exposes official configuration/launch APIs, but the reviewed `WslGetDistributionConfiguration` and `WslLaunch` contracts establish only that these APIs do not directly return a home path. This supports “no direct home-path field in the documented APIs reviewed,” not an exhaustive proof that no other interface of any kind exists.

### Gaps

- No Microsoft Learn interface located in this review returns a selected Linux user's home path directly. The Win32 API pages are older (last updated 2024-02-22); if relying on a newer WSL API, verify the current WSL SDK/API catalog separately.
- `sh`, `$HOME`, and `getent` behavior is Linux-side behavior rather than a WSL home-path API contract. Minimal/custom distros can differ, and profiles or environment overrides can make `$HOME` differ from the account database home field.

## 3. Context variables, registration, and Windows file access caveats

### Takeaway

Practical interpretation (the variable behavior itself is not explicitly specified in the Learn pages reviewed): `WSL_DISTRO_NAME` identifies the current distro context where WSL provides it, and `HOME` is the current Linux process's home environment value. Neither is a way for a Windows process in one context to query an arbitrary other distro; query another by launching it explicitly with `wsl.exe --distribution <name>`. Use WSL's UNC filesystem view rather than assuming that a Linux home maps to a Windows profile path. — [Basic commands for WSL | Microsoft Learn](https://learn.microsoft.com/en-us/windows/wsl/basic-commands); [Working across file systems | Microsoft Learn](https://learn.microsoft.com/en-us/windows/wsl/filesystems)

### Cited Findings

- **Selecting another context:** Microsoft documents `--distribution <name>` to run a specific distro and `--user <name>` to select a specific Linux user. This explicit launch selection is distinct from inspecting whichever distro is currently executing a process. — [Basic commands for WSL | Microsoft Learn](https://learn.microsoft.com/en-us/windows/wsl/basic-commands)
- **Documented environment-variable bridge:** Microsoft's filesystem/interop page describes `WSLENV` as a special list of variables shared between Windows and WSL and explains direction/path-translation flags. It does not document `WSL_DISTRO_NAME` as a cross-distro lookup API. — [Working across file systems | Microsoft Learn](https://learn.microsoft.com/en-us/windows/wsl/filesystems) (dated 2021-09-27; page updated 2026-06-02)
- **Working-directory and Windows privilege behavior:** Linux binaries invoked from Windows with `wsl <command>` use the current CMD/PowerShell working directory, run as the WSL default user, and have the same Windows administrative rights as the calling process. Commands are handled as WSL commands; file paths passed to Linux tools must use WSL path format. — [Working across file systems | Microsoft Learn](https://learn.microsoft.com/en-us/windows/wsl/filesystems)
- **Supported Windows view of distro files:** Microsoft documents entering `\\wsl$` in File Explorer to view available distributions and their root filesystems. The `wsl.conf` article also demonstrates a distro path using `\\wsl.localhost\\Ubuntu-20.04\\etc\\wsl.conf`. — [Working across file systems | Microsoft Learn](https://learn.microsoft.com/en-us/windows/wsl/filesystems); [Advanced settings configuration in WSL | Microsoft Learn](https://learn.microsoft.com/en-us/windows/wsl/wsl-config)
- **Cross-filesystem considerations:** Microsoft recommends keeping files in the Linux filesystem for Linux command-line work and in the Windows filesystem for Windows command-line work, noting performance benefits. Linux-root files follow Linux behavior, including Linux permissions and case sensitivity. — [Working across file systems | Microsoft Learn](https://learn.microsoft.com/en-us/windows/wsl/filesystems); [FAQ's about Windows Subsystem for Linux | Microsoft Learn](https://learn.microsoft.com/en-us/windows/wsl/faq) (FAQ page updated 2026-07-30)
- **Registration is scoped to the Windows user:** Microsoft's troubleshooting page advises checking for separate Windows accounts when an installed distro appears missing and notes the built-in Administrator is a separate account whose WSL distro list can be empty. — [Troubleshooting Windows Subsystem for Linux | Microsoft Learn](https://learn.microsoft.com/en-us/windows/wsl/troubleshooting) (dated 2026-04-15; page updated 2026-06-02)
- **Custom/imported distro names and removal:** `wsl --import <Distribution Name> ...` registers a distro under the supplied name; the Win32 API describes the name as a unique distribution name. `wsl --unregister <name>` removes it and permanently deletes its associated data, settings, and software. — [Basic commands for WSL | Microsoft Learn](https://learn.microsoft.com/en-us/windows/wsl/basic-commands); [WslGetDistributionConfiguration function (wslapi.h) | Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/wslapi/nf-wslapi-wslgetdistributionconfiguration)
- **UNC access can fail:** Microsoft's troubleshooting guidance notes that Windows access through `\\wsl$` relies on a 9P file server on the Linux side and can fail if that service did not start correctly. — [Troubleshooting Windows Subsystem for Linux | Microsoft Learn](https://learn.microsoft.com/en-us/windows/wsl/troubleshooting#cannot-access-wsl-files-from-windows)

### Inferences

- Treat `WSL_DISTRO_NAME` as a current-context identifier only, not as a command to select a target. The reviewed Learn material documents `WSLENV` as an environment-variable bridge but did not establish a documented compatibility contract for `WSL_DISTRO_NAME`; for automation, explicitly pass `--distribution` and don't trust a caller's inherited `HOME` or distro variable to describe a different target. — [Working across file systems | Microsoft Learn](https://learn.microsoft.com/en-us/windows/wsl/filesystems)
- Avoid constructing a Windows path such as `C:\\Users\\<WindowsUser>` or `/home/<LinuxUser>` from assumptions. The actual Linux home is distro- and account-specific; after querying it in the selected context, a Windows caller can use the distro's UNC namespace (for example `\\wsl.localhost\\<registered-distro><linux-path>`) when supported and accessible.
- Because names may be chosen during import, use names returned by the current Windows account's installed-distro listing rather than deriving names from online catalog labels or distro family names. Recheck existence immediately before launching when registration can change concurrently; list-then-launch is not an atomic transaction.
- `--unregister` is destructive and should never be used as a discovery/cleanup shortcut. A query command launched under an elevated Windows process also inherits the Windows administrative-rights context documented by Microsoft.

### Gaps

- I did not find a current Microsoft Learn page explicitly specifying the behavior, provenance, or stability guarantee of `WSL_DISTRO_NAME`. Its current-context interpretation is widely used but remains a documentation gap in the official Learn material reviewed; avoid making core selection logic depend on it.
- Learn describes `--list --quiet` as showing names, but does not guarantee output encoding, escaping, or atomicity if distributions are concurrently installed/unregistered. For automation involving unusual/custom registration names, validate on the target WSL version and handle command errors.
- Microsoft documents `\\wsl$`/`\\wsl.localhost` access and troubleshooting, but the exact availability and permissions of a particular home UNC path depend on the selected distro, account, and running WSL file-sharing service.
