## Summary

Durable automatic recovery is feasible with this architecture; native execution continuity remains provider- and topology-dependent. The goal is to preserve active-work intent and automatically reconcile/resume after laptop sleep, network loss, provider/backend crashes, and application relaunch. Local execution cannot progress while the laptop is asleep. An independently running remote process may continue; recovery must first attach to that process or retrieve its result, rather than run the work again.

TypeScript owns durable recovery intent, reconciliation scheduling and continuation decisions. Rust supplies bounded native execution and delivery capabilities, returning evidence that TypeScript reconciles through existing canonical command paths. Extend the existing Rust workspace agent where operation receipts, output retention and attachment need improvement; keep the Rust desktop supervisor focused on committed-event delivery. Thread recovery does not require a new desktop-supervisor protocol or shared delivery/work scheduler.

This revision applies the user's approved ownership recommendation after review of all four decision documents. The existing filename is retained to preserve references; its historical `rust-coordinated` wording does not describe the revised ownership.

Restoring a conversation is not the same as restoring a live execution. The invariant is **reconcile before continuing; never blindly replay potentially accepted work**. When evidence cannot establish a tool's outcome, preserve the thread and ask for a targeted resolution. Ordinary connectivity recovery should not require a Resume click.

## Problem

Existing reconnection mostly restores transports and UI event delivery. It does not durably establish whether a provider accepted an interrupted turn, whether tools completed, or whether continuing would duplicate work.

Code-derived gaps, not reproduced runtime failures:

1. Startup reconciliation maps a missing in-memory provider session to `stopped` and clears its active turn. A newly started server naturally has empty adapter maps; this can discard recoverable active intent and permit queued follow-ups prematurely.
2. Canonical command acceptance is transactional, but provider execution workers/deduplication are in memory. A crash after acceptance and before provider handling is different from a crash after provider acceptance but before persistence; current receipts alone cannot distinguish them.
3. Resume support varies substantially across nine registered providers. Some restore history, some create a fresh native session, and most lack generic active-turn inspection.
4. Native delivery supervision is volatile and starts through delivery demand. That is its existing delivery boundary, not a defect requiring a thread scheduler in Rust. Unfinished work needs its own backend-scoped TypeScript recovery lifecycle independent of renderer subscriptions.
5. Remote operation output can be acknowledged while still only in local memory. A backend crash then loses output the remote agent may already have pruned. Remote evidence also has short retention limits relative to an overnight absence.

Confidence is high in these inspected paths, bounded on provider runtime behavior: no live provider, sleep, remote-host, or crash reproduction was performed during planning. Provider-native recovery capabilities are implementation validation gates, not assumed guarantees.

## Goals

1. Preserve accepted active work continuously, before external dispatch; never depend on a last-moment sleep/shutdown callback to save it.
2. Resume safely after wake/network return while the app is running, and after reopening following crash, deliberate quit, reboot, or a long absence.
3. Recover all registered providers over their supported local and remote topologies. Recover many threads independently, respecting parent/child dependencies and one active execution per thread.
4. Use Rust for bounded native execution evidence, attachment and delivery reliability; TypeScript owns the thread recovery workflow in accordance with the accepted decisions.
5. Reattach running execution, ingest known completion, or issue one durable continuation from an established safe boundary. Do not repeatedly send the original prompt.
6. Require a recovery-specific decision only for unresolved execution/tool effects. Existing approvals, credentials, permission repair, missing resources, and provider compatibility requirements remain effective.
7. Preserve history, partial messages, attachments, queued prompts, approvals, delegated-thread/watch identities, workspace/runtime selection, and user settings.

### Settled product behavior

| Event                                 | Required behavior                                                                                                                    |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Laptop sleeps / network disappears    | Preserve intent; do not infer cancellation. Surviving remote work remains attached to its original identity.                         |
| Wake / network available              | Automatically probe, reconcile, reattach, and safely continue. Network hints are not proof that a target is reachable.               |
| Unexpected backend/provider exit      | Reconstruct durable intent; inspect original execution before any resend or replacement.                                             |
| Explicit app quit / update restart    | Suspend intent durably, perform bounded shutdown, resume when app next runs. Quit is not thread Stop.                                |
| Reboot / days away                    | Same reconciliation policy on reopening; no arbitrary age-based confirmation. Missing outcome evidence remains explicit uncertainty. |
| Explicit thread Stop                  | Durably revoke continuation before cancellation; never auto-resume that intent. Cancellation success is a separate fact.             |
| Explicit destructive remote Reconnect | Retain existing deliberate interruption behavior for affected work; fence recovery so it cannot undo the user's restart decision.    |
| Completed/deleted work                | Never restart it. Retain only evidence needed for deduplication and deletion-safe cleanup.                                           |

## Non-Goals

- Keeping a sleeping laptop executing, preventing sleep, moving provider credentials to a cloud worker, or automatically launching the app at OS login.
- A new OS daemon that revives Electron without the user reopening it; existing Electron backend restart remains the process recovery hatch while Electron is alive.
- New remote OS/runtime support, restarting SSH/hosts, installing newer remote binaries silently, or replacing project configuration.
- Exactly-once execution of arbitrary external side effects without a supporting identity/receipt contract; model text is not proof that a tool ran.
- Replaying terminal input, rerunning completed tasks, changing scheduled-task semantics, or recreating delegated threads as a recovery strategy.
- Replacing desktop delivery authority, canonical replay/baselines, mobile recovery, provider SDKs, or unrelated dirty work.
- Moving thread scheduling, provider recovery policy or product lifecycle into Rust; adding a thread-intent protocol to the desktop supervisor; refactoring delivery fallback merely to host recovery work.

### Architecture and engineering defaults

| Responsibility                                                                                                                          | Owner                                      |
| --------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| Discover unfinished threads, schedule reconciliation, classify outcomes, enforce Stop/approvals/dependencies and authorize continuation | TypeScript orchestration recovery service  |
| Interpret provider protocols, restore native sessions and recover provider results                                                      | TypeScript provider adapters/services      |
| Canonical intent, acceptance, ordering, events, checkpoints, receipts and transactions                                                  | TypeScript canonical command path / SQLite |
| Native operation execution, stable identity checks, attachment, bounded journal/output retention and typed execution facts              | Existing Rust workspace-agent capabilities |
| Committed-event delivery, delivery generations, replay, backpressure and UI application ACK                                             | Existing Rust desktop delivery supervisor  |
| Observe suspend/resume and supervise the backend process through existing lifecycle machinery                                           | Electron                                   |

- **Durability:** reuse canonical SQLite for recovery intent, provider delivery attempts, output receipts and settlement outbox. Rust retains only bounded operational evidence; it neither queries thread inventory nor writes orchestration tables or stores provider credentials.
- **Coordination owner:** a focused `ThreadRecoveryCoordinator` service in the existing TypeScript orchestration `Services/` and `Layers/` structure. Start it at backend lifecycle scope, integrate existing provider-turn supervision, and keep one owner of thread recovery scheduling/claims. It does not depend on event consumers or the desktop delivery sidecar.
- **Process lifetime:** Electron restarts the backend while alive. Reopened backend reloads SQLite and starts its recovery service. Native operations are inspected/reattached through existing owners; no new background OS service or shared delivery/work supervisor is needed.
- **Capability failures:** a missing/incompatible desktop delivery binary follows its existing delivery fallback and does not disable safe provider reconciliation. Missing native execution/receipt support blocks only operations that require it, retaining intent and reporting the prerequisite. Never bypass accepted native operations through an unsafe alternative execution path. A server-side recovery feature gate controls automatic continuation independently of delivery routing.
- **Scheduling defaults:** 4 concurrent reconciliations globally, 1 target connectivity probe per target, 1 claimed recovery action per thread; up to 128 scheduled records/256 KiB metadata per page. Full-jitter exponential retry starts at 1 second and caps at 60 seconds; retries do not expire intent. Target health hints can bring one probe forward, not all thread retries. Use a 10-second inspection deadline and 20-second transport-attempt deadline, separate from existing execution deadlines. Tune only with measured evidence.
- **Time:** wall-clock due timestamps are durable hints; reconstruct elapsed timing after startup and clamp clock jumps. Never persist monotonic values across process lifetimes. Suspend/wake observations are hints and may be missed; periodic target probes/time-gap reconciliation provide the fallback.
- **Compatibility:** no new dependency is planned; use current Effect schemas, SQL, protobuf and native owner mechanisms. Dependency additions require the Rust instructions' separate review/approval. Every materially edited authored source/test remains <=400 lines.

These are implementation defaults, not claims that these capabilities exist. Verify limits with deterministic clocks/load tests, and revalidate SDK/CLI versions during provider conformance work. Current Electron documentation confirms native suspend/resume events; use the installed Electron API rather than legacy examples: https://github.com/electron/electron/blob/main/docs/api/power-monitor.md (queried via Context7 on 2026-09-10). Shutdown notifications differ by platform and are never the durability mechanism.

**Distinct acknowledgement boundaries:** canonical command acceptance is not provider acceptance; durable local receipt of native results is not UI application ACK. Persist provider acceptance evidence, advance native output receipts only after durable storage, and retain existing renderer application-ACK semantics independently. None of these frontiers alone means the thread has recovered.

**Canonical ingress:** public recovery controls use authenticated `CommandGateway` admission through current normalization/dispatch wiring. Internal provider/startup recovery follows established internal reaction/command conventions; do not route internal work through a WebSocket-facing helper. Canonical continuation and lifecycle changes use those command paths; infrastructure lease/due-time/receipt bookkeeping uses its owning repositories without gaining canonical decision authority. Add newly introduced mutation ingress to the gateway inventory during implementation as required by that document. Provider/native calls remain outside SQLite transactions.

#### Stop/control disposition and dispatch ordering

Wire these decisions at canonical command acceptance/event persistence in `OrchestrationEngine.commandProcessing.ts`, not only later in `ProviderCommandReactorHandlers.session.ts`. Existing UI sources are `apps/web/src/components/chat/view/ChatView.turnActions.logic.ts:59-88` and `ChatView.promptQueue.logic.ts`; both use `thread.turn.interrupt`, with different payload intent. Preserve command compatibility by deriving disposition from validated existing control metadata; add explicit metadata only where the current command cannot distinguish it.

| Accepted operation                                                                                     | Recovery disposition                                                                                                                                                                                                                                                                                                                                   |
| ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Plain `thread.turn.interrupt` / `thread.turn-interrupt-requested` from Stop, no continue reservation   | Revoke automatic continuation of the matching original intent, even if native runtime is missing. Retain outcome/cancellation reconciliation; reject stale turn/epoch targeting rather than revoke newer work.                                                                                                                                         |
| `thread.session.stop` / `thread.session-stop-requested`                                                | Revoke current session's applicable active recovery intents; a later explicit new send creates a new intent.                                                                                                                                                                                                                                           |
| Interrupt-and-continue / send-now with `operation.reservedPromptIds` or validated pending flush intent | Supersede old-turn continuation but retain the durable control operation and reserved next prompts. Flush once only after authoritative old-turn settlement; do not infer settlement from missing runtime. Reuse `completeInterruptContinue` (`ProviderCommandReactorHandlers.session.ts:82-105`) and correct its missing-runtime branch at `234-258`. |
| App teardown / update / shutdown `stopAll`                                                             | Suspend, not revoke. Carry lifecycle reason through cleanup so it cannot be mistaken for accepted user Stop.                                                                                                                                                                                                                                           |
| Explicit destructive remote Reconnect                                                                  | Revoke automatic continuation for the affected old-runtime intents as part of the durable restart interruption fence, before replacement admission. Preserve outcome records and other runtimes.                                                                                                                                                       |

Use a shared per-thread dispatch-admission gate for user control acceptance and the final provider-send admission. Within that gate, transactionally CAS the intent/revision and persist may-have-been-sent, then release the gate before awaiting provider I/O. This transaction is the linearization point: Stop committed first prevents dispatch; dispatch admission committed first is potentially accepted work, so a later Stop revokes further continuation and requests cancellation/reconciliation without declaring the effect absent. On a crash in that latter window, reconcile the existing attempt and never resend it automatically. Both normal workers and recovery sends must use this gate; an independent final read before send is insufficient. Serialize database revisions across controller generations, not just an in-memory lock.

Tests must cover crash immediately after Stop acceptance, Stop with no native session, stale Stop against newer work, send-now preserving reserved prompts, and both orderings of final dispatch admission versus Stop.

**Exit:** fault tests show canonical acceptance cannot lose execution intent; missing memory cannot clear unresolved work; a failed/duplicated settlement can safely finish later; >256 queued threads cannot deadlock bootstrap.

#### Evidence reclamation lifecycle

Implement and test an explicit reclamation policy before enabling the new retention contract. Thread Stop revokes continuation; it is not acknowledgement of an operation's effects and does not authorize forgetting unresolved execution evidence.

| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Output durably received locally                | Remote output payload may be pruned only through the committed contiguous receipt watermark; retain completion/operation identity until its separate reconciliation boundary.                                                                     |

| Journal capacity exhausted                     | Reject new admission before reserved completion capacity is consumed. Continue permitted receipt processing and compaction so acknowledgement can release capacity.                                                                               |

## Risks And Decision Gates

- **External execution ambiguity:** neither Rust nor SQLite can prove arbitrary remote side effects after evidence loss. Resolve from native receipts/history or present targeted uncertainty. Do not promise universal live-stack checkpointing.
- **Shutdown distinction:** quit now preserves intent while Stop revokes it. Test direct exit, updater, crash and reboot; teardown must not emit cancellation that erases the chosen resume policy.
- **Two persistence domains, one product authority:** local SQLite and remote journal cannot transact together. Durable-before-ACK receipts plus immutable IDs/CAS make response loss reconcilable; no whole-operation retry to bridge the gap. Native execution facts are evidence, not a second source of thread lifecycle decisions.
- **Storage pressure:** long absence cannot imply unbounded transcript/output storage. Reserve evidence capacity, bound outputs, retain compact unresolved identity and expose gaps; never delete uncertainty to admit work.
- **Ownership races:** old adapters, coordinator generations, manual Stop, remote restart and deletion can race recovery. Check current revision/epoch at each effect boundary; lost responses reconcile existing attempts.
- **Dependency/API uncertainty:** provider-native inspection/results differ by installed version. A failed probe is a documented capability limit and release gate for that automatic path, not permission for fallback duplication. New provider versions require revalidation.
- **Scope of platform coverage:** desktop macOS/Windows/Linux are included. Existing remote Linux/Unix restrictions remain. Do not claim a skipped native Linux test passed because macOS checks are green.
- **Rollback:** disable the recovery coordinator/continuation gate, drain/fence current claims and retain durable pending state, receipts, queues and history. Do not drop additive tables or revert to pre-recovery queue eligibility while unresolved intents exist. Code rollback requires a compatibility build that understands recovery fences; older binaries are not automatically safe. Existing delivery fallback remains separate.
