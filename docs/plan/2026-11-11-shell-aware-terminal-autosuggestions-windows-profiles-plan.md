## 2. Summary, goal, and definition of done

Deliver two related but independently releasable capabilities:

1. Explicit execution-host shell profiles, including Windows discovery, a persisted default, and per-terminal selection without changing running terminals.
2. Terminal-local, shell-owned inline history suggestions. Accepting with unmodified Right Arrow at end of line or Tab inserts text only; accepting never executes it.

The execution host's interactive shell, not xterm or React, owns the editable buffer, cursor, cwd, command history, and candidate selection. There is no AI request per keystroke, no frontend reconstruction of the command line, and no browser-side history/completion database.

### Observable acceptance criteria

- **AC1 — Windows defaults:** A provably fresh Windows installation initially selects an installed, executable PowerShell 7, otherwise Windows PowerShell, otherwise cmd. An existing or uncertain installation retains today's implicit `ComSpec`/cmd behavior. Migration is durable, idempotent, and cannot reinterpret a lost/corrupt settings file as a fresh installation.
- **AC2 — Explicit choice:** The settings default and per-terminal picker persist stable host-scoped profile identities. New terminals use the selected profile. Running terminals and recovered owners retain their actual launch identity. An unavailable explicitly selected profile produces an actionable failure, never an unannounced shell substitution. Local, SSH, WSL, and both remote-agent creation paths support this profile-only release with first-party suggestions off; required discovery/protocol/owner compatibility is delivered before the UI release, not deferred behind zsh qualification.
- **AC3 — Safe insertion:** A qualified adapter displays one bounded history suffix and accepts it only in its own positively identified editing context, at the end of the buffer, against the matching candidate/edit revision and current control lease. Acceptance changes the shell buffer but emits no Enter, carriage return, or line feed. Tab with no valid suggestion and Right Arrow midline retain their original behavior.
- **AC4 — Safe inactivity:** No first-party suggestion/acceptance occurs during command execution, password prompts, alternate-screen applications, multiline input, uncertain editor state, paste, IME composition, unsupported keymaps, disconnected control, or stale generations/revisions. Prompt OSC markers or absence of alternate-screen mode alone never enable acceptance. After suspension/control failure, potentially accepting Tab/Right input is released only after acknowledged shell invalidation or guaranteed shell-local lease expiry; a completed PTY write, RPC response, or application timer is not proof.
- **AC5 — Remote authority:** Local, Direct SSH, and remote-agent terminals use execution-host history and shell discovery. Both owned and nonowned remote-agent creation paths use the same launch policy. Reattachment never reinjects startup or creates a replacement owner when outcome is unknown.
- **AC6 — Compatibility:** User rc files, prompt plugins, custom bindings, native suggestions, WSL identities, terminal scripts, ordered input, output recovery, and restart fences are preserved. When compatibility is not proven, launch the requested shell without first-party suggestions and explain why.
- **AC7 — Privacy and trust:** No command buffer/history candidate is added to contracts, telemetry, diagnostic logs, or settings. No user profile modification, silent plugin installation, workspace-sourced integration code, weakened SSH trust, credential forwarding, or remote-to-local history fallback occurs.
- **AC8 — Honest support:** Settings distinguish qualified first-party history suggestions, native-managed behavior, disabled behavior, unavailable capability, and unknown/probing state. cmd has no first-party suggestions initially. PowerShell support follows actual loaded PSReadLine capabilities, not executable branding.
- **AC9 — Platform proof:** Automated tests and actual platform/manual evidence are recorded separately. zsh is first, across local/SSH/both agent paths; Bash, fish, PowerShell, WSL, and Git Bash have explicit qualification boundaries. Unsupported native providers are not counted as satisfying AC3–AC4.
- **AC10 — Maintainability:** Every materially edited or newly authored source/test file is at most 400 lines, split by concern using repository conventions. Focused formatting, lint, configured package typechecks, and relevant tests pass before implementation completion. Broad checks need separate approval.
- **AC11 — Approved toolbar UX:** Place a compact current-profile selector (for example, “PowerShell ▾”) beside `+` in the existing top-right floating terminal toolbar, retaining split/rename/close/minimize/maximize controls. Selection is per pane and independent of the global default. `+` and split inherit the active/source pane's actual profile and execution host unless an explicit menu action selects another. “Open in new terminal” is the safe default and preserves the running session; “Replace this terminal…” requires confirmation before ending/restarting it. Never imply live shell mutation. Validate cwd mapping on the destination host, scope profile discovery to that execution host, and expose discovery unavailability without substituting desktop/local profiles. Keyboard/menu/dialog focus, stale generation rejection, and replacement failure behavior are tested.

## 5. Scope and settled behavior

### In scope

- Shell profile discovery, host-scoped stable IDs, server-authoritative defaults, per-terminal launch selection, actual launch identity, and capability/status UX.
- Conservative fresh/existing migration; Windows backend selection for supported PTYs.
- Shared launch planning for local, SSH, WSL, owned agent, and nonowned agent paths.
- Trusted session assets and private bounded status/control negotiation.
- zsh first-party history-only integration first, then separately qualified Bash/fish/PowerShell adapters.
- Shell-native coexistence reporting, explicit fallback, bounded cancellation/cleanup, security and platform validation.

### Explicit non-goals

- AI/LLM completions, filesystem/spec-driven suggestions, Fig generators, executing commands to discover suggestions, popup completion menus, or a browser prompt-input model.
- Clink installation/integration; cmd first-party suggestions.
- A Windows remote-agent PTY implementation.
- Changes to user's profiles, global shell defaults, system PATH, registry associations, execution policy, or installed shell modules/plugins.
- Copying Warp/VS Code terminal UI code or replacing xterm.
- Opportunistic upgrades of Bun, Electron, xterm, Effect, PSReadLine, or other dependencies.
- Generic cleanup of concurrent orchestration/settings work; root-wide validation or Git operations.

### Must remain unchanged

- Existing implicit launch fallback behavior where the user has not selected an explicit profile.
- Terminal input order, output replay and recovery, shell/agent identity, resize and lifecycle behavior, command-script execution semantics, and no retry after unknown input outcomes.
- Normal shell completion when no valid first-party suffix exists; ordinary cursor movement midline; modifiers and unsupported keymaps.
- User-native plugins and bindings when the adapter cannot compose safely. Disabling first-party integration must not disable the user's own plugin.
- Existing remote-agent owners and WSL selections; changing a setting never switches an active shell.

## 6. Target architecture and contracts

### 6.1 Profile identities and capabilities

Add focused schema modules, proposed as `packages/contracts/src/workspace/terminalShell.ts` and `packages/contracts/src/core/settings.terminalShell.ts`, rather than expanding the existing terminal/settings files beyond their limits.

Define the following concepts; final TypeScript names may follow nearby naming conventions, but retain these semantics:

- `TerminalShellProfile`: opaque `profileId`, host scope, shell kind (`zsh`, `bash`, `fish`, `pwsh`, `windows-powershell`, `cmd`, `other`), display name, executable identity, fixed launch arguments, platform, availability, and integration capability/reason. Reject NUL/CR/LF in executable identity and enforce bounded field/array sizes.
- `ShellHostScope`: local server host, selected SSH target/account, selected agent runtime/workspace binding, or pinned WSL distro/user. IDs contain no password, raw connection string, or workspace command text.
- `ShellSelection`: either explicit `profileId` or the compatibility `legacy-auto` policy. This is not an arbitrary executable/command-string input API.
- `ShellLaunchIdentity`: actual profile/host/shell kind, integration asset digest/version, and actual capability outcome. Include it in open/restart snapshots and started/restarted state; preserve it in recovery persistence and launch bindings.
- `ShellIntegrationStatus`: `probing`, `qualified-history`, `native-managed`, `disabled`, `unavailable`, or `unknown`, plus bounded reason codes, adapter/protocol version, immutable integration session ID, and current binding/control lease. No buffers, cursor positions, cwd samples, or candidates travel with status.

Discovery runs on the execution host and is cached per host/identity with bounded TTL, explicit refresh, cancellation on target changes, and in-flight coalescing. Use a proposed five-minute TTL, three-second probe timeout, and 64-profile ceiling; make these internal constants with tests. Invalidate on executable disappearance, target reconnect/change, or explicit refresh. Discovery failure returns unavailable/unknown, not a fake local profile.

Profile IDs must be stable across discovery order and display-name changes. Generate them from host scope plus canonical executable identity and fixed launch variant; do not use array positions, localized labels, or settings timestamps. For Windows, normalize path case and separators for identity while preserving the executable path used for spawn. WSL distro and user are part of guest scope, not folded into an ambiguous command string. Do not persist a profile catalog as the source of executable truth.

At launch, resolve the stored ID against the current host inventory and revalidate the executable. Spawn executable and argv separately. Never remove quotes by whitespace splitting, build `-Command` strings from executable paths, expand workspace variables, or treat labels as commands. A removed/invalid explicit profile yields an actionable error and a choice to select another profile; automatic retry through a different shell is reserved for `legacy-auto` compatibility.

### 6.2 Defaults, migration, and settings persistence

Shell defaults belong in server settings, not only client local storage. Use a versioned atomic `terminalShells` settings object containing a migration version/origin, host-default selections, and the first-party suggestion policy (`off` or `qualified-history`). The default decoded/uninitialized object is explicitly version zero; it is not evidence of freshness. Persist the entire versioned object atomically and exempt its migration marker/identity fields from default stripping.

Concrete startup algorithm:

1. Before `ensureServerDirectories`, DB creation, log creation, or settings initialization, capture a small immutable prior-state classification in startup configuration. Fresh requires that the selected application's state root did not exist and no already-supported legacy-state location applicable to that root contains prior authoritative state. Existing directories, even empty ones, existing settings/DB/keybindings/ownership records, read errors, access errors, conflicting evidence, and unrecognized legacy layouts mean existing/uncertain. Inventory actual legacy path aliases from startup code before coding; do not scan a user's home recursively.
2. Under settings initialization/update synchronization, load/recover settings using existing field-wise recovery. An already valid version-one selection always wins. Preserve an explicit recognized choice from any intermediate schema; do not replace it merely to apply the new ranking.
3. If uninitialized and Windows is provably fresh, discover installed shells on that Windows host and choose one concrete stable profile ID: executable PowerShell 7 first, then Windows PowerShell, then cmd. Noninteractive discovery must not run profiles. Discovery errors are not evidence that no shell exists: retain `legacy-auto` and report the inability to select rather than making a false profile ID.
4. If uninitialized and existing/uncertain, persist `legacy-auto` for the local default. This continues the current `ComSpec`/cmd resolution and fallback policy; it does not reinterpret the installation as pwsh-capable migration eligibility.
5. On Unix, preserve current `$SHELL`/fallback semantics unless the user selects an explicit profile. Newly seen remote scopes and WSL guests preserve their current account/guest-shell policy until explicitly selected; local Windows ranking does not select a remote shell.
6. Atomically persist migration origin/version and selection before exposing the new default to terminal launches. Do not change first-run behavior on a second startup because the new shell happened to equal a schema default. A selected concrete fresh default remains selected when additional shells are installed later.
7. A failed migration write must not switch a launch to the new fresh default. Surface a settings warning and continue with compatibility behavior (or the last durably confirmed explicit choice). On retry, use the original conservative evidence; a crash after directory creation must not upgrade the next run to fresh.

Do not require a SQLite migration merely to store these settings. If inspection during implementation establishes a real persistence-table need, allocate the then-current next migration and register it conventionally; do not reuse the concurrent migration number 168 or edit an unrelated migration.

The suggestion policy can be persisted as `qualified-history`, but the adapter rollout allowlist remains off until its gates pass. Rollback disables adapters without deleting profile choices or migration evidence.

### 6.3 Shared launch planning and immutable running identity

Introduce a focused server launch-planning service, with pure policy helpers separate from host discovery and transport. Proposed files are `terminal/Services/ShellProfiles.ts`, `terminal/Services/ShellLaunchPlanner.ts`, and concern-split implementations under `terminal/Layers/`.

Inputs: terminal identity, host scope, requested selection, execution target/cwd, launch kind, terminal size, caller runtime env, recovery/owner identity, and prior actual launch identity when restarting or restoring. Output: validated executable/argv, execution-host cwd/env policy, drop-path mode, immutable profile identity, asset requirements, and capability/bootstrap plan. Contracts contain schemas only; planning and filesystem/network work stay server-side.

- New manual terminals without an active/source pane use per-terminal explicit selection, otherwise the server default for that host, otherwise `legacy-auto`. The toolbar `+` is different: it inherits the active pane's actual profile and execution host, not a recently changed global default; an explicit menu action can select another profile for the new terminal.
- A split inherits the source terminal's actual profile and target unless the user explicitly selects another; it must not silently use a newly changed default. If a legacy or unconfirmed pane's actual profile cannot be identified, require an explicit destination-host choice for the new pane and label the uncertainty; never silently inherit launch intent, current defaults, or desktop profiles. Deliberate selection of the host's legacy policy remains an explicit choice, not inferred actual identity.
- Restart retains the terminal's actual selection/profile. A different profile is launched through “Open in new terminal” by default; “Replace this terminal…” requires confirmation before ending/restarting the identified session. Both actions use the immutable launch context and current operation/generation fences; neither mutates a running shell or changes the global default.
- Command/script routing includes shell identity in launch-context compatibility checks. It must not send a command into a different bound shell merely because cwd matches. Existing intentional command submission still appends Enter; suggestion acceptance does not.
- Existing legacy snapshots/owners without identity stay legacy/unknown until a deliberate new launch. Infer neither a historical executable nor integration readiness from today's defaults.
- WSL profiles resolve/run inside the pinned guest. Preserve existing script-routing and file-link/drop restrictions; do not silently move existing automation into WSL or a different distro.
- Manager and both agent creation paths consume the same resolved policy. Remote-agent host-side validation remains authoritative; client data cannot override HOME/PATH/SHELL/account identity.

On Windows, select node-pty for local terminals even when the server runtime is Bun, using existing NodePTY unavailable-native-module handling. On other hosts retain the current backend policy. Prove Bun-on-Windows can load the required node-pty runtime before promising it; otherwise report that backend unavailable and document the supported Node/Electron path. Discovery success alone does not equal PTY capability.

### 6.4 Shell-owned suggestions and acceptance invariants

Use first-party session-only shell adapters. Do not add a browser ghost-text overlay or candidate acceptance RPC. The candidate and editing revision remain in the shell; ordinary Tab/Right bytes still use the existing generation-fenced input lane.

**Requested visual refinement:** Show a muted right-arrow hint after the suggested suffix with a small gap (initial target: two display cells). The requested design reference is `<HugeiconsIcon icon={ArrowRight03Icon} />`; xterm's PTY text cannot embed a React/SVG component. Preserve shell-owned rendering and the prohibition on browser ghost-text overlays; use a shell-rendered arrow glyph when that is the compatible representation. The hint is decoration only, never part of the candidate, editable buffer, accepted suffix, or submitted command. Clear it with the rendered suffix on invalidation. Qualification must cover line wrapping/display width and confirm acceptance inserts neither the gap nor the arrow. Do not introduce candidate-bearing metadata or browser buffer reconstruction to position an icon.

For zsh, start from ZLE state and hooks: `BUFFER`, `CURSOR`, active keymap, line-init/line-finish, pre-redraw/buffer-change observation, `POSTDISPLAY`, and wrappers around captured original widgets. A prompt event only announces readiness; an active known ZLE editing context and current adapter lease are required to display/accept.

Maintain shell-local immutable integration session ID, control lease, editor epoch, editing revision, and the tuple associated with the suffix actually rendered. Every acceptance widget must independently check a shell-local validity predicate immediately before insertion: matching session/lease and rendered revision, active supported editing context, no suspension, and an unexpired finite execution-host monotonic lease deadline. Expired/invalid leases clear the tuple/suffix and call only the original widget; they cannot accept even if no control callback or redraw has run. A change in buffer, cursor, keymap, line lifecycle, paste/composition suspension, or control lease invalidates that tuple and removes the suffix before the next redraw. Acceptance must compare the saved rendered tuple against current state and buffer prefix; it must not recompute a new candidate inside the accept widget and accept that new candidate without an intervening render.

Unmodified Right Arrow accepts only at end of buffer. Tab accepts only a valid current suffix; otherwise call the captured original Tab widget exactly once. Right Arrow midline calls the original movement widget. If there is a stale first-party rendered tuple, clear it and perform only the original key behavior; never insert stale candidate text. Enter is never wrapped to perform implicit acceptance. Begin with known emacs-mode bindings; vi modes and custom widget ownership are unavailable until separately qualified.

Filter every candidate and insertion suffix before rendering and again before insertion. Reject NUL, CR, LF, ESC, C0/C1 controls, DEL, Unicode line/paragraph separators, and directionality/format controls that can conceal terminal input. Reject multiline buffers/history entries and over-limit strings. Do not sanitize by dropping bytes and then accept a different command. Literal shell punctuation in a single-line history command is allowed; it is inert until the user separately executes it.

History-only v1: case-sensitive prefix matching of the current nonempty single-line buffer, newest valid distinct entry first, maximum 1,000 inspected entries and 4,096 candidate characters. Use the execution shell's already loaded history and options; do not force-load other users' history, query local history for a remote shell, or write/merge history. No external process or dynamic completion generator runs per edit. Coalesce redraw work; stop searching at the bound. No result is preferable to exceeding the budget. Rich command/file completions require a later plan.

The revision requirement here is shell-local validation of the candidate the adapter rendered, not a claim that the browser has acknowledged every displayed frame. Do not introduce stale candidate payloads in the browser to simulate that guarantee. Gate G1 must test rapid edits/acceptance and verify the precise invariant.

### 6.5 Composition, reconnect, and private control

A shell cannot reliably infer browser IME composition from PTY bytes. An OSC prompt marker cannot solve this. Use a narrowly scoped out-of-band control bridge; do not inject magic escape sequences or commands into PTY input to toggle suggestion state.

Proposed Unix bridge: a per-integration private directory with two bounded framed FIFO streams, one shell-status direction and one control direction. The host controller owns descriptor lifetime. zsh monitors its descriptor through supported editor readiness hooks; nothing reads the foreground application's stdin. A trusted shell helper can carry these streams over a separate non-TTY SSH exec using the existing SSH authentication/escaping policy, without requiring remote Node/Python. The agent owns equivalent bridge descriptors locally and transports control/status through additive agent protocol messages. Gate G1/G2 must validate this architecture, including FIFO open deadlocks, EOF behavior, SSH multiplexing policy, and OS support, before implementation is considered ready.

The bridge carries only protocol/version, session/lease identifiers, bounded revision counters, suspend/resume/disable acknowledgements, and status/reason codes. No candidate, command buffer, history entry, or credentials. It grants no general shell-command execution endpoint. All frames are length-bounded, strictly decoded, deadline-limited, and rejected on unknown session/lease/version. Filesystem ownership and private permissions establish scope; a UUID in an OSC string is not authentication. Same-user malicious processes are outside an authentication guarantee, but workspace output cannot grant readiness or execute controller commands.

Extend the existing logical terminal input queue to order tagged operations (`data` and restricted interaction-state operations). Adjacent data operations may still coalesce; interaction operations form barriers. This is one dispatch/order lane, not an independent acceptance lane. Forward browser composition-start/end, paste boundaries where needed, attach/detach, and capability teardown through a typed interaction API and host bridge. Never put a control frame into `proc.write`. Continue to fence all operations with runtime generation, and never retry an uncertain write/control outcome.

On composition start, immediately inhibit first-party acceptance in the viewport's composing key handling and enqueue a shell suspension/invalidation. Clear the rendered suffix through shell redraw, not a browser model. Do not swallow keys needed by the IME. On composition end, forward the committed input in xterm's observed order, then resume only after a new acknowledged shell editing revision. No ghost should be re-enabled based solely on a DOM event. Gate G1 must prove the actual xterm composition/data event order on supported browsers and show that no Tab/Right used by the IME reaches a first-party accept widget. Failure keeps the adapter unavailable rather than weakening the guarantee.

**Write completion is not shell acknowledgement.** `TerminalInputQueue.ts:47–69` waits for its writer promise before draining, but `Manager.session.controls.ts:21–27` completes after invoking `proc.write` and observing recovery input. Neither proves that ZLE processed an invalidation. A typed suspension barrier needs a session-/lease-/revision-matched acknowledgement emitted only after the shell has disabled acceptance and invalidated its rendered tuple. Clearing the queue or reporting unavailable cannot establish that state.

**Release invariant:** After suspension, composition/paste inhibition, lost control, or an ambiguous control outcome, release potentially accepting Tab/Right only after (a) that acknowledged invalidation or (b) a proven upper bound on expiry of every shell lease that could still accept. An application timeout alone never permits release. Preserve ordering by holding the logical input lane at the barrier rather than letting later data bypass it; classify key operations before byte coalescing, or conservatively hold all downstream data when classification is uncertain. Do not scan/coerce arbitrary coalesced PTY bytes into alleged safe keys.

**Timeout/expiry relationship to prove in G1:** The proposed acknowledgement deadline `T_ack = 250 ms` is an early fault-detection budget, not lease expiry. Prototype a finite shell-enforced lease maximum `L_max` (initial target 1,000 ms) and a conservative execution-host clock/transport safety margin such that the controller can prove a latest possible expiry `D_safe` after suspension. A proposed total recovery budget is 1,500 ms from suspension, with `T_ack < L_max` and `D_safe` within that recovery budget. Exact primitives/numbers may change based on evidence, but the release invariant may not. G1 must establish the monotonic clock/deadline relationship and account for every outstanding grant/renewal; delayed/replayed renewals or lost acknowledgements must not extend acceptance beyond `D_safe`. Stop renewal on suspension/fault. A wall-clock guess, “250 ms elapsed,” bridge closure alone, or an unbounded remote-clock assumption is insufficient.

**Bounded recovery:** At `T_ack` without valid invalidation acknowledgement, mark integration unavailable/unsafe-pending and stop grants; retain the barrier until valid invalidation or guaranteed expiry. After that proof, disable the first-party lease and release ordered ordinary input within the recovery budget; no automatic rearming or retry of ambiguous controls occurs. If the prototype cannot provide that bounded proof, it fails qualification and first-party integration must never be enabled on that path. If a qualified runtime violates its expiry/clock assumptions, fail the pending operation within the recovery budget, discard unsent dependent input with an explicit input-safety error (never replay it), and keep potentially accepting input fenced rather than pass through to a possibly live widget. Offer a confirmed restart/new terminal without integration using existing lifecycle/definitive-stop rules; do not silently kill the session. This is an explicit recoverable failure state, not an indefinitely unresolved queue promise or an unsafe timeout bypass. The empirical G1 failure-injection proof remains required before any claim of safe ordinary-input recovery.

One active view/controller lease enables first-party behavior for a PTY. Detach, lost controller, and bridge EOF suspend it. An immutable shell integration session ID is distinct from the manager's reconnect/runtime generation. On durable-owner attach, bind the surviving integration to the new manager generation with a fresh control lease and invalidation acknowledgement; never assume the shell's original environment UUID equals the new manager generation. Before that handshake, ordinary recovery works and first-party suggestions remain off.

### 6.6 Startup compatibility, native plugins, and later shells

Bootstrap scripts must be trusted application assets and run only for the launched session. Preserve whether the existing launch is login/nonlogin and interactive; do not globally add `--noprofile`, `--norc`, `-NoProfile`, or replace startup files as a shortcut.

- **zsh:** Prototype a generated private `ZDOTDIR` wrapper directory that chains the user's actual startup files once, retains normal global startup ordering, and installs the adapter after user customization. Keep original user `ZDOTDIR`, follow allowed changes deterministically, and restore externally visible environment. If startup redirection, rc recursion, global files inspecting wrapper paths, `RCS`/`GLOBAL_RCS`, or plugin/widget composition cannot be preserved, bypass integration before launch where detectable, or mark it unavailable in-session without rerunning rc. G1 must prove the supported envelope; a transparent wrapper for arbitrary rc code is not assumed.
- **Native plugins:** Detect known zsh autosuggestion ownership and occupied `POSTDISPLAY`/widget hooks after startup. Default to `native-managed` without injecting another suffix or rebinding keys. Preserve custom Tab/Right behavior unless a verified composable wrapper exists. Disabling bigbud suggestions must not disable user-native behavior. Do not claim native-managed satisfies first-party safety criteria.
- **Bash:** Bare Readline does not establish a safe inline redisplay/acceptance seam. `bind -x` and `READLINE_LINE/READLINE_POINT` alone are insufficient evidence. First qualify startup/binding/redisplay/control behavior; otherwise launch Bash with first-party unavailable. An existing ble.sh instance is native-managed. Adding/vendoring ble.sh needs explicit dependency/license/compatibility approval; do not install it.
- **fish:** Native suggestions remain native-managed initially. Prove filtering, invalidation, acceptance-only bindings, composition suspension, and no override of user bindings before qualifying a first-party/native adapter. Shell branding is not qualification.
- **PowerShell:** Probe the actual session after normal profile loading: loaded PSReadLine module/version, availability of prediction source/view options and key-handler APIs, and active Tab/Right handlers. Use a structured, noninteractive bounded discovery probe without profiles only for inventory; do not equate it with the actual interactive module state. Set history-only prediction and inline view only where supported and where doing so does not replace existing configured predictors/view/bindings. Any required override means native-managed/unavailable, not forced configuration. Never change execution policy, install/update PSReadLine, or add a profile. A standalone native prediction toggle does not prove newline/control filtering and revision semantics; Gate G4 decides qualification.
- **cmd:** Normal launch and profile selection supported. Settings text: “Inline suggestions are not provided for cmd. Choose an installed supported shell for suggestions.” Clink is deferred.
- **WSL:** Apply the qualified guest adapter and trusted guest asset delivery under the pinned distro/user. Windows host PowerShell discovery does not qualify the guest shell.
- **Git Bash:** Recognize for launch only after validating executable identity/path conversion and node-pty behavior. First-party Bash suggestions remain unavailable until the Bash gate also passes. Do not assume MSYS semantics match Linux.

### 6.7 Approved per-pane selector and safe launch actions

The approved placement follows the user-described screenshot of the existing top-right floating terminal action strip, not a new global settings toolbar. `apps/web/src/components/terminal/ThreadTerminalDrawerFloatingActions.tsx` positions the shared toolbar at `right-2 top-2`; `ThreadTerminalDrawerToolbar.tsx` currently places `TerminalTargetPicker` immediately before `+`, followed by split, rename, close, and optional minimize/expand controls. Add the compact current-profile selector beside `+` while retaining the existing target picker and actions. Reuse the shared toolbar for the sidebar variant through `ThreadTerminalDrawerSidebar.tsx`; do not duplicate profile logic across layouts.

- **Current pane versus default:** The trigger displays the active pane's actual running shell/profile, with host context in its accessible label or supporting text. A pending new-profile choice must not relabel a still-running pane. Focus/activation of another pane updates the selector to that pane's identity. Profile choices are scoped to the affected/new pane; only the settings default control changes the global/host default.
- **New and split inheritance:** Clicking `+` opens a new terminal using the active pane's actual profile and execution host; split does the same from its source pane. Capture source pane identity before asynchronous discovery/launch and bind the chosen identity before mounting the new viewport. An explicit profile menu can choose a different profile. If the inherited profile is unavailable, report it instead of silently choosing the global default or a local shell.
- **Safe default action:** Choosing another profile offers “Open in new terminal” as the default action, creating a new terminal/pane and leaving the original shell and running processes intact. Merely opening/browsing the selector does not launch, replace, or change settings. Use accurate launch wording, not “switch live shell.” Failure to open the new terminal leaves the original session usable and unchanged.
- **Explicit replacement:** Offer “Replace this terminal…” separately. Confirmation names the affected pane/current profile and destination profile/host and warns that the existing session and running processes will be ended. Cancel/Escape makes no lifecycle request. Capture terminal ID, execution target, and expected runtime generation; revalidate them before applying confirmation. If that pane restarts, changes host, or otherwise changes generation while confirmation is open, reject the stale action and require fresh confirmation rather than targeting the currently active pane.
- **Preflight and replacement failure:** Validate the destination profile, host availability, and cwd mapping before ending the current session; a preflight failure leaves it running. After confirmation use existing fenced restart/operation handling and stop barriers. Disable duplicate submission while pending. If stop/remote ownership outcome is unknown, retain the existing ownership evidence and do not spawn a replacement. If the old process definitively ends but the new launch fails, show the stopped/error state and explicit retry/new-terminal action; do not claim the old process survived, automatically relaunch a different profile, or retry unknown outcomes. Update the displayed actual profile only from the successful authoritative launch snapshot.
- **Cwd boundaries:** Preserve a known cwd only when it exists and is valid on the destination execution host. Across Windows/WSL, distro/user, or host boundaries, use only established validated mapping; never reuse a `C:\\...` path as a Unix cwd, guess a WSL mapping, or send a remote path to the desktop. With no valid mapping, use the destination workspace's validated cwd or the destination profile's normal default directory and disclose the fallback before a destructive confirmation. A failed required cwd validation fails preflight rather than closing the original session. No command-buffer inference is introduced to discover cwd.
- **Host-specific menus:** On SSH or agent terminals, discover/list profiles on that remote execution host/account only, never on the desktop. WSL lists guest profiles for the pinned guest identity; local macOS/Linux uses that local execution host's available shells. Show bounded loading, unavailable/error, and retry states. A remembered unavailable remote profile can remain labeled unavailable, but discovery failure must not replace the list with desktop/local profiles or enable an unvalidated replacement. Invalidate stale results when the target/account/guest/pane context changes.
- **Accessibility and focus:** Reuse existing accessible menu/select and confirmation-dialog primitives. Give the compact trigger a descriptive accessible name including current profile, expose expanded/selected/disabled states, support keyboard open/navigation/activation and Escape, and keep focus visible. Menu/dialog cancellation returns focus to the originating selector when present, otherwise an appropriate surviving toolbar control. Successful new/split launch focuses the new pane through the existing focus-request path; failed launch or canceled replacement does not steal focus into a dead viewport. Async discovery must not unexpectedly move menu focus.

## 7. Trusted assets, transports, and security boundaries

Use one canonical first-party asset tree, proposed as `crates/bigbud-remote-agent/assets/shell-integration/`, with scripts split by shell/bootstrap/control concern and all authored code at most 400 lines. This location permits the agent crate to package/embed its trusted assets without depending on a workspace-relative file outside the crate. Server bundling explicitly copies the same assets into its runtime asset directory. Verify Cargo package inclusion rather than assuming local builds imply distributability.

A manifest records protocol version, asset version/digest, allowed filenames, and licenses. Resolve development assets from a fixed application source location; resolve bundled assets beside the server runtime. Never search cwd, workspace ancestors, PATH, user profiles, or environment-supplied replacement directories for integration code. Verify manifest/digest before staging or sourcing. Caller-supplied terminal env cannot override private asset paths, bridge addresses, session identity, or lease configuration; construct those after the normal environment filter.

### Local and WSL

- Create private host/guest state directories, not workspace files; Unix directories mode 0700, files/FIFOs 0600, validated owner/type, no symlink traversal. Windows asset/cache directories use the current user's appropriate private app-state permissions.
- WSL asset probes/staging run inside the selected guest with identity checks, argv-based parameters, and guest-safe paths. Do not source host `C:\...` paths in guest shells.
- Stop using an asset only after all relevant sessions release it. Do not remove the FIFO/control directory while a surviving PTY still needs it.

### Direct SSH

- Discover remote account shell/capabilities and stage versioned trusted files under a remote account-private cache/state directory outside the workspace. Reuse existing SSH connection/authentication and host-key verification; do not add a permissive SSH transport or forward provider credentials.
- Transfer only manifest-allowlisted bytes using an established binary-safe channel; remote `sh` helper creation uses fixed trusted source, while all dynamic paths/IDs are separately escaped arguments. Never interpolate remote cwd/profile names into shell source.
- Verify owner, mode, regular-file types, no symlink substitution, and digest before sourcing. Commit asset sets atomically from a private temporary directory. Explicitly verify the remote digest mechanism; absent prerequisites mean ordinary shell fallback, not silent installation.
- Keep staging/probing/control cancellable with bounded concurrency (proposed two host operations), transfer size (proposed 256 KiB per asset set), and an overall ten-second bootstrap budget. A timeout cancels integration work, not an already running terminal or an unknown-outcome launch.
- Use a session reference/lease for cleanup. Remove transient failed staging files only when ownership is proven. Reconcile stale unreferenced assets on future connection; never delete a cache version referenced by a live session. No cleanup command may recurse into user-selected paths.
- Direct SSH reconnect does not gain durable PTY semantics from this feature. Preserve current recovery behavior; clean up only resources demonstrably no longer used.

### Remote-agent

- Negotiate profile discovery/explicit launch independently from suggestion assets/control. Phase 2R delivers profile-only capability and both spawn paths before UI/release, with no dependency on G1/G2 or asset staging. Old agents retain ordinary legacy launch; unsupported explicit selection fails visibly without shell substitution.
