# Choose API-first OpenCode Without Inventing Guarantees

**API-first is the right architecture for bigbud to use an already-running, user-installed OpenCode V2 service; an embedded SDK is unnecessary for that purpose.** For public session operations, the API and V2 SDK share a contract, rather than competing feature sets. The V1 SDK was already an HTTP client, not an embedded agent runtime. However, embedding adds host-local customization that ordinary network requests cannot supply. Neither API adoption nor first-party client usage guarantees future compatibility, every bigbud feature, or identical platform behavior. Retiring database probes is therefore a reasonable proposal only with an explicit revision of physical-storage identity/protection requirements—not a claim that HTTP preserves those guarantees.

This assessment synthesizes the three supplied research notes and checks official V2 documentation and source. Release evidence is pinned to **2.0.24** (`e7a34f09…`) and **2.0.26** (`9b4ec571…`); the explicit V1 comparison uses **1.17.13** (`10c894bd…`). These are assessed baselines, not claims about the newest release. bigbud code references use commit `420f0c83…`, not concurrent working changes. No native service calls, implementation, or runtime qualification were performed.

## 1. Public API versatility matches the generated client, not every SDK extension

**Direct answer to question 1: yes for the shared public operation contract and official integration status; no for blanket V1 feature parity, embedded customization, or equivalent support guarantees.** The package names conceal an important architectural distinction:

| Package                  | Actual role at the assessed version                                      | Implication                                             |
| ------------------------ | ------------------------------------------------------------------------ | ------------------------------------------------------- |
| V1 `@opencode-ai/sdk`    | Generated HTTP/SSE client, plus optional executable-launch helpers       | It was not an embedded runtime.                         |
| V1 `@opencode-ai/sdk/v2` | An export inside that same V1 package                                    | `/v2` does **not** mean released OpenCode V2.           |
| V2 `@opencode/client`    | First-party generated network client, with Promise/Effect facades        | Correct attachment layer for an existing service.       |
| V2 `@opencode/sdk`       | Application-owned server/runtime; client calls its HTTP router in memory | A separate hosting choice, not an attachment mechanism. |

V1’s `createOpencode()` starts a child server, then constructs an HTTP client. V2’s Promise SDK imports `@opencode/client`, passes `host.fetch`, spreads the client, and adds plugin registration/disposal. Network and embedded route construction share the handler graph. Thus ordinary session/permission/form operations are not inherently less capable over the network. ([V1 construction](https://github.com/anomalyco/opencode/blob/10c894bdeef3618f5666fb506ef7f9491bb964d8/packages/sdk/js/src/v2/index.ts#L10-L23), [V1 package exports](https://github.com/anomalyco/opencode/blob/10c894bdeef3618f5666fb506ef7f9491bb964d8/packages/sdk/js/package.json), [V2 SDK construction](https://github.com/anomalyco/opencode/blob/9b4ec5714d481559990db0a816d5dec19541a814/packages/sdk/src/promise.ts#L25-L68), [shared routes](https://github.com/anomalyco/opencode/blob/9b4ec5714d481559990db0a816d5dec19541a814/packages/server/src/routes.ts#L80-L114))

**Hooks, tool transforms/registration, plugin storage and host ownership are different capabilities.** They execute server-side, not as arbitrary callbacks uploaded through public HTTP. A network client can invoke extension RPC only when the user’s server already has the implementing plugin configured. The inspected Effect SDK additionally exposes direct Core session/workspace methods beyond the generated facade. None justifies silently embedding or injecting plugins when an attachment lacks a feature. ([Plugin capabilities](https://opencode.ai/v2/docs/build/plugins), [RPC prerequisite](https://opencode.ai/v2/docs/build/client#plugin-rpc), [Effect SDK exceptions](https://github.com/anomalyco/opencode/blob/9b4ec5714d481559990db0a816d5dec19541a814/packages/sdk/src/effect/opencode.ts#L19-L67))

V1-to-V2 is a **semantic migration**, not a package rename: V2 prompts acknowledge inbox admission, not assistant completion; questions become typed forms; events, pagination and staged reverts change. One genuine gap defeats blanket parity: V2 preserves `lsp` configuration but does not run language servers, expose LSP tools or produce diagnostics. ([Official migration boundary](https://opencode.ai/v2/docs/migrate-v1#server-api-and-clients), [pinned LSP limitation](https://github.com/anomalyco/opencode/blob/9b4ec5714d481559990db0a816d5dec19541a814/services/www/src/docs/content/migrate-v1.mdx#L415-L416))

## 2. Existing-service attachment fits bigbud, without guaranteeing feature support

**Direct answer to question 2: API-first makes more sense under the stated ownership constraints, but cannot guarantee better support across services or features.** Official docs identify the network client as the client used by the TUI and desktop. Source corroborates this: the TUI imports `@opencode/client`; the desktop consumes the shared app, whose server API constructs `OpenCode.make`. This is first-party architectural alignment, not an SLA. ([Build positioning](https://opencode.ai/v2/docs/build/), [TUI client](https://github.com/anomalyco/opencode/blob/9b4ec5714d481559990db0a816d5dec19541a814/packages/tui/src/context/client.tsx#L1-L39), [desktop app](https://github.com/anomalyco/opencode/blob/9b4ec5714d481559990db0a816d5dec19541a814/packages/desktop/src/renderer/desktop-app.tsx#L3-L16), [app HTTP client](https://github.com/anomalyco/opencode/blob/9b4ec5714d481559990db0a816d5dec19541a814/packages/app/src/runtime/server/api.ts#L22-L38))

The following maps native capability to bigbud responsibility, **not completed implementation**. Native operations are documented in the [V2 API](https://opencode.ai/v2/docs/api) and [pinned session handlers](https://github.com/anomalyco/opencode/blob/9b4ec5714d481559990db0a816d5dec19541a814/packages/server/src/handlers/session.ts#L125-L713).

| bigbud requirement                   | Native API fit                                        | Remaining qualification or orchestration                                                |
| ------------------------------------ | ----------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Borrow existing service              | Endpoint/auth client; discovery without starting      | Never ensure/start/stop/reconfigure the daemon.                                         |
| Session/history continuity           | Create/get/list, messages, metadata, inbox            | Verify binding/ownership; persist bigbud journal independently.                         |
| Text/thinking/tools/usage            | Live events and persisted assistant state/tokens/cost | Normalize provider-dependent reasoning; costs are not billing guarantees.               |
| Approvals                            | Pending permission get/list/reply                     | `always` saves project-scoped grants, not session-only approval.                        |
| Questions/forms                      | Typed form get/list/reply/cancel                      | Current UI supports a subset; reject unsupported fields safely.                         |
| Model/provider/agent/skill selection | Native catalogs and session switching                 | Availability depends on native configuration, plugins and credentials.                  |
| Attachments                          | Inline `data:` or server-reachable `file:` inputs     | Freeze media; validate actual model-visible formats and host paths.                     |
| Native tools/MCP                     | Use configured native execution and MCP catalog       | No shared MCP/config mutation; permissions are not containment.                         |
| Custom tools/delegation/learning     | Installed plugin RPC; ordinary prompt primitives      | Canonical bigbud children, memory review and scheduling remain app-owned.               |
| Background work/cancellation         | Background supported tools; interrupt/cancel inbox    | Not cron, exactly-once jobs, or proof all plugin work stopped.                          |
| Fork/rewind/restore                  | Fork, staged revert, experimental import/export       | Adapter currently disables fork/rewind; transfer is not live-runtime restoration.       |
| Remote/SSH targets                   | HTTP can reach an existing remote service             | Current shared adapter rejects remote; tunnels/path/media semantics need qualification. |

These gaps are visible in bigbud’s [capability declarations](https://github.com/youpele52/bigbud/blob/420f0c83f59eb87158679881c0c96c572dd23f3b/apps/server/src/provider/Layers/OpencodeV2/Adapter.capabilities.ts#L4-L18), [form mapping](https://github.com/youpele52/bigbud/blob/420f0c83f59eb87158679881c0c96c572dd23f3b/apps/server/src/provider/Layers/OpencodeV2/Runtime.forms.ts#L6-L105) and [target admission](https://github.com/youpele52/bigbud/blob/420f0c83f59eb87158679881c0c96c572dd23f3b/apps/server/src/provider/Layers/OpencodeV2/Application.targets.ts#L19-L42). “Different services” also needs separation: OpenCode’s own model providers share its API, but Codex app-server, Claude and Copilot still require their own bigbud adapters.

Prefer **the official typed client over bespoke fetch** for contract maintenance, without conflating this with SDK embedding. Both follow an API explicitly described as experimental; no stability, LTS, SLA or universal future-feature guarantee was established. A `>=2.0.24 <3` capability gate is **bigbud’s acceptance policy**, not a vendor semver promise. ([Client guide](https://opencode.ai/v2/docs/build/client), [pinned experimental annotation](https://github.com/anomalyco/opencode/blob/9b4ec5714d481559990db0a816d5dec19541a814/packages/protocol/src/api.ts#L190-L198))

## 3. Discovery can be narrow; native execution cannot promise zero side effects

The safe attachment scope is discovery plus authenticated `GET /api/info` and `/openapi.json`, without service lifecycle, credential, configuration, plugin or MCP administration. Use `Service.discover()`, not `ensure()` or the convenience `opencode api` command, which can start a missing service. Closing bigbud should detach, not stop the borrowed daemon. ([Service discovery](https://opencode.ai/v2/docs/build/client#local-background-service), [API CLI behavior](https://opencode.ai/v2/docs/api))

**Do not label every GET “read-only discovery.”** Session get/list can directly read saved records, but location-scoped catalogs/config/MCP requests can instantiate the Location graph, discover existing configuration, activate plugins/MCP and install missing configured plugin packages. Already configured plugins can themselves write files. Session permissions do not disable arbitrary plugin setup. Therefore “bigbud performs no administrative writes” is compatible with authorized native session operations; “using this service causes no service-related disk writes” is not. Session/history persistence also necessarily writes native state. ([Location initialization](https://github.com/anomalyco/opencode/blob/e7a34f09bfd9134dfade5a8ddb843f7030bc9a69/packages/server/src/location.ts#L57-L84), [instance services](https://github.com/anomalyco/opencode/blob/e7a34f09bfd9134dfade5a8ddb843f7030bc9a69/packages/core/src/instance.ts#L59-L159), [plugin activation/install](https://github.com/anomalyco/opencode/blob/e7a34f09bfd9134dfade5a8ddb843f7030bc9a69/packages/core/src/plugin/supervisor.ts#L153-L173))

An independent bigbud privacy sandbox can constrain **bigbud-owned file tools**. It does not automatically contain native OpenCode shell/tools/plugins: shell has host-user filesystem/process/network authority, and arbitrary trusted plugins need not obey tool permission checks. Prompts and API policy alone cannot enforce strict exclusion of bigbud/native database directories. Retiring directory probes therefore requires an explicit revised protection contract or a separately enforceable boundary; an API switch is not that boundary. ([Native permission warning](https://opencode.ai/v2/docs/permissions#directories), [bigbud shared trust policy](https://github.com/youpele52/bigbud/blob/420f0c83f59eb87158679881c0c96c572dd23f3b/apps/server/src/provider/Layers/OpencodeV2/Runtime.policy.shared.ts#L7-L36))

## 4. Portable identity and recovery require explicit weaker guarantees

The API exposes no attested physical database path/inode/store identifier. Logical binding can instead preserve bigbud thread identity, native session ID, stored Location, connection identity, ownership metadata and admission provenance. **Copied/imported databases retaining those records represent the same logical lineage under that policy—not proven physical identity.** Endpoint/PID/directory tags cannot distinguish an original database from its clone. This is an explicit portability tradeoff, not equivalent storage attestation. ([Server info fields](https://github.com/anomalyco/opencode/blob/e7a34f09bfd9134dfade5a8ddb843f7030bc9a69/packages/server/src/server-info.ts#L5-L15), [current physical binding](https://github.com/youpele52/bigbud/blob/420f0c83f59eb87158679881c0c96c572dd23f3b/apps/server/src/provider/Layers/OpencodeV2/Runtime.binding.ts#L14-L51))

Metadata checks establish bigbud’s intent to mutate only verified sessions, **not exclusive ownership** against another authenticated native client. Authentication is a service boundary; there is no per-client session lease/CAS. Repeated prompt IDs likewise do not compare complete request bodies or guarantee exactly-once tool execution. Retain immutable fingerprints, serialized writes, turn/generation fences and fail-closed drift handling. ([Mutable session contract](https://github.com/anomalyco/opencode/blob/e7a34f09bfd9134dfade5a8ddb843f7030bc9a69/packages/protocol/src/groups/session.ts#L174-L776), [inbox reconciliation](https://github.com/anomalyco/opencode/blob/e7a34f09bfd9134dfade5a8ddb843f7030bc9a69/packages/core/src/session/inbox.ts#L154-L201))

**V2 event subscriptions are live-only, without automatic reconnection or replay.** bigbud must resubscribe with bounded backoff and repair from messages, inbox, active execution, forms and permissions. Experimental durable session logs can assist qualified recovery, but are not guaranteed replay of transient text/reasoning deltas. A timeout/disconnect is not confirmed cancellation; uncertain admission must never trigger automatic resend. ([Stream contract](https://opencode.ai/v2/docs/build/client#stream-events), [experimental log operation](https://github.com/anomalyco/opencode/blob/9b4ec5714d481559990db0a816d5dec19541a814/packages/client/src/promise/generated/client.ts#L966-L989), [existing bigbud recovery](https://github.com/youpele52/bigbud/blob/420f0c83f59eb87158679881c0c96c572dd23f3b/apps/server/src/provider/Layers/OpencodeV2/Runtime.recovery.ts#L74-L244))

This enables one OS-neutral recovery state machine, **not already-proven identical behavior**. Supplied project status reports earlier Windows HTTP/auth CI success but final qualification failure at physical probing. That distinguishes transport success from integration acceptance; Windows is not currently green, and this research did not rerun it.

## Conclusion

Adopt API-first for user-facing session tasks, retaining the existing adapter/journal/recovery investment. First approve the logical-identity and storage-protection tradeoffs; then qualify the consumed schema and failure semantics against both assessed releases and macOS/Linux/Windows. Keep unsupported features disabled, and add optional experimental or installed-plugin capabilities only behind independent acceptance gates. Missing/incompatible services should yield setup guidance, never automatic provisioning or embedding.

Migration must preserve old bindings and quarantined journals rather than automatically rewriting them into “equivalent” identities. Resume, fork and import are distinct user-visible operations; uncertain legacy admissions stay quarantined until reconciled. The architectural benefit is a cleaner, portable ownership boundary—not a promise of stronger isolation or better vendor guarantees.
