# Resolve WSL Home Inside Its Target

> Historical research report: repository claims below describe the pre-`93e43aa7492c77550d778e9f82448fdc90bd1217` snapshot. Current bigbud implements selected-distro **manual terminal** selection and target-bound process Home resolution; this does not add a WSL workspace/provider/filesystem target. See the [2026-10-12 follow-up validation](../validation/wsl-terminal-followup-2026-10-12.md). Native Windows/WSL runtime execution remains unverified on this macOS host.

The statement is **accurate about bigbud today, but misleading if read as a WSL platform limitation**: bigbud has no selected-WSL target dispatcher or Home lookup API, while Microsoft provides supported ways to name a distro and run a command in it. The documented WSL configuration and launch APIs reviewed do not return a Linux Home path directly; the safe route is to query Linux from a process launched in the exact selected distro and user. In bigbud, a WSL shell name currently affects dropped-path formatting only; non-local execution is otherwise routed through SSH. Robust support therefore needs coordinated target identity, same-target Home/cwd probing, and a WSL-specific PTY launch—not merely a Home lookup or a `wsl.exe` shell label. **Selected-distro WSL Home remains deferred and is not implemented.**

## Microsoft selects a distro and user when it launches a command

**Documented behavior:** `wsl --list --quiet` lists installed distro names; `wsl --list --verbose` also reports running/stopped state. `wsl --distribution <name>` (or `-d`) runs a command in a named distro, while `--set-default` changes which distro unqualified commands select. Use the former for a lookup: changing the user's default is unnecessary and would make the result depend on mutable host configuration. Microsoft also documents `--user <name>` (`-u`) for an existing Linux account; a nonexistent account is an error. `--exec` runs a command without the default Linux shell, though the installed `wsl --help` and `wsl --version` remain the version-specific references for CLI options. ([Basic commands for WSL](https://learn.microsoft.com/en-us/windows/wsl/basic-commands); [WSL release notes](https://learn.microsoft.com/en-us/windows/wsl/release-notes#build-18305))

When `--user` is omitted, WSL uses that distro's configured default account. The per-distro `/etc/wsl.conf` `[user] default` setting controls it; imported distributions can default to root. Neither the distro label, Windows username, nor `/home/<name>` reliably identifies that account or its Home. A stopped distro is not necessarily missing: a named launch can start it, so resolution can have a startup side effect. ([WSL configuration](https://learn.microsoft.com/en-us/windows/wsl/wsl-config#user-settings); [Import any Linux distribution](https://learn.microsoft.com/en-us/windows/wsl/use-custom-distro); [Basic commands for WSL](https://learn.microsoft.com/en-us/windows/wsl/basic-commands))

## WSL launches provide context, not a Home-path lookup

**Documented fact:** the reviewed `WslGetDistributionConfiguration` API returns configuration including the default UID and environment-variable settings, not a Home path. `WslLaunch` starts a process in a named distro and returns a process handle; its contract does not return the launched user's Home. WSL's `~` behavior and `wslpath` translate or navigate paths, but neither discovers an arbitrary selected user's Home. This supports the precise claim that **no direct Home-path field was found in the reviewed Microsoft APIs**, not the broader claim that WSL has no target-selection interfaces at all. ([WslGetDistributionConfiguration](https://learn.microsoft.com/en-us/windows/win32/api/wslapi/nf-wslapi-wslgetdistributionconfiguration); [WslLaunch](https://learn.microsoft.com/en-us/windows/win32/api/wslapi/nf-wslapi-wsllaunch); [WSL interop](https://learn.microsoft.com/en-us/windows/dev-environment/wsl-interop))

**Design inference:** decide what “Home” means before implementing it. For the terminal process's environment Home, run a fixed query such as `printf '%s\n' "$HOME"` inside the explicitly selected distro and user. For the account database's configured Home, query that account through NSS—for example, `getent passwd <account>` and read its home field—rather than constructing `/home/<name>`. These are different values if the environment overrides `HOME`; Microsoft does not guarantee that all distros or non-interactive invocations set it identically, and minimal/custom distros may lack `getent`. If the distro default user is selected, determine the effective user inside that same invocation before querying its account record. Treat unsupported utilities or ambiguous/malformed output as resolution failures, not as permission to guess. ([getent(1)](https://man7.org/linux/man-pages/man1/getent.1.html); [passwd(5)](https://man7.org/linux/man-pages/man5/passwd.5.html); [Bash startup files](https://www.gnu.org/software/bash/manual/html_node/Bash-Startup-Files.html))

For Windows access to Linux files, Microsoft's supported interface is the distro UNC namespace (`\\wsl$` or `\\wsl.localhost`), with lifecycle and default-user permission caveats; it is not a substitute for querying the target user's Home. Keep the result a Linux/POSIX path for terminal use, converting only at a Windows API boundary. Do not inspect or mutate distro backing files under AppData: Microsoft warns that Windows-side access can corrupt a distro. ([Working across file systems](https://learn.microsoft.com/en-us/windows/wsl/filesystems); [WSL file permissions](https://learn.microsoft.com/en-us/windows/wsl/file-permissions); [Manage WSL disk space](https://learn.microsoft.com/en-us/windows/wsl/disk-space))

## bigbud carries target identity but dispatches only local or SSH

`ExecutionTargetId` is a trimmed nonempty string with `local` as its default; it does not declare target kinds. Server-side `isLocalExecutionTarget` tests only whether the ID equals `local`. In [`makeResolveTerminalFolder`](../../apps/server/src/terminal/Layers/Manager.cwd.ts#L90), a local target expands Home using injected `localHome` (default `os.homedir()`) and validates through the host filesystem; every non-local target is checked by `assertSshExecutionTargetReady` and probed through `runSshCommand`. The SSH parser accepts `ssh:` IDs only ([`baseSchemas.ts`](../../packages/contracts/src/core/baseSchemas.ts#L11), [`executionTargets.ts`](../../apps/server/src/executionTargets.ts#L3), [`sshExecutionTarget.ts`](../../apps/server/src/ssh/sshExecutionTarget.ts#L20)). Consequently, adding a `wsl:<name>` string alone would not select WSL; it would enter non-local/SSH routing and fail or be misrouted.

The same dispatch gap exists at process start: [`startSessionWith`](../../apps/server/src/terminal/Layers/Manager.process-drain.ts#L195) chooses local shell candidates or `buildRemoteTerminalShellCandidate`; the non-local PTY path uses host `homedir()` as its outer cwd and sends the resolved cwd as `remoteCwd`. By contrast, `wsl.exe` recognition in [`resolveShellDropPathMode`](../../apps/server/src/terminal/Layers/Manager.shell.ts#L79) only sets drop-path formatting. It does not pin a distro or affect Home resolution. These paths must share one explicit WSL identity, or a terminal could probe one environment and spawn in another.

There is useful plumbing to reuse: [`TerminalOpenInput`, `TerminalRestartInput`, and `TerminalSessionSnapshot`](../../packages/contracts/src/workspace/terminal.ts#L43) already carry optional `executionTargetId`; [`TerminalSessionState`](../../apps/server/src/terminal/Layers/Manager.types.ts#L31) retains it, and [`runBoundTerminalCommand`](../../apps/web/src/lib/terminalLaunchBinding.command.ts#L24) binds and checks launch context. `Manager.cwd.ts` already distinguishes ordinary cwd errors from target/connection errors and falls back to target Home only for the former; [`Manager.cwd.test.ts`](../../apps/server/src/terminal/Layers/Manager.cwd.test.ts#L136) covers SSH Home and target failure. The current HEAD commit, `79e2119689`, explicitly says selected-distro WSL Home remains deferred. This is a narrow terminal-context gap, not evidence that all WSL-related behavior is absent.

## A robust minimum adds one target-bound terminal adapter

**Recommended design, not current behavior:** add explicit WSL target parsing and selection, using the exact registered distro name returned by a server-side installed-distro query (or a separately validated target field). Preserve that identity in the existing terminal request/session/snapshot flow; an explicit Linux user can be part of the target, while “distro default user” must be a deliberate policy. Do not infer a distro from ambient `WSL_DISTRO_NAME`, and do not resolve against whichever distro is currently default. The existing generic ID can carry an identifier syntactically, but it needs WSL-specific validation and routing. Keep this first implementation terminal-scoped; project-level WSL targets would also require decisions and routing for filesystem, Git, worktrees, providers, and other workspace operations.

Add a WSL adapter used for both requested-folder validation and Home resolution. Every invocation must pass the same explicit distro and user, query the chosen Home semantics inside Linux, validate/canonicalize the directory there, and return a bounded POSIX path. Use a fixed command and structured process arguments where the runtime permits; validate the selected name against the installed list, and never interpolate distro names, usernames, or paths into shell source. Bigbud's [`runProcess`](../../apps/server/src/utils/processRunner.ts#L129) currently uses `shell: true` on Windows, so an invocation builder must explicitly account for Windows command-line quoting and be tested with spaces, quotes, option-like names, and shell metacharacters rather than assuming the argument array alone prevents interpretation. Cap output and apply a wall-clock deadline across process startup, WSL startup, lookup, and output collection. A killed host wrapper is not documented proof that the guest process stopped; do not claim otherwise or run `wsl --terminate` as automatic cleanup, since that can interrupt unrelated work. ([OWASP OS Command Injection Defense Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/OS_Command_Injection_Defense_Cheat_Sheet.html); [Basic commands for WSL](https://learn.microsoft.com/en-us/windows/wsl/basic-commands))

Fail closed on an unregistered/stale distro, missing explicit user, unavailable WSL, timeout, failed account lookup, malformed output, or inaccessible Home. Do not retry against the default distro, host `os.homedir()`, another user, or a guessed Linux/Windows path. Only a requested-cwd failure **after the selected target is confirmed** should trigger `directoryFallback`, and that fallback must resolve Home from the same distro/user. A preflight list can improve UX but races with unregister/re-register; the launch result remains authoritative. Tell users when resolving a stopped distro can start it, display the effective Linux identity where relevant, and explain fallback rather than silently switching context.

Implement in stages: first add the target model/listing and UI only for terminal selection, preserving existing local and SSH defaults; next add the bounded target-bound resolver and explicit WSL PTY spawn branch; then validate end-to-end launch binding and compatibility on Windows with multiple distros and users. Tests should prove that requested cwd, Home fallback, and PTY all receive the identical selected ID; returned Home comes from that distro rather than host Home; target/user failures never fall through; only confirmed-target cwd errors fall back; and POSIX paths remain unmodified by Windows path normalization. Add timeout, output-cap, cancellation/late-result, spawn-not-started-on-resolution-failure, adversarial argument, and open/restart/snapshot identity tests. Extend the existing fallback and command-binding regressions so project/setup commands remain blocked on fallback or target mismatch. Treat these as acceptance criteria for future work, not existing coverage for WSL.

## Conclusion

The deferral is a bigbud implementation gap, not a WSL inability to select a distro: the platform can run a command in a named distro and optionally a named Linux user, but Home must be queried from within that context. The core reliability boundary is identity continuity—one chosen distro/user from selection through lookup, fallback, PTY launch, and command binding. A terminal-only adapter can reuse much of bigbud's current target/session machinery without pretending that broader WSL workspace support exists.
