# OpenCode

OpenCode uses V2 for new chats. **Production supports only the borrowed shared native service and local native Locations.** There is no executable isolated/private-profile, development-environment or SSH fallback. Legacy `opencode`, retained isolated V2 and unsupported/unproved native bindings remain read-only canonical history: no migration, replacement, recursor or admission replay. Existing private paths/mode tags remain decodable historical evidence, not an executable option. V2 is enabled for fresh installations but is not the global default over other providers; explicit disables and unrelated choices are preserved.

**Discovery is not execution readiness.** The client package remains pinned to **2.0.26**, but that is not a runtime version allowlist. Every canonical stable **OpenCode 2.x.y** release is a compatibility candidate, without a minor/patch minimum. V1, V3, prereleases, custom build suffixes and malformed versions are rejected. Shared discovery still requires compatible APIs. Canonical tools additionally require macOS ARM64 and fresh API/source/bootstrap, callback and ownership checks; the major version alone never grants execution. Missing retail semantic qualification is disclosed, not a version-only execution gate; recorded incompatibilities still block. **The current working registry is empty:** historical partial 26/27 probes and synthetic tests are not promoted to retail qualification. This policy supersedes the version minimum and qualification-required gate in the [historical compatibility amendment](../plan/2026-10-14-opencode-v2-contract-compatibility-plan.md); see the [working evidence](../validation/opencode-v2-stable-bootstrap-working-evidence-2026-10-13.md). This source is not final release acceptance.

## Use your existing TUI account

1. In **Settings → Providers → OpenCode**, enable the shared integration. No binary/profile path or second sign-in is required. If retained isolated configuration is reported, explicitly choose **Use shared native service for new chats**; paths/history are preserved, not migrated.
   If the composer reports **Native service trust consent required**, choose **Set up OpenCode** in the provider picker to open the expanded OpenCode settings. Read the explanation and explicitly switch on **Trust native service execution** if you accept it. Opening setup never grants consent or selects a model. Enable alone is intentionally insufficient; without acknowledgement, health discovery can succeed while native models and execution remain blocked. An empty picker in an existing OpenCode chat also offers setup. After acknowledgement, wait for provider discovery or use **Refresh provider status**, then select an available native model in a new OpenCode chat.
2. Before **Trust native service execution** is acknowledged, background discovery reads only secure registration, health and required API capabilities: no Location activation, model/agent/skill catalog, session creation or event subscription. A custom native service registration file can be selected; changing it, changing mode or resetting provider settings clears acknowledgement in this UI. Explicit serialized acknowledgement survives settings export/import; old settings never manufacture it.
3. Expanded acknowledgement covers existing native execution/history and **automatic installation/upgrades of only bigbud's required global thread-tools plugin entry**. Older `host-user-v1` acknowledgement remains historical execution trust but grants no plugin-configuration write authority; acknowledge the expanded explanation once, not once per chat. Native tools/plugins run as your host user, **not in a bigbud sandbox**. bigbud does not edit native accounts, credentials, models, permissions, unrelated plugin entries or JSON/JSONC configuration. Shared discovery uses the official Promise HTTP client and a connection-only descriptor, not process/DB-file probing. Registration remains bounded/private, literal-loopback-only and redirect-free; Windows retains its same-handle owner/DACL helper and x64/ARM64 packaging. Remote shared targets remain unsupported. Automatic managed publication currently fails closed outside macOS ARM64; broader platform discovery evidence does not qualify installation. See the [API-first validation ledger](../validation/opencode-v2-api-client-2026-10-11.md) for tested discovery platforms.
4. If no healthy service is registered, open your installed V2 TUI or start its native service yourself. bigbud never starts a competing daemon, upgrades the CLI or replaces your service. Automatic safe missing-service startup is not claimed.
5. Select the exact native provider/model. Connected native inventory ranks ahead of public-only setup options. **Native availability unverified** identifies public-only or invalidated cached inventory, not proof that an account needs login and not a silent model switch. A discovery failure reports its phase and configured Location; inspect that status before changing native accounts. OpenAI and Azure remain distinct even for the same model slug. Native account metadata refreshes every 15 seconds while enabled and consented; no credential endpoint or vendor prompt is used.
6. Required setup is automatic after expanded acknowledgement or on foreground execution preflight. The actual chat/project/worktree **Location is inferred**, not an input field. bigbud publishes one signed app-owned autoload entry referencing an immutable artifact under the native **user-level plugin configuration directory**, reused across projects/worktrees. JSON/JSONC and existing plugins/comments remain untouched. **Native plugin configuration directory override** in settings changes only this placement, **never chat CWD**. Blank uses `OPENCODE_CONFIG_DIR`, or `$XDG_CONFIG_HOME/opencode`, or `~/.config/opencode`; the selected root must match the qualified native global source metadata before any local write. A different native environment/unsafe path fails clearly without fallback or permission repair. Opening settings/model discovery does not install. **Show detected setup** is read-only; **Retry required setup** explicitly retries after expanded trust.
   A uniquely verified compatible manual entry can be reused after runtime checks; it never gains a second autoload copy. Historical signed artifacts keep their original constraints: N0 accepts exactly 26/27, and N1 requires >=2.0.26. They are never rewritten or relabeled by the new major-V2 policy; legacy L entries are cleanup-only and report explicit manual remediation. Duplicate/foreign namespaces and unrelated files are never replaced based on their names. A native removal/deny, removed managed entry or uncertain publication is not automatically repaired. First installation and bootstrap replacement wait for known busy work and retain physical/uncertain ownership—not merely lease expiry. Missing retirement proof or reserved tool receipts require reconciliation, not deleting evidence or replaying work. Activation is best effort: another native client can start work between observations/publication, and watched suffix plugins can be unloaded. There is no global atomic-idle guarantee or automatic native restart. Routine compatible implementation/evidence updates do not rewrite native bootstrap files. See the [stable-bootstrap architecture](../plan/2026-10-13-opencode-v2-stable-bootstrap-maintenance-plan.md), as amended by the policy above; historical ledgers do not establish current acceptance.
   A normal foreground setup timeout may leave a separately owned setup-only continuation, bounded by its original five-minute deadline; it never queues or replays the prompt. Explicit cancellation/revocation stops new work, not proof of settlement of already-issued work. The short activation gate releases on deadline while unresolved physical operations and writer evidence stay owned. An exited-owner signed lock requires independently safe exceptional remediation: bigbud does not automatically reclaim it with a pathname unlink or erase uncertain history.
7. Required setup must pass before native session creation/update and before each new turn. Wrong scope, missing/unverified plugin, wrong issuer/artifact/version/inventory or a retained deny fails closed without prompt, new admission, history replacement or another provider/runtime fallback; independently valid model inventory stays visible. Compatible verified foreground chats enroll automatically after expanded trust/setup. There is no optional bridge flag or per-chat opt-in. Hidden review/learning work remains tool-disabled and cannot trigger installation or acquire canonical caller credentials.
8. Restart bigbud after changing the shared service connection. Verified shared resume preserves exact IDs and opaque tokens. Copied/imported histories can represent the **same logical lineage**; this does not prove physical storage, exclusivity or another writer's absence. Untagged/isolated/unsupported bindings remain read-only without reacquiring private native history. Missing/conflicting retained evidence fails closed. Path-first desktop/browser upload, paste/drop and canonical references remain available; mobile remains text-only.

Shared mode borrows one authenticated loopback client/event hub across local Locations. Disable/shutdown detaches its subscriptions and interrupts only exact bigbud-owned sessions; the daemon and unrelated TUI history remain alive. Transport loss/registration replacement is not physical-exit proof and never clears mutation quarantine. A native-generation change currently requires app restart; uncertain admissions remain blocked.

Backend acceptance of a relevant settings change synchronously revokes captured request/publication revisions. Late registration checks, queued replies and native responses cannot dispatch or publish for an old revision, including after revoke/regrant. Revocation does not prove native execution stopped. Exact original-owner interrupt (`resume:false`), inbox cancellation and local release remain available; permission/form replies, even declines, require consent. External file edits take effect only when the settings watcher accepts a validated reload.

Shared creation reserves a durable binding and records dispatch intent **before** calling native create. A lost acknowledgement can leave only that intent, without a cursor or prompt journal; it is never treated as permission to recreate. Recovery GETs the exact retained native ID, never searches/rekeys an entire native session inventory. Saved admissions/fingerprints, legacy restrictive policy order, attachment material and hidden-learning identities are conserved. Missing evidence or an uncertain intent never triggers create/prompt replay, replacement, isolated fallback or terminal-result application.

## Required canonical thread tools

Exactly five executable definitions are exposed to enrolled foreground sessions: `bigbud_thread_v1_create_thread`, `bigbud_thread_v1_send_thread_message`, `bigbud_thread_v1_get_thread_status`, `bigbud_thread_v1_list_threads`, and `bigbud_thread_v1_rename_thread`. Create/send use canonical orchestration and provider-independent eligible targets, not native forks. Rename changes canonical metadata/title locking for the current thread or an eligible same-project/direct-child target; native session rename is not a substitute. Native subagent spawning remains denied for app-owned sessions. Attachment/history content does not grant authoring authority.

The callback channel encrypts callback credentials and arguments and requires fresh signed, request/owner/lease-bound replies. Canonical HTTP credentials remain app-internal. Required/auto-edits modes require canonical once-only exact-action approval; session-wide acceptance is rejected. Native catalog deny order and actual custom-tool ask behavior remain retail qualification obligations; a known security incompatibility blocks execution, not permission to fabricate asks, append grants or weaken canonical approval. Full-access canonical behavior follows existing automatic-action rules.

Compatible A/B handlers are immutable, release-bundled broker code. Each enrollment/call keeps its captured handler; changing or rolling back the default does not hot-switch existing owners. Completed receipts retain their exact interpreted JSON, while reserved/uncertain outcomes never redispatch. Qualification metadata is not embedded in the bootstrap, and evidence-only additions cannot change its bytes, imports, fingerprints or setup lifetime. Changing the generated version guard changes bootstrap bytes and therefore requires safe managed replacement, including for the major-V2 policy; source updates alone do not update the loaded native plugin.

## Qualification and source trust limits

Native version, OpenAPI and source metadata are checks within the acknowledged honest-host trust model, **not executable byte attestation**. OpenAPI `info.version` is not the native release version; native health, registration and bootstrap versions must agree. Unsupported source ordering or policy forms fail closed. System/managed policy is inspected only through bounded canonical native projections; machine directories are never publication targets and raw plists/credentials are not read to repair setup.

Retail qualification is blocked until an approved clean macOS ARM64 VM/disposable runner supplies machine/system/MDM, account/mount/keychain and loopback-egress provenance. Isolated HOME/XDG alone is insufficient for 2.0.28. Fixtures refuse retail launch by default, including `--version`; no runtime setting or environment boolean grants qualification. No infrastructure provisioning, CLI installation/upgrade or current-host native execution is implied. Retry/status polling does not run a qualification daemon or bypass this gate.

## Full model catalog

V2 uses the same grouped/searchable/recent model picker as V1 and Pi. Friendly provider/model names come from real metadata; persisted routing keeps the exact subprovider and model IDs, so identical model slugs on different providers remain distinct. Native discovery supplies custom endpoints, aliases and exact variants. Public-only entries have unknown native capabilities/variants, not guessed effort settings.

The pinned V2 `model.list` and `provider.list` APIs return **available** entries, not the full catalog. bigbud separately reads OpenCode's official public [model feed](https://models.opencode.ai/api.json), merges native entries over it, and marks missing native entries as setup-only. Retired V1 provider aliases, deprecated models and non-text models are excluded. Available/free models do not prove an authenticated account. A provider's automatic activation is not used as authentication evidence.

Public catalog reads send no credentials, reject redirects, are bounded to 5 seconds / 8 MiB / 1,000 providers / 10,000 model entries, and use a scoped single-flight one-hour cache with a 30-second failed-refresh retry window. A temporary failure retains the last good catalog with a warning. The native fetch-disable flag remains intact: it disables native network refresh, **not** its bundled snapshot. There is no V1 cache/profile/credential reuse and no change to stream/event/other response bounds.

Before new history/model changes/prompt admission, bigbud rechecks the exact native model/variant. Unavailable selection fails before mutation without fallback. Accepted-request replay does not require current availability. Connect your provider in the native TUI; shared metadata refresh detects changes. Catalog/account metadata is not proof of successful billed execution.

## Access and limitations

- **Supervised:** co-located native file/shell operations ask for approval.
- **Auto edits:** shared execution allows ordinary native edits and asks for other native built-in actions; this is host-user trust, not a bounded-edit sandbox. The five canonical custom tools retain their independent once-approval boundary described above.
- **Full access:** trusts ordinary native tools with host-user filesystem, process, and network authority. This is **not a sandbox**; external-directory requests still ask.
- Direct native read/edit policy denies protect the verified registration directory and conventional native data/config/state directories. Compatible restrictive historical denies are retained. Custom database roots are not inferred or exhaustively discoverable from the V2 API; these rules do not contain native plugins or approved shell commands. Required setup reads bounded config-source files only to validate paths/plugin/removal controls; it does not rewrite or persist/log their credential contents.
- Production rejects remote/synthetic Locations without local/private/SSH fallback. Private-runtime coding/shell/remote factories exist only in explicit disposable qualification fixtures and are unreachable from production composition.
- Typed supported forms preserve native field/option identities. Conditional, hidden, external and other unsupported presentations cancel with a limitation warning instead of submitting invented answers or leaving a permanently waiting request.
- Saved native project approvals can override session `ask` rules. bigbud fails closed when such grants exist; review them in OpenCode. It never deletes user approvals or sends `always`, or rewrites user MCP/unrelated plugins. The required plugin filters canonical tools to exact enrolled sessions/Locations and revalidates executor authority; unrelated sessions do not gain canonical caller credentials.
- Attachments use verified immutable managed snapshots, never arbitrary desktop `sourcePath` rereads. Target-reachable paths are preferred with existing reading tools and approvals; shared bounded document/OCR text is supplemental. Native image/PDF delivery is retained where the adapter supports it. V2 native media supports PNG/JPEG/GIF/WebP, not PDF/Office binaries: those use extracted text or reachable reading tools. Known visionless V2 models receive OCR only, with explicit visual-loss limitations; unavailable required extraction fails before model mutation/prompt admission.
- Text/CSV/code and DOCX/PPTX/XLSX extraction reuse existing readers. PDF text and OCR depend on already available system helpers; nothing is installed automatically. Scanned-PDF OCR is only a preview of up to the first three pages. Extracted item text is limited to 32,000 characters and supplemental aggregate text to 60,000, plus truncation markers/metadata; notices identify truncation/unavailable extraction. OCR is not equivalent to visual analysis, and extracted PDF/Office text does not preserve every chart/layout detail.
- V2 production uses local native Locations only. Other providers retain workspace references for their existing target reading tools, without promising automatic remote document/OCR extraction. Directory references remain tool references and thread references expand canonically. Unsupported/denied remote reads never fall back to same-named host files.
- V2 persists immutable attachment preparation in **private bigbud state**, not the shared native profile, before admission. Replay does not rerun OCR/reread snapshots/resend. Historical text-only fingerprints and bounds remain. The 10 MiB stress probe remains excluded. See [attachment evidence](../validation/shared-attachments-2026-10-09.md).
- Native rewind, fork, steer, transparent process-loss recovery, and continuation are unsupported. Inspection is best effort. Idle model/variant switching preserves history, verifies selection by readback and blocks further prompts on uncertain outcomes. Verified new admissions may refresh truthful app-owned instructions without replacing native/user entries; retained admissions keep their original instruction/fingerprint material. No native history deletion is used to repair tool setup.

## Disable and rollback

Disable OpenCode in Providers settings; V1/Kilo IDs, configuration, and history remain independent. Legacy OpenCode is retired, not a rollback runtime. Stop/archive/shutdown retain V2 native history and durable replay protection. Never replay uncertain work through another provider: a lost acknowledgement does not prove nothing ran.

**Do not run shared execution in an older build that lacks `OpencodeV2SharedBindings` recovery.** Either retain these recovery/consent fences in the rollback build, or durably set the common `providers.opencodeV2.enabled:false` setting through the settings service/RPC, wait for its acknowledgement, drain bigbud-owned requests/owners without clearing uncertainty, and stop bigbud before downgrade. This build exposes a warning when logical binding records exist. Older binaries can ignore new markers; this is an operational boundary, not a universal downgrade interlock. Re-enabling an older shared implementation is unsupported.

Keep the new table/rows, creation intents, cursors, journals/tombstones and immutable attachments. Do not drop the migration, restore a pre-intent bigbud database snapshot over current state, delete/rekey records, or create fresh history to “repair” it. Native daemon restart/shutdown is not part of rollback. Return to an API-aware build to reconcile exact retained history before re-enabling. If the fence cannot be preserved or shared cannot remain disabled, preserve state and report the blocker.

Historical isolated profile qualification is not a production rollback option. Changing a package pin does not undo native schema migrations; old disposable probes do not authorize user-database replacement, private-history acquisition or overwriting current recovery evidence.
